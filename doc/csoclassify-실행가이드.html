1 빠른 시작

이 도구는 명령줄(CLI) 프로그램입니다. 더블클릭하면 검은 창이 깜빡이고 닫힙니다(정상) — 반드시 문서를 인자로 줘야 합니다.

이 폴더에서 터미널(주소창에 cmd 입력)을 연 뒤:

:: 문서 1개를 C/S/O 로 분류(기본 동작 — 모드 플래그 불필요)
csoclassify.exe --file "샘플.hwp"

:: 폴더 전체를 분류해 결과를 파일로 저장(가장 많이 쓰는 형태)
csoclassify.exe --dir "D:\collected" -r --embed-needed --format jsonl --out result.jsonl

:: 임베딩 벡터만 뽑기(분류 없이) — --embed
csoclassify.exe --embed --file "샘플.hwp"
처음 실행은 onedir 첫 기동과 모델을 메모리에 올리느라 수십 초 걸립니다(정상). 모델은 models\e5-small-ko\에 이미 풀려 있어 압축 해제 단계는 없습니다. 이후에는 모델이 메모리에 상주(데몬)해 빨라집니다.

2 패키지 구성

onedir 방식으로 패키징하며 Windows·Linux 2종을 각각 제공합니다 (dist-onedir\windows\, dist-onedir\linux\). 실행본체(csoclassify)와 파이썬 런타임(_internal\)이 한 폴더에 함께 있고, 규칙셋·모델·추출기는 그 옆에 외장 리소스로 둡니다. 모델은 이미 폴더로 풀려(models\e5-small-ko\) 있어 별도 압축 해제가 없습니다. 폴더 안의 상대 위치를 바꾸지 마세요.

① Windows — dist-onedir\windows\

windows\ ├─ csoclassify.exe 실행 파일(명령줄 도구) ├─ _internal\ 파이썬 런타임·의존 DLL(onedir). exe 와 한 세트 — 지우거나 옮기지 말 것 ├─ cso_rules.yaml C/S/O 분류 규칙셋(외장) — exe 옆에 필수. 재빌드 없이 교체 가능 ├─ doc_taxonomy.yaml 문서분류체계 스냅샷 — 업무분류 축의 필수 파일(없으면 축을 끄고 C/S/O 만) ├─ doc_rule.yaml 업무분류 규칙셋(선택) — 없으면 규칙 대신 seed 전파로 분류 ├─ class_seed.jsonl 전파용 seed 저장소(선택) — 있으면 보류 문서 구제/승격에 사용 ├─ models\ │ └─ e5-small-ko\ 임베딩 모델(model.onnx 등). 폴더째 exe 옆에 — 압축 해제 불필요 ├─ synap\ │ └─ windows\ 사이냅 문서필터 — 기본 모드는 필수, --hybridparse 는 없어도 됨 │ ├─ snf_exe.exe │ └─ snf_win.dll └─ log\ 실행 로그(자동 생성)
주의: _internal\은 exe 와 한 세트라 지우거나 따로 옮기면 실행이 안 됩니다. 추출기는 synap\windows\snf_exe.exe 경로에 있어야 합니다(과거처럼 synap\ 바로 아래 평평하게 두는 방식이 아님). 규칙셋 cso_rules.yaml·모델 models\e5-small-ko\는 exe 와 같은 폴더 기준으로 찾습니다. 규칙셋이 없으면 분류 실행 시 "어디에 두라"는 안내를 내고 종료(코드 3)합니다.
업무분류 축은 doc_taxonomy.yaml 이 있어야 켜집니다. doc_rule.yaml 은 없어도 됩니다 — 규칙 대신 class_seed.jsonl 과의 임베딩 전파로 분류합니다(seed 도 없으면 전부 미분류). 자세한 내용은 4장.
사이냅(synap\)은 기본 모드에서 필수입니다 — 없으면 분류를 시작하자마자 snf_exe 를 찾을 수 없음 으로 멈춥니다. --hybridparse 를 주면 자체 파서가 1차이고 사이냅은 폴백 전용이라 폴더째 없어도 동작합니다 2026-08-26 부터 구형 doc/xls/ppt/hwp 포함.

② Linux — dist-onedir/linux/

linux/ ├─ csoclassify-onedir-linux.tgz 실행본체(csoclassify + _internal). ※ 리눅스에서 풀어야 함(심볼릭링크·권한 보존) ├─ cso_rules.yaml C/S/O 분류 규칙셋(외장) ├─ doc_taxonomy.yaml 문서분류체계 스냅샷(업무분류 축의 필수 파일) ├─ doc_rule.yaml 업무분류 규칙셋(선택 — 없으면 seed 전파로 분류) ├─ class_seed.jsonl 전파용 seed 저장소(선택) ├─ models/ │ └─ e5-small-ko/ 임베딩 모델(int8) ├─ synap/ │ └─ linux/ │ └─ snf_exe 텍스트 추출기(리눅스) └─ README.txt 설치·실행 안내

리눅스 설치·실행(리눅스 서버에서):

# 1) 이 폴더를 리눅스 서버로 복사한 뒤, 실행본체를 푼다(심볼릭링크·권한 보존)
cd <이 폴더> && tar xzf csoclassify-onedir-linux.tgz
# 2) 실행 권한 부여
chmod +x csoclassify synap/linux/snf_exe
# 3) 실행
./csoclassify --file "문서.pdf"
주의: .tgz는 반드시 리눅스에서 풀어야 합니다 — Windows 에서 풀면 심볼릭링크가 깨집니다. 압축을 풀면 csoclassify 실행본체와 _internal/이 나오며, cso_rules.yaml·synap/linux/snf_exe·models/e5-small-ko/는 csoclassify와 같은 폴더에 있어야 합니다. 업무분류 축을 쓸 때는 doc_taxonomy.yaml·doc_rule.yaml도 같은 폴더에 둡니다.
사이냅을 못 받았다면 — --hybridparse 를 붙이면 synap/ 폴더 없이도 돕니다. pdf·hwp·hwpx·현대 docx/xlsx/pptx 는 물론 구형 doc/xls/ppt/hwp 까지 자체 파서가 처리합니다 2026-08-26 수정분 — 그전 배포본은 구형 4종이 미분류가 됩니다. 5장 '추출 방식'. 기본 모드(플래그 없음)는 사이냅이 없으면 시작하지 못합니다. 
./csoclassify --dir "/data/문서함" --hybridparse --format jsonl --out result.jsonl

3 실행 모드

모드는 플래그로 정해집니다. 아무 모드 플래그가 없으면 C/S/O 분류가 기본입니다. 임베딩 벡터만 필요하면 --embed, 추출 텍스트만 필요하면 --text-only 를 줍니다.

① 분류 (기본) — 모드 플래그 불필요

두 축을 한 번에 분류합니다(2026-08-25). 문서를 한 번 읽어 보안등급 축(security) = C/S/O 와 업무분류 축(doctype) = 문서분류체계 노드를 동시에 판정하고, 결과 레코드의 labels 아래에 축별로 나눠 담습니다. 업무분류 축은 doc_taxonomy.yaml(분류체계)이 있으면 켜지고, 없으면 지금까지처럼 C/S/O 만 나옵니다. 규칙 파일 doc_rule.yaml 은 선택입니다 — 없으면 class_seed.jsonl 과의 임베딩 전파가 대신 분류합니다. → 4장

여러 판정 신호(내용·민감정보·보안분류 스탬프·경로·파일명)로 등급을 판정합니다. --file/--dir 만 주면 바로 분류합니다(예전의 --classify 는 이제 붙일 필요가 없습니다). 출력은 기본 json — --file 단건은 객체 하나, --dir 배치는 레코드들의 JSON 배열 [ … ](그대로 뷰어로 열림)입니다. 줄단위로 스트리밍/처리하려면 --format jsonl(문서당 1줄).

검출 PII 유형 (20종 · 검출 엔진 ko-pii) — 문서에서 자동 검출하는 개인정보 유형과 기본등급입니다. 대량(bulk 임계 이상)이면 상향됩니다.

기본등급유형 (ko-pii 라벨)
S 민감주민등록번호(RRN) · 외국인등록번호(FRN) · 신용카드번호(CARD) · 계좌번호(ACCOUNT) · 여권번호(PASSPORT) · 운전면허번호(DRIVER_LICENSE) · 주소(ADDRESS) · 의약품EDI(EDI_DRUG) · 차량번호(VEHICLE) · 사건번호(COURT_CASE) · 부동산고유번호(PNU) · 국적(NATIONALITY)
C 기밀건강보험번호(MEDICAL_INSURANCE) · 처방전(PRESCRIPTION_ID)
O 공개 대량→S휴대전화번호(PHONE) · 이메일(EMAIL) · 사업자등록번호(BUSINESS_REG) · 법인등록번호(CORP_REG) · URL · IP주소(IP) 〔URL·IP 2026-08-15 추가〕

※ 검출은 ko-pii(패턴·체크섬·문맥·우회방어 내장)가 담당하고, 여기 표의 유형→등급 정책은 cso_rules.yaml 또는 UI 규칙설정(PII 유형 표)에서 조정할 수 있습니다.

판정 신호 (5종 + 전파) — 최종 등급은 아래 신호들 중 가장 민감한 등급으로 융합됩니다(보수적 max). 각 신호는 등급을 올릴 수만 있고 함부로 내리지 않습니다. 어느 신호로도 못 정하면 보류(none) → 검토 대상.

keywords(기밀사전)는 내용과 파일명 둘 다에 적용됩니다. 본문에서는 rule 신호로, 파일 이름(폴더 제외)에서는 name 신호로 같은 단어 목록이 쓰입니다. 따라서 name 은 별도 규칙 섹션이 없고(cso_rules.yaml 에 name: 섹션 없음), keywords: 에 단어를 추가하면 내용·파일명 양쪽에 반영됩니다. PII 정규식·스탬프·민감정보는 내용 전용이라 파일명엔 적용되지 않습니다.

결합식별성(combo) 2026-08-15 신규 — 개별론 낮아도 여러 PII가 한 문서에 모이면(개인정보보호법·GDPR '결합용이성') 상향됩니다. 예: 주민번호+계좌 → C, 주민번호+주소 → C, 전화·이메일·주소 중 2종+ → S. rule 신호의 layer:"COMBO" 히트로 표시됩니다.

스탬프(stamp)는 본문 한복판의 단발 언급("이 문서는 대외비가 아님")은 무시하고, 표식이 문서 머리(앞 400자)에 있거나 2회 이상 반복될 때만 인정해 오탐을 줄입니다("관계자 외 열람금지" 같은 명시 문구는 위치·반복 무관 1건도 인정). 머릿범위/반복횟수는 환경변수로 조정.

※ sensitive·stamp·combo의 정책(단어·범주·조합·등급)은 cso_rules.yaml의 sensitive/stamps/pii_combos 섹션에서 조정합니다.

📖 규칙셋 cso_rules.yaml의 모든 섹션·필드 의미는 별도 레퍼런스 문서 CSO_Rule.html(규칙셋 필드 레퍼런스)에서 표로 확인할 수 있습니다.
🧪 추출 옵션 --hybridparse: 파일 내용을 감지해 포맷별 오픈소스 파서로 추출(사이냅 없이) — pdf→pypdfium2, hwp→HWP5, hwpx→zip/OWPML, 구형 doc/ppt→자체 파서, xls→xlrd, 현대 docx/xlsx/pptx→zip/OOXML 직접파싱(stdlib), text→직접읽기. 각 파서 실패 시 snf 폴백. 설계·측정은 CSO_HybridParse.html 참고. 미지정 시 기본은 지금처럼 사이냅(snf) 그대로입니다.
🗜️ 압축파일 자동 확장: 입력이 압축파일이면 내부 파일을 임시폴더에 풀어 파일별로 개별 분류합니다(중첩 압축 재귀). 지원 포맷: zip · tar · tar.gz · tar.bz2 · tar.xz · gz · bz2 · xz(무의존) · 7z · rar(번들 unrar). 결과는 파일별 레코드의 JSON 배열이고, 각 레코드의 file 은 "<압축경로>/<내부경로>" 로 표기돼 어느 내부 파일이 C/S/O 인지 바로 압니다. 처리 후 임시폴더는 자동 삭제됩니다. (docx/xlsx/pptx/hwpx 는 내부가 zip 이라도 '문서 1개'로 취급 — 펼치지 않음.)
🏷️ 압축파일 '자체'의 등급: 압축은 그 안에서 가장 높은 위험등급(C>S>O) 을 자기 등급으로 받습니다. 결과에 {"archive":true, "grade":"<최고위험>", "contains":{C,S,O,미분류,total}} 요약 레코드가 뒤에 붙어 압축만 봐도 위험도를 압니다. (총계 중복 없음.)

분류 방식 선택 (배타) — 기본은 규칙으로 등급을 내고, 필요할 때만 임베딩을 씁니다. 아래 두 옵션으로 한쪽만 쓰도록 강제할 수 있습니다(동시 지정 불가).

옵션동작임베딩seed
--rule-only규칙(내용·민감정보·스탬프·경로·파일명)만으로 분류. 벡터·전파 안 함안 함(가장 빠름)불필요
--vector-only규칙 검사 없이, 문서 벡터를 seed 와 비교(전파)해서만 등급 결정전량 임베딩필수 --seeds
:: 규칙만 — 가장 빠른 분류(임베딩 모델 불필요)
csoclassify.exe --dir "D:\collected" -r --rule-only --format jsonl --out result.jsonl

:: 벡터만 — 규칙 무시, seed 와의 임베딩 유사도로만 분류(비교 기준 seed 필수)
csoclassify.exe --dir "D:\collected" -r --vector-only --seeds "class_seed.jsonl" --format jsonl --out result.jsonl

--vector-only 결과는 signals에 embed만 있고(규칙 신호 없음) decided_by:["embed"]로 나옵니다. seed 와의 유사도가 임계 미만이면 보류(none)가 됩니다. --vector-only인데 --seeds 파일이 없으면 인자 오류로 안내 후 종료합니다.

:: 규칙만으로 빠르게(임베딩 없음)

📊 최종 요약 — 분류가 끝나면 화면(stderr)에 [summary] 총 N개 / 검출 M, C=… S=… O=… 미분류=…, 총시간=…ms 한 줄을 냅니다. 총시간은 exe 실행(기동/startup)부터 완료까지의 실제 전체 소요시간입니다. --out 결과 파일(json/jsonl)에도 맨 마지막에 같은 내용을 {"summary": {"total":…, "detected":…, "C":…, "S":…, "O":…, "unclassified":…, "elapsed_total_ms":…}} 로 덧붙입니다(json 배열의 마지막 원소).

C 기밀 S 민감 O 공개 · 어느 신호로도 못 정하면 보류(none) → 검토 대상.

기본 동작에서 자동 전파(2026-08-16 변경). exe 옆에 class_seed.jsonl 이 있으면 --file/--dir 만 줘도 규칙으로 미분류(보류)된 문서를 그 seed 와 임베딩(문맥) 비교해 자동으로 전파·분류합니다(보류 문서 임베딩은 자동 활성화, 확정 문서는 건너뜀). seed 파일이 없으면 전파 없이 규칙만으로 끝냅니다.

· 전파를 원치 않으면 --rule-only 를 주세요 — seed 파일이 옆에 있어도 순수 규칙 분류만 합니다.
· 대량 배치는 분류(--embed-needed) 후 --propagate 2차 패스로 나눠 처리해도 됩니다.

4 업무분류(doctype) 축 2026-08-25 신규

지금까지의 보안등급 축(C/S/O)에 더해, 문서가 무슨 업무 문서인지(계약서·회의록·요구사항정의서 …)를 같이 판정하는 두 번째 축입니다. 분류 기준은 MpowerV11 의 문서분류체계(DOC_CLASSIFICATION)를 그대로 내려받은 스냅샷이라, DB 의 분류 트리와 같은 이름·같은 ID로 결과가 나옵니다.

두 축의 차이 — 왜 따로 다루나

보안등급 축 security업무분류 축 doctype
값의 성격서열이 있음 (O < S < C)서열 없는 분류 트리(형제끼리 우열 없음)
결과 개수항상 1개(단일 등급)여러 개 가능(한 문서가 계약서이면서 법무 문서)
충돌 처리max 고정 — 가장 민감한 쪽 채택(안전측)all(전부) 또는 top_n:N(상위 N개) — 선택 가능
실행 시 변경불가 — --conflict security=… 는 오류(코드 4)가능 — --conflict doctype=top_n:3
못 정했을 때grade: null(보류) → 검토 대상values: [](빈 목록) — 정상

보안등급은 낮게 나오는 실패가 사고라서 안전측 고정이 유일하게 정당합니다. 반면 업무분류는 "계약서이면서 동시에 법무 문서"가 둘 다 맞는 상황이라 하나로 줄일 이유가 없어, 전략을 고를 수 있게 열어 뒀습니다.

축을 켜는 법 — 필수 1개 + 분류 수단 2가지

파일무엇필수?어디서 오나
doc_taxonomy.yaml분류체계 스냅샷 — 노드 ID·부모·제목·사용여부필수 없으면 축 자체가 꺼짐DB 내보내기 JSON → --export-taxonomy 로 변환
doc_rule.yaml규칙으로 분류 — 어떤 단어/파일명/경로면 어느 노드인지선택--scaffold-doc-rule 로 골격 생성 후 사람이 채움
class_seed.jsonl전파로 분류 — 이미 분류가 확정된 문서의 벡터+라벨선택사람이 확정한 문서를 seed 로 승격

세 파일 모두 --rules 와 같은 규칙으로 찾습니다: 인자 우선 → exe 옆 → CSOCLASSIFY_POLICY_DIR (seed 는 --seeds).

규칙 파일이 없어도 분류됩니다 2026-08-25 변경
doc_rule.yaml 이 없으면 축을 끄지 않고 'seed 전파 전용' 모드로 돌립니다 — 규칙 대신 class_seed.jsonl 과의 임베딩 유사도만으로 분류합니다. 규칙을 한 줄도 안 쓰고 확정된 문서 몇 건만 seed 로 넣어 업무분류를 시작할 수 있습니다.
이전에는 규칙 파일이 없으면 축을 통째로 껐습니다. 축을 끄면 결과에 labels.doctype 키가 아예 안 생겨 전파 단계까지 건너뛰게 되므로, "seed 로라도 분류"가 불가능했습니다.
이 모드로 들어가면 시작할 때 이렇게 알립니다: 
[csoclassify] doc_rule.yaml 이 없어 업무분류(doctype)를 'seed 전파 전용'으로 돌립니다.
              규칙 대신 class_seed.jsonl 과의 임베딩 유사도로만 분류합니다(seed 도 없으면 전부 미분류).
              찾은 경로: ...\doc_rule.yaml
결과 레코드의 doctype_rule_version 도 "none" 으로 찍혀, 나중에 결과만 보고도 규칙 없이 돌았다는 걸 구분할 수 있습니다.
가진 것업무분류 동작결과
규칙 + seed규칙으로 1차 분류 → 전파가 후보를 더함가장 넓게 분류됨

골격(scaffold)은 filename 만 채워집니다. 노드 제목(예: "계약서")을 파일명 규칙으로 넣어 주고 terms: [](본문 키워드)는 비워 둡니다 — 본문 규칙은 업무를 아는 사람이 채워야 정확하기 때문입니다. 이미 doc_rule.yaml 이 있으면 덮어쓰지 않고 건너뜁니다(손으로 채운 규칙 보호).

규칙 한 건의 모양 — doc_rule.yaml

conflict: all                  # 축 전체의 충돌 전략: all | top_n(+ n)
version: doc-2026.08.1
doctype_rules:
- id: dt_dc_006_001            # 규칙 식별자(중복 불가)
  node: DC_006_001             # 이 규칙이 가리키는 분류체계 노드 ID
  weight: medium               # high | medium | low — 신뢰도로 환산
  terms: ["용역계약", "계약조건"]   # 본문에 있으면 매칭
  exclude: ["계약해지 안내"]        # 이 말이 있으면 매칭 취소(오탐 방지)
  filename: ["계약서"]             # 파일 이름에 있으면 매칭
  paths: ["/법무/"]               # 이 폴더 아래면 매칭(텍스트 안 엶)

weight → 신뢰도: 본문(terms) high 0.85 / medium 0.70 / low 0.50, 경로(paths) high 0.90 / medium 0.70 / low 0.50, 파일명(filename)은 항상 0.60. 보안등급 축의 같은 이름 상수와 값을 맞춰, "같은 확신 수준"이 두 축에서 같은 숫자가 되게 했습니다.

임베딩 전파(embed) — 규칙이 못 잡은 문서 분류

보안등급 축과 마찬가지로, seed 저장소가 있으면 업무분류도 임베딩 유사도로 전파합니다. 규칙 파일이 없는 배포에서는 이것이 유일한 분류 수단입니다. 두 축의 전파 방식은 다릅니다:

보안등급업무분류
대상보류(grade=null) 문서만 구제모든 문서 — 이미 라벨이 있어도 후보를 더한다
득표 임계0.70 (이웃의 70% 이상이 같은 등급)0.25 (라벨마다 따로 계산)
이유등급은 하나뿐이라 다수결이 성립표가 동시에 맞는 여러 라벨로 갈리므로 같은 잣대를 쓰면 아무것도 못 넘김

전파로 붙은 라벨은 from 에 "embed" 가 들어갑니다. 이웃 문서와 거의 같은 문서(near-dup)면 그 문서의 라벨 집합 전체를 그대로 물려받고, 그렇지 않으면 라벨별로 따로 신뢰도를 계산합니다. 전파 후에도 조상 흡수와 충돌 전략은 다시 적용되므로, 규칙과 임베딩이 섞여도 결과 형태는 같습니다. 실행하면 화면에 [전파][업무분류] seed=… embed기여=… 벡터없음=… 한 줄이 나옵니다.

전파하려면 그 문서의 벡터가 있어야 합니다 — 임베딩은 느린 단계라 필요한 문서에만 겁니다. 기본(--embed-needed 포함)에서 벡터를 만드는 대상은 아직 못 정한 축이 하나라도 있는 문서입니다:
· 보안등급이 보류이거나 seed_eligible 이거나,
· 업무분류 라벨이 하나도 안 붙은 문서 2026-08-25 추가
두 번째 조건이 없으면, 규칙 없이 도는 배포에서 보안등급만 멀쩡히 나온 문서는 벡터가 안 만들어져 업무분류가 영영 미분류로 남습니다. --rule-only 는 임베딩을 아예 안 하므로 전파도 하지 않습니다(규칙 없이 --rule-only 를 주면 업무분류는 전부 미분류).

seed 만들기 — 관리자가 분류한 결과를 seed 로 승격 2026-08-25

규칙 없이 돌리려면 seed 가 곧 정답지입니다. seed 저장소(class_seed.jsonl)는 문서 한 건이 한 줄인 JSONL 이고, 업무분류 전파에 필요한 필드는 단 두 개입니다.

두 축은 서로 독립적으로 같은 파일을 읽습니다 — 한 줄에 grade 와 labels.doctype 을 둘 다 넣어도 되고, 한쪽만 넣어도 됩니다. 해당 필드가 없는 줄은 그 축이 조용히 건너뜁니다(구버전 seed 파일을 그대로 써도 안전).

--propagate 도 두 판 모두 2026-08-26 Rust 추가

1차 결과 파일을 읽어 전파만 다시 도는 2차 패스입니다. 두 판의 인자·출력·통계 줄이 같으므로, 파이썬으로 1차를 내고 Rust 로 전파하거나 그 반대로 해도 됩니다.

실측(2026-08-26) — 같은 1차 파일(d:\sample 18건, 벡터 포함)을 두 판에 각각 전파: seeds=71 already_graded=10 embed_decided=4 still_unclassified=4 로 통계가 같고, 18개 레코드의 grade·confidence·method·decided_by·labels·signals.embed 가 전부 일치했습니다. 업무분류 seed 를 넣은 경우도 embed_contributed=4 로 같고 labels.doctype·signals.doctype_embed 까지 일치했습니다.
두 가지 사소한 차이
  • 1차 파일 끝의 {"summary":…} 줄 — Rust 는 문서가 아니라고 보고 버리지만, 파이썬은 레코드로 취급해 통계에 no_vector=1·axis_off=1 로 한 건 더 세고 결과 파일에도 다시 씁니다. 이때 다시 쓰이는 요약은 전파 이전 숫자라 실제 결과와 어긋납니다.
  • 동점 이웃의 나열 순서 — 유사도가 똑같은 seed 가 둘 이상이면 signals.embed.neighbors 의 순서가 다를 수 있습니다. 파이썬이 쓰는 np.argsort 가 불안정 정렬이라 파이썬 쪽 순서도 보장되지 않습니다. 등급 판정에는 영향이 없었습니다(18건 전부 일치).

같은 모델 파일(model.onnx md5 동일)이라도 ONNX Runtime 이 OS·CPU 마다 미세하게 다른 수를 냅니다 (int8 양자화 모델이라 특히 민감). 엔진(파이썬/Rust) 차이가 아니라 런타임 차이입니다.

비교최저 코사인 18건뜻

임계값 바로 옆에 있는 문서는 OS 에 따라 판정이 갈릴 수 있습니다. 전파는 1등 유사도가 0.55 미만이면 보류로 둡니다. 실측에서 한 문서가 Windows top_sim=0.554(등급 C) / Linux 0.549(보류) 로 갈렸습니다 — 두 판(파이썬·Rust) 모두 같은 OS 에서는 같은 판정을 냈으므로 엔진 문제가 아닙니다.
운영에서 결과를 재현해야 한다면 1차 분류와 전파를 같은 OS 에서 돌리고, seed(class_seed.jsonl)도 그 OS 에서 만든 것을 쓰세요.
2026-08-26 이전 Rust 배포본의 벡터는 파이썬과 미묘하게 달랐습니다 코사인 0.94~0.98 — Rust 가 추출 원문을 그대로 임베딩했고 파이썬은 정제(clean_text)한 텍스트를 임베딩했기 때문입니다. 파일 끝 개행 하나만 달라도 벡터가 이만큼 벌어집니다. class_seed.jsonl 과 코사인으로 비교하는 전파 판정에도 영향이 있었으므로, 옛 Rust 배포본으로 만든 seed 가 있다면 새 판으로 다시 만드는 편이 좋습니다.

::   아무것도 못 잡으면(암호 zip·이미지 등) 그때만 C

9 주의사항

  • 더블클릭 금지 — 명령줄 도구라 창만 깜빡입니다. 반드시 인자와 함께 실행.
  • 경로에 공백이 있으면 "큰따옴표"로 감싸세요.
  • --out은 절대경로 권장 — 상대경로는 실행 위치(작업폴더)에 따라 엉뚱한 곳에 저장될 수 있습니다.
  • --out 확장자가 출력 형식을 정합니다 2026-08-26 변경 — --out result.jsonl 이면 --format 을 안 줘도 jsonl 로 씁니다. 추론이 일어나면 화면에 --out 확장자에 맞춰 --format jsonl 로 저장합니다 한 줄이 나옵니다.
    전에는 .jsonl 로 저장해도 안에는 JSON 배열이 들어가, 뷰어가 Unexpected token ',' … is not valid JSON 으로 열지 못했습니다(파일이 깨진 게 아니라 형식이 안 맞았던 것).
  • 한글 파일명/출력은 UTF-8로 고정되어 깨지지 않습니다.
  • 첫 실행이 느린 것은 onedir 첫 기동과 모델을 메모리에 올리기 때문이며 정상입니다(이후 빠름).
  • 오프라인 동작 — 인터넷 없이 됩니다. 실행 오류 시 대상 PC에 Microsoft Visual C++ Redistributable x64 설치, 백신 예외 등록.
