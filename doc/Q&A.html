1. 업무분류 · 분류체계

Qdoc_rule.yaml 을 만들 때 최상위(경영/관리)가 안 들어갑니다.
A

의도된 동작입니다. 최상위 분류는 서랍 이름이라 문서에 그대로 적히는 말이 아니기 때문입니다. 규칙에 경영/관리 를 넣으면 문서에서 그 글자를 찾게 되는데, 그렇게 적힌 문서는 거의 없습니다.

서랍(규칙을 걸지 않는 분류) = 최상위이면서 자식이 있는 분류
분류 모양보기규칙왜
최상위 + 자식 있음경영/관리, 법무/규정안 만듦 서랍 이름 — 문서에 그대로 적히지 않음
최상위 + 자식 없음경영/관리(단독)만듦 그 자체가 최종 분류
중간 + 자식 있음기술/개발 > 설계문서만듦 “설계문서” 는 문서에 적히는 말
잎… > 요구사항정의서만듦—

지금 분류체계는 최상위 6개가 모두 자식을 가지므로, 27개 중 21개에 규칙이 만들어집니다.

늘릴 말이 있느냐로 봐도 같습니다 — 잎은 여러 표기로 불어나지만 서랍은 그 이름 하나뿐입니다.

분류자동으로 채워지는 말
요구사항정의서 (잎) 요구사항정의서, 요구사항 정의서, 요구사항명세서, 요구정의서, SRS …
경영/관리 (서랍) 경영/관리  — 늘릴 말이 없음
2026-09-01 에 고친 점 — 예전 기준은 “부모가 없으면 제외” 라서 자식이 없는 최상위도 함께 빠졌습니다. 그건 서랍이 아니라 그 자체가 최종 분류인데도 규칙을 만들어 주지 않으면서 [T12] 경고만 났고, [분류 불러오기] 를 눌러도 사라지지 않는 경고가 됐습니다. 지금은 위 표대로 동작합니다.
Q그럼 “경영/관리” 로는 문서가 분류되지 않나요?
A

분류됩니다. 자식으로 잡히면 부모까지 함께 올라갑니다(조상 흡수).

[summary][업무분류] 인사/총무 1 (복리후생 1) / 법무/규정 1 (사내규정 1)
                    ↑ 부모(서랍)          ↑ 실제로 걸린 분류

보고서 로 잡힌 문서는 경영/관리 > 보고서 이므로 “경영/관리 밑의 문서”를 찾는 데 지장이 없습니다. 결과 레코드에도 path_ids 로 부모까지 담깁니다.

그래도 최상위 자체에 규칙을 걸고 싶다면 막지 않습니다 — 설정/분류 ▸ 2️⃣ 판단 기준 ▸ 업무분류 ▸ [분류 하나만 직접 추가하기] 에 최상위 6개가 후보로 나옵니다. 자동으로 만들지 않을 뿐입니다.

넣는다면 단어를 반드시 손보세요. 시작값 경영/관리 는 문서에 거의 안 적힙니다. 그 회사에서 실제로 쓰는 말(경영보고, 경영지원, 임원보고)로 바꿔야 쓸모가 있습니다. 쓰임새 — 하위 세 분류 어디에도 안 걸리는 문서를 “경영/관리 일반” 으로 모으고 싶을 때.
Q[T12] 경고 / 화면의 “N개 분류에는 기준이 없습니다” 는 뭔가요?
A

둘은 같은 뜻입니다 — “이 분류로는 자동분류될 문서가 없습니다”, 즉 규칙을 채우라는 알림입니다. 오류가 아니라 경고여서 종료코드에 영향을 주지 않고 분류도 그대로 진행됩니다.

코드무엇을 보나결과
T5규칙이 가리키는 분류가 분류체계에 실제로 있나종료 4(중단)
T6참조한 분류가 꺼진(STATUS=0) 것인가경고
T12어떤 규칙도 참조하지 않는 분류가 있나경고
T13분류체계 스냅샷이 90일 넘게 묵었나경고

이 경고가 보이면 [🔄 분류 불러오기] 를 누르면 대부분 해결됩니다. 그래도 남는 분류는 화면 표에서 직접 단어를 채워 주세요.

2026-08-31 에 고친 점 — 예전에는 이 숫자가 서랍까지 세고 있었습니다. 그래서 규칙을 아무리 채워도 “6개 분류에는 기준이 없습니다” 가 사라지지 않았고 (그 6개가 전부 최상위 서랍), 실행할 때마다 고칠 수 없는 [T12] 경고가 6줄씩 떴습니다. 지금은 규칙을 거는 대상만 세므로 다 채우면 실제로 사라집니다.

2. 실행 · 연동(CLI)

Q다른 프로그램에서 csoclassify.exe 를 불러 쓰려고 합니다. 이런 것을 CLI 프로그램이라고 해도 되나요?
A

예, CLI 도구(command-line tool) 가 맞습니다. 명령줄 인자를 받아 실행되고, 결과를 내고, 끝납니다. 사람이 터미널에서 직접 쳐도 되고 다른 프로그램이 서브프로세스로 불러도 똑같이 동작합니다 — 실제로 관리 화면(Streamlit)이 그렇게 쓰고 있습니다.

다만 순수한 CLI 도구는 아닙니다. 임베딩 모델을 매번 읽으면 느려서 상주 데몬 모드(--serve · --status · --stop)를 함께 가집니다. 정확히 적자면 “CLI 도구 + 선택적 데몬” 입니다.

문서나 대화에서는 “분류 엔진을 CLI 도구로 제공하고, UI·배치 시스템이 서브프로세스로 호출한다” 처럼 쓰면 오해가 없습니다. 그냥 “CLI 프로그램” 이라고만 하면 사람이 터미널에서 치는 것으로 읽히기 쉽습니다.

Q남이 부르는 도구로서 갖춰야 할 것은 다 되어 있나요?
A

다른 프로그램이 부르는 도구는 사람이 눈으로 보고 판단하는 부분이 없어야 합니다. 아래가 그 조건이고, 전부 갖춰져 있습니다.

요건이 도구
종료 코드로 성패를 알린다 0 정상 · 2 파일 문제 · 3 인자 오류 · 4 규칙셋 오류
결과가 기계가 읽는 형식--format json|jsonl · --out 파일
stdout / stderr 분리결과는 stdout, 진행·경고는 stderr
진행 상황 보고--progress → [progress] 3/120 경로
물어보지 않는다대화형 입력 없음 — 끝까지 실행하고 끝난다
실행 흔적log/class_YYYYMMDD.log · 오류는 log/class_err_*.log
# 파이썬에서 부르는 예
r = subprocess.run([exe, "--dir", folder,
                    "--format", "jsonl", "--out", out_path],
                   capture_output=True)
if r.returncode != 0:
    # 이유는 stderr 와 log/class_err_*.log 양쪽에 남아 있다
    raise RuntimeError(r.stderr.decode("utf-8", "replace"))
결과는 --out 으로 파일에 받으세요. stdout 으로 받으면 결과가 클 때 파이프 버퍼가 차서 교착에 빠집니다 — 부르는 쪽이 다 읽기 전에는 이 프로그램이 못 쓰고, 이 프로그램이 다 쓰기 전에는 부르는 쪽이 못 읽는 상태가 됩니다.
Q호출하는 쪽이 파이썬이어야 하나요? 문서가 많으면 느리지 않나요?
A

언어는 상관없습니다. 프로세스를 실행할 수 있으면 됩니다 — Java·C#·스케줄러·다른 서버. 주고받는 것이 명령줄 인자와 JSON 파일 뿐이라 언어에 매이지 않습니다. Rust 판(csoclassify-rs.exe)이 같은 인자·같은 출력 형식을 쓰는 것도 그래서 가능합니다 — 부르는 쪽을 고치지 않고 실행 파일만 바꿔 낄 수 있습니다.

속도는 부르는 방식이 좌우합니다. 임베딩을 쓰면 모델 적재가 가장 큰 비용입니다.

상황이렇게
문서가 많다--dir 한 번으로 부르세요 — --file 을 수백 번 부르는 것보다 훨씬 빠릅니다
임베딩이 필요 없다--rule-only — 모델을 아예 안 읽습니다(가장 빠름)
한 건씩 자주 부른다데몬을 켜 두세요 — 모델이 메모리에 남습니다
규칙을 바꿔도 다시 빌드하지 않습니다. 규칙셋(cso_rules.yaml · doc_rule.yaml)과 분류 체계는 실행 파일 옆의 외장 파일이라, 파일만 바꾸면 다음 실행부터 적용됩니다. 바꾼 뒤에는 --check-rules 로 먼저 검사하세요 — 규칙이 잘못됐으면 분류를 시작하지 않고 종료코드 4 로 멈춥니다.

인자·종료코드의 전체 목록은 실행가이드(doc/csoclassify-실행가이드.html) 5·6장에 있습니다.

3. 코드 읽기

Qcli.py 를 보면 옵션을 읽는 방식이 두 가지입니다. getattr(args, "check_rules", False) 와 args.propagate — 뭐가 다른가요?
A

차이는 딱 하나입니다 — 그 옵션이 없을 때 죽느냐, 안 죽느냐.

args.propagate                        # 없으면 → AttributeError 로 즉시 멈춤
getattr(args, "check_rules", False)   # 없으면 → False (안 멈추고 계속 진행)

그런데 이 프로그램에서는 둘 다 항상 존재합니다. build_parser() 가 모든 옵션을 default 와 함께 등록하기 때문에, parse_args() 를 거친 args 에는 옵션이 빠질 수가 없습니다.

등록안 주고 실행하면
--check-rules (action="store_true") args.check_rules = False
--propagate (default=None) args.propagate = None

즉 _main() 안에서 두 방식은 동작이 완전히 같습니다. getattr 쪽이 방어적으로 한 겹 더 쌌을 뿐입니다.

그럼 왜 getattr 이 30곳 넘게 쓰였나 — args 가 parse_args() 산물이 아닌 경로가 실제로 있기 때문입니다. 테스트가 필요한 필드만 담은 가짜 args 를 만들어 내부 함수를 직접 부릅니다.

# tests/test_cli_doctype.py — 필드가 3개뿐인 가짜 args
args = SimpleNamespace(axis="security", taxonomy=..., doc_rules=None)
cli._load_doctype_axis(args, _fake_log())
# 이 함수가 args.with_text 를 직접 읽었다면 여기서 AttributeError 로 터진다
어디서무엇을 쓰나왜
_main() 안 (args 출처가 확실) args.check_rules 없으면 그건 버그 — 즉시 드러나야 한다
여러 곳에서 불리는 하위 함수 getattr(args, "x", 기본값) 부분 args 로 부르는 경로가 실제로 있다
“안 죽는다” 가 항상 이득은 아닙니다. dest 이름을 바꾸거나 getattr 문자열에 오타가 나면 ("chek_rules") 조용히 False 가 돌아옵니다. 그러면 사용자가 --check-rules 로 규칙셋만 검사하려 했는데 그 지시가 무시된 채 문서 스캔이 시작되고, 종료코드는 0 이라 규칙에 오타가 있어도 “검사했더니 정상” 으로 보입니다.
여기서의 선택은 “죽는다 vs 안 죽는다” 가 아니라 “바로 드러나는 실패 vs 결과가 틀린 채 성공” 입니다. 분류 도구에서는 틀린 결과를 조용히 내는 것이 가장 나쁜 실패이므로, 없을 수 없는 자리에서는 직접 접근이 오히려 안전합니다.
getattr 을 쓸 땐 기본값을 파서와 맞추세요. 세 번째 인자가 add_argument(..., default=...) 와 다르면, 같은 옵션이 부르는 경로에 따라 다르게 동작합니다. 이건 화면에 아무 표시도 없이 결과만 갈리므로 찾기가 매우 어렵습니다.

같은 원리가 fail_code() 에도 있습니다 — 이 함수는 프로그램을 끝내지 않고 종료코드를 돌려주기만 하므로 반드시 return fail_code(...) 처럼 return 과 함께 써야 합니다. return 을 빠뜨리면 오류 메시지·로그만 남고 실행이 그대로 이어집니다.

알아둘 점내용
log 는 이미 있다 _main() 안에서 logsetup.get_logger("csoclassify.cli") 로 이미 만들어져 있습니다. import 추가가 필요 없습니다.
f-string 대신 %s 이 프로젝트의 다른 로그와 같은 방식입니다. DEBUG 가 꺼져 있을 때 문자열 포매팅 비용을 안 치릅니다.
log.debug 는 --verbose 필요 setup_logging() 이 verbose 가 아니면 레벨을 INFO 로 둡니다. 항상 전체 목록을 보려면 log.debug → log.info.
이 시점의 원소는 문자열 바로 아래 zip 확장을 거치면 (src, label, origin) 튜플이 섞입니다. 그 뒤에서 찍을 땐 _as_job() 으로 풀어야 합니다.

화면으로도 보고 싶다면 — 진단 출력에 stdout 을 쓰면 안 됩니다. stdout 은 결과 JSON 전용이라 한 줄만 섞여도 이 CLI 출력을 파싱하는 쪽이 깨집니다. --filelist 안내처럼 stderr 로 내세요.

    print(f"[csoclassify] 대상 수집 {len(files)}건", file=sys.stderr)
    for f in files:
        print(f"[csoclassify]   {f}", file=sys.stderr)
--progress 가 이미 stderr 로 파일별 진행을 내므로, 접두사를 [progress] 와 겹치지 않게 두는 편이 낫습니다.
