1차 메타데이터 필터 — PII · 사전(키워드)

① PII 검출 (ko-pii 20종)

주민·외국인·카드·계좌·여권·면허·주소·건강보험·처방전·차량·소송·국적 …

패턴 + 체크섬 + 문맥 검증으로 오탐 차단

건수 임계 초과 시 대량(bulk) 상향

② 결합식별성 (COMBO)

개별론 낮아도 한 문서에 모이면 상향

주민+계좌 → C

전화·메일·주소 2종+ → S

③ 기밀사전 (키워드)

대외비·극비·기밀 관련 문구 및 업무 도메인 키워드

본문·파일명 공통 적용

사전은 cso_rules.yaml 로 외장 — 고객사별 교체

④ 법상 민감정보

건강·유전·성생활·사상/정치·노조·범죄경력·인종

개인정보보호법 제23조 → C (독립 신호)

⑤ 보안분류 스탬프

문서에 찍힌 표식 — "대외비/기밀"→C, "내부용"→S

머리(앞 400자) 또는 2회 이상 반복일 때만 인정 → 본문 단발 언급 오탐 차단

⑥ 경로 · 파일명

//hr-server/ · /인사/ · /public/ 택소노미

본문을 열지 않는 값싼 출처 신호 — 소프트캠프 방식을 보조로만 흡수

보수적 max 융합 — 5종 신호 중 가장 민감한 등급을 채택. 각 신호는 등급을 올릴 수만 있고 함부로 내리지 않는다. 어느 신호로도 못 정하면 보류(none) → 2차로 이관

프라이버시 불변식 — 매칭된 원문 PII 값은 저장하지 않음(유형 id·건수만). 로그에는 [pii N detected] 만 기록

2차 AI 필터 — 문맥(벡터) 비교

룰은 "쓰여 있는 것"만 잡는다. 표현·양식이 달라 룰에 안 걸린 문서를 의미가 비슷한 기존 문서(Seed) 와 비교해 구제하는 단계.

무엇을 하나

1차에서 보류(none) 로 남은 문서만 벡터화

모델 e5-small-ko · 384차원 · int8 경량화

Seed 문서와 코사인 유사도 비교 → 임계 이상이면 등급 전파

유사도 미달(too_far)은 여전히 보류 → 3차로 이관

왜 이 순서인가

엠클라우독 방식은 전 문서를 임베딩 — 비용·시간이 크다

우리는 보류분만 임베딩 → 실측 401건 중 167건(41.6%)만 벡터 생성

임베딩 소요는 전체 시간의 15%(23.5초/158.7초)에 그침

Seed 자동 부트스트랩

Seed 0건에서도 룰만으로 1차 분류 완료 가능

룰로 확정된 고신뢰 문서(seed_eligible)를 Seed 로 자동 승격

실측 시 Seed 72건으로 운영 — 사전 수집 작업 불필요

안전장치 — 임베딩은 보류 구제용 보조 신호일 뿐, 1차에서 확정된 등급을 뒤집지 않는다. 전파로 결정된 건은 decided_by:["embed"] 로 표시돼 나중에 구분·추적 가능

03 · 제안 방식 › 3차

3차 관리자 필터 — 수동 검토

자동분류는 끝이 아니라 초안이다. 기계가 확신하지 못한 것을 사람에게 넘기고, 사람의 판단을 다시 기계에 되먹인다.

검토 큐로 넘어오는 것

· 1·2차로도 등급이 안 나온 보류 문서

· 신뢰도(confidence)가 낮은 문서

· 과분류 의심(O 인데 C 로 튄 케이스 등)

· 스캔·이미지 등 텍스트 추출 실패 문서

담당자가 하는 일

Streamlit 검토 UI 에서 문서·판정근거 확인

등급 확정 또는 수정

원본은 불변 — 오버라이드는 cso_override.jsonl 에 append-only 기록

규칙 편집(주석 보존) · .bak 자동 백업·버전 상향

환류 — 자가 학습 루프

확정 결과를 Seed 에 추가 → 2차 AI 필터 정확도 상승

반복 오탐은 규칙셋 수정으로 반영 → 1차 필터 정밀도 상승

회차를 거듭할수록 3차로 넘어오는 물량이 줄어든다

최종 산출 — C / S / O 등급 + 판정 근거(어느 신호가 무엇을 몇 건 잡았는지) + 감사 로그. 타사 대비 우리의 결정적 차별점은 여기 "소명 가능성" 에 있다

압축파일(ZIP) — 겉과 속이 다르다

ZIP 은 그 자체로는 아무 내용도 없다. 타사 출처기반 방식은 압축 해제 시점에 출처가 소실되고, 문맥기반은 압축 파일을 열지 못한다 — 실무에서 가장 흔한 사각지대.

우리 처리 방식

  • 입력이 압축파일이면 임시폴더에 풀어 내부 파일을 하나하나 개별 분류 (중첩 압축도 재귀)
  • 지원: zip · tar · tar.gz/bz2/xz · gz · bz2 · xz · 7z · rar
  • 결과의 file 은 "<압축경로>/<내부경로>" 로 표기 → 어느 내부 파일이 C 인지 특정 가능
  • 압축 자체의 등급 = 내부 최고 위험등급(C>S>O) 롤업 → archive:true · contains:{C,S,O,미분류} 요약 레코드 추가
  • 처리 후 임시폴더 자동 삭제 — 민감정보 잔존 방지
  • 단, docx/xlsx/pptx/hwpx 는 내부가 zip 이라도 '문서 1개' 로 취급(내용 감지로 구분)

실제 사례 — LGCNS교육.zip

전개된 내부 파일27건 (pdf 3 · ipynb 23 · txt/py 등)
내부 등급 분포C 2 S 20 O 2 미분류 3
압축 자체 등급C ← 내부 최고 위험등급 롤업
내부 처리 시간16.5초 (27건, 건당 0.61초)
핵심 시사점 — 파일 이름은 "교육 자료" 지만 내부에 C 등급 2건이 들어 있었다. 겉면만 보는 방식(출처·파일명)으로는 절대 잡히지 않는 케이스.

이 ZIP 하나가 전체 401건 중 27건(6.7%)을 차지 — 압축 1개가 실질 처리량을 27배로 늘린다는 점은 성능 산정 시 반드시 고려해야 한다.

검토사항 ① 품질 측정 방안

지금까지의 실측은 "몇 건이 어떻게 분류됐는가" 일 뿐, "그 분류가 맞는가" 는 아직 측정하지 못했다. 정답셋(ground truth)이 없다.

왜 어려운가

· C/S/O 는 조직 정책에 따라 정답이 달라진다 — 절대 정답이 없음

· 401건 전수 수동 라벨링은 비현실적

· 단순 정확도(accuracy)는 무의미 — 어느 방향으로 틀렸는지가 훨씬 중요

제안 — 2가지 오류를 분리 측정

과소분류 C·S 를 O 로 판정
→ 유출 사고 직결. 가장 치명적.
C 재현율(Recall) 을 1순위 지표로.

과대분류 O 를 C·S 로 판정
→ 업무 마비·활용 저해.
C 정밀도(Precision) 로 관리.

실행 방안

1) 층화 표본 라벨링
등급·포맷·판정신호별로 200~300건 층화 추출 → 담당자 2인 교차 라벨링(불일치는 협의)

2) 오버라이드 로그 재활용
3차 관리자가 수정한 cso_override.jsonl 을 정답으로 축적 → 운영하면서 정답셋이 저절로 쌓인다

3) 회귀 테스트셋 고정
규칙셋 수정 시마다 동일 표본 재측정 → 튜닝이 다른 곳을 망가뜨리지 않는지 확인

목표 지표(안) — C 재현율 ≥ 95%(놓치면 사고) · O→C 과대분류율 ≤ 10%(업무 마비 방지) · 보류율 ≤ 15%(현재 24.9% → 3차 부담 경감)

결정 필요 — 표본 규모와 라벨링 담당자 지정, 목표 수치의 합의

검토사항 ③ 스캔·이미지 문서 — OCR 부재

우리 방식은 본문 텍스트를 읽어서 판정한다. 텍스트가 없는 문서는 구조적으로 검출이 불가능하다 — 현재 가장 큰 사각지대.

어떤 문서가 해당되나

  • 스캔 PDF — 종이를 스캔한 이미지 PDF. 계약서·인사서류·신분증 사본 등 정작 가장 민감한 문서가 여기 많다
  • 문서 내 첨부 이미지 — HWP·DOC·PPT 안에 그림으로 붙인 표·명단·신분증 캡처
  • 이미지 파일 자체 — jpg·png 로 저장된 화면 캡처
→ 텍스트 추출 결과가 0~수십 자에 그쳐 PII·키워드가 하나도 안 잡힌다.
→ 1차 룰 통과 못 함 → 2차 AI 도 벡터가 무의미 → 전부 보류(none) 로 떨어진다.

다행인 점 — 우리는 이런 문서를 임의로 O 판정하지 않고 보류로 남긴다. --failsafe 옵션으로 기본 S 부여도 가능.

대응 방안(안) — ① 단기: 페이지 대비 추출 글자수가 임계 미만이면 "OCR 필요" 플래그 → 3차 관리자 큐로 강제 이관(현재도 보류로 넘어가나, 사유를 명시해 우선순위 부여)

② 중기: OCR 엔진 연동 — 단, 속도·배포 크기가 다시 문제(페이지당 수백ms~수초, 엔진 수십~수백MB). 대상 문서를 한정한 선택적 OCR 권장

③ 정책: 텍스트 추출 실패 문서에 기본 등급 S 강제 여부 결정 — 결정 필요
