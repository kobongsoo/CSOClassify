C 임베딩 모델 로딩과 --files-from

파일을 하나씩 따로 분류하면 느립니다. 왜 그런지, Rust 판은 왜 Python 처럼 데몬으로 돌지 않는지, 그래서 무엇을 넣었는지를 한자리에 정리했습니다. 실측 2026-09-02.

C-1. 무엇이 느린가 — 모델 로딩이 매번 되풀이된다

전파(Signal B)·--vector-only·--with-vector 처럼 임베딩이 필요한 실행은 ONNX 모델(e5-small-ko, 129MB)을 메모리로 읽어야 합니다. 이 로딩이 실행 한 번에 약 1.4초입니다. 문서를 읽고 규칙을 돌리는 시간과 무관한 고정비라, 파일 200개를 200번 따로 실행하면 이 1.4초를 200번 물게 됩니다.

판모델을 언제 읽나개별 호출이 반복될 때
Python 첫 호출에서 상주 데몬을 자동 기동해 모델을 메모리에 물고 있음(기본 on) 2회차부터 모델 로딩 0
Rust 실행할 때마다 새로 읽고, 프로세스가 끝나면 버림 매번 다시 1.4초

--rule-only 는 모델을 아예 읽지 않으므로 이 이야기와 무관합니다. 규칙만 필요하면 개별 호출도 빠릅니다.

C-2. Rust 는 왜 데몬으로 돌지 않나

먼저 사실관계 — 설계 문서·계획 문서를 뒤져도 "Rust 데몬을 검토했다가 기각했다"는 기록이 없습니다. 기각한 것들은 이유가 남아 있습니다 (libhwp: 실문서 4개 중 2개에서 Rust 패닉, xberg: 117MB·CentOS7 불가·PDF 느림). 데몬에는 그런 기록이 없으니, 검토 후 뺀 것이 아니라 아직 손대지 않은 후속 과제로 보는 것이 맞습니다.

기술적으로 어렵지는 않습니다 — 오히려 Rust 가 유리합니다

Python 데몬은 845줄입니다(client.py 307 · server.py 241 · registry.py 177 · ipc.py 108). 설계서 결정5 가 요구하는 항목을 Rust 로 옮길 때의 난이도는 이렇습니다.

그런데도 Rust 판에서는 껄끄러운 점들 판단

아래는 문서에 적힌 결정이 아니라, 지금 구조를 놓고 본 평가입니다.

  • 정체성 충돌 — Rust 판의 존재 이유가 "정적 단일 바이너리·이식성"인데, 데몬은 상주 프로세스입니다. 방화벽 팝업·백신 오탐·프로세스 잔류 같은 배포 마찰이 생겨, "exe 하나 던지면 끝"이라는 장점을 정면으로 깎습니다.
  • 보안 심사 대상 확대 — 이 도구 자체가 기밀·민감 문서를 다루는 등급 분류기입니다. loopback 소켓을 여는 상주 프로세스는 고객사에서 별도 승인 대상이 됩니다.
  • 이중 유지보수 — IPC 프로토콜·레지스트리 규약이 두 벌이 되고, 두 판의 데몬이 서로를 보지 못하므로 엔드포인트 이름 충돌까지 따로 설계해야 합니다.
  • 우선순위 — Rust 판은 parity(정확도 동등성) 검증이 1순위였고, 데몬은 성능 최적화입니다.
주의 — Rust 는 --serve 를 조용히 무시합니다

--daemon · --no-daemon · --serve · --status · --stop 은 Rust 판에서 인자만 받고 아무 일도 하지 않습니다 (main.rs 의 "파이썬 판에만 있는 옵션들"). 두 판을 같은 명령으로 부르던 호출부가 깨지지 않게 하려는 의도지만, 오류도 안 나고 데몬도 안 뜹니다. 스크립트가 --serve 로 상주시킨 줄 알고 있으면 계속 느린 채로 돕니다. --status 도 빈 출력이라 확인조차 되지 않습니다.

C-3. 그래서 넣은 것 — --files-from <목록> 2026-09-02 신설

데몬을 만드는 대신, 여러 파일을 한 프로세스에 넘기는 길을 열었습니다. 모델을 한 번만 읽으면 되므로 반복 로딩이 사라집니다. Python 판과 Rust 판 모두 같은 이름·같은 규칙으로 들어갔습니다.

E look-behind 가 뭔가 — 그리고 Rust 가 못 하는 것

D절에서 “Rust 정규식은 되돌아가기가 없어 빠르다”고 했습니다. 그 속도는 공짜가 아니라 기능을 포기하고 얻은 것입니다. 포기한 대표가 look-around 이고, 그걸 코드로 흉내 내다 이번에 버그가 여럿 나왔습니다.

개념 — “먹지 않고 앞을 흘긋 보는 조건”

(?<![0-9])[0-9]{3}-?[0-9]{2}-?[0-9]{5}
└───────┘ └────────── 실제로 잡을 모양 ──────────┘
  조건: 바로 앞이 숫자면 시작하지 마라

?<! 는 “뒤(behind)를 보되(look), 아니어야(!) 한다” 는 뜻입니다. 반대로 ?<= 는 “앞이 반드시 ○○여야 한다”입니다. 핵심은 확인만 하고 결과에는 넣지 않는다는 점입니다.

왜 필요한가 — 실측

사업자 220-81-62517 입니다.220-81-62517220-81-62517
주문번호 9220-81-62517 입니다. 220-81-62517 ← 오탐(없음) ✓
계좌 3333220-81-62517 220-81-62517 ← 오탐(없음) ✓

원래 숫자는 9220-81-62517 인데 앞의 9 를 버리면 뒤 12자리가 우연히 사업자등록번호 모양이 됩니다. 체크섬까지 통과하면 오검출입니다. look-behind 는 “숫자 덩어리 한가운데서 시작하지 마라” 로 이를 막습니다.

Rust 는 이걸 못 합니다 — 그래서 생긴 버그 두 갈래

Rust regex 는 look-around 를 지원하지 않아, 정규식으로 찾은 뒤에 코드로 앞뒤 글자를 검사했습니다. 그런데 둘은 미묘하게 다릅니다.

정규식 안의 조건은 실패하면 엔진이 알아서 더 짧은 답을 시도합니다. 밖에서 검사하면 그 재시도가 없습니다. RE_LOOSE_FULL(끝을 한 글자씩 줄이며 다시 맞춰 보기)로 흉내 냈습니다. 숫자 그룹 안에서도 되돌아갑니다 — 강남구 56 실패 → 강남구 5 로 줄여 성립.

Rust 의 ADDRESS·URL 손실은 검출기가 아니라 추출기가 글자를 다르게 뽑은 결과입니다 — (가) 표에서 두 라벨 모두 1.000 인 것이 근거입니다. 포팅 정확도를 말할 때는 (가), 실사용 체감을 말할 때는 (나) 를 보십시오.

① HTML — 버릴 구역 정규식을 태그별로 분리

1) 세 낱말부터 — TP · FP · FN

검출기가 문서에 밑줄을 긋는다고 생각하면 쉽습니다. 밑줄과 정답을 맞춰 보면 경우의 수는 셋뿐입니다.

기호우리말무슨 일이 벌어졌나부록 F 표의 이름
TP맞게 잡음진짜 PII 에 밑줄을 그었다—
FP오탐PII 가 아닌 데 밑줄을 그었다오탐 열
FN미탐진짜 PII 인데 그냥 지나쳤다미탐 열

2) 두 지표 — 분자는 같고 분모만 다르다

정밀도(Precision) = TP / (TP + FP)   ← 분모 = 검출기가 찍은 개수
재현율(Recall)    = TP / (TP + FN)   ← 분모 = 실제로 있는 개수
지표답하는 질문낮으면 생기는 일
정밀도“찍은 것들 중 진짜는 몇 %냐”헛알람이 많다 → 검토 비용 ↑, 문서가 과하게 마스킹돼 못 읽는다
재현율“있는 것들 중 몇 %를 잡았냐”PII 가 샌다 → 유출 사고
둘의 분자는 TP 로 똑같습니다. 다른 것은 분모뿐이고, 분모가 작은 쪽의 값이 큽니다. 이 한 줄이 아래 모든 이야기의 뿌리입니다.

3) 예 — 계약서 한 장

어떤 계약서에 실제 PII 가 20개(주민번호 5 · 휴대폰 8 · 이메일 7) 있습니다. 검출기가 18곳에 밑줄을 그었고, 그중 15개가 진짜였습니다.

TP = 15    (밑줄 18개 중 진짜였던 것)
FP = 3     (18 − 15)  ← 오탐
FN = 5     (20 − 15)  ← 미탐

정밀도 = 15 / 18 = 0.833   → 알람 6번 중 1번은 헛것
재현율 = 15 / 20 = 0.750   → 실제 PII 4개 중 1개가 그대로 통과

무엇이 오탐이고 무엇이 미탐이었는지를 원문으로 보면 감이 확실히 잡힙니다.

4) 왜 둘은 반대로 움직이나

규칙을 느슨하게/빡세게 조이면 두 지표가 시소를 탑니다.

규칙예정밀도재현율실제로 벌어지는 일
느슨“6자리−7자리 숫자면 무조건 RRN”0.600.95 사업자번호·문서번호·계좌번호까지 다 걸려서 문서가 온통 까맣다
빡셈“체크섬까지 통과한 것만 RRN”0.990.70 조용하고 깔끔하지만 PII 30%가 그대로 밖으로 나간다

극단으로 밀면 왜 한쪽만 봐서는 안 되는지가 분명해집니다.

  • 문서의 모든 단어를 PII 라고 하면 → 재현율 1.000, 정밀도 거의 0
  • 가장 확실한 한 개만 PII 라고 하면 → 정밀도 1.000, 재현율 0.05
한쪽 숫자만 적힌 보고서는 아무것도 말해 주지 않습니다

“정밀도 99%” 만 적힌 보고서는 위의 두 번째 경우와 구분되지 않습니다. 정밀도·재현율은 항상 짝으로, 그리고 가능하면 분모(정답 건수)까지 함께 적으십시오. 부록 F 의 표가 정답 열을 굳이 남겨 둔 이유입니다.

5) 재현율이 정밀도보다 작은 게 정상인가 — 아니오

정해진 방향은 없습니다. 2)에서 본 대로 분모가 작은 쪽이 큽니다.

조건결과어떤 검출기인가
찍은 개수 < 실제 개수정밀도 > 재현율보수적 — 확실한 것만 찍는다 (모델·NER 계열)
찍은 개수 > 실제 개수재현율 > 정밀도과잉 — 의심되면 다 찍는다 (정규식 계열)
찍은 개수 = 실제 개수정밀도 = 재현율우연히 균형

3)의 예는 20개 중 18개만 찍은 보수적 경우라 정밀도가 높게 나왔습니다. 같은 검출기가 25곳을 찍고 그중 15개가 맞았다면 정확히 뒤집힙니다 — 정밀도 15/25 = 0.600, 재현율 15/20 = 0.750.

PII 도구는 오히려 재현율이 더 큰 것이 정상 상태입니다. 미탐 비용이 압도적으로 크므로 대부분 과잉 검출 쪽으로 맞춥니다. 운영 중인 PII 검출기에서 정밀도가 재현율보다 한참 높게 나온다면, 그것은 “정확한 검출기”가 아니라 놓치는 게 많은 검출기라는 경고로 읽어야 합니다.

6) F1 은 왜 산술평균이 아닌가

F1 = 2 × 정밀도 × 재현율 / (정밀도 + 재현율)      ← 조화평균

두 값을 그냥 더해 반으로 나누면 한쪽이 형편없어도 점수가 버텨 줍니다. 조화평균은 낮은 쪽에 끌려 내려가므로 그런 눈속임이 통하지 않습니다.

정밀도재현율산술평균F1F2읽는 법
1.0000.1000.5500.1820.122 “정밀도 100%” 자랑이 F1 앞에서 무너진다
0.6000.9800.7900.7440.870 과잉 검출형. F1 은 깎지만 F2 는 인정한다
0.8330.7500.7920.7890.765 3)의 계약서. 균형이 잡히면 셋이 거의 붙는다
0.7900.7900.7900.7900.790 두 값이 같을 때만 산술평균과 정확히 일치한다

F2 는 재현율에 2배 가중을 준 변형입니다 — F2 = 5PR / (4P + R). 미탐이 오탐보다 훨씬 비싼 PII 에서는 F1 대신 F2 로 튜닝 목표를 잡는 편이 실제 위험에 더 맞습니다.

세 숫자의 쓰임이 다릅니다. 재현율은 위험(얼마나 새는가)을, 정밀도는 비용(검토자가 얼마나 헛일하는가)을, F1/F2 는 두 검출기 중 무엇이 나은지 한 줄로 줄 세울 때 씁니다. 튜닝 목표를 F1 하나로 잡지 말고 “재현율 0.995 이상을 지키면서 정밀도 최대화” 처럼 하한선 + 최적화 형태로 잡는 것이 안전합니다.

7) 부록 F 의 표를 이 눈으로 다시 읽기

F-3 의 (가) 표는 미탐·오탐 건수로 적혀 있습니다. 정답 건수로 나누면 이렇게 됩니다.

표에서 바로 읽히는 것 세 가지입니다.

  • 양쪽 다 “보수적” 검출기입니다 — 오탐이 거의 없어 정밀도가 1.000 에 붙어 있고, 떨어지는 쪽은 전부 재현율입니다. ko-pii 규칙이 원래 그렇게 짜여 있다는 뜻입니다.
  • F1 로 줄 세우면 Rust·RRN 이 제일 낮습니다(0.990). 그런데 0.990 이면 숫자만으로는 훌륭해 보입니다 — 여기서 F1 을 믿으면 안 됩니다.
  • 왜냐하면 RRN 은 최고 민감도 라벨이라, 놓친 7건이 곧 주민등록번호 7개 유출이기 때문입니다. 부록 F 가 “pii_corpus.yaml 에 회귀 사례로 넣을 값어치가 있다”고 적은 근거가 이것입니다.
라벨을 뭉쳐 평균 내지 마십시오

부록 F 의 “전체 재현율 Rust 99.73%” 는 정답 10,166건을 통째로 더한 값입니다. 이 한 숫자 안에서 RRN 7건 미탐이 완전히 사라집니다. 라벨마다 유출 시 피해가 다르므로 반드시 라벨별로 따로 재고, 전체 평균은 참고용으로만 쓰십시오. IP 19건과 RRN 7건은 건수로는 IP 가 크지만, 고쳐야 할 순서는 RRN 이 먼저입니다.

8) 잴 때 반드시 먼저 정해야 하는 것

정할 것왜
“맞았다”의 기준
완전일치 / 부분겹침		 정답이 010-1234-5678 인데 검출기가 1234-5678 만 잡았다면 — 완전일치로 세면 미탐·오탐 각 1건, 부분겹침으로 세면 TP 1건입니다. 같은 검출기인데 점수가 10~20%p 씩 움직입니다. PII 마스킹은 일부만 가리면 유출이므로 완전일치(또는 “PII 전체를 덮었는가”)로 세는 것이 맞습니다.
재현율의 분모
정답셋		 정밀도는 검출기가 찍은 것만 사람이 확인하면 나오지만, 재현율은 문서 전체에 PII 가 몇 개인지를 알아야 나옵니다. 정답셋 없이는 계산 자체가 불가능해서 현장에서 정밀도만 보고하고 재현율은 얼버무리기 쉬운데, 위험한 쪽은 재현율입니다. 부록 F 가 ko-pii 출력을 정답으로 삼은 이유가 이것입니다.
정답의 출처가 누구에게 유리한가 F-4 의 (나) 표가 구조적으로 파이썬에 유리했던 것과 같은 함정입니다. 정답을 만든 도구와 재는 대상이 겹치면 점수가 아니라 편향을 재게 됩니다.
한 줄 요약 — 정밀도가 낮으면 사람이 고생하고, 재현율이 낮으면 사고가 납니다. PII 에서는 재현율에 하한선을 못 박고(예: RRN 1.000) 그 안에서 정밀도를 올리십시오. F1 은 검출기끼리 줄 세울 때만 쓰고, 라벨별로 나눠 보기 전에는 어떤 평균도 믿지 마십시오.
