B-4. 감사 파일에 무엇이 들어가나 개인정보 취급

보관 기간을 정하려면 그 파일이 얼마나 민감한지를 알아야 합니다. 기본값(--with-pii 없이)에서는 이렇습니다.

들어가는 것보기
규칙 id 와 건수{"id":"email","count":10} — 이메일 10건 검출
걸린 사전 낱말 L2 규칙 {"term":"소스코드","count":11} — 정책 파일에 적힌 낱말이지 문서 원문 발췌가 아닙니다
파일 경로 · 해시 · 등급 · 확신"hash":"3f47ecd5…"
검출된 원문 값은 들어가지 않습니다. "주민번호 12건 검출"이지 그 번호 자체는 저장하지 않는 것이 이 도구의 불변식입니다. 그래서 감사 파일은 결과 파일과 같은 등급으로 취급하면 됩니다 — 따로 더 무겁게 다룰 이유가 없습니다.
단 --with-pii 를 준 실행은 다릅니다. 그때는 검출된 원문 PII 값이 레코드에 실립니다. 그 감사 파일은 원본 문서와 같은 등급으로 다루고, 보관 기간도 짧게 잡으세요. 정기 분류에는 --with-pii 를 쓰지 않는 것을 권합니다.

참고 — --simple-why 의 why 요약에는 사전 낱말(term)조차 넣지 않습니다. 규칙 id 와 건수만 남기므로 연동용으로 내보내기에 더 안전합니다.

지우기 전에 확인할 것 하나 — 그 기간의 상태 줄이 남아 있는지입니다. 감사 파일을 지우고 상태 줄도 없으면 그 실행은 흔적 없이 사라집니다. 상태 줄을 따로 모아 두는 것을 권합니다(실행마다 한 줄이라 1년치도 몇 MB 입니다).
:: 상태 줄만 따로 쌓기 — 실행할 때마다 한 줄씩 이어 붙인다
csoclassify.exe --dir "D:\collected" --json-errors --simple --nosummary ^
    --format jsonl --out "D:\audit\%DATE%.jsonl" >> "D:\audit\runs.jsonl"

C 임베딩 모델 로딩과 --files-from

파일을 하나씩 따로 분류하면 느립니다. 왜 그런지, Rust 판은 왜 Python 처럼 데몬으로 돌지 않는지, 그래서 무엇을 넣었는지를 한자리에 정리했습니다. 실측 2026-09-02.

C-1. 무엇이 느린가 — 모델 로딩이 매번 되풀이된다

전파(Signal B)·--vector-only·--with-vector 처럼 임베딩이 필요한 실행은 ONNX 모델(e5-small-ko, 129MB)을 메모리로 읽어야 합니다. 이 로딩이 실행 한 번에 약 1.4초입니다. 문서를 읽고 규칙을 돌리는 시간과 무관한 고정비라, 파일 200개를 200번 따로 실행하면 이 1.4초를 200번 물게 됩니다.

판모델을 언제 읽나개별 호출이 반복될 때
Python 첫 호출에서 상주 데몬을 자동 기동해 모델을 메모리에 물고 있음(기본 on) 2회차부터 모델 로딩 0
Rust 실행할 때마다 새로 읽고, 프로세스가 끝나면 버림 매번 다시 1.4초

--rule-only 는 모델을 아예 읽지 않으므로 이 이야기와 무관합니다. 규칙만 필요하면 개별 호출도 빠릅니다.

C-2. Rust 는 왜 데몬으로 돌지 않나

먼저 사실관계 — 설계 문서·계획 문서를 뒤져도 "Rust 데몬을 검토했다가 기각했다"는 기록이 없습니다. 기각한 것들은 이유가 남아 있습니다 (libhwp: 실문서 4개 중 2개에서 Rust 패닉, xberg: 117MB·CentOS7 불가·PDF 느림). 데몬에는 그런 기록이 없으니, 검토 후 뺀 것이 아니라 아직 손대지 않은 후속 과제로 보는 것이 맞습니다.

기술적으로 어렵지는 않습니다 — 오히려 Rust 가 유리합니다

Python 데몬은 845줄입니다(client.py 307 · server.py 241 · registry.py 177 · ipc.py 108). 설계서 결정5 가 요구하는 항목을 Rust 로 옮길 때의 난이도는 이렇습니다.

요구사항Rust 에서
엔드포인트 원자적 생성으로 싱글턴 보장(TOCTOU 방지)같음 — OS 기능이라 언어 무관
loopback 바인딩 + 랜덤 토큰 인증같음
모델별 데몬 레지스트리 · 버전 핸드셰이크같음
자기 자신을 --serve 로 재실행 더 쉬움 — current_exe(). Python 은 PyInstaller onefile 때문에 sys.executable 우회가 필요했다
동시 요청 직렬화더 쉬움 — GIL 없는 실제 스레드
유휴 자동종료 · stale pid 정리같음

즉 기술적 장벽이 아니라 작업량 문제입니다. Python 이 감수해야 했던 성가신 제약이 Rust 에는 오히려 없습니다.

그런데도 Rust 판에서는 껄끄러운 점들 판단

아래는 문서에 적힌 결정이 아니라, 지금 구조를 놓고 본 평가입니다.

  • 정체성 충돌 — Rust 판의 존재 이유가 "정적 단일 바이너리·이식성"인데, 데몬은 상주 프로세스입니다. 방화벽 팝업·백신 오탐·프로세스 잔류 같은 배포 마찰이 생겨, "exe 하나 던지면 끝"이라는 장점을 정면으로 깎습니다.
  • 보안 심사 대상 확대 — 이 도구 자체가 기밀·민감 문서를 다루는 등급 분류기입니다. loopback 소켓을 여는 상주 프로세스는 고객사에서 별도 승인 대상이 됩니다.
  • 이중 유지보수 — IPC 프로토콜·레지스트리 규약이 두 벌이 되고, 두 판의 데몬이 서로를 보지 못하므로 엔드포인트 이름 충돌까지 따로 설계해야 합니다.
  • 우선순위 — Rust 판은 parity(정확도 동등성) 검증이 1순위였고, 데몬은 성능 최적화입니다.
주의 — Rust 는 --serve 를 조용히 무시합니다

--daemon · --no-daemon · --serve · --status · --stop 은 Rust 판에서 인자만 받고 아무 일도 하지 않습니다 (main.rs 의 "파이썬 판에만 있는 옵션들"). 두 판을 같은 명령으로 부르던 호출부가 깨지지 않게 하려는 의도지만, 오류도 안 나고 데몬도 안 뜹니다. 스크립트가 --serve 로 상주시킨 줄 알고 있으면 계속 느린 채로 돕니다. --status 도 빈 출력이라 확인조차 되지 않습니다.

C-3. 그래서 넣은 것 — --files-from <목록> 2026-09-02 신설

데몬을 만드는 대신, 여러 파일을 한 프로세스에 넘기는 길을 열었습니다. 모델을 한 번만 읽으면 되므로 반복 로딩이 사라집니다. Python 판과 Rust 판 모두 같은 이름·같은 규칙으로 들어갔습니다.

기존 --dir 은 폴더 하나 아래만 훑을 수 있어서, 대상이 여러 폴더에 흩어져 있으면 배치로 묶을 방법이 없었습니다. --files-from 은 그 제약을 없앱니다.

규칙동작
목록 형식파일 경로를 한 줄에 하나씩. - 를 주면 표준입력에서 읽음
빈 줄 · # 로 시작하는 줄무시(주석으로 쓸 수 있음)
따옴표로 감싼 경로따옴표를 벗겨서 처리(dir /b 결과를 그대로 써도 됨)
BOM흡수 — 메모장으로 저장한 목록도 첫 줄이 유실되지 않음
같은 경로가 여러 번처음 것만 — 같은 문서를 두 번 임베딩하지 않음
없는 경로 · 폴더건너뛰고 몇 건 건너뛰었는지 stderr 로 알림
처리 순서목록에 적은 순서 그대로(정렬하지 않음)
--file/--dir 과 함께 주면 오류(bad_args, 종료코드 3) — 어느 쪽이 진짜 대상인지 모호해지므로 그 자리에서 막는다
:: 목록 만들기 (Windows) — 여러 폴더를 한 목록으로
dir /b /s "D:\분류함\인사" "D:\분류함\계약" > list.txt

:: 한 프로세스로 전부 처리
csoclassify-rs.exe --files-from list.txt --simple --nosummary --format jsonl --out out.jsonl
csoclassify.exe    --files-from list.txt --simple --nosummary --format jsonl --out out.jsonl

:: 파이프로 바로 넘기기 (표준입력)
dir /b /s D:\분류함\*.pdf | csoclassify-rs.exe --files-from - --simple

C-4. 벤치마크 결과

대상 — D:\분류함 의 문서 1,050건 중 두 판이 모두 추출을 지원하는 포맷만 골라 균등 간격으로 200건을 뽑았습니다. pdf 69 · txt 64 · pptx 28 · docx 18 · md 11 · xlsx 6 · hwpx 3 · html 1

doc·ppt·hwp·xls(구형 OLE)는 일부러 뺐습니다 — Rust 는 이 포맷들의 추출을 지원하지 않아 건너뜁니다. 넣으면 Rust 가 일을 덜 하고도 빨라 보여 비교가 왜곡됩니다.

조건 — --with-vector(모든 문서를 임베딩해 고정비가 반드시 드러나게), 동일 PC.

읽는 법 — 네 가지

  1. --files-from 의 효과가 가장 큽니다. Rust 320.6초 → 44.0초, 데몬 끈 Python 471.6초 → 62.8초. 엔진을 바꾸는 것보다 호출 구조를 바꾸는 쪽이 훨씬 크게 먹힙니다.
  2. 배치에서는 Rust 가 빠릅니다(44.0초 vs 62.8~84.0초). 모델 로드 고정비가 200건에 희석되면서 추출·규칙 처리 속도가 그대로 드러납니다. 문서 10건짜리 작은 실험에서는 Python 이 앞섰는데, 그건 고정비가 희석될 여지가 없었기 때문입니다.
  3. 개별 호출에서는 Python(데몬 on)이 빠릅니다(265.5초 vs 320.6초). 데몬이 모델 로드를 0 으로 만들기 때문이며, 이것이 Rust 의 실제 갭입니다.
  4. 그런데 --files-from 을 쓰면 데몬이 할 일이 없어집니다. 한 프로세스면 모델 로드가 어차피 1회라, Python 도 데몬을 끈 쪽(62.8초)이 켠 쪽(84.0초)보다 느리지 않았습니다. → Rust 에 데몬을 포팅할 필요가 그만큼 줄었습니다.
권장 — 외부 시스템이 이 CLI 를 부를 때는 파일마다 부르지 말고 목록을 만들어 --files-from 으로 한 번에 넘기십시오. 두 판 모두에서 가장 큰 이득이고, 상주 프로세스도 필요 없습니다.

C-5. 측정 조건과 한계 중요

  • 산포가 큽니다. 배치 3회 반복에서 Rust 32.6~57.0초, Python(데몬) 66.6~143.0초로 흔들렸습니다(디스크 캐시 워밍 영향). 표의 값은 중앙값입니다.
  • 200회 개별 호출은 시간 때문에 1회만 측정했습니다.
  • 따라서 배수(7배)와 대소 관계는 견고하지만, 초 단위 절대값은 ±30% 로 보십시오.
  • 결과 대조에서 두 판의 보안등급 199/200(99.5%) 일치를 확인했습니다. 업무분류 축은 179/200(89.5%) 로 별도 갭이 있으며, 이는 --files-from 과 무관한 기존 사안입니다.
대조 중 발견 — Python 배포본에 seed 파일이 없습니다. dist-onedir/windows/ 에는 cso_seed.jsonl.bak-20260831(백업)만 있고 활성 seed 가 없어, 전파(Signal B)가 아예 돌지 않고 보류 문서 21건이 등급 없이 (null) 나갔습니다. Rust 쪽에는 class_seed.jsonl(19건)이 있습니다. Rust 의 seed 를 --seeds 로 지정해 다시 돌리자 위의 99.5% 가 나왔습니다 — 엔진 문제가 아니라 배포 폴더에 파일이 빠진 것입니다.
