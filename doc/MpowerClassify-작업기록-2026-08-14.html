1 L1 PII 검출 성능 최적화

규칙 스캔(classify/rules.py)이 쓰던 ko_pii.detect_all()은 28개 검출기를 전부 돌린 뒤 결과만 필터링해 낭비가 컸다. 세 단계로 최적화하되 검출 결과는 동일하게 유지.

#최적화방법효과(실측)
1부분 검출detect_all → 필요한 검출기만 도는 _detect_subset() (18종 → 2026-08-15 URL·IP 추가로 20종, 아래 §10)~54% ↓ (179→82ms/10KB)
2지연 가드
(초판)		_KOPII_MAX_CHARS 300K→10K + 환경변수 CSOCLASSIFY_KOPII_MAX_CHARS — 2026-08-15 청킹으로 교체(아래 개정 참조)최악 20s → 0.08s
3주소 프리필터주소 신호 없으면 무거운 address.detect(O(n²)) 건너뜀주소無 문서 ~34% ↓
안전성 — 부분검출은 매핑 못한 라벨이 오면 전체 엔진으로 자동 폴백. 주소 프리필터는 address.detect 의 4개 패턴이 반드시 포함하는 신호((대로|로|길|동|읍|면|리)+숫자 또는 _LOOSE_ANCHORS)로만 판정 → 실제 주소 표본 전건 통과, 미탐 0. 정규화·겹침해소는 ko-pii 내부 함수 재사용.

검토 후 기각: python-stdnum(전화·주소 모듈 없음), phone/account 자체 정규식 대체(현실 비중 1~9%로 실익 없음). 무거운 건 address 하나뿐.

개정 (2026-08-15) — 지연 가드를 '청킹'으로 교체: 위 ②의 '앞 10K 절단'은 10K 넘는 문서에서 뒤쪽 phone/address 를 놓치는 미탐 문제가 있어 다음 설계로 교체했다. ⑴ 선형/초선형 분리 — 초선형 비용 원인인 phone·address·account만 청킹 대상(_KOPII_SUPERLINEAR), 나머지 선형 검출기는 전량 스캔(상한 없음, 문서 끝의 주민·카드·이메일도 커버). ⑵ 초선형 청킹 — 10K 창으로 나눠 돌려 초선형 비용을 선형화(50K 0.9s→~0.4s, 300K 20s→~2.4s). ⑶ 경계 처리 — 인접 창 오버랩 128 + 절대 오프셋 구간 병합으로 경계 미탐·이중계수 제거. ⑷ 지연 캡 — 초선형은 앞 100K까지(_KOPII_MAX_TOTAL). ⑸ 소형 문서(≤10K, 대다수)는 단일패스라 검출 결과 불변. env _KOPII_MAX_CHARS 의미가 '절단 상한'→'청크 크기'로 바뀌고 _MAX_TOTAL/_OVERLAP 신설. 회귀 테스트 3건 추가(21→24). 상세는 plan/설계서.md 결정7 개정 이력.

2 처방전 라벨 버그 + 회귀 테스트

발견: cso_rule.yaml의 처방전 라벨이 PRESCRIPTION인데 ko-pii 검출기는 PRESCRIPTION_ID를 내보내 처방전이 한 건도 검출되지 않던 상태. 라벨을 PRESCRIPTION_ID로 수정.

회귀 테스트 6건 추가(tests/test_rules.py 15→21 pass): 처방전 검출/anchor, 규칙 라벨 == 검출기 라벨 구조 가드(이런 오타 재발 차단), _detect_subset == detect_all 동일성, 주소 프리필터 미탐0·게이트 동일성.

4 출력 · 인자 개선

기본 출력 JSON

DEFAULT_FORMAT text→json. --file 단건은 JSON 객체, --dir 배치는 JSON 배열 [ … ](유효 JSON 파일). 스트리밍/줄단위는 --format jsonl. 공용 output.RecordWriter 가 배열 경계를 관리. --propagate는 배열·객체·jsonl 입력을 모두 인식.

회귀 수정 — 기본을 json으로 바꾸며 배치가 "들여쓴 객체를 이어붙여" 무효 JSON이 되던 문제를, 배치=배열로 감싸 해결(--dir --out X.json 이 뷰어로 열림).

인자 대시 통일

-file/-dir(비표준) → --file/--dir(GNU 관례)로 통일. 하위호환으로 -file/-dir는 별칭 유지. 내부 호출부(ui/gerunner.py)·.bat·help·문서 모두 갱신.

5 규칙셋 외장화

C/S/O 규칙셋(cso_rule.yaml)을 exe에 내장하지 않고 exe 옆 외장 파일로 배포 → 재빌드 없이 규칙 교체. 우선순위: CSOCLASSIFY_POLICY_DIR > --rules > exe 옆.

  • default_rules_path(): frozen(exe) → exe 옆 / 소스 → resources/policy
  • 두 spec에서 정책 번들 제거
  • 파일 누락 시 원시 스택 대신 "어디에 두라"는 안내 후 EXIT_ARG_ERROR(3) 종료

6 크로스플랫폼(리눅스)

플랫폼 분기 + OS 하위폴더

사이냅 필터를 OS별로 분리: synap/windows/{snf_exe.exe, snf_win.dll}, synap/linux/snf_exe. resources.synap_exe_name()/synap_os_subdir()/synap_exe_path()가 OS별 이름·폴더를 자동 해석(평면 배치 폴백). spec collect_synap()은 빌드 OS 폴더에서 번들.

리눅스 snf_exe는 정적 링크 ELF라 단독 실행 — libsnf.a/.h는 네이티브 링크용이라 불필요.

7 onedir 기본 배포 정리

onefile은 실행마다 자기 압축해제로 웜 시작 ~4.6초 → 대화형에 불리. onedir(웜 ~2초)를 기본 배포로 채택. 두 방식 모두 사이냅·모델·규칙셋을 exe 옆 외장으로 두는 구성으로 통일.

배포폴더실행파일웜 시작
onedir 권장dist-onedir/{windows,linux}폴더(exe+_internal/)~2초
onefiledist-pkg/단일 exe~4.6초
dist-onedir/ dist-pkg/ (onefile, 정리됨) ├─ windows/ ├─ MpowerClassify.exe # Windows │ ├─ MpowerClassify.exe + _internal/ ├─ MpowerClassify_linux.exe # Linux(143MB) │ ├─ cso_rule.yaml ├─ cso_rule.yaml │ ├─ synap/windows/ ├─ e5-small-ko.tar.xz │ └─ models/e5-small-ko/ ├─ synap/{windows,linux}/ └─ linux/ └─ 샘플.hwp · 사용법.txt · 문서_임베딩_테스트.bat ├─ csoclassify-onedir-linux.tgz # 리눅스에서 tar 풀기(심볼릭링크 보존) ├─ cso_rule.yaml · synap/linux/ ├─ models/e5-small-ko/ └─ README.txt
리눅스 주의 — csoclassify-onedir-linux.tgz는 반드시 리눅스에서 풀 것(Windows에서 풀면 _internal의 .so 심볼릭링크가 깨짐). 푼 뒤 chmod +x csoclassify synap/linux/snf_exe. 외장 snf_exe는 복사 시 실행권한이 사라지므로 반드시 chmod +x.

검증: Windows onedir — 분류 C · 임베딩 dim 384 · 웜 ~2s. Linux onedir — 서버 빌드·분류 검증(C).

9 진단 · Q&A

elapsed_ms 는 밀리초

"total": 17.73 = 17.73ms = 0.018초(1.7초 아님). 단, 체감 시간은 exe 자기 압축해제·파이썬 시작·모델 로딩이 지배 — 실측 onefile 웜 ~4.6초/콜드 ~24초 vs onedir 웜 ~0.65~2초. elapsed_ms엔 이 오버헤드가 안 잡힌다.

hwpx 분류가 null 로 나온 이유

추출은 정상(29KB). 문서가 제안서 양식이라 PII 0건·기밀 키워드 0건 → grade=null(보류)이 정확한 결과. "비밀"(5회)은 오탐 방지를 위해 규칙에서 의도적으로 제외(대외비/극비/기밀 등 구체어만 사용).

seed 자동 전파?

--classify 단독은 폴더의 cso_seed.jsonl을 자동으로 쓰지 않는다(설계상, 규칙 확정 문서 과분류 방지). --auto-propagate --seeds cso_seed.jsonl 명시 필요. test.hwpx는 전파해도 최근접 seed 유사도 0.489 < MIN_SIM 0.55라 too_far(보류) — 이것도 정상(보수적). 분류하려면 비슷한 seed 추가/임계값 조정/규칙 추가.

10 PII 유형 확장(URL·IP) + 원문값 출력 옵션 (2026-08-15)

① URL·IP 검출 추가 (18종 → 20종)

ko-pii 의 url·ip 검출기를 활성 PII 에 추가. cso_rule.yaml 에 URL·IP 규칙(네트워크 식별자 → base_grade O·대량이면 S), rules.py 의 라벨→검출기 맵에도 등록. 실측: url·ip·email 정상 검출.

② 검출 원문 PII 출력 옵션 --with-pii

이 도구의 핵심 원칙은 "원문 PII 값 미저장"(기본은 유형+건수만). 사용자가 --with-pii 로 명시 요청할 때만 검출된 원문 값을 결과의 pii 필드에 싣는다.

프라이버시 설계 — 기본 off. 원문 PII 는 --out 파일에만 남고 로그엔 절대 안 남는다(_loggable_record 가 [pii N detected] 로 가림). 결과 파일 취급 주의.
MpowerClassify.exe --classify --with-pii --file "문서.hwp" --out result.json
──
"pii": [
  { "label": "RRN",  "value": "900101-1234568",      "start": 7,  "end": 21 },
  { "label": "IP",   "value": "192.168.0.10",         "start": 70, "end": 82 }
]

구현: rules.collect_pii() · engine.build_record(with_pii=) · cli --with-pii · _loggable_record 가림. 회귀 테스트 24종 통과. 4개 배포본 모두 재빌드(Windows·Linux × onefile·onedir), 규칙셋(URL/IP)은 외장이라 각 배포 폴더에 복사.
