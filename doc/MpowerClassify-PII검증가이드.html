Rust PII 포팅 검증 가이드

골든 픽스처(정답표)로 MpowerClassify-rs 의 PII 검출이 ko-pii 와 같은지 확인하는 방법 — 프로그래밍을 몰라도 순서대로 따라 할 수 있게 썼습니다.

이 문서는 무엇인가

“Rust 판이 만든 PII 검출 결과가 진짜 정답과 같은지 어떻게 확인하느냐”를 다룹니다. 명령 두 줄이면 끝나지만, 왜 그 두 줄인지와 빨간불이 떴을 때 무엇을 봐야 하는지까지 적었습니다.

읽는 사람: 이 프로젝트를 처음 만진 개발자 / 인수인계 받는 담당자 / ko-pii 버전을 올려야 하는 사람.

1왜 검증이 필요한가

이 프로젝트에는 실행파일이 두 개 있고, 둘은 PII(개인정보)를 서로 다른 방식으로 찾습니다.

실행파일PII 검출 방식
MpowerClassify.exe
Python 판		 ko-pii 라이브러리를 그대로 가져다 씁니다. 외부에서 만든 검증된 부품을 끼워 넣은 셈입니다.
단, 빌드할 때 exe 안에 복사해 넣습니다(_internal\ko_pii). 그래서 exe 는 만들어진 날의 ko-pii 를 그대로 들고 다닙니다.
MpowerClassify-rs.exe
Rust 판		 ko-pii 를 쓰지 않고, 같은 알고리즘을 직접 옮겨 적었습니다(Rust/src/pii.rs, 약 1,000줄). 파이썬 없이 도는 단일 실행파일을 만들기 위해서입니다.

여기서 문제가 생깁니다. Rust 판은 ko-pii 를 쓰는 게 아니라 베껴 적은 것이라, ko-pii 가 바뀌어도 Rust 는 저절로 따라가지 않습니다. 아무 오류도 안 나고, 조용히 다른 답을 내기 시작합니다. 그래서 검증이 필요합니다.

ko-pii 버전이 네 곳에 따로 존재합니다 중요

이 프로젝트에서 “ko-pii 버전”은 하나가 아닙니다. 아래 네 곳이 각자 따로 놉니다.

#어디에언제 바뀌나
①requirements.txt 에 적힌 버전
= 우리가 쓰기로 선언한 버전		 사람이 파일을 고칠 때
②MpowerClassify.exe 안에 박힌 ko-pii
= 배포본이 실제로 쓰는 버전		 Python exe 를 새로 빌드할 때만
③개발 PC 의 pip 환경
= 정답표를 만드는 버전		 pip install 할 때
④Rust/src/pii.rs 에 옮겨 적힌 로직
= Rust 판이 쓰는 사본		 사람이 코드를 고칠 때만
가장 흔한 오해: pip install --upgrade ko-pii 를 하면 프로그램이 새 ko-pii 를 쓴다.
→ 틀렸습니다. 그건 ③만 바꿉니다. MpowerClassify.exe(②)는 빌드할 때 복사해 넣은 옛 ko-pii 를 계속 씁니다.
ko-pii 를 진짜로 올리려면 ① requirements.txt 의 버전을 고치고 ② Python exe 를 새로 빌드해야 합니다. 자세한 순서는 절차 B.

버전이 맞는지 확인하는 법 — --version + pip show

두 exe 는 자기가 어느 ko-pii 기준인지 직접 찍어 줍니다. 여기에 개발 PC 에 실제로 깔린 버전(③) 까지 더해 세 줄의 버전 숫자가 모두 같아야 같은 기준으로 도는 것입니다. ②·④ 만 맞춰 보면 정답표를 만드는 ③ 이 어긋난 걸 놓칩니다.

MpowerClassify.exe --version
csoclassify 0.1.0 (ko-pii 1.15.2)          ← ② exe 안에 박힌 버전

MpowerClassify-rs.exe --version
MpowerClassify-rs 0.1.0 (ko-pii 포팅 기준 1.15.2)   ← ④ 옮겨 적을 때 본 버전

pip show ko-pii
Name: ko-pii
Version: 1.15.2                             ← ③ 이 PC 에 깔린 버전(정답표를 만드는 버전)
Summary: 한국어 PII 검출 + 가역 가명화 라이브러리 (ML 없이 룰 기반)
Home-page: https://github.com/Marker-Inc-Korea/ko-pii
License: MIT
Location: C:\Users\...\Python312\Lib\site-packages

표기가 다른 이유가 있습니다. Python 판은 ko-pii 를 실제로 품고 있어서 그 버전을 읽어 찍고, Rust 판은 품은 게 없어서 “어느 버전을 보고 옮겨 적었는지” 를 찍습니다. 역할은 같습니다 — 기준이 같은지 맞춰 보는 용도입니다.

Rust 쪽 숫자는 사람이 손으로 적는 값이라 낡을 수 있습니다. 그래서 cargo test 에 포팅기준_버전이_정답표와_같다 테스트가 있어, 정답표를 새 ko-pii 로 다시 뽑으면 이 숫자가 먼저 깨집니다. --version 이 거짓말을 하지 못하게 묶어 둔 것입니다.
pip show 를 꼭 같이 보세요. exe 두 개는 빌드할 때 정해진 값을 찍을 뿐이라, 지금 이 PC 에서 pytest · 정답표 생성이 어느 ko-pii 로 도는지는 알려 주지 못합니다. 그건 pip show 만 답할 수 있습니다.
가상환경을 쓴다면 테스트를 돌릴 바로 그 환경을 활성화한 뒤 찍어야 합니다. conda/venv 마다 버전이 다를 수 있어, 엉뚱한 환경에서 찍은 pip show 는 아무것도 보증하지 않습니다. 확실히 하려면 python -m pip show ko-pii 로 인터프리터를 고정해 부르세요. 출력의 Location: 줄을 보면 어느 환경인지 드러납니다.
선언값(①)까지 한 번에 보려면 — 아래 한 줄이면 네 곳 중 ①·③ 을 같이 확인합니다.
저장소 루트에서 실행:
findstr ko-pii requirements.txt ui\requirements.txt && python -m pip show ko-pii
핀은 requirements.txt 와 ui/requirements.txt 두 곳에 있습니다. 한쪽만 고치면 CLI 와 검토 UI 가 서로 다른 ko-pii 로 돌게 됩니다.
여기서 진짜 함정이 나옵니다. 정답표는 ③(개발 PC 의 pip) 으로 만듭니다. 그런데 검증하고 싶은 대상은 ②(배포 exe 가 실제로 쓰는 ko-pii) 입니다. ③과 ②가 다르면, cargo test 가 초록불이어도 배포된 두 exe 는 다른 답을 냅니다.
예: 개발 PC 에 1.16 을 깔고 정답표를 다시 뽑으면 Rust 는 1.16 기준으로 검증되지만, 재빌드하지 않은 MpowerClassify.exe 는 여전히 1.15.2 로 동작합니다.
그래서 ① = ② = ③ 을 항상 같게 유지하는 것이 이 검증 체계의 전제입니다.
등급만 비교하면 안 되는 이유. “두 exe 를 돌려 최종 등급(C/S/O)이 같으면 됐지”라고 생각하기 쉽지만 부족합니다. 등급은 라벨별 건수를 임계값으로 뭉갠 결과라서, Rust 가 전화번호를 3건 놓쳐도 다른 라벨 덕에 등급이 같으면 그냥 통과합니다. 그래서 PII 는 라벨별 건수까지 내려가서 봐야 합니다.

(체크섬·전화 7패턴 등 10건)		 코드를 고칠 때마다

3층

평소에는 1·2층만 돌리면 됩니다. 3층은 무겁습니다 — pdfium·사이냅 필터·ONNX 모델·정책 yaml 을 전부 갖춰야 한 번 돌아갑니다. 반면 1·2층은 ko-pii 도, 파이썬도, 문서 파일도 필요 없이 명령 하나로 끝납니다.

2층(골든 픽스처)이 정확히 무슨 뜻인가

골든(golden) = 정답, 픽스처(fixture) = 고정해 둔 검사용 데이터입니다. 합치면 “정답을 미리 뽑아 파일로 굳혀 둔 것”입니다. 이 문서에서는 정답표라고 부릅니다.

[한 번만] 진짜 ko-pii 에게 물어서 정답을 받아 파일로 저장 ko-pii ──▶ "이 문장에는 전화번호 1건, 주소 1건" ──▶ pii_golden.json [매번] Rust 가 같은 문장을 풀고, 저장해 둔 정답과 맞춰 본다 Rust ──▶ "전화번호 1건, 주소 1건" ──▶ 정답표와 대조 ──▶ ✅ 또는 ❌

학원에서 답안지를 미리 받아 두고 채점하는 것과 같습니다. 채점할 때마다 선생님(ko-pii)을 부를 필요가 없으니 빠르고, 답안지가 파일로 남아 있으니 누가 언제 돌려도 같은 기준으로 채점됩니다.

3준비 (딱 한 번만)

1PowerShell 열기

키보드에서 Windows 키를 누르고 powershell 이라고 친 뒤 Windows PowerShell 을 엽니다. 검은(또는 파란) 글자 창이 뜨면 성공입니다. 여기에 명령을 한 줄씩 붙여넣고 Enter 를 누르면 됩니다.

2프로젝트 폴더로 이동

cd D:\Project\MpowerClassify

앞으로 나오는 명령은 모두 이 폴더 기준입니다. 창을 새로 열 때마다 이 줄부터 다시 실행하세요.

3필요한 도구가 깔려 있는지 확인

python --version
cargo --version

아래처럼 버전이 나오면 준비된 것입니다. (숫자는 조금 달라도 괜찮습니다)

Python 3.12.10
cargo 1.98.0 (797e8a9bc 2026-08-05)

'cargo' 은(는) ... 인식되지 않습니다 라고 나오면 Rust 가 없는 것입니다 → rustup.rs 에서 설치하고 PowerShell 을 새로 열어 다시 확인하세요.

4ko-pii 설치 — 정답표를 만들거나 확인할 때만 필요

pip install -r requirements.txt
버전을 직접 타이핑하지 말고 requirements.txt 를 통해 까세요. 거기 적힌 버전(현재 ko-pii==1.15.2)이 이 프로젝트의 기준이고, 정답표도 그 버전이 만든 답입니다. 다른 버전을 깔면 “정답표가 낡았다”고 나옵니다. 일부러 올리는 경우라면 절차 B 를 보세요.

참고: 채점(cargo test)만 할 거라면 ko-pii 도 파이썬도 필요 없습니다. 정답이 이미 파일로 저장돼 있기 때문입니다.

4【절차 A】 평소 검증 — 명령 두 줄

PII 관련 코드를 고쳤다면 반드시 이 두 줄을 돌립니다.

1정답표가 최신인지 확인

python scripts/gen_pii_golden.py --check

지금 깔린 ko-pii 로 정답을 다시 뽑아서, 저장된 정답표와 같은지 비교만 합니다. 파일을 고치지는 않으므로 안심하고 돌려도 됩니다.

정상: [확인] 정답표가 최신이다(31건).
다름: [다름] 정답표가 현재 ko-pii(...) 결과와 다르다. → 개발 PC 의 ko-pii 버전이 정답표를 만든 버전과 다릅니다. 둘 중 하나입니다.
  • 모르게 바뀐 것(대부분) → pip install -r requirements.txt 로 선언된 버전으로 되돌립니다.
  • 일부러 올리는 중 → 절차 B 를 끝까지 밟습니다(재빌드 포함).

ko-pii 를 안 깔았다면 이 단계는 건너뛰고 2번만 해도 됩니다. 다만 “정답표가 낡았는지”는 확인되지 않습니다.

2Rust 채점하기

cd Rust
cargo test

Rust 코드 전체 테스트가 돕니다. PII 만 빨리 보고 싶으면 이렇게 하세요.

cargo test pii

처음 한 번은 컴파일하느라 1~2분 걸릴 수 있습니다. 두 번째부터는 몇 초입니다.

돌려야 하는 세 가지 PII 테스트

테스트 이름무엇을 보나깨지면 의미
정답표와_라벨별_건수가_같다 사례마다 라벨별 건수가 ko-pii 와 같은가 못 잡았거나(미탐), 없는 걸 잡았다(오탐)
정답표와_검출값이_같다 잡은 글자 자체가 같은가 건수는 맞지만 범위가 틀렸다
예: +82-10-... 에서 +82 가 잘림
정답표가_20라벨을_모두_덮는다 정답표가 20라벨을 빠짐없이 검사하는가 어떤 라벨이 검사에서 빠졌다
= Rust 가 0건을 내도 통과해 버리는 상태
세 번째가 왜 필요한지 헷갈릴 수 있습니다. 정답표에서 어떤 라벨이 한 번도 안 나오면, Rust 가 그 라벨을 아예 못 잡아도 앞의 두 테스트는 초록불이 됩니다. “검사한 줄 알았는데 안 한” 상태를 막는 그물입니다.

5결과 읽는 법

✅ 통과했을 때

running 13 tests
test pii::golden::정답표가_20라벨을_모두_덮는다 ... ok
test pii::tests::유효한_사업자등록번호는_검출한다 ... ok
... (중략) ...
test pii::golden::정답표와_검출값이_같다 ... ok
test pii::golden::정답표와_라벨별_건수가_같다 ... ok

test result: ok. 13 passed; 0 failed; 0 ignored; 0 measured; 127 filtered out
맨 아랫줄 test result: ok 와 0 failed 만 보면 됩니다. 이 둘이면 통과입니다. cargo test 전체는 140 passed; 0 failed 가 나옵니다.

filtered out 은 “이번엔 안 돌린 다른 테스트”라는 뜻이지 실패가 아닙니다. ignored·measured 도 0이면 신경 쓸 것 없습니다.

어느 쪽이 잘못인지 먼저 판단하세요. 두 가지 경우가 있고, 대응이 정반대입니다.

7【절차 B】 ko-pii 버전을 올렸을 때

ko-pii 를 새 버전으로 바꾸면 정답 자체가 바뀝니다. 그래서 “선언 → 설치 → 정답표 → Rust → 재빌드” 순서를 끝까지 밟아야 합니다.

중간에 멈추면 안 됩니다. pip install 만 하고 끝내면 개발 PC(③)만 새 버전이 되고, MpowerClassify.exe(②)는 옛 버전 그대로입니다. 그 상태에서 정답표를 다시 뽑으면 Rust 는 새 버전 기준으로 검증되는데 배포본은 옛 버전으로 도는, 가장 나쁜 어긋남이 생깁니다(1장 참고).

1선언부터 고치기 — requirements.txt

requirements.txt 의 ko-pii==1.15.2 줄을 올릴 버전으로 바꿉니다. 여기가 기준점이라 가장 먼저 고칩니다.

ko-pii==1.16.0         # L1 PII 검출 엔진

2개발 PC 에 설치

pip install -r requirements.txt

requirements.txt 를 통해 깔면 ①과 ③이 자동으로 같아집니다. pip install ko-pii==1.16.0 로 직접 깔면 ①을 고치는 걸 잊기 쉽습니다.

3정답표 다시 뽑기 — 이번엔 --check 없이

cd D:\Project\MpowerClassify
python scripts/gen_pii_golden.py
[생성] D:\Project\MpowerClassify\Rust\tests\pii_golden.json
       사례 31건 / 검출 42건 / ko-pii 1.16.0

4무엇이 달라졌는지 눈으로 확인

git diff Rust/tests/pii_golden.json

여기 나오는 차이가 곧 “새 ko-pii 가 달라진 지점” 입니다. 아무 차이도 없으면 이번 업데이트는 우리가 쓰는 20라벨에 영향이 없다는 뜻이니 그대로 끝내면 됩니다.

5Rust 를 새 정답에 맞추기

여기서 깨지는 항목이 Rust 가 따라가야 할 변경분 목록입니다. 하나씩 Rust/src/pii.rs 를 고쳐 초록불로 만듭니다.

7마무리 — 기록과 커밋

README.md 의 설치 안내에 적힌 ko-pii 버전도 함께 바꿉니다. 그리고 requirements.txt·정답표·pii.rs 를 한 커밋으로 같이 올리세요 — 따로 올리면 중간 커밋이 깨진 상태가 됩니다.

이 절차의 가치는 “일이 늘어난다”가 아니라 변경분이 눈에 보이게 된다는 데 있습니다. 정답표가 없으면 ko-pii 업데이트로 무엇이 달라졌는지 아무도 모른 채 지나갑니다.
반대 방향의 사고도 조심하세요. 개발 PC 에서 다른 작업 때문에 ko-pii 가 딸려 올라가는 경우가 있습니다(다른 프로젝트, --upgrade, 새 가상환경 등). 그러면 절차 A 의 --check 가 “정답표가 낡았다”고 알려 줍니다. 이때 무심코 정답표를 다시 뽑지 말고, 먼저 pip install -r requirements.txt 로 선언된 버전으로 되돌리는 것이 맞습니다.

8【절차 C】 릴리스 전 exe 대조

골든 픽스처는 PII 로직만 봅니다. 문서에서 글자를 뽑아내는 과정(추출), 정책 파일 읽기, CLI 옵션 처리까지 포함해서 확인하려면 두 exe 를 실제로 돌려 비교해야 합니다. 무겁기 때문에 배포 직전에만 합니다.

# Rust 판
MpowerClassify-rs --dir <검사폴더> --rules <규칙파일> --simple --nosummary --format jsonl

# Python 판
MpowerClassify.exe --dir <검사폴더> --hybridparse --rule-only --simple --nosummary --format jsonl

두 결과를 파일명 기준으로 놓고 등급이 같은지 봅니다. 라벨별로 더 깊이 보려면 양쪽에 --with-pii 를 붙여 검출된 값까지 비교할 수 있습니다.

대조 전에 MpowerClassify.exe 가 최신 빌드인지 확인하세요. exe 안의 ko-pii 는 빌드할 때 고정됩니다(1장의 ②). requirements.txt 를 바꾼 뒤 재빌드하지 않았다면, 이 대조는 옛 ko-pii 로 만든 exe 와 새 정답 기준으로 고친 Rust 를 비교하는 셈이라 엉뚱한 차이가 나옵니다. 의심스러우면 pyinstaller build/csoclassify.spec 로 다시 빌드하고 시작하세요.
차이가 나도 PII 버그가 아닐 수 있습니다. 두 판은 문서에서 글자를 뽑는 방식이 달라서, PII 검출이 같아도 결과가 갈릴 수 있습니다.
  • 이미지(jpg·png): 양쪽 다 글자를 못 뽑습니다 — 사이냅 문서필터는 OCR 엔진이 아니라 문서 텍스트 추출기입니다. 두 판 모두 등급 없이(null) 추출 실패로 끝나므로 비교해도 차이가 안 나지만, 분류도 안 됩니다.
  • 구형 오피스(doc·xls·ppt·hwp): Rust 도 자체 파서로 읽습니다. 실측에서 .doc·.hwp 는 완전 일치했고, .xls 는 1,434건 중 1건 차이가 있었습니다 — 추출 단계의 미세한 차이입니다.
  • html: Rust 는 정규식으로 태그를 걷어내 <script> 안의 글자가 새어 나올 수 있습니다.
가장 깨끗한 비교는 .txt·.md 입니다. 자세한 갭 목록은 Rust/README.md 의 “아직 안 된 것”에 있습니다.

9정답표는 어떻게 만들어지나

정답표(Rust/tests/pii_golden.json)는 사람이 손으로 쓰는 파일이 아닙니다. scripts/gen_pii_golden.py 가 진짜 ko-pii 에게 물어본 답을 받아 적습니다.

만드는 명령

cd D:\Project\MpowerClassify
python scripts/gen_pii_golden.py            # 만들기/갱신 (파일을 덮어씀)
python scripts/gen_pii_golden.py --check    # 최신인지 확인만 (덮어쓰지 않음)
옵션하는 일
(없음)코퍼스를 ko-pii 로 검사해 정답표를 새로 씁니다.
--check지금 ko-pii 로 다시 뽑아 기존 파일과 같은지만 봅니다. 다르면 종료코드 1.
--corpus <파일>검사 문장 YAML 을 바꿉니다(기본 Rust/tests/pii_corpus.yaml).
--corpus-dir <폴더>그 폴더의 .txt·.md 를 코퍼스에 더합니다(최대 200개).
--out <경로>출력 위치를 바꿉니다(기본 Rust/tests/pii_golden.json).

안에서 벌어지는 일

scripts/gen_pii_golden.py │ ├─ load_corpus() Rust/tests/pii_corpus.yaml 을 읽는다 │ └─ 검사할 문장 목록 — 사람이 손대는 유일한 파일(아래 9장) │ ├─ scan(text) ko-pii detect_all(text, include=<20라벨>) 호출 │ └─ 라벨별 건수와 검출값을 모은다 (0건 라벨은 아예 안 담는다) │ ├─ make_case() 사례 1건을 레코드로 — counts / values / values_comparable │ ├─ find_uncovered_labels() 20라벨 중 한 번도 안 잡힌 게 있으면 경고 │ └─ Rust/tests/pii_golden.json 으로 저장
정답 기준은 detect_all 입니다. 운영 코드(classify/rules.py)에는 속도를 위한 부분검출·청킹 최적화가 들어 있지만, 정답표는 그 우회로가 아니라 원본 엔진에게 묻습니다. 최적화는 “결과가 같다”가 전제인 지름길이지 기준이 아니기 때문입니다.

   "name": "phone_휴대폰",            ← 실패 메시지에 찍히는 이름
   "text": "연락처 010-1234-5678 로 주세요.",
   "values_comparable": true,        ← 값까지 비교해도 되는가
   "counts": {"PHONE": 1},           ← 라벨별 건수 (정답)
   "values": {"PHONE": ["010-1234-5678"]}
  }, ...
 ]
}
이 파일을 손으로 고치지 마세요. 테스트를 통과시키려고 숫자를 바꾸는 것은 답안지를 고쳐 100점을 만드는 것과 같습니다. 고칠 일이 있으면 코퍼스를 고치고 다시 뽑습니다.

코퍼스는 얼마나 촘촘해야 하나 중요

“라벨마다 10개씩” 같은 일정한 숫자는 기준이 되지 못합니다. 라벨마다 내부 갈래 수가 다르기 때문입니다 — EMAIL·URL·PNU 는 정규식이 하나뿐이라 10개를 넣어도 같은 길만 열 번 밟습니다. 반대로 PHONE 은 갈래가 7개(휴대폰·서울·지역 × 국내/국제 + 대표번호)라 5개로는 모자랍니다.

그래서 이 프로젝트는 갈래 하나당 최소 하나를 기준으로 삼습니다.

넣어야 할 것왜
양성 — 갈래마다 1건 이상
구분자 변형, 국내/국제, 접두 종류 …		 Rust 가 그 갈래를 못 잡으면(미탐) 바로 드러납니다. 미탐은 문서가 실제보다 낮은 등급을 받게 하므로 더 위험합니다.
음성 — 게이트마다 1건 이상
체크섬 오류, 전부-0, 문맥 없는 맨 숫자 …		 Rust 가 없는 걸 잡으면(오탐) 드러납니다. 정규식을 조금만 느슨하게 옮겨도 생깁니다.
혼합 — 여러 라벨이 한 문서에
인적사항 양식, 표, 붙어 있는 PII …		 겹침 해소와 span 경계가 실제로 개입하는 자리입니다.

현재 121건이고, 그중 24건은 “검출 0건이 정답”인 음성 사례입니다. 라벨별 사례 수는 갈래 수를 따라 PNU 1건부터 PHONE 20건까지 고르지 않습니다 — 의도된 불균형입니다.

실제로 이렇게 버그를 찾았습니다. 코퍼스가 31건이던 때는 라벨마다 사실상 1건씩뿐이라 모든 테스트가 초록불이었습니다. 갈래 단위로 108건까지 늘리자 포팅 버그 4건이 한 번에 드러났습니다.
  • 사업자등록번호: ko-pii 는 하이픈만 받는데 Rust 는 공백도 받아 436 38 20718 을 잡았습니다 → 오탐.
  • 여권번호: S·G·PS 접두를 Rust 만 잡았습니다 → 오탐. 원인을 따라가 보니 ko-pii 의 호모글리프 폴딩(S→5, O→0 …)이 Rust 에 빠져 있었습니다.
그리고 그 빠진 폴딩은 반대 방향으로 훨씬 위험했습니다 — 주민번호를 95lOO6-1068003 처럼 숫자 닮은 글자로 가려 적은 문서를 Rust 가 통째로 놓쳐, 같은 문서에 Rust=O(공개) / Python=S 등급을 주고 있었습니다. 지금은 폴딩을 옮겨 심어 양쪽 모두 S 로 일치합니다.

즉 “31건으로 충분한가”의 답은 아니오였습니다. 그리고 이 사실은 사람의 감이 아니라 코퍼스를 늘리자 테스트가 빨간불이 되면서 드러났습니다.

10검사 사례(코퍼스) 추가하기

현재 정답표는 121개 사례로 20라벨의 갈래를 훑습니다(9장 기준). 현장에서 오검출·미검출을 발견했다면 그 문장을 사례로 넣어 두면 같은 문제가 다시는 안 생깁니다(회귀 방지).

1사례 한 줄 추가

Rust/tests/pii_corpus.yaml 을 메모장으로 열고 cases: 아래에 두 줄을 넣습니다. 파이썬을 몰라도 됩니다 — 코퍼스는 코드가 아니라 데이터라 규칙셋(cso_rule.yaml)처럼 밖으로 빼 두었습니다.

cases:
  # ... 기존 사례들 ...

  - name: neg_사번_오탐                       # ← 추가
    text: "사번 20240101-0001 은 개인정보가 아니다."
    note: 사번은 개인정보가 아니므로 잡히면 오탐이다.   # 선택

여러 줄짜리 문장은 |- 블록으로 적습니다(따옴표·역슬래시 신경 쓸 필요 없음).

  - name: mix_표형식
    text: |-
      번호 | 성명 | 연락처
      1 | 홍길동 | 010-1234-5678

이름 규칙: 잡혀야 하면 <라벨>_, 안 잡혀야 하면 <라벨>_neg_, 여러 라벨이 섞이면 mix_ 로 시작하면 읽기 좋습니다. note 는 사람이 읽는 설명이라 검출에는 안 쓰입니다.

2정답표 다시 뽑고 확인

python scripts/gen_pii_golden.py
cd Rust
cargo test pii

정답은 사람이 적는 게 아니라 ko-pii 가 정합니다. 내가 기대한 것과 다르게 나왔다면, 그건 ko-pii 의 실제 동작이 내 예상과 달랐다는 뜻입니다.

실제 문서를 통째로 넣기

python scripts/gen_pii_golden.py --corpus-dir D:\검사할텍스트폴더

폴더 안의 .txt·.md 를 사례로 추가합니다(최대 200개). pdf·hwp 는 일부러 받지 않습니다 — 추출 과정의 차이가 섞이면 PII 버그인지 추출 버그인지 구분할 수 없기 때문입니다.

실제 개인정보가 든 문서는 넣지 마세요. 정답표에는 원문이 그대로 저장되고 git 에 커밋됩니다. 기존 121개 사례의 번호는 전부 체크섬만 맞춘 가짜값입니다.

한계 — 알고 쓰세요

  • 정답표는 사례가 밟은 경로만 검증합니다. 갈래마다 최소 1건은 밟지만, 갈래 안의 모든 값 조합까지 덮지는 않습니다(9장).
  • 문자 정규화표(Rust/src/pii_fold.rs)는 자동 생성물입니다. ko-pii 를 올리면 python scripts/gen_pii_fold.py 로 다시 뽑아야 하며, --check 로 최신 여부를 확인할 수 있습니다.
  • 정답표는 뽑던 시점의 ko-pii 동작만 담습니다. 그래서 버전을 올릴 때 절차 B 로 다시 뽑아야 합니다.
  • 정답표가 검증하는 것은 ③(개발 PC 의 ko-pii) 기준입니다. 그것이 ②(배포 exe 안의 ko-pii) 와 같은지는 아래 --version 대조로 사람이 확인해야 하며, 자동으로 막히지는 않습니다.
  • 현재 이 프로젝트에는 CI(자동 실행)가 없습니다. 사람이 기억해서 돌려야 하며, 잊으면 검증되지 않은 채 커밋됩니다.
