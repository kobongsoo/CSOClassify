1 무엇을 만드는가

D:\Project\MpowerClassify\Rust\ 의 Rust 소스를 컴파일해서 그 자체로 돌아가는 폴더 하나를 만듭니다. 이 폴더를 통째로 복사하면 어느 PC/서버에서든 별도 설치 없이 실행됩니다.

왜 파일 하나가 아니라 폴더인가?
실행파일 자체는 7.5MB로 작지만 임베딩 모델(129MB)·ONNX Runtime·pdfium(PDF 추출) 은 실행파일 안에 넣지 않고 옆에 파일로 둡니다. 그래야 ① 실행파일이 작고 ② 규칙셋 (cso_rule.yaml)을 재빌드 없이 교체할 수 있고 ③ PDF·임베딩을 안 쓰면 그 파일들을 빼도 됩니다. 프로그램은 자기 실행파일이 있는 폴더에서 이 파일들을 찾습니다.

Q. Windows 에서 리눅스용을 한 번에 만들 수는 없나요?
없습니다. Rust 자체는 크로스컴파일을 지원하지만, 이 프로젝트가 쓰는 tokenizers 크레이트가 내부에 C 라이브러리(oniguruma) 를 품고 있어 대상 OS 용 C 컴파일러가 별도로 필요합니다. Windows 에는 그것이 없으므로 리눅스 배포본은 리눅스에서 빌드해야 합니다. (원본 파이썬판도 PyInstaller 때문에 같은 제약이 있습니다.)
왜 하필 CentOS 7 에서 빌드하나?
리눅스 실행파일은 빌드한 glibc 버전 이상에서만 돌아갑니다. CentOS 7 의 glibc 2.17 은 현재 쓰이는 리눅스 중 가장 낮은 축이라, 여기서 빌드하면 CentOS7/RHEL7 이후 사실상 모든 배포판에서 그대로 실행됩니다. 반대로 Ubuntu 24.04 에서 빌드하면 CentOS 7 에서 안 돕니다.

:: 파이썬 빌드가이드 4장 '정책 파일 정본 확인' 을 먼저 읽고 최신본이 있는 쪽에서 복사할 것.

6 .zip 으로 묶기 권장 배포 형태

남에게 전달할 때는 zip 한 개로 묶는 편이 편합니다. 받는 쪽에서 압축만 풀면 바로 실행됩니다 (Windows 는 실행권한 개념이 없어 리눅스처럼 chmod 할 일이 없습니다).

먼저 배포용 이름의 폴더로 복사합니다 — 압축을 풀었을 때 그 이름으로 나오게 하기 위해서입니다.

# PowerShell 에서 실행
$stage = "$env:TEMP\csopkg"
Remove-Item -Recurse -Force $stage -ErrorAction SilentlyContinue
New-Item -ItemType Directory -Force $stage | Out-Null
Copy-Item -Recurse "D:\Project\MpowerClassify\Rust\dist-onedir\windows" "$stage\MpowerClassify-rs-windows"

$out = "D:\Project\MpowerClassify\Rust\dist-onedir\MpowerClassify-rs-windows.zip"
if (Test-Path $out) { Remove-Item -Force $out }
Compress-Archive -Path "$stage\MpowerClassify-rs-windows" -DestinationPath $out -CompressionLevel Optimal

Get-Item $out | Select-Object Name, @{n='MB';e={[math]::Round($_.Length/1MB,1)}}
(Get-FileHash $out -Algorithm SHA256).Hash          # 전달 후 대조용

158MB → 약 91MB 로 줄어듭니다. Compress-Archive 는 Windows 에 기본 내장이라 별도 프로그램이 필요 없습니다.

내용 확인 — 최상위가 MpowerClassify-rs-windows\ 하나여야 합니다.

Add-Type -AssemblyName System.IO.Compression.FileSystem
$zip = [System.IO.Compression.ZipFile]::OpenRead($out)
$zip.Entries | Select-Object FullName, Length | Format-Table -AutoSize
$zip.Dispose()
받는 쪽에서는 이것만 하면 됩니다.
  1. zip 우클릭 → 압축 풀기 (또는 tar -xf MpowerClassify-rs-windows.zip)
  2. 생긴 MpowerClassify-rs-windows\ 폴더로 들어가 주소창에 cmd 입력
  3. MpowerClassify-rs.exe --help
메일·웹으로 받은 zip 이 이상하게 동작한다면 — Windows 가 “다른 컴퓨터에서 온 파일”로 표시(Mark of the Web)해 DLL 로딩이 막히는 경우가 있습니다. 압축을 풀기 전에 차단을 해제하세요. 
Unblock-File .\MpowerClassify-rs-windows.zip
또는 zip 우클릭 → 속성 → 아래쪽 ‘차단 해제’ 체크 → 확인

왜 Compress-Archive -Path windows 로 바로 안 만드나? 그렇게 하면 압축을 풀었을 때 폴더 이름이 windows\ 가 되어 무엇인지 알 수 없습니다. 그래서 배포용 이름으로 한 번 복사한 뒤 묶습니다. (리눅스 tgz 도 같은 이유로 cp -a 로 이름을 바꿔 묶습니다 → 4-6)

2 서버에서 빌드

서버에 접속해 압축을 풀고 빌드합니다. 환경변수 RUSTFLAGS 가 핵심입니다.

ssh mpower@10.10.4.10

export PATH=/MOCOMSYS/.cargo/bin:$PATH
cd /MOCOMSYS/dev/bong/cso_rust_build
tar xzf rustsrc.tgz

# ★ 실행파일에 "내 옆 폴더에서 .so 를 찾아라" 규칙(RPATH)을 새겨 넣는다
export RUSTFLAGS='-C link-arg=-Wl,-rpath,$ORIGIN -C link-arg=-Wl,--disable-new-dtags'

cargo build --release
RUSTFLAGS 두 줄이 무슨 뜻인가요?
  • -rpath,$ORIGIN — “필요한 .so 는 실행파일이 있는 그 폴더에서 찾아라”. $ORIGIN 은 리눅스 로더가 이해하는 특수 문자열로, 실행 시점의 실행파일 폴더로 바뀝니다. 덕분에 LD_LIBRARY_PATH 를 설정하지 않아도 됩니다.
  • --disable-new-dtags — 요즘 링커는 기본으로 RUNPATH 를 쓰는데, RUNPATH 는 “실행파일이 직접 쓰는 라이브러리”에만 적용되고 그 라이브러리가 다시 부르는 라이브러리에는 적용되지 않습니다. 우리는 libonnxruntime.so 가 부르는 libstdc++.so.6 까지 옆 폴더에서 찾게 해야 하므로, 옛 방식인 RPATH 를 강제합니다.
이 옵션을 빼면 CentOS 7 에서 CXXABI_1.3.8 not found 오류가 납니다(7-①).

1분 30초 정도 뒤 Finished `release` profile 이 나오면 성공입니다. 확인:

ls -la target/release/MpowerClassify-rs
readelf -d target/release/MpowerClassify-rs | grep -i rpath
0x…(RPATH) Library rpath: [$ORIGIN] 이 보이면 제대로 새겨진 것입니다.

업무분류 축을 함께 켜면 — 같은 집계 레코드에 contains_doctype 이 붙습니다({"DC_001_001":2, "DC_003_002":1, "unclassified":1}). 등급은 C>S>O 서열이 있어 최고 위험 하나로 롤업되지만, 업무분류는 서열이 없고 한 문서가 여러 라벨을 가질 수 있어 대표를 고르면 반드시 무언가를 버립니다 — 그래서 고르지 않고 건수 분포를 그대로 싣습니다. 그래서 다중 라벨 문서 때문에 분포의 합계가 contains.total 보다 클 수 있고, 축을 안 쓴 실행에서는 키 자체가 없습니다("분류 못 함"과 "축을 안 씀"의 구분). 두 판이 같은 모양·같은 값을 내야 하므로 빌드 뒤 대조 지점으로 씁니다 (--doctype 을 켜고 압축을 하나 넣어 contains_doctype 을 비교).
지원: zip · tar(+gz/bz2/xz) · gz · bz2 · xz · 7z · rar. 새로 들어간 의존(tar·bzip2-rs·lzma-rs·sevenz-rust2·rars)은 전부 순수 Rust라 C 컴파일러가 필요 없습니다 — 정적 단일 바이너리 목표와 CentOS 7 빌드가 그대로 유지됩니다.

못 하는 것 두 가지(둘 다 결과에 표식이 남으므로 조용히 빠지지 않습니다):
  • 분할 볼륨(.7z.001·.z01·.partN.rar 등) — 조각을 잇지 않습니다. 파이썬 판도 zip·tar·7z 는 마찬가지라(라이브러리 차원 미지원) 두 판이 같은 수준입니다. 결과에 kind=split_volume 과 "파일이 깨진 것이 아닙니다" 안내가 나갑니다.
  • rar 하드링크·심볼릭링크 — 파일로 내놓지 않습니다. 원본은 그대로 분류되고 '같은 내용의 다른 이름'만 빠집니다. 요약에 압축 일부 누락 으로 뜹니다.
rar 을 rars 로 고른 이유 — 다른 길인 unrar 크레이트는 UnRAR C 소스를 빌드에 포함해 C 컴파일이 생기고(CentOS 7 빌드가 까다로워집니다) 라이선스 조건을 상용 배포 관점에서 따로 확인해야 합니다. rars 는 순수 Rust(MIT/Apache-2.0)라 둘 다 피합니다.
넣기 전에 참조 구현(번들 unrar.exe)과 RAR 픽스처 177개를 바이트 단위로 대조했습니다 — 단일 아카이브 131건 기준 판정 일치 95.4%, 참조가 푸는데 rars 가 못 푼 경우 0건, 손상 입력 117건에서 패닉·멈춤 0건. 실제 분류 대조에서는 파이썬 판과 공통 554건의 등급이 100% 일치했고, 차이 7건은 정확히 위 두 한계(분할 2 · 하드링크 3 · 심볼릭 2)였습니다.
보안등급 신호가 4개로 정리됐습니다 2026-09-08
rule(본문) · sensitive · stamp · name(파일명) 넷입니다. 경로(paths) 신호는 걷어냈습니다 — 실측(레코드 3,715건)에서 경로가 단독으로 정한 등급 8건이 전부 오탐이었고(제품명이 든 파일 이름·공개 데이터셋 폴더), acl_restricted fail-safe 는 0건 걸렸습니다.
파일명 신호는 이제 규칙의 filename 목록을 봅니다 — 본문용 terms 를 빌려 쓰지 않습니다. 안 적은 규칙은 파일 이름을 보지 않습니다.

빌드 뒤 확인 — ① --check-rules 요약에 paths= 칸이 없어야 합니다(regex_pii=20 · pii_combos=5 · keywords=9 · sensitive=7 · stamps=3). ② 옛 paths: 가 남은 규칙셋을 넣으면 V12 로 거절되어야 합니다(두 판 같은 문구). ③ 같은 문서·같은 규칙셋으로 두 판을 돌려 등급이 같은지 봅니다.
주의 — 배포본 폴더의 cso_rule.yaml 도 함께 바꿔야 합니다. 옛 paths: 가 남아 있으면 새 exe 가 V12 로 막혀 실행되지 않습니다.

7 자주 나는 오류와 해결

① CXXABI_1.3.8 not found / GLIBCXX_3.4.29 not found Linux

thread 'main' panicked at ort-2.0.0-rc.10/src/lib.rs:111:33:
An error occurred while attempting to load the ONNX Runtime binary at
`…/libonnxruntime.so`: /lib64/libstdc++.so.6: version `CXXABI_1.3.8' not found

원인 — libonnxruntime.so 는 최신 컴파일러로 만들어져 새 C++ 런타임을 요구하는데, CentOS 7 에 기본 설치된 /lib64/libstdc++.so.6(gcc 4.8.5) 은 CXXABI_1.3.7 까지밖에 제공하지 않습니다.

해결 — 두 가지를 모두 해야 합니다.

  1. 빌드할 때 RUSTFLAGS='-C link-arg=-Wl,-rpath,$ORIGIN -C link-arg=-Wl,--disable-new-dtags' → 실행파일에 “옆 폴더를 뒤져라(RPATH)” 규칙을 새깁니다.
  2. 배포본에 libstdc++.so.6(conda 의 6.0.34)·libgcc_s.so.1 을 함께 넣습니다.
--disable-new-dtags 를 빼면 RUNPATH 가 생기는데, RUNPATH 는 간접 의존(라이브러리가 부르는 라이브러리)에는 적용되지 않아 이 오류가 그대로 납니다. 반드시 함께 주세요.

확인: readelf -d MpowerClassify-rs | grep -i rpath → (RPATH) … [$ORIGIN]

② Permission denied Linux

Windows 를 거쳐 복사하면 실행권한이 사라집니다.

chmod +x MpowerClassify-rs

③ 임베딩이 조용히 동작하지 않음 공통

기본 모드로 돌렸는데 [전파] … 줄이 안 뜨면, 모델·런타임을 못 찾아 전파를 생략한 것입니다(오류 없이 넘어갑니다).

  • 파일 이름이 정확한가 — onnxruntime.dll / libonnxruntime.so (버전 숫자 붙으면 안 됨)
  • models/e5-small-ko/ 안에 model.onnx·tokenizer.json 이 있는가
  • class_seed.jsonl 이 실행파일 옆에 있는가 (없으면 전파 자체가 꺼짐)

④ link.exe not found / linker 'cc' not found Windows

C++ 빌드 도구가 없습니다. Visual Studio Installer → C++를 사용한 데스크톱 개발 을 설치하고 터미널을 새로 여세요.

⑤ 크레이트를 못 받음 (네트워크/프록시) 공통

error: failed to get `serde` as a dependency … Couldn't connect to server

사내망 프록시라면 ~/.cargo/config.toml 에 프록시를 적거나, 인터넷이 되는 PC 에서 한 번 빌드해 ~/.cargo/registry/ 를 통째로 복사하면 오프라인 빌드(cargo build --release --offline)가 됩니다.

⑥ PDF 만 결과가 비어 있음 공통

pdfium.dll/libpdfium.so 가 없거나 이름이 다릅니다. 다른 포맷은 정상이므로 놓치기 쉽습니다.

⑦ musl 정적 빌드는 되나요?

README.md 에는 x86_64-unknown-linux-musl 이 적혀 있지만, 이 서버에는 musl-gcc 가 없어 tokenizers 의 C 코드(oniguruma)를 musl 로 컴파일할 수 없습니다. 현재 배포본은 CentOS 7(glibc 2.17) gnu 타깃이며, 실용적으로는 이쪽이 호환 범위가 더 넓습니다 (musl 로 만들어도 libonnxruntime.so·libpdfium.so 는 어차피 외부 glibc 라이브러리라 완전 정적이 되지 않습니다).

폴더를 열면 하단 상태바에 rust-analyzer 진행 표시가 뜹니다. 이 프로젝트는 의존 크레이트가 많아 첫 인덱싱에 1~3분 걸립니다(target\ 캐시가 있으면 더 빠름). 진행 중에 자동완성이 비어 있는 것은 정상이니 끝날 때까지 기다리세요.

정상 동작 확인
① src\main.rs 를 열고 아무 변수에 마우스를 올리면 타입이 말풍선으로 뜬다
② 함수 이름에서 F12 → 정의로 점프한다
③ 문법을 일부러 틀리면(예: 세미콜론 삭제) 저장하지 않아도 빨간 밑줄이 생긴다
④ 함수 위에 ▶ Run | Debug 같은 회색 글씨(CodeLens)가 보인다

9-2. 오프라인 설치 폐쇄망·빌드서버

마켓플레이스 접속이 막힌 PC 라면 .vsix 파일을 들고 가서 설치합니다.

  1. 인터넷 되는 PC 에서 마켓플레이스 페이지(marketplace.visualstudio.com → rust-analyzer)의 Download Extension 으로 .vsix 를 받습니다.
    플랫폼별 파일이 다릅니다. rust-analyzer 는 언어서버 실행파일을 확장 안에 품고 있어 ...-win32-x64.vsix / ...-linux-x64.vsix 로 나뉩니다. 설치할 PC 의 OS·아키텍처에 맞는 파일을 받아야 합니다.
  2. 대상 PC 로 복사한 뒤 설치: 
    code --install-extension D:\down\rust-analyzer-win32-x64.vsix

    GUI 로 하려면: 확장 패널 우측 상단 ··· → Install from VSIX…

  3. VS Code 재시작(Ctrl+Shift+P → Developer: Reload Window).
빌드서버(10.10.4.10)에서 고칠 때는 서버에 VS Code 를 설치하지 말고, 내 PC VS Code 의 Remote-SSH 확장으로 접속하는 쪽이 편합니다. 이때 rust-analyzer 는 서버 쪽에 다시 설치되므로(원격 확장), 폐쇄망이면 위 linux-x64.vsix 를 서버에 올려 code --install-extension 으로 깔면 됩니다.

9-3. 이 프로젝트에 맞춘 권장 설정

Rust\.vscode\settings.json 을 만들고 아래를 넣습니다(파일이 없으면 새로 만드세요). 팀 공용 설정이 되므로 개인 취향 항목은 넣지 않는 편이 좋습니다.

{
  // 저장할 때마다 clippy(린터)로 검사 — cargo check 보다 잡아내는 게 많다
  "rust-analyzer.check.command": "clippy",

  // 타입/파라미터 이름을 코드 사이에 회색으로 표시. 어지러우면 false
  "rust-analyzer.inlayHints.typeHints.enable": true,
  "rust-analyzer.inlayHints.parameterHints.enable": true,

  // 저장 시 rustfmt 자동 정렬 — 사람마다 다른 서식으로 diff 가 지저분해지는 걸 막는다
  "editor.formatOnSave": true,
  "[rust]": { "editor.defaultFormatter": "rust-lang.rust-analyzer" },

  // 빌드 산출물(약 3GB)은 파일감시·검색에서 제외 — 안 하면 VS Code 가 느려진다
  "files.watcherExclude": { "**/target/**": true },
  "search.exclude":       { "**/target/**": true }
}
rust-analyzer 와 cargo build 는 같은 target\ 폴더를 씁니다.
저장할 때마다 도는 check 가 터미널의 cargo build --release 와 겹치면 서로 락(lock)을 기다리며 한쪽이 멈춰 보일 수 있습니다. 빌드가 유난히 느리면 아래를 추가해 분석 전용 폴더를 분리하세요(디스크를 1~2GB 더 씁니다). 
"rust-analyzer.cargo.targetDir": true

9-4. 파이썬 코드와 같이 보고 싶다면 (멀티 루트)

이 저장소는 루트가 파이썬이고 Rust 는 Rust\ 하위에 있습니다. 상위 MpowerClassify 폴더를 그냥 열면 rust-analyzer 가 Cargo.toml 을 찾지 못합니다. 방법은 두 가지:

  • (권장) 워크스페이스 파일 — File → Add Folder to Workspace… 로 MpowerClassify 와 MpowerClassify\Rust 를 둘 다 추가하고 .code-workspace 로 저장합니다. 각 폴더가 독립 루트가 되어 rust-analyzer 가 Rust 쪽을 정상 인식합니다.
  • 수동 지정 — 상위 폴더의 .vscode\settings.json 에: 
    { "rust-analyzer.linkedProjects": ["Rust/Cargo.toml"] }

    경로는 연 폴더 기준 상대경로이며 슬래시 / 를 씁니다.
