업무분류체계 분류 작업 가이드

업체 현장에서 문서분류체계를 받아 규칙을 만들고, 전체 문서를 분류해 내기까지 — 일곱 단계를 순서대로. 모든 명령과 화면은 MpowerClassify-rs.exe 를 실제 실행해 옮긴 것입니다.

0.시작 전에 — 준비물과 전체 그림

이 작업이 만들어 내는 것

최종 결과물은 둘입니다.

결과물무엇인가
doc_rule.yaml “이런 말이 나오면 이 분류” 를 적어 둔 업무분류 규칙 파일. 업체마다 다릅니다.
result.jsonl 문서 하나하나에 보안등급(C/S/O) 과 업무분류(dc_id) 를 붙인 판정 결과.

일곱 단계 흐름

1체계 내보내기엠파워 UI
2seed 목록 작성사람이 손으로
3기준 문서 등록--seed-add-from
4규칙 만들기--build-doc-rule
5검수·본문 저장--textsave
6키워드 보강--suggest-terms
7전체 분류--dir --out

6단계에서 규칙을 손보면 4단계로 되돌아가 규칙을 다시 만듭니다. 이 왕복이 이 작업의 핵심입니다.

작업 폴더 만들기

exe 가 있는 폴더 밑에 업체용 정책 폴더(여기서는 policy01)를 하나 만들고 모든 정책 파일을 그 안에 모읍니다. 이렇게 해 두면 업체가 둘 이상이어도 폴더만 갈아 끼우면 됩니다.

D:\Project\MpowerClassify\Rust\dist-onedir\windows\ ├─ MpowerClassify-rs.exe ← 실행 파일 ├─ models\ onnxruntime.dll pdfium.dll ← exe 와 한 세트. 따로 옮기지 않는다 └─ policy01\ ← 이 업체의 정책 폴더(직접 만든다) ├─ cso_rule.yaml 보안등급 규칙 (기본 제공물 복사) ├─ doc_classification_export.json 1단계 산출물 ├─ doc_rule_template.yaml 규칙 본보기 (기본 제공물 복사) ├─ doc_rule.local.yaml 업체별 조정 — 사람이 적는 유일한 규칙 파일 ├─ synonyms\ 유의어 사전 (기본 제공물 복사) │ ├─ doc_synonyms.core.yaml │ ├─ doc_synonyms.education.yaml … 업종 사전들 │ └─ doc_synonyms.local.yaml 이 업체에서만 쓰는 말 (필요할 때 만든다) ├─ seedlist.jsonl 2단계 산출물 ├─ class_seed.jsonl 3단계 산출물 └─ doc_rule.yaml 4단계 산출물 — 손으로 고치지 않는다

cso_rule.yaml·doc_rule_template.yaml·synonyms\ 는 배포본에 들어 있는 것을 그대로 복사하면 됩니다.

명령을 어디서 실행하나

윈도우 명령 프롬프트(cmd) 를 열고 exe 가 있는 폴더로 이동한 뒤 실행합니다. 아래 모든 예시는 이 자리를 기준으로 상대경로(policy01\…)를 씁니다.

명령 프롬프트
C:\> d:
D:\> cd D:\Project\MpowerClassify\Rust\dist-onedir\windows
D:\Project\MpowerClassify\Rust\dist-onedir\windows> MpowerClassify-rs.exe --help
MpowerClassify-rs 1.x — 한국어 문서 → C/S/O 보안등급 · 업무분류 자동분류
…(인자 도움말이 ①~⑩ 묶음으로 나옵니다)
세 가지 규약을 먼저 기억하세요.
  1. 정책 경로는 항상 명시합니다. 빼먹으면 exe 옆의 기본 파일을 조용히 씁니다(업체 파일이 아닌 것).
  2. doc_rule.yaml 은 손으로 고치지 않습니다. 4단계에서 통째로 다시 만들어지는 생성물입니다.
  3. 사람이 적는 규칙 파일은 doc_rule.local.yaml 하나뿐입니다.

1.문서분류체계 내보내기 엠파워 개발

무엇을 하나

업체의 업무분류체계(대분류 > 중분류 구조와 이름)는 엠파워v11 안에 이미 들어 있습니다. 그것을 이 도구가 읽을 수 있는 JSON 파일로 꺼냅니다.

  1. 엠파워v11 관리 화면 → 문서분류체계 설정
  2. 내보내기 → doc_classification_export.json 저장
  3. 그 파일을 policy01\ 안에 넣습니다.
[개발사항] 엠파워 문서분류체계를 JSON 으로 내보내는 기능이 필요합니다.

파일이 어떻게 생겼나

분류 하나가 노드 하나입니다. dc_id 가 앞으로 모든 단계에서 분류를 가리키는 열쇠가 됩니다.

{
  "nodes": [
    { "dc_id": "DC_001",     "title": "CS",           "parent": null },
    { "dc_id": "DC_001_001", "title": "제안서",        "parent": "DC_001" },
    { "dc_id": "DC_001_003", "title": "PM구축자료",     "parent": "DC_001" },
    { "dc_id": "DC_002_006", "title": "프로그래밍 강좌", "parent": "DC_002" }
  ]
}
dc_id 의 구분자는 밑줄(_) 입니다. DC_006-003 처럼 붙임표를 쓰면 어느 분류와도 맞지 않습니다.

2.seed 목록 만들기(수작업) 업체 담당자

무엇을 하나

“이 분류는 이런 문서다” 를 도구에게 보여 주는 견본 문서를 고르는 일입니다. 분류마다 10건쯤이 적당합니다. 이 견본이 뒤에 나오는 키워드 추출과 임베딩 전파의 재료가 됩니다. 이 단계의 품질이 전체 성적을 좌우합니다.

① 분류별 폴더에 문서를 담는다

분류마다 폴더를 두 곳 이상으로 나누세요

키워드 추출(6단계)은 “근거 문서 3건 이상 + 서로 다른 폴더 2곳 이상” 을 넘은 말만 후보로 올립니다. 같은 폴더에 있는 문서는 아무리 많아도 1곳으로 셉니다. 한 폴더에 몰아 담으면 후보가 거의 안 나옵니다.

이렇게 하면 후보가 안 나옵니다이렇게 담으세요
SEED\DC_001_003\ 에 10건 전부 SEED\DC_001_003\2024년\ 5건
SEED\DC_001_003\2025년\ 5건

연도·고객사·프로젝트 등 아무 기준이어도 됩니다. 나뉘어 있기만 하면 됩니다. 왜 이렇게 세는지는 부록 D 에서 설명합니다.

② seedlist.jsonl 을 적는다

한 줄에 문서 하나. 담당자가 등급과 분류를 직접 적습니다(도구가 추측하지 않습니다).

칸넣는 값필수
file본문을 뽑을 실제 파일 경로. 상대경로면 명령을 실행하는 폴더 기준필수
grade보안등급 — C(기밀) / S(사내) / O(공개) 중 하나. 숫자 0 이 아니라 영문 대문자 O선택
doctype업무분류 dc_id 목록(대괄호). 예: ["DC_001_003"]선택
doc_id엠파워V11 의 문서 sfileid. 나중에 결과를 엠파워와 맞출 때 씁니다선택
note / reviewer줄마다 다른 메모·확정자를 줄 때(없으면 명령에서 준 값을 씁니다)선택

grade 와 doctype 은 둘 중 하나만 적어도 됩니다.

{"file":"D:\\분류함1\\SEED\\CS\\제안서\\2024_현대제철_제안서.pptx","doc_id":"SF-100231","grade":"C","doctype":["DC_001_001"]}
{"file":"D:\\분류함1\\SEED\\CS\\매뉴얼\\사용자매뉴얼_v2.hwp","doctype":["DC_001_005"]}
{"file":"D:\\분류함1\\SEED\\영업\\견적서\\2025_견적.xlsx","grade":"O"}
JSON 이라 지켜야 하는 것 — 경로의 역슬래시는 \\ 로 두 번 적습니다. 파일은 UTF-8 로 저장하고 줄 끝에 쉼표를 붙이지 않습니다(한 줄이 곧 한 건).
[개발사항] 엠파워에서 문서를 골라 등급·분류체계를 지정하면 이 목록이 자동으로 나오는 UI 가 있으면 이 단계가 사라집니다.

3.기준 문서 등록 — class_seed.jsonl exe

무엇을 하나

2단계의 목록을 도구가 쓰는 기준 문서 저장소(class_seed.jsonl)로 바꿉니다. 이때 도구가 문서를 실제로 열어 지문(SHA-256) 과 의미 벡터(384차원) 를 만들어 함께 저장합니다. 그래서 이 단계는 시간이 좀 걸립니다.

명령

MpowerClassify-rs.exe --seed-add-from policy01\seedlist.jsonl ^
  --seed-reviewer "홍길동" ^
  --seed-note "신규 seed 등록" ^
  --seeds policy01\class_seed.jsonl ^
  --cso-rules policy01\cso_rule.yaml ^
  --doc-rules policy01\doc_rule.yaml

cmd 에서 줄을 나눌 때는 끝에 ^ 를 붙입니다. 한 줄로 이어 써도 됩니다. 맨 처음에는 doc_rule.yaml 이 아직 없으니 --doc-rules 를 빼고 실행하고, 4단계 뒤에 다시 등록해도 됩니다.

인자 설명

인자뜻
--seed-add-from <목록>줄마다 값이 다른 문서를 한꺼번에 등록. - 를 주면 표준입력. 문서마다 같은 값을 줄 거면 --seed-add <문서…> 를 씁니다(둘은 함께 못 씁니다)
--seed-reviewer <이름>필수. 누가 확정했는지. 없으면 종료코드 3 으로 멈춥니다
--seed-note <메모>선택. 왜 등록했는지 한 줄
--seeds <파일>저장할 기준 문서 파일. 있으면 잠그고 병합합니다. 주지 않으면 화면에만 찍고 파일은 건드리지 않습니다(미리보기로 쓰기 좋음)
--seed-grade <C|S|O>--seed-add 로 문서를 직접 나열할 때 모두에게 줄 등급
--seed-doctype <dc_id,…>같은 방식으로 줄 업무분류(콤마로 여럿)
--seed-audit <경로>변경 기록 파일. 안 주면 --seeds 옆 class_seed_audit.jsonl

실제 실행 화면

명령 프롬프트 — 2건 등록 예
> MpowerClassify-rs.exe --seed-add-from mini.jsonl --seed-reviewer "홍길동" --seed-note "신규 seed 등록" --seeds policy01\demo_seed.jsonl --cso-rules policy01\cso_rule.yaml --doc-rules policy01\doc_rule.yaml

                규칙이 못 정한 문서는 미분류로 남습니다. 의도한 것이면 --rule-only 로 명시하세요.

첫 등록이라 비교할 seed 가 아직 없다는 안내입니다(정상). 두 번째 실행부터는 나오지 않습니다.

확인 포인트 — approved_by 에 이름이 들어갔는지 보세요. 6단계 키워드 추출은 사람이 승인한 seed 만 재료로 씁니다. 이름이 없는 줄은 없는 것으로 취급됩니다.

4.업무분류 규칙 만들기 — doc_rule.yaml exe

무엇을 하나

분류체계 JSON 의 분류 이름을 유의어 사전으로 부풀려 “이런 말이 나오면 이 분류” 규칙을 자동으로 짓습니다. 문서를 읽지 않으므로 몇 초면 끝납니다.

재료는 네 가지뿐

재료역할
doc_classification_export.json분류 이름과 계층 — 규칙의 뼈대
synonyms\core(공통) + 업종 사전 + local(이 업체 말) 순으로 겹쳐 말을 늘림
doc_rule_template.yaml점수·문턱 같은 공통 설정의 본보기
doc_rule.local.yaml이 업체만의 조정 — 말 추가/제거, 문턱 조정
class_seed.jsonl 은 규칙 생성 재료가 아닙니다. 6·7단계에서 씁니다. 같은 폴더에 있어도 무해합니다.

명령

MpowerClassify-rs.exe --build-doc-rule --doc-rules policy01\doc_rule.yaml
인자뜻
--build-doc-rule규칙 생성 모드. 문서·모델을 읽지 않습니다
--doc-rules <파일>만들어 낼 규칙 파일의 경로. 나머지 재료는 이 파일이 놓일 같은 폴더에서 이름으로 찾습니다 — 그래서 한 폴더에 모아 두는 것입니다
--export-input <파일>분류체계 JSON 을 다른 이름·다른 자리에서 읽을 때만

실제 실행 화면

명령 프롬프트
> MpowerClassify-rs.exe --build-doc-rule --doc-rules policy01\doc_rule.yaml
[MpowerClassify-rs] policy01\doc_rule.yaml 생성 — 규칙 16개(회사 조정 0개) · 판 doctype-gen-4aaae0aa131b · 입력 12개
읽는 법뜻
규칙 16개만들어진 분류 규칙 수. 분류체계의 말단 분류 수와 맞는지 확인하세요
회사 조정 0개doc_rule.local.yaml 에서 반영된 조정 수. 6단계에서 말을 넣으면 이 숫자가 오릅니다
판 doctype-gen-…재료 내용으로 계산한 지문. 재료가 같으면 늘 같은 값 → 배포본끼리 같은 규칙인지 이 값으로 비교합니다
입력 12개읽은 재료 파일 수(사전 파일들 포함)
분류 수가 모자라면 doc_classification_export.json 을 잘못 넣은 것입니다. --doc-rules 로 준 경로의 옆에 있는지 확인하세요.

값만 검사해 보려면 --check-rules 를 씁니다(정상 0, 검증 실패 4).

5.규칙 검수 + 본문 미리 뽑기 exe

① 규칙 파일을 눈으로 본다

policy01\doc_rule.yaml 을 열어 분류별로 어떤 말이 잡혀 있는지 봅니다. 아래 셋을 봅니다.

  • 분류 이름이 한 단어라 말이 거의 없는 분류(예: “인공지능”) — 6단계 보강 대상
  • 서로 비슷한 말을 공유하는 분류(예: 제안서 ↔ 제품소개서) — 헷갈릴 자리
  • 업체에서만 쓰는 줄임말·제품명이 빠져 있는 분류

② seed 문서의 본문을 미리 뽑아 둔다

6단계 키워드 추출은 미리 저장해 둔 본문을 읽습니다. 지금 한 번 뽑아 두면 키워드 추출을 몇 번이든 빨리 돌릴 수 있습니다.

MpowerClassify-rs.exe --dir "D:\분류함1\SEED" ^
  --textsave "D:\분류함1\SEED_TEXT" ^
  --cso-rules policy01\cso_rule.yaml ^
  --doc-rules policy01\doc_rule.yaml ^
  --simple-why --progress --out text_pass.jsonl
인자뜻
--dir <폴더>이 폴더를 하위까지 훑습니다. 압축파일은 안을 펼쳐 각각 분류

--nosummary맨 끝 요약을 빼고 파일별 결과만

6.키워드 뽑아 규칙에 넣기 exe 사람 판단

무엇을 하나

seed 문서의 본문을 훑어 “이 분류에만 자주 나오는 말” 을 찾아 줍니다. 단순히 많이 나온 말이 아니라 다른 분류에는 거의 안 나오는 말을 고릅니다(그래야 구분에 쓸모가 있습니다). 도구는 보여 주기만 하고 규칙 파일은 고치지 않습니다.

명령

MpowerClassify-rs.exe --suggest-terms DC_001_003 ^
  --doc-rules policy01\doc_rule.yaml ^
  --seeds policy01\class_seed.jsonl ^
  --text-dir "D:\분류함1\SEED_TEXT"
인자뜻
--suggest-terms <dc_id|all>훑을 분류 하나. all 이면 확정 문서가 있는 분류 전부
--seeds <파일>재료 ① 기준 문서. 반드시 주세요 — 빠뜨리면 exe 옆의 옛 파일을 읽습니다
--text-dir <폴더>재료 ② 5단계에서 --textsave 로 저장한 본문 폴더. 인자 이름에 붙임표가 있습니다(--textdir 아님). 없으면 제목·파일 이름만 봅니다
--overrides <파일>재료 ③ 검토 화면에서 확정·거절한 이력. 기본은 정책 폴더 옆 cso_override.jsonl
--doc-rules <파일>거르기용. 이미 규칙에 있는 말, 다른 분류의 이름을 후보에서 뺍니다
--stopwords <파일>제안하지 않을 말 목록. 기본은 정책 폴더 옆 doc_rule_stopwords.yaml
--suggest-json <경로>결과를 JSON 으로도 남깁니다(엑셀 정리용)
--suggest-min-docs <수>제안을 시작할 최소 확정 문서 수(기본 3)

올바른 자리 — doc_rule.local.yaml

분류별 말 추가·제거는 policy01\doc_rule.local.yaml 의 rules: 아래에 적습니다. 칸마다 add(더하기) / remove(빼기) / clear(비우기) 를 쓸 수 있습니다.

rules:
  DC_001_003:                      # PM구축자료
    add:
      title_terms: ["요구사항정의서", "착수보고", "검수확인서"]   # 제목에 나오면
      head_terms:  ["구축 범위"]                                # 문서 앞부분에 나오면
      terms:       ["요구사항정의서"]                            # 본문에 나오면
      filename:    ["요구사항정의서"]                            # 파일 이름에 나오면
    remove:
      terms: ["구축"]              # 너무 흔해 헷갈리게 하는 말을 뺀다

  DC_003_003:                      # 라이센스증서
    add:
      title_terms: ["Agreement"]
칸어디를 보나제안 화면의 표기
title_terms문서 제목제목
head_terms본문 앞부분앞부분
terms본문 전체본문
filename파일 이름파일이름
업체에서만 쓰는 줄임말·다른 표기(같은 뜻의 다른 말)는 규칙이 아니라 사전에 적습니다 → policy01\synonyms\doc_synonyms.local.yaml. 같은 칸에 add 와 clear 를 함께 쓰면 비우기가 먼저 적용됩니다.

적었으면 4단계로 돌아갑니다

MpowerClassify-rs.exe --build-doc-rule --doc-rules policy01\doc_rule.yaml

회사 조정 숫자가 올랐고 판 값이 바뀌었으면 제대로 반영된 것입니다. 숫자가 그대로면 dc_id 오타이거나 파일을 다른 폴더에 적은 것입니다.

이제 6단계를 다시 돌려 같은 말이 후보에서 사라졌는지 확인하고 다른 분류로 넘어갑니다. 이 4↔6 왕복을 분류가 만족스러워질 때까지 반복합니다.

인자뜻
--dir <폴더>분류할 문서 폴더(하위까지). 여러 곳에 흩어져 있으면 --files-from <목록>
--cso-rules <파일>보안등급 규칙
--doc-rules <파일>업무분류 규칙 — 6단계까지 다듬은 그 파일

--simple-why필요한 칸만 + 판정 근거. 이 인자를 주면 <out>.full.jsonl 도 함께 생깁니다
--nosummary맨 끝 요약 생략. 처음에는 빼고 돌려 요약을 보는 편이 좋습니다
--json-errors실패할 때 오류를 JSON 한 줄로 — 다른 프로그램이 읽기 쉽게
--progress진행 상황 표시
--rule-only규칙만 쓰고 임베딩·전파를 끕니다(가장 빠름, 대신 미분류가 늘어남)
--filelist <목록>엠파워V11 이 준 {path, sfile_id} 목록. 결과의 doc_id 를 이걸로 채웁니다

D.단어 제안 문턱값 — 왜 폴더를 나누라고 하나

키워드 제안은 “많이 나온 말” 이 아니라 “이 분류에만 나오는 말” 을 찾습니다. 그런데 같은 폴더의 문서들은 서로 닮기 쉽습니다 — 같은 프로젝트, 같은 작성자, 같은 양식이니 그 폴더에서만 쓰는 말이 “이 분류의 말” 처럼 보입니다. 그래서 같은 폴더 문서는 합쳐서 1건으로 세고, 서로 다른 폴더 2곳 이상에서 나온 말만 신뢰합니다.

기준값뜻
최소 확정 문서3건이보다 적은 분류는 제안 자체를 건너뜁니다(--suggest-min-docs 로 조정)
말이 나온 문서 수3건 이상우연히 한두 번 나온 말을 걸러냅니다
말이 나온 폴더 수2곳 이상한 폴더에만 몰린 말은 그 폴더의 습관일 수 있습니다
다른 분류 등장률5% 이하이 값으로 실제로 거릅니다. 낮을수록 이 분류 전용
문서 끝말이 아닌 말다른 분류 2% 이하 + 덮는율 50% 이상 “…서/…표/…계획” 처럼 문서를 가리키는 끝말이 아닌 말(예: 사람 이름, 제품명)은 기준을 더 엄하게 봅니다
글자 수3자 이상
(앞부분·본문)		두 글자 말은 뜻이 겹쳐 오분류를 늘립니다. 제목·파일 이름은 두 글자도 허용
한 폴더 전용 예외5건 이상 · 3자 이상 · 그 폴더 쏠림 90% 이상폴더가 1곳이어도 참고 후보로는 보여 줍니다
