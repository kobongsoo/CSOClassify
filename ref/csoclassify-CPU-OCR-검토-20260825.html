로컬 CPU OCR 타당성 검토

CSOClassify에 GPU 없는 OCR을 붙일 수 있는가

문서 안 이미지에서 한글 텍스트를 뽑아내되 GPU는 쓸 수 없다는 조건으로, 실제 스캔 문서 9종 38쪽에 CPU 전용 OCR 엔진 두 종을 돌렸다. 결론은 가능하다. 다만 기본 설정 그대로 쓰면 절반의 정확도를 잃는다.

측정일 2026-08-25 환경 Windows 11 · 16 logical cores · GPU 미사용 표본 실제 스캔 PDF 9종 38쪽 · 300dpi

결론

정확도와 속도가 정반대로 갈린다. 어느 쪽을 고를지는 CSOClassify가 OCR 결과를 무엇에 쓰느냐로 결정된다.

먼저 밟게 되는 함정 넷

세 가지 모두 기본값을 그대로 쓰면 반드시 마주친다. 도입을 결정한다면 설계 단계에서 미리 걷어내야 할 항목이다.

함정 1 · 잘못된 언어 모델

RapidOCR 기본 설치본은 중국어 모델이다

rapidocr-onnxruntime이 번들하는 인식 모델은 PP-OCRv4 중국어다. 한글 문서를 넣으면 출장여비규정이 叶 / 日 / 是 같은 한자로 깨진다. 3쪽에서 475자밖에 못 뽑았다.

신규 rapidocr v3 + LangRec.KOREAN 으로 교체

함정 2 · 정확도를 절반으로 깎는 기본 옵션

각도 분류기가 한글 줄을 뒤집는다

한국어 모델로 바꾼 뒤에도 계약서 첫 문단이 통째로 우h료HonJ로i릉olRl… 로 무너졌다. 각도 분류기(use_cls)가 한글 줄의 방향을 오판해 뒤집힌 상태로 인식한 것이다.

이 옵션 하나를 끄자 정확도가 48.4% → 94.3%로 뛰었고, 속도까지 50.7초 → 34.0초로 빨라졌다. 켜 둘 이유가 없다.

Global.use_cls = false

함정 3 · 눕혀서 스캔된 페이지

회전 스캔에서 Tesseract는 아무것도 못 읽는다

유진그룹 제안서는 4-up 슬라이드 핸드아웃을 가로로 스캔해 페이지가 90° 누워 있었다. Tesseract는 한글 비율 19%로 사실상 전멸했고, RapidOCR은 검출 단계에서 기울어진 박스를 바로 세우기 때문에 85%를 유지했다. 두 엔진 일치도가 1%까지 떨어진 것이 이 차이다.

실무 문서 더미에는 이런 페이지가 섞여 있게 마련이다. Tesseract를 택한다면 회전 감지·보정 단계를 앞에 따로 붙여야 한다.

함정 4 · 오프라인 배포

한국어 모델은 실행 시점에 내려받는다

RapidOCR v3는 한국어 모델을 ModelScope에서 자동 다운로드한다. 폐쇄망이나 단일 exe 배포에서는 모델을 미리 번들해야 한다. 참고로 한국어 server 모델은 onnxruntime 백엔드를 지원하지 않아 mobile만 선택할 수 있다.

Tesseract 쪽도 같은 성격의 제약이 있다. 설치본에 한국어가 빠져 있어 kor.traineddata(15MB)를 따로 배치해야 한다.

CSOClassify에 붙일 때

현재 코드베이스를 기준으로 실제 작업이 필요한 지점들이다.

  • 전량 적용은 금물. 평균 쪽당 36초, 최악 83초는 배치라도 무겁다. pdf_pdfium.py가 텍스트를 뽑지 못했을 때만 OCR로 넘어가는 폴백 구조가 전제다. 해당 파일에 이미 "스캔 PDF는 텍스트층이 없어 빈 결과 → OCR은 별도" 주석이 달려 있어, 붙일 자리는 이미 표시돼 있는 셈이다.
  • "image" 처리기가 비어 있다. extract/detect.py는 PNG·JPEG 매직바이트를 읽어 이미지로 분류하지만, build_extractor()의 엔진 표에 "image" 키가 없어 실제로는 snf 폴백으로 흘러간다. OCR을 넣는다면 이 자리가 맞다.
  • PyInstaller의 PIL 제외를 재검토해야 한다. 용량 절감 목적으로 spec에서 Pillow를 명시적으로 빼 두었는데, 어느 OCR 경로든 이미지 디코딩이 필요하다.
  • 배포 궁합만 놓고 보면 Tesseract가 낫다. 외장 exe를 subprocess로 부르는 방식이 snf_exe와 동일해 기존 아키텍처를 거의 건드리지 않는다. 다만 이번 측정에서는 그 이점이 정확도 손실을 상쇄하지 못했다. RapidOCR도 onnxruntime을 이미 임베딩(embed/onnx_embedder.py)에 쓰고 있어 새 런타임이 추가되지는 않는다.
  • 스캔 판별은 전 페이지를 봐야 한다. 앞 3쪽만 검사했을 때 D:\분류함에서 16건이 스캔으로 잡혔지만, 전 페이지를 확인하니 순수 스캔은 9종이었다. 나머지는 앞부분만 이미지인 혼합 문서로, 쪽 단위로 OCR 여부를 판단해야 한다.
  • 띄어쓰기는 두 엔진 모두 망가진다. 다만 C/S/O 분류가 목적이라면 완전한 문장 복원보다 키워드 보존율이 중요하므로, 85~94%면 분류 신호로는 충분할 가능성이 높다.
  • 문서 내장 이미지는 별도 작업이다. office_ooxml.py는 docx·pptx를 zip으로 직접 파싱하지만 삽입된 그림을 꺼내는 코드가 없다. 스캔 PDF와 독립 이미지 파일까지만 1차 범위로 잡는 편이 현실적이다.

이 측정의 한계

결론을 그대로 신뢰하기 전에 감안해야 할 것들.

  • 정확도를 수치로 잰 것은 9종 중 2종뿐이다. 나머지 7종은 한글 비율과 두 엔진 일치도라는 간접 지표에 눈으로 한 대조를 더해 판단했다. 방향은 일관되지만 퍼센트로 말할 수 있는 값은 아니다.
  • 한글 비율은 영문이 많은 문서에서 오작동한다. LGCNS 교안의 23%는 인식 실패가 아니라 원문에 영문 논문 인용이 많았기 때문이다.
  • 큰 문서는 무작위 5쪽 표본이라 문서 전체의 평균이 아니다. 특히 33쪽·68쪽 문서는 쪽마다 밀도 편차가 커서 표본이 달라지면 수치도 달라진다.
  • 쪽당 시간 편차가 크다. RapidOCR은 13.5초에서 82.7초까지 벌어졌는데, 조밀한 슬라이드일수록 검출되는 텍스트 줄이 많아 인식 호출이 그만큼 늘기 때문이다. 용량 산정은 평균이 아니라 최악값으로 잡아야 한다.
  • 본문형 정확도는 계약서 1쪽을 직접 눈으로 옮겨 적은 정답지에 대한 값이다. 전사 과정의 오차가 그대로 들어간다.
  • PaddleOCR은 paddlepaddle 의존성이 무겁고 PyInstaller 패키징에서 문제가 잦아, EasyOCR은 이미 spec에서 배제한 torch에 의존해 각각 제외했다. 실측하지 않았다.
초기 합성 스캔 측정이 정반대 결론을 냈던 이유

처음에는 디지털 PDF를 200dpi 이미지로 렌더링해 만든 합성 스캔본으로 측정했고, Tesseract가 속도·정확도 모두 우세하다는 결과가 나왔다(91.5% 대 81.5%).

그 표본은 노이즈도 기울어짐도 번짐도 없는 깨끗한 렌더링이라, 전통적 이미지처리 기반인 Tesseract에 유리한 조건이었다. 실제 스캔본으로 바꾸고 각도 분류기 문제를 걷어내자 순위가 뒤집혔다. 합성 스캔으로 OCR 엔진을 고르면 안 된다는 것 자체가 이번 측정의 소득이다.

측정 환경: Tesseract 5.4.0 (winget 설치, 한국어 kor.traineddata 별도 배치) · rapidocr 3.9.2 (onnxruntime CPU, korean PP-OCRv4 mobile) · pypdfium2 렌더링 · Python 3.12 격리 venv. CSOClassify 코드는 수정하지 않았다.

대상은 D:\분류함 전체 PDF에서 전 페이지에 텍스트 레이어가 없는 것만 골라낸 순수 스캔본 9종이며 D:\분류함\스캔PDF에 모아 두었다. 페이지 표본은 시드 20260825로 고정해 언제든 같은 표본으로 재현할 수 있다.
