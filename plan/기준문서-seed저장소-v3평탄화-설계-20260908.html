1 왜 바꾸나 — 실측

실제 운영 파일 ui/policy/class_seed.jsonl(19행, 173,013 바이트)를 그대로 재어 본 값이다. 추측이 아니다.

재어 본 것v2v3(안)
한 줄의 메타 바이트(벡터 제외)평균 663 B평균 273 B 59% 감소
중첩 깊이4단(axes.security.value)2단 한 겹
같은 등급이 적히는 곳3곳 — 19행 전부1곳 진실이 하나
축별 승인자·메모가 실제로 다른 행0 / 19— 쓰이지 않는 유연성
축 상태active 37개 (전부)— 해제·의심 0건

“같은 등급이 3곳”이 이 설계의 핵심 문제다. 등급 C 하나가 grade, labels.security, axes.security.value 세 군데에 적힌다. 셋이 어긋나면 어느 것이 참인지 파일만 보고는 알 수 없다. 지금은 project() 라는 함수가 저장 직전에 항상 세 곳을 맞춰 주기 때문에 어긋나지 않는다 — 즉, 이 구조는 “함수를 반드시 통과해야만 올바른” 파일 형식이다. CLI(--seed-add)나 웹처럼 다른 프로세스가 이 파일을 쓰기 시작하면 그 규율을 강제할 방법이 없다. 그래서 지금 편다.

바뀌지 않는 것 — 전파(propagate) 알고리즘, 임계값, 등급 판정, 업무분류 부여, 벡터. v3 는 같은 값을 다른 모양으로 적을 뿐이다. 이행 뒤 19행 전부에 대해 등급·분류코드가 한 글자도 바뀌지 않음을 §14 에서 확인한다.

3 누가 이 파일을 읽는가

평탄화가 안전한지는 읽는 쪽이 무엇을 보느냐로 정해진다. 코드를 찾아 확인했다.

읽는 쪽보는 칸위치

Rust 등급 전파file · grade · vector Rust/src/propagate.rs:40

결정적 사실 — 분류 엔진 네 곳 중 어느 것도 axes 를 읽지 않는다. 엔진은 언제나 파생값(grade, labels.doctype)만 본다. axes 는 오직 UI 화면만 쓰는 칸이다. 즉 v3 는 “엔진이 이미 읽고 있는 평평한 값을 진실로 승격하고, UI 전용 중첩을 없애는” 일이다.
그래서 유일한 엔진 변경점은 하나뿐이다 — 업무분류를 labels.doctype 이 아니라 doctype 에서 읽게 하는 것. §11 에서 다룬다.

5 빼는 칸과 그 근거

빼는 칸왜잃는 것
labels.securitygrade 와 항상 같은 값(19/19). 읽는 코드 없음 없음
labels.doctypedoctype 으로 올린다(이름만 바뀜) 없음 — 엔진 2벌 수정(§11)
axes.*.valuegrade·doctype 이 곧 그 값 없음
axes.*.state실측 전부 active. 비정상만 hold 로(§6) 없음
axes.*.approved_by·note축별로 다른 행 0/19. 줄 단위 칸으로 합침(§7) 축별 분리 — §7 참조
axes.*.ts줄의 ts 로 합침. 축별 이력은 class_seed_audit.jsonl 이 갖는다 축별 시각
doc.size읽는 코드가 한 줄도 없다. 원본이 있으면 언제든 다시 잰다 없음
doc.mtime같음 — 변경 판정은 hash 로만 한다 원본의 나이를 눈으로 보던 단서
embed.ts줄의 ts 와 실측 동일. dim 만 올린다 없음
doc.mtime 을 빼는 것은 판단이 필요한 항목이었다. mtime(원본이 마지막으로 저장된 때)과 ts(이 기록이 만들어진 때)는 주어가 다른 시각이라 서로 대신할 수 없다. 그런데도 빼는 근거는 두 가지다:
① 판정에 쓰이지 않는다. 원본이 바뀌었는지 보는 코드는 check_seeds()·sync_with_records() 둘뿐이고, 둘 다 doc.hash 만 비교한다(ui/seedstore.py:933, :1024).
② 만든 쪽 주석도 그렇게 적어 두었다 — ui/app.py seed_doc_meta(): “크기·수정시각은 사람이 눈으로 확인할 때 쓰는 보조 정보다”.
잃는 것: 원본이 지워진 뒤 “이 기준문서는 몇 년도 문서였나”를 이 파일만 보고는 알 수 없게 된다. 다만 그 정보가 필요한 화면이 지금 없고, 필요해지면 ts 와 함께 class_seed_audit.jsonl 에 남길 수 있다.

6 축 상태(해제·의심)를 어떻게 담나

여기가 이 설계에서 유일하게 어려운 대목이다. v2 에는 축 상태가 셋 있다.

상태누가 붙이나뜻실측
active사람지금 기준으로 쓴다37건(전부)
retired사람이 축은 기준에서 뺀다0건
suspect시스템원본이 바뀌었거나 없어졌다 → 잠시 뺀다. 값은 지우지 않는다(사람이 확인해 되살린다)0건

retired 는 “지운다”와 사실상 같다 — 코드로 확인

주석에는 “해제해도 값은 지우지 않는다(되살릴 수 있어야 한다)”라고 적혀 있지만, 코드는 그렇게 동작하지 않는다.

  • project() 가 grade·labels 를 지우므로 엔진은 그 값을 영영 보지 못한다.
  • save_seeds() 는 keepable_axes() 가 비면 그 줄을 파일에서 뺀다 — 두 축을 모두 해제하면 값은 실제로 사라진다.
  • set_axis() 는 이전 상태와 무관하게 active 로 덮는다 — retired 가 재등록을 막지도 않는다.
  • 해제할 때 append_seed_audit(..., before=이전값) 로 이전 값이 감사 로그에 남는다(ui/app.py:3086).

⇒ v3 에서 retired 는 그 칸을 지운다. 이력은 class_seed_audit.jsonl 이 갖는다. 잃는 것이 없고, “값이 남아 있는데 아무도 안 읽는” 유령 칸도 사라진다.

suspect 는 값을 보존해야 한다 — hold 칸

suspect 는 다르다. 시스템이 붙이고 사람이 푸는 것이므로 값이 남아야 한다. 그런데 v3 는 grade 가 곧 진실이라, 값을 그 자리에 두면 엔진이 그대로 읽어 버린다. 그래서 보류된 값은 다른 칸으로 옮긴다.

{
  "v": 3, "file": "d:/sample/03.○○○규정_12.01.01.doc",
  "hash": "2438eafe…",
  "doctype": ["DC_006_002"],                   ← 이 축은 살아 있다
  "hold": {                                    ← 보안축만 보류됨
    "grade": { "value": "O", "reason": "stale",
               "ts": "2026-09-08 10:12:00" }
  },
  "approved_by": "고봉수", "ts": "…", "dim": 384, "vector": [ … ]
}
이 방식의 장점 — 엔진을 고칠 필요가 없다. 보류되면 grade 칸이 존재하지 않으므로 엔진은 자동으로 그 줄을 등급 기준에서 뺀다 (지금 project() 가 하던 일을 키 이름 하나로 대신한다). 되살리기는 hold.grade.value 를 grade 로 되돌리고 hold 를 지우는 것 — 한 줄이다.
정상 행에는 hold 칸이 아예 없다. 파일을 열면 이상한 줄만 눈에 띈다.
조용히 사라지지 않게 하는 장치 — 보류는 “값이 없다”와 모양이 같아지므로, 세는 곳이 반드시 있어야 한다. check_seeds() 가 hold 가 있는 줄을 suspect 목록으로 세고(지금과 같다), 점검 화면이 사유(stale/missing/orphan/dim)와 함께 보여 준다. 세지 않으면 “왜 이 기준문서가 안 먹지”를 아무도 알 수 없게 된다.

다른 안을 검토한 이유

안모양왜 안 골랐나
(가) 상태 칸 두 개"grade_state":"suspect" 정상 행 19개 전부에 "active" 가 두 개씩 붙는다 — 평탄화의 목적을 절반 잃는다. 엔진도 이 칸을 봐야 해서 두 판 수정이 필요하다
(나) 값을 그대로 두고 off:["grade"]"grade":"O","off":["grade"] 엔진이 off 를 안 보면 보류가 무력해진다. 두 판 수정이 필요하고, 한쪽만 고쳐지면 Python 과 Rust 결과가 갈린다 — 가장 나쁜 종류의 버그
(다) hold 로 옮김위 예시 권고. 엔진 수정 0. 값 보존 O. 정상 행은 칸이 늘지 않음

7 축별 승인자·메모를 잃는가

v2 는 축마다 approved_by·note·source·ts 를 따로 갖는다. “보안등급은 A 가, 업무분류는 B 가 확정” 같은 경우를 담으려는 설계였다. v3 는 줄 단위로 합친다.

재어 본 것결과
두 축의 approved_by·note 가 다른 행0 / 19
두 축의 ts 가 다른 행1 / 19 — 같은 일괄 등록 중 1초 차이
화면이 메모를 쓰는 방식ui/app.py:3088 — 이미 줄 단위로 쓴다 ({**x, "note": …}). 축별 메모는 화면에서 만들 수단이 없다

즉 축별 분리는 코드가 지원만 하고 아무도 쓰지 않는 유연성이다. source 만 실제로 갈린다(phase4 vs phase6) — 그 값은 “화면의 어느 단계에서 등록됐나”를 뜻하고, 판정에는 쓰이지 않는다.

그래서 무엇을 잃나 — 앞으로 두 사람이 서로 다른 축을 확정하는 운영을 하게 되면 줄의 approved_by 는 마지막 사람만 남는다. 다만 그 이력은 class_seed_audit.jsonl 에 축과 함께 남으므로(axis= 칸이 있다) “누가 무엇을 확정했나”는 추적할 수 있다. 화면의 approvers() 함수는 남기되 줄의 approved_by 를 돌려준다 (표의 “검토자” 칸이 비지 않는다). 축별 추적이 필요할 때 보는 곳은 감사 로그다.
구현하며 정정한 대목 2026-09-08 — 이 자리에 처음에는 “approvers() 가 감사 로그를 보도록 바꾼다”고 적었지만, 그 함수는 줄 하나만 받고 감사 로그 경로를 모른다. 경로를 넘기도록 고치면 호출부(ui/app.py:3141)와 화면 표 계산이 파일 입출력을 하게 되는데, 표 한 칸을 채우려고 매 줄마다 감사 로그를 읽는 것은 값이 맞지 않는다. 그래서 함수는 줄의 값을 돌려주고, 축별 이력은 사람이 변경 이력 화면에서 본다.

source 는 줄 단위로 남기되, 두 축의 값이 다르면 둘을 이어 붙인다: "source": "phase4+phase6". 뜻을 잃지 않으면서 칸은 하나다.

8 v2 → v3 변환표

이 표가 곧 승격 함수 ensure_v3() 의 사양이다.

9 이행 — 읽기는 둘 다, 쓰기는 v3

배포판이 여러 벌(§13) 돌아가는 상황이라, “어느 날 다 같이 바뀐다”는 전제를 세울 수 없다.

읽기:  v 없음 → v1 로 보고 승격  ┐
       v == 2  → ensure_v3() 승격 ├→  모든 코드는 v3 모양만 다룬다
       v == 3  → 그대로            ┘
       v > 3   → 경고 후 그 줄 건너뜀 (모르는 미래 형식을 추측하지 않는다)

쓰기:  언제나 v3
구판 실행 파일이 v3 파일을 읽으면 어떻게 되나 — 이것이 이행의 진짜 위험이다. 구판 엔진은 grade 는 읽지만 labels.doctype 이 없으므로 업무분류 전파만 조용히 0건이 된다(깨지지 않고 그냥 안 된다). 거버넌스 도구에서 가장 나쁜 실패다.
막는 방법: 신판 --check-seeds 가 파일의 v 를 찍고, 구판·신판이 섞인 배포를 §13 의 점검 목록으로 한 번에 확인한 뒤 6벌을 동시에 교체한다. doctype 이 있는 줄을 구판이 읽으면 몇 건이 사라지는지 숫자로 먼저 보고한다.

10 seedstore API 는 그대로 둔다

ui/app.py 는 seedstore 함수를 60여 곳에서 부른다 (axis_value 13, set_axis 7, active_axes 4, axis_state 3 …). 화면 코드는 손대지 않는다 — 같은 이름의 함수가 v3 를 읽도록 속만 바꾼다.

def axis_value(entry, axis):
    # v2 때는 axes[axis]["value"] 였다. v3 는 평평한 칸이 곧 값이다.
    return entry.get("grade") if axis == "security" else (entry.get("doctype") or [])

def axis_state(entry, axis):
    key = "grade" if axis == "security" else "doctype"
    if key in (entry.get("hold") or {}):  return STATE_SUSPECT
    return STATE_ACTIVE if entry.get(key) else STATE_RETIRED
왜 접근 함수를 남기나 — 화면이 e["grade"] 를 직접 읽기 시작하면 다음에 형식을 바꿀 때 또 60곳을 고쳐야 한다. 이번 변경이 화면 60곳을 건드리지 않고 끝나는 이유가 바로 그 함수들이 있었기 때문이다. 그 이점을 버리지 않는다.

사라지는 함수: ensure_v2(→ensure_v3), project(파생값이 없으므로 불필요), _blank_axis, keepable_axes(→ grade·doctype 유무로 판단).
