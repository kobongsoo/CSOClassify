# CSOClassify 설계서

> 한국어 문서 → 텍스트 추출 → 임베딩 벡터 출력 (로컬 PC용 단일 실행파일)
> 작성일: 2026-08-12 · 상태: 초안(설계 검토용)
> 개정: 2026-08-14 — §3 결정7(L1 PII 검출 성능 최적화: 부분검출·지연가드·주소 프리필터) 추가

---

## 1. 목적 · 개요

- **목적**: 한국어(및 다국어) 문서에서 본문 텍스트를 추출하고, 그 텍스트의 **임베딩 벡터**를 출력한다.
- **동작 형태**: 인터넷 연결 없이 **로컬 PC에서 단일 `.exe`** 로 동작. (오프라인, 서버 불필요)
- **기본 사용 예**:
  ```bash
  csoclassify.exe -file D:\AAA.hwp
  ```
  → 표준출력으로 **파일명 + 임베딩 벡터**를 출력.
- **핵심 제약**:
  - 임베딩 모델은 **작은 사이즈**(CPU 로컬 추론 가능).
  - 텍스트 추출은 `MpowerAI_v10` 이 쓰던 **사이냅 문서필터(Synap Document Filter)** 를 활용하되, **리팩토링이 아니라 신규 구현**.
  - Python 으로 작성, **PyInstaller 로 exe 변환** 가능해야 함.

## 3. 핵심 설계 결정

### 결정 1 — 텍스트 추출: `snf_exe.exe` subprocess 호출 (권장)

- 사이냅 배포본의 `snf_exe.exe` 를 `subprocess` 로 호출하여 문서 → UTF-8 텍스트 변환.
- 장점: **컴파일 불필요**, DLL 링킹 이슈 없음, PyInstaller 는 exe/dll 을 데이터로 번들만.
- 추출기 인터페이스( `TextExtractor` )로 추상화 → 추후 ctypes/DLL 방식으로 교체 가능하게 설계.
- **대안(2순위)**: `snf_win.dll` 을 `ctypes` 로 직접 로드해 `snf_flt_filter_m` 계열 API 호출. 프로세스 기동 오버헤드가 없고 콜백 스트리밍이 가능하지만 구현 난이도↑. 대량 처리 성능이 문제될 때 전환.

> `snf_exe.exe` 의 정확한 CLI 인자는 사이냅 매뉴얼/`--help` 로 실측 확정 필요(§14). 매뉴얼 부재 시 초기에는 DLL ctypes 방식으로 바로 갈 수도 있음 — 스파이크로 먼저 검증.

### 결정 2 — 임베딩: 작은 다국어/한국어 모델 + **ONNX + onnxruntime** (권장)

- `sentence-transformers` + PyTorch 를 그대로 번들하면 exe 가 **~2GB+** 로 비대해지고 느리다.
- 모델을 **ONNX 로 변환**해 **`onnxruntime`(CPU)** 로 추론하면: exe 크기·기동시간·추론속도 모두 유리하고 PyInstaller 친화적.
- 토크나이저는 `tokenizers`(Rust, 경량) 사용.

### 결정 3 — 문서 단위 벡터 (기본) + 청크 벡터 (옵션)

- 긴 문서는 모델 최대 토큰을 초과 → **청킹(overlap 포함)** 후 각 청크 임베딩.
- 기본 출력: 청크 벡터들의 **평균 풀링 → 문서 1벡터**(정규화). 요구사항 "파일명 + 벡터값"에 부합.
- 옵션 `--per-chunk`: 청크별 벡터 배열 출력(추후 RAG 인덱싱용).

### 결정 4 — 모델 로딩 시점: **지연 로딩(lazy) + 텍스트 추출과 병렬 예열**

**문제**: `csoclassify.exe` 를 매번 새로 띄우면 그때마다 ONNX 모델·토크나이저를 메모리에 올려야 한다. e5-small(ONNX ~120MB) 은 CPU 로딩에 대략 **0.5~2초**(디스크 캐시·기기에 따라) 소요된다. 단일 파일 1회 처리에는 이 "콜드 스타트"가 전체 시간의 대부분을 차지할 수 있다.

**언제 로딩하나 — 케이스별 전략:**

| 실행 형태 | 로딩 전략 | 근거 |
|---|---|---|
| 단일 파일(`-file`) | **텍스트 추출(snf_exe subprocess)과 모델 로딩을 병렬** 실행 | 추출도 프로세스 기동이 필요(~수십 ms~수백 ms). 그 사이 별도 스레드에서 모델을 예열하면 콜드 스타트를 **가림** |
| 폴더 배치(`-dir`) | 모델을 **1회만 로딩 후 전체 파일 재사용**(프로세스 유지) | 파일 N개에 대해 로딩 1회로 분할상환 → 콜드 스타트 무의미 |
| 반복 호출(외부에서 매번 exe 실행) | **상주 데몬 모드**(결정 5) | 모델을 상주시키고 클라이언트가 재사용 → 2회차부터 로딩 0. 상세·race 대응은 §결정 5 |

**핵심 결정:**
1. **지연 로딩(lazy import & load)**: `onnxruntime`/모델은 `import` 시점이 아니라 **실제 임베딩 직전**에 로드하는 `Embedder.ensure_loaded()` 로 캡슐화. `--text-only`(추출만) 나 인자 오류로 끝나는 경우 **모델을 아예 안 올려** 빠르게 종료.
2. **추출-로딩 병렬화(단일 파일)**: 파이프라인이 `snf_exe` 호출을 시작하는 즉시 백그라운드 스레드에서 `ensure_loaded()` 를 킥오프 → 추출이 끝나면 모델은 대개 이미 준비됨.
3. **onnxruntime 설정**: 세션 옵션에서 스레드 수 제한(`intra_op_num_threads`)·`graph_optimization_level` 조정으로 로딩·추론 균형. 최초 실행 후 OS 파일 캐시로 2회차부터는 로딩이 크게 빨라짐.
4. **배치 우선 권장**: 문서가 여러 개면 `-dir`(또는 파일목록 stdin) 로 **한 번의 프로세스**에서 처리하도록 README 에 안내 → 로딩 비용 최소화.

> 즉, "처음 실행 시 로딩이 길다"는 우려는 (a) 단일 파일은 추출과 병렬로 가려서, (b) 다중 파일은 배치로 1회 분할상환해서, (c) 외부에서 매번 exe 를 호출하는 반복 시나리오는 **결정 5(상주 데몬 모드)** 로 해결한다.

### 결정 5 — 상주 데몬 모드(Resident Daemon): **채택(옵션), in-process 폴백 유지**

**요구**: 모델을 한 번 로딩하면 **상주 프로세스로 계속 유지**하고, 이후 파일 처리 요청이 올 때마다 **상주 데몬이 살아있는지 확인 → 살아있으면 재사용, 아니면 다시 로딩(=데몬 재기동)**.

이 방식은 "외부 시스템이 파일마다 `csoclassify.exe` 를 새로 호출하는데 배치로 바꾸기 어려운" 상황에서 콜드 스타트를 원천 제거하는 **정석 해법**이다. 다만 순진한 "확인 후 없으면 실행"에는 **경쟁 조건(race)** 과 **생명주기 관리** 이슈가 있어 아래처럼 설계한다.

#### 5-1. 역할 분리 (같은 exe, 두 모드)

- `csoclassify.exe -file X` → **클라이언트**(얇은 프런트). 데몬에 요청을 위임하고 결과만 출력.
- `csoclassify.exe --serve` → **데몬**(모델 상주). 클라이언트가 없으면 **자동 자식으로 기동**(사용자가 직접 칠 필요 없음). PyInstaller onefile 이라도 `sys.executable` 로 자기 자신을 `--serve` 인자로 재실행.

#### 5-2. 클라이언트 요청 흐름 (사용자 제안 반영 + race 보강)

```
① 데몬 엔드포인트 접속 시도(짧은 timeout, 예: 300ms) 후 PING
      │
   ┌──┴───────────────┐
 살아있음               죽었음/무응답
   │                     │
 ② 모델키·버전 일치?    ③ 데몬 자동 기동(아래 5-3 싱글턴 규칙)
   │  일치 → 재사용        │  기동 완료까지 PING 폴링(최대 N초)
   │  불일치 → 재기동 요청  │
   ▼                     ▼
 ④ {op:"embed", path, opts} 전송 → 벡터 수신 → stdout 출력 → 클라이언트 종료
   (데몬은 계속 상주. 유휴 타이머 리셋)
```

- "동작중인지 확인 → 아니면 다시 로딩"은 위 ①→③ 그대로. **핵심 보강은 ③의 기동을 원자적으로** 만들어 동시 요청 시 데몬이 중복 생성되지 않게 하는 것.

#### 5-3. 싱글턴 & 경쟁 조건 (가장 중요)

순진하게 "접속 실패 → 무조건 spawn" 하면 **두 클라이언트가 동시에** 데몬을 두 개 띄운다(TOCTOU). 해결:

- **엔드포인트 생성 자체를 잠금으로 사용**: 데몬은 시작 시 고정 이름의 **Named Pipe**(권장) 또는 **loopback 소켓**을 **독점 생성**한다. 이미 존재하면 `EADDRINUSE`/생성 실패 → **두 번째 데몬은 즉시 종료**하고 클라이언트로 전환. 즉 "먼저 바인딩한 자가 유일한 데몬".
- 클라이언트의 spawn 도 **한 번만** 시도하고, 실패 시 "다른 프로세스가 이미 띄우는 중"으로 간주해 **PING 폴링으로 대기**.
- 보조로 `%LOCALAPPDATA%\CSOClassify\daemon-<modelkey>.json`(pid·endpoint·version·pid_started) discovery 파일 기록 → `--status`/`--stop` 및 stale 판별에 사용.

#### 5-4. IPC 방식 선택 (Windows 우선)

| 방식 | 장점 | 단점 | 채택 |
|---|---|---|---|
| **Named Pipe** `\\.\pipe\csoclassify_<user>_<modelkey>` | 포트 불필요, 로컬 전용, 생성이 원자적(싱글턴 겸용), 기본 ACL=현재 사용자 | Windows 전용 API | **1순위(Windows)** |
| TCP loopback `127.0.0.1:<port>` + 포트파일 | 크로스플랫폼, 파이썬 표준 `socket` | 포트 충돌·방화벽 팝업 가능, 타 로컬 사용자 접근 가능 → 토큰 필요 | 2순위/리눅스 |
| stdin/stdout 파이프 | 단순 | 데몬 재사용 불가(1:1) → 요건 불충족 | 미채택 |

- 전송 포맷: 길이-프리픽스 **JSON** 라인(요청/응답). 벡터는 배열 또는 base64(float32) — 대량이면 base64 로 파싱비용↓.

#### 5-5. 생명주기 / 상태 확인 / 재로딩

- **모델키(modelkey)**: `--model` 값 해시. 데몬은 자신이 로드한 모델키를 PING 응답에 실어 보냄 → 클라이언트가 요청 모델과 **불일치면** (a) 데몬이 다중 모델 LRU 캐시를 지원하거나 (b) 모델키를 엔드포인트 이름에 포함해 **모델별 데몬**을 따로 둔다(초기엔 (b) 가 단순·안전).
- **버전**: 핸드셰이크에 exe 버전 포함 → exe 업그레이드 후 **구버전 데몬이 남아있으면** 클라이언트가 `--stop` 신호를 보내고 새로 기동.
- **헬스 = 모델 준비 여부**: PING 응답에 `model_ready: true/false`. 로딩 실패·이상 시 not-ready → 클라이언트가 **재기동 트리거**("동작중이 아니면 다시 로딩"의 실제 구현).
- **유휴 자동 종료**: 데몬은 마지막 요청 이후 `--idle-timeout`(기본 예: 10분) 지나면 **스스로 종료**(메모리 회수). 다음 요청이 오면 다시 콜드 스타트 1회 → 이후 다시 상주.
- **stale 데몬 정리**: discovery 파일의 pid 가 죽어 있으면(프로세스 부재) 파일 제거 후 새로 기동.

#### 5-6. 동시성 · 보안 · 폴백

- **동시 요청**: 데몬은 요청을 **큐로 직렬화**(onnxruntime 세션 재사용, 필요시 배치)하거나 요청별 스레드 + 세션 락. 초기엔 직렬화로 단순하게.
- **보안**: Named Pipe 는 기본적으로 현재 사용자 세션 한정. TCP 폴백이면 **127.0.0.1 바인딩 + discovery 파일의 랜덤 토큰**을 요청에 요구해 타 로컬 사용자 접근 차단. 데몬은 절대 외부 인터페이스에 바인딩하지 않음.
- **민감문서**: 데몬은 추출 텍스트를 **메모리에서만** 다루고 디스크에 남기지 않음(§7-1 임시파일 규칙 동일 적용, 요청 종료 시 삭제).
- **항상 동작 보장(폴백)**: 데몬 기동/IPC 가 어떤 이유로든 실패하면 클라이언트는 **결정 4의 in-process 로딩 경로로 폴백**해 그 요청을 직접 처리 → 데몬 문제로 기능이 멈추지 않음.

#### 5-7. 관련 CLI (§6 에 추가)

- `--daemon` / `--no-daemon` : 데몬 사용 on/off(**초기 릴리스 기본 on**). 단발성/디버그 시 `--no-daemon` 으로 in-process 강제.
- 환경변수 `CSOCLASSIFY_DAEMON=0` 으로 전역 off 가능.
- `--serve` : 데몬 프로세스로 직접 기동(수동/서비스 등록용, 보통 내부 자동 사용).
- `--status` : 상주 데몬 상태(pid·모델·버전·유휴시간) 출력.
- `--stop` : 상주 데몬 정상 종료.
- `--idle-timeout <sec>` : 유휴 자동 종료 시간(기본 600).

#### 5-8. 장단점 & 결론

| 장점 | 단점/비용 |
|---|---|
| 반복 호출 시 콜드 스타트 완전 제거(2회차부터 로딩 0) | 구현 복잡도↑(IPC·싱글턴·생명주기) |
| 외부 시스템이 파일단위로 exe 를 불러도 빠름 | 상주 메모리 점유(모델 상주) |
| 배치로 바꾸기 어려운 파이프라인에 이상적 | stale/버전불일치/보안 등 엣지케이스 관리 필요 |

**결론(확정)**: **초기 릴리스부터 데몬 기본 on**. 첫 호출에서 데몬을 자동 기동해 모델을 상주시키고, 2회차부터 로딩 0 으로 처리한다. 데몬 기동/IPC 실패 시에는 **결정 4의 in-process 경로로 자동 폴백**하므로 데몬 문제로 기능이 멈추지 않는다(항상 동작 보장). `--no-daemon`(또는 `CSOCLASSIFY_DAEMON=0`)으로 단발성·디버그 시 in-process 강제 가능. **개발 우선순위**: 데몬이 기본 경로이므로 결정 4(병렬 예열+배치)와 결정 5(데몬·IPC·싱글턴·폴백)를 **함께 초기 릴리스 범위**로 구현하고, 데몬 엣지케이스(stale·버전·유휴종료)를 골든테스트로 충분히 검증한 뒤 배포한다.

### 결정 6 — 임베딩 시점: **선택적·지연 임베딩 (2단계)** — 확정 문서는 임베딩 생략

**배경**: CSO 분류의 1차 판정은 규칙(Signal A)·경로(Signal C)·파일명(Signal D)만으로 이뤄지고, **임베딩(Signal B)은 등급 결정에 관여하지 않는다**(1차 분류는 레코드에 벡터를 싣기만 함). 임베딩 라벨 전파는 **보류(grade=None) 문서에만** 적용되고, 이미 확정된 C/S/O 는 임베딩으로 흔들지 않는다(주제는 잡아도 민감도는 보증 못 하므로 공개문서 과분류 방지). 따라서 규칙/경로/파일명으로 이미 확정된 문서의 벡터는 **그 문서의 분류엔 불필요**하다. 임베딩은 파이프라인에서 가장 느린 단계라, 확정 문서까지 전부 임베딩하면 큰 낭비다.

**결정**: 임베딩을 "필요한 문서에만" 수행하고, 나머지는 **승격 시점으로 지연**한다.

| 단계 | 임베딩 | 내용 |
|---|---|---|
| **실행(기본)** | ❌ 없음 | 규칙/경로/파일명만으로 전체 분류 → C/S/O + 보류 산출 (빠름) |
| **보류 구제(선택)** | 보류 문서만 | 외부 seed(`class_seed.jsonl`) 기준으로 보류만 임베딩·전파. (외부 seed 없으면 내부 seed용으로 `seed_eligible` 확정문서도 임베딩) |
| **seed 승격** | 승격 문서만 | 그때 on-demand 로 임베딩 |

**정확도 불변**: 1차 분류는 원래 벡터를 쓰지 않고, 전파는 여전히 보류 문서만 구제하므로 **최종 등급은 전량 임베딩과 동일**하다. 바뀌는 건 "어떤 문서에 벡터를 계산하느냐"뿐이다.

**전파 기준 seed = 외부 + 내부 병합**: 보류 문서는 **외부 큐레이션 seed(`class_seed.jsonl`)** 와 **코퍼스 내부 seed(`seed_eligible` 확정문서)** 를 **합친 기준**과 비교해 등급을 전파한다(둘 중 가까운 쪽으로 구제). 외부 seed 가 없으면 내부 seed 만 쓴다.
- ⇒ 보류를 C 로 끌어올리려면 **C 기준(seed)의 벡터**가 있어야 한다. 그래서 `seed_eligible=True` 확정문서는 (확정이어도) 임베딩해 내부 seed 로 삼는다. 반대로 `seed_eligible=False` 확정문서(예: 연락처 단독=O)는 임베딩을 생략한다.

**구현 매핑**:
- CLI: `--embed-needed`(보류거나 `seed_eligible` 인 문서만 임베딩). 기존 `--with-vector`(전량)·무옵션(임베딩 없음)도 유지. 요약줄에 `emb=N`(실제 임베딩 수) 표기.
- 전파: `propagate_records` 가 외부 seed + 내부 `seed_eligible` seed 를 `SeedIndex.merge` 로 합쳐 비교.
- 승격: 벡터가 없는 문서를 seed 로 올릴 때 그 문서만 `--classify --with-vector -file` 로 **on-demand 임베딩**(개별·일괄 모두).
- UI '실행' 기본이 `--embed-needed` → 규칙으로 확정되는 대다수 문서의 임베딩을 건너뛰어 대폭 빨라진다.

### 결정 7 — L1 PII 검출(ko-pii) 성능 최적화: **부분검출 + 지연가드(청킹) + 주소 프리필터** (2026-08, 지연가드 청킹 개정 2026-08-15)

**배경**: Signal A(규칙 스캔, `classify/rules.py`)는 L1 PII 검출을 ko-pii 에 맡긴다. 초기 구현은 `ko_pii.detect_all()` 을 호출했는데, 이 함수는 **28개 검출기를 전부 실행한 뒤** `include` 로 결과만 필터링한다 → CSOClassify 가 쓰는 18개 라벨 외에 `person`·`personal_attr`(밀집 입력 O(n²)) 등 **안 쓰는 검출기까지 매번 돌아** 낭비다. 실시간 UI 경로라 문서당 지연이 중요하다.

**결정**: 세 단계로 최적화하되 **검출 결과는 `detect_all` 과 100% 동일**하게 유지한다(정규화·전각/제로폭 방어·역매핑·겹침 해소는 ko-pii 내부 함수를 그대로 재사용).

| # | 최적화 | 방법 | 효과(실측) |
|---|---|---|---|
| 1 | **부분 검출** | `detect_all` 대신 설정 라벨에 해당하는 18개 검출기만 도는 `_detect_subset()` | 검출 시간 **~54%↓** |
| 2 | **지연 가드(청킹)** | 선형 검출기는 전량 스캔, 초선형(phone·address·account)은 10K 청크(오버랩 128)로 나눠 스캔+절대오프셋 병합, 앞 100K 까지. env `CSOCLASSIFY_KOPII_MAX_CHARS`(청크)/`_MAX_TOTAL`(총상한)/`_OVERLAP` | 지연 **선형화**(청크당 ~0.08초) + **10K 뒤 미탐 해소** |
| 3 | **주소 프리필터** | `address.detect`(정규식 4개, 밀집 시 O(n²)) 실행 전 주소 신호가 없으면 건너뜀 | 주소 없는 문서 **추가 ~34%↓** |

**① 부분 검출 — 안전장치**: 라벨→검출기 매핑(`_LABEL_TO_DETECTOR`)에 없는 라벨이 요청되면(향후 yaml 확장 등) 전체 엔진으로 자동 폴백해 미검출을 막는다. 검출기 실행 순서는 `ko_pii.detect.DETECTORS` 를 보존해 겹침 해소의 '동점 시 먼저 시작한 span' 규칙까지 동일하게 맞춘다.

**② 지연 가드(청킹) — 근거·설계**: subset 이후에도 `phone`(O(n²))·`address`·`account` 때문에 검출 시간이 입력 길이에 **초선형**으로 는다(실측 10K≈0.08s / 50K≈0.9s / 300K≈20s). 초기(2026-08-14)엔 앞 10K 만 남기고 **잘라** 지연을 눌렀으나, 그러면 **10K 뒤쪽 PII 를 전부 놓치는** 문제가 있었다(10K 넘는 문서에서 phone/address 미탐). 이를 아래 **청킹 설계**로 교체(2026-08-15)해 *커버리지 회복 + 지연 선형화* 를 동시에 얻는다:
- **선형/초선형 분리**: 초선형 비용의 원인은 `phone`·`address`·`account` 세 검출기뿐이다(`_KOPII_SUPERLINEAR`). 나머지(선형)는 전체 텍스트를 **1회 전량** 스캔(길이 비례·저비용, 상한 없음) → 문서 끝의 주민번호·카드·이메일도 놓치지 않는다.
- **초선형 청킹**: 초선형 검출기는 `_KOPII_MAX_CHARS`(=청크 크기, 10K) 창으로 잘라 돌린다. 통짜 1회의 초선형 비용(50K=0.9s) 대신 창마다 0.08s 고정이라 총비용이 **선형**이 된다(50K=5×0.08≈0.4s, 300K=30×0.08≈2.4s).
- **경계 처리(핵심)**: 인접 창을 `_KOPII_OVERLAP`(128자, 최장 PII span 보다 큼)만큼 겹쳐 창 경계에 걸친 PII 미탐을 막고, **절대 오프셋 구간 병합**(`_count_merged_spans`)으로 겹침 중복은 1건으로 합쳐 이중계수를 없앤다(경계에서 문맥 차로 span 이 미세하게 달라져도 '겹치면 1건').
- **지연 캡**: 초선형 스캔 범위는 앞 `_KOPII_MAX_TOTAL`(기본 100K ≈ ~1s)로 상한을 둬 최악 지연을 묶는다. 실시간 경로는 낮추고 배치는 올린다(세 값 모두 env 조절).
- **소형 문서(≤10K, 대다수)**: 예전과 **동일한 단일 패스** → 교차라벨 겹침해소까지 100% 보존(완전 파리티).
- **주의(트레이드오프)**: 큰 문서에서 초선형↔선형 라벨의 span 이 겹치는 드문 경우, 두 패스가 분리돼 `detect_all` 의 교차라벨 겹침해소가 적용되지 않아 양쪽이 각각 세어질 수 있다(건수 기반 등급엔 영향 미미).

**③ 주소 프리필터 — 안전 불변식**: `address.detect` 의 4개 패턴은 모두 아래 두 신호 중 하나를 **반드시** 포함한다 → 신호가 없으면 매칭도 없으므로 건너뛰어도 **미탐이 생기지 않는다**.
- 도로명/지번: `(대로|로|길|동|읍|면|리)` 바로 뒤 숫자(전각 숫자 포함)
- 대화체/단독: `_LOOSE_ANCHORS`(주소·자택·살던·이사·명함 …) — **ko-pii 원본에서 import** 해 버전 간 동기화 어긋남 방지(import 실패 시 프리필터는 '항상 실행'으로 안전 폴백)
- 실측: 실제 주소 표본 전건이 프리필터를 통과(미탐 0), 게이트 유무에 따른 검출 집합 동일.

**검토에서 기각한 대안**:
- **python-stdnum 로 전화/주소 대체** → 부적합. stdnum 의 한국 모듈은 `brn`(사업자)·`rrn`(주민) 둘뿐이고 **전화·주소 모듈이 아예 없다**(주소는 체크섬이 없어 원천적으로 대상 아님). rrn/brn 조차 ko-pii 가 국세청 가중합·주민 체크섬으로 더 정확.
- **phone/account 를 자체 정규식으로 대체** → 실익 없음. 현실 문서에서 phone 은 1~6%, account 는 3~6% 비중이라 대체 이득이 미미하다(무거운 건 `address` 하나뿐이며, 그건 사전 기반이라 정규식 대체 시 오탐이 커져 부적합).

**정확도 불변**: 세 최적화 모두 검출 결과를 바꾸지 않는다. `tests/test_rules.py` 회귀 테스트로 고정 — 부분검출↔전체엔진 동일성, 주소 프리필터 미탐 0·게이트 동일성, 라벨↔검출기 라벨 일치 가드.

**부수 수정(설정 버그)**: `cso_rules.yaml` 의 처방전 라벨이 검출기 실제 라벨과 달라(`PRESCRIPTION` vs `PRESCRIPTION_ID`) **처방전이 한 건도 검출되지 않던 것**을 바로잡았다.

**구현 매핑**:
- `classify/rules.py`: `_detect_subset()`(+`_LABEL_TO_DETECTOR`); 지연가드 청킹 — `_kopii_counts()` 선형/초선형 분리 + `_chunk_windows()`·`_count_merged_spans()`, `_KOPII_SUPERLINEAR`, env `_KOPII_MAX_CHARS`(청크)/`_MAX_TOTAL`(총상한)/`_OVERLAP`; `_address_prefilter()`/`_gated_address_detect()`.
- `resources/policy/cso_rules.yaml`: 처방전 `label: PRESCRIPTION_ID` 로 수정.
- `tests/test_rules.py`: 회귀 테스트 6건 추가(15→21); 청킹 개정으로 3건 추가(21→24: 청크 뒤 검출·오버랩 dedup·선형전량/초선형캡).

**개정 이력**:
- **2026-08-14** — 지연 가드 초판: `_KOPII_MAX_CHARS` 300K→10K, **앞 10K 만 남기고 초과분 절단**(env `CSOCLASSIFY_KOPII_MAX_CHARS` 상향 가능). 최악 지연 20s→0.08s. 한계: 10K 넘는 문서에서 뒤쪽 PII 전부 미탐.
- **2026-08-15** — 지연 가드를 **청킹**으로 교체: 선형=전량 / 초선형=10K 청크(오버랩 128, 절대오프셋 병합)+앞 100K 상한. 절단 대신 커버리지 회복 + 지연 선형화. env 의미 변경(`_KOPII_MAX_CHARS` = *절단 상한* → *청크 크기*), 신규 env `_KOPII_MAX_TOTAL`/`_OVERLAP` 추가. 위 ② 항목이 현재 설계.

- 사유: e5-small 계열의 **소형(384차원)** 을 유지하면서 **한국어 파인튜닝**으로 정확도를 끌어올린 모델 → "작은 사이즈 + 한국어" 요구에 최적.
- e5 계열이므로 입력에 **`passage:` / `query:` 프리픽스** 규약을 그대로 따른다(문서 임베딩은 `passage:`). 프리픽스 처리는 `onnx_embedder.py` 가 자동 부착.
- 폴백: 다국어 범용이 필요하면 `intfloat/multilingual-e5-small`, 순수 한국어 STS 우선이면 `jhgan/ko-sroberta-multitask` 로 `--model` 교체.
- 모델 파일은 완전 오프라인을 위해 **exe 에 번들**(`resources\models\e5-small-ko\`).

## 5. 처리 파이프라인

```
문서파일
  │  ① 포맷 판별 (확장자 + 사이냅 자동감지)
  ▼
[Extractor]  사이냅(snf_exe.exe) → 임시 출력파일(UTF-8) → 원시 텍스트
  │            (임시파일은 기본 자동삭제 / --save-text 시 보존 · §7-2)
  │  ② 정제(clean): 제어문자 제거, 공백/개행 정규화, (옵션) 페이지 마커 제거
  ▼
정제 텍스트
  │  ③ 청킹: 토큰 기준 max_tokens / overlap 으로 분할
  ▼
[청크1, 청크2, ...]
  │  ④ 임베딩: 토크나이즈 → onnxruntime → 청크별 벡터 → L2 정규화
  ▼
청크 벡터들
  │  ⑤ 풀링: mean-pool → 문서 벡터(정규화)  (--per-chunk 이면 생략)
  ▼
[Output] 파일명 + 벡터 + 처리시간(단계별+총합, §7-1) (stdout/JSON/파일)
```

## 7. 출력 포맷

**text (기본, stdout)** — 파일명 + 벡터(공백 구분):
```
D:\AAA.hwp<TAB>0.0123 -0.0456 0.0789 ... (dim=384)
```

**json**:
```json
{
  "file": "D:\\AAA.hwp",
  "model": "multilingual-e5-small-ko",
  "dim": 384,
  "chunks": 3,
  "vector": [0.0123, -0.0456, ...],
  "elapsed_ms": {
    "extract": 41.2,     // 파일 로딩+파싱(snf_exe)
    "clean": 1.3,        // 정제
    "chunk": 0.8,        // 청킹
    "embed": 58.7,       // 토크나이즈+onnx 추론+풀링
    "model_load": 0.0,   // 이 호출에서 실제 로딩한 시간(데몬 재사용 시 0)
    "total": 102.0       // 전체 wall-clock
  }
}
```

**jsonl** (배치 시 파일당 1줄) — `--per-chunk` 이면 `"vectors": [[...],[...]]` 형태.

- 종료 코드: `0` 성공, `1` 추출 실패, `2` 임베딩 실패, `3` 인자 오류. 오류 메시지는 **stderr** 로 분리(파이프 안전).

### 7-1. 처리 시간 측정 · 출력 (`--timing`, 기본 on)

"파일 로딩 → 파싱 → 임베딩" 전 과정을 단계별로 재고 **총합**을 함께 출력한다.

**측정 단계(서버/처리 관점, 단위 ms):**

| 키 | 구간 | 비고 |
|---|---|---|
| `extract` | snf_exe 호출~텍스트 확보 | **파일 로딩+파싱이 snf_exe 내부에서 합쳐져** 있어 하나로 측정(내부 분리 불가). 프로세스 기동 시간 포함 |
| `clean` | 텍스트 정제 | 보통 매우 작음 |
| `chunk` | 토큰 청킹 | |
| `embed` | 토크나이즈+onnx 추론+풀링 | 문서/청크 수에 비례 |
| `model_load` | 이 호출에서 **실제 모델 로딩**한 시간 | 데몬 재사용·예열 완료 시 **0**. 콜드 스타트 때만 값 발생 |
| `total` | 전체 wall-clock | 아래 출력 규칙의 기준 |

- **`total` 의 관점**: 사용자가 체감하는 값이 우선이므로 **클라이언트 프로세스의 wall-clock**(호출~결과)을 `total` 로 삼는다. 데몬 모드에서는 여기에 IPC 왕복이 포함되고, 단계별 세부(`extract`/`embed` 등)는 **데몬이 측정해 응답에 실어** 보낸다. `total ≈ extract+clean+chunk+embed(+model_load) + IPC/오버헤드`.

**출력 위치(포맷별):**
- **text 모드**: stdout 의 벡터 라인은 **파싱 안전**을 위해 건드리지 않고, 시간 요약을 **stderr** 로 1줄 출력.
  ```
  [timing] D:\AAA.hwp  extract=41.2  embed=58.7  model_load=0.0  total=102.0 ms
  ```
- **json / jsonl 모드**: 위 예시처럼 본문에 `elapsed_ms` 객체로 포함(stdout).
- `--no-timing` 이면 위 출력 전부 생략(순수 결과만).
- 배치(`-dir`) 종료 시: 파일별 `total` 합계와 평균/최댓값 요약을 stderr 로 1줄 추가(데몬 상주 효과 확인용).

**구현 메모:** 각 단계는 단조시계(`time.perf_counter()`)로 측정. 데몬은 단계별 값을 응답 JSON 에 담고, 클라이언트는 자신의 wall-clock 을 `total` 로 채운다. `-v/--verbose` 면 청크 수·모델키·데몬 재사용 여부도 함께 로깅.

### 7-2. 추출 텍스트 파일 보존 (`--save-text`)

**배경**: `snf_exe.exe` 는 어차피 추출 결과를 **출력파일**로 쓴다(§9-1에서 신뢰성 위해 출력파일 방식 채택). 기본은 이 파일을 **임시폴더에 만들고 임베딩 후 자동 삭제**한다. 하지만 추출 텍스트 자체를 검수·재사용하고 싶은 경우가 있어 **보존 옵션**을 제공한다.

**동작 규칙:**

| 상태 | 임시 추출파일 위치 | 처리 후 |
|---|---|---|
| 기본(옵션 없음) | `-W` 로 지정한 작업폴더 아래 유니크명(예: `<tmp>\<uid>.txt`) | 임베딩 완료 후 **삭제** |
| `--save-text` (경로 생략) | 기본 보존폴더 `<출력기준>\_extracted\` | **유지** |
| `--save-text <dir>` | 지정 폴더 `<dir>\` | **유지** |
| `--save-raw` 병행 | 위 폴더에 `<원본명>.raw.txt`(정제 전) + `<원본명>.txt`(정제 후) | **유지** |

- **파일명 규칙**: 원본 파일명 기반 + 충돌 방지(동일명 존재 시 `__2`, `__3` … 또는 상위 폴더 해시 접두). 배치에서 서로 다른 폴더의 동일 파일명 충돌 대비.
- **인코딩**: UTF-8(무 BOM). 내부 정제 후 텍스트를 그대로 기록.
- **보존/삭제 일원화**: 임시파일 생성·삭제·보존 전환은 `pipeline.py` 의 컨텍스트매니저(`with ExtractedTextFile(save=...) as tf:`)로 관리 → 성공/실패/예외 어느 경로든 **누수·미삭제 방지**.
- **실패 시**: 추출 실패(출력파일 미생성)면 보존할 텍스트가 없으므로 옵션과 무관하게 오류 처리(§9-1 규칙).
- **주의**: `--save-text` 는 디스크에 원문 텍스트를 남기므로 민감문서 처리 시 사용자가 의식적으로 켜는 옵션으로 둔다(기본 off).

## 9. 사이냅 필터 연동 상세 (분석 반영)

- **배포 파일 재사용**: `snf_exe.exe`, `snf_win.dll` (+ 필요 리소스)를 `resources\synap\` 로 복사해 번들.
- **초기화 옵션(참고)**: 기존은 `snf_gbl_setcfg` 에 `ARCHIVE_EXTRACT | EXTENSION_NO_CHECK | EXCEL_NOLIMIT | EXCEL_SEPARATE | NO_USE_SPACE_REMOVER | MAIL_ATTACH_FILTER` 등을 지정. DLL 방식으로 갈 경우 동일 옵션 참고.
- **인코딩**: 사이냅 출력(UCS-2/UTF-16) → 파이썬 `str` → 내부 UTF-8 통일.
- **압축/첨부**: 기본은 본문만. 아카이브 내부 텍스트 포함 여부는 옵션(`--include-archive`)으로 후속 검토.

### 9-1. `snf_exe.exe` CLI 실측 결과 (2026-08-12 검증 완료) ✅

> 배포본: `filter4-v4.29.0` / `snf_exe.exe` (v4.29.0, Release 2022/02/15). HWP·HWPX·PDF·DOCX 실파일로 검증.

**전체 Usage:**
```
Usage: snf_exe [-OPTION]... <input_file> [output_file]
  -D                  input directory (폴더 배치)
  -O                  process embedded OLE documents
  -S                  extract summary info
  -C <Encoding>       set output character encoding
  -U / -U8            set output unicode / utf8 encoding
  -E <Encoding>       set default character encoding
  -NO_WITHPAGE        exclude page marker
  -W <WorkDirPath>    set working folder (임시 작업폴더)
  -WSIZE <Size>       set min file size to use a temporary file
  -TIMEOUT <Sec>      set time out
  -XML                set output format to xml
  -SNF_GBL_SEPTYPE_* <SEP>   set separator
  -V                  print license and version info
지원 인코딩: utf8, unicode, cp949, sjis, eucjp, big5, gb2312
```

**본 프로젝트 권장 호출 패턴:**
```
snf_exe.exe -U8 [-NO_WITHPAGE] <input_file> <output_file>
```

**실측으로 확정된 핵심 동작:**

| 항목 | 실측 결과 | 설계 반영 |
|---|---|---|
| UTF-8 출력 | `-U8` 로 정상 추출. **BOM 없음**(clean UTF-8, `ED 95 9C…`) | 파이썬에서 `encoding='utf-8'` 로 바로 read |
| 출력 대상 | 인자 없으면 **stdout**, `output_file` 지정 시 파일로 | **출력파일 방식 채택**(신뢰성/파싱안전) |
| 성공 시 stdout | 출력파일 지정하면 stdout **완전히 빔**(배너 없음) | 성공 판별 단순화 |
| **종료코드** | 성공·실패·손상파일 **모두 `0`** ⚠️ | **종료코드로 오류판별 불가** |
| 실패 시 동작 | 출력파일 **미생성**, 배너+`Error : …` 를 **stdout** 으로(❗stderr 아님) | 아래 오류판별 규칙 참조 |
| 손상/미지원 파일 | 오류 없이 텍스트로 **조용히 격하**(부분 출력) | 허용, 후처리에서 최소길이 체크 |
| 페이지 마커 | 기본은 `..PAGE:N` **텍스트 라인**으로 삽입(form-feed 아님) | `-NO_WITHPAGE` 로 제거 or 정제단계에서 제거 |
| 폴더 배치 `-D` | 폴더 전체를 한 출력파일에 `--- Processing File : <path> ---` 구분자로 연결 | 자체 배치 루프가 더 유연 → 파일단위 호출 채택 |
| 성능 | **~36 ms/파일**(프로세스 기동 포함) | subprocess 방식으로 충분, DLL 불필요 확정 |

**오류 판별 규칙(종료코드 못 쓰므로 필수):**
1. 호출 전 파이썬에서 `os.path.exists(input)` 선검사.
2. **항상 `output_file` 인자 사용** → 호출 후 **출력파일이 생성되고 비어있지 않으면 성공**, 미생성/0바이트면 실패.
3. 보조: 캡처한 stdout 에 `"Error : "` 또는 배너(`"Synap Document Filter v"`) 포함 시 실패로 간주.
4. 추출 텍스트가 과도하게 짧으면(예: 임계 미만) 경고 로깅(손상파일 조용한 격하 대비).

**subprocess 안전 팁:** 프로세스에 **timeout**(`-TIMEOUT` + `subprocess timeout` 이중) 적용, `-W <WorkDirPath>` 로 임시폴더를 프로그램 관리 경로로 고정, 인자는 리스트로 전달(경로 공백/한글 안전).

## 10. PyInstaller 패키징 전략

- **onedir 우선(초기)** → 안정화 후 **onefile**(`csoclassify.exe` 단일) 검토. onefile 은 매 실행 시 임시폴더 해제 오버헤드 있음.
- **데이터 번들**: `resources\synap\*`, `resources\models\*` 를 `--add-data` 또는 spec `datas` 로 포함.
- **리소스 경로 해석**: 런타임에 `sys._MEIPASS`(번들) vs 소스 경로 분기 → `resources.py` 에서 일원화.
- **경량화**: PyTorch 미포함(ONNX 사용), `--exclude-module` 로 불필요 패키지 제거, UPX 는 DLL 호환성 확인 후 선택.
- **검증**: 깨끗한 오프라인 Windows 에서 `csoclassify.exe -file <샘플.hwp>` 스모크 테스트.

3. ✅ **임베딩**: `onnx_embedder.py`(지연 로딩 + `passage:` 프리픽스 + 마스크 평균풀링) 구현. **`export_onnx.py` 로 `e5-small-ko` ONNX(model.onnx 470MB fp32) 생성 완료 → 384차원 벡터 실측·L2정규화(norm=1.0) 확인.**
4. ✅ **파이프라인/CLI**: 청킹·풀링·정밀도·출력(text/json/jsonl)·시간측정·배치·`--text-only`·`--save-text` 구현.
5. ✅ **상주 데몬(기본 경로)**: `daemon/`(server·client·ipc·registry) 구현 — loopback+토큰 IPC, 원자적 싱글턴(race 대응), 유휴종료, 버전/모델키 핸드셰이크, in-process 폴백. (IPC 는 초기엔 loopback TCP; Named Pipe 는 후속 개선)
6. ✅ **테스트/E2E**: 단위·통합 16 pass. **데몬 end-to-end 검증 완료** — cold(데몬 자동기동)→warm(model_load=0 재사용), `--status`/`--stop`, 배치(`-dir`)·`--save-text`·`--per-chunk`·jsonl·배치 시간요약 동작 확인.
7. ✅ **패키징 준비**: `build/csoclassify.spec`(onedir, 사이냅+모델 datas 번들, torch 제외) 작성. ⏳ 실제 exe 빌드·오프라인 스모크만 남음.
8. ✅ **문서화**: `README.md`(사용법/데몬/개발셋업/빌드/현황).

9. ✅ **모델 경량화**: `scripts/quantize_onnx.py` 동적 int8 양자화 — **model.onnx 470MB(fp32) → 118MB(int8), 25%**. fp32 는 `model.fp32.onnx` 로 백업(번들 제외). 품질검증: int8 self-cosine 0.961(vs fp32)이나 **retrieval 랭킹은 완전 보존**(테스트 쿼리 top-3 fp32와 동일). fp16(235MB, cosine 1.0)도 검토했으나 랭킹이 int8로 충분히 보존되어 **int8 채택**(크기 최우선). spec 은 백업본(`*.fp32.onnx`/`*.fp16.onnx`) 제외하고 번들 → **총 번들 ~143MB**(int8 모델118+tokenizer17+사이냅8).

10. ✅ **exe 빌드/스모크**: `pyinstaller build/csoclassify.spec` → `dist/csoclassify/csoclassify.exe`(onedir, 총 ~227MB). 엔트리는 패키지 밖 `csoclassify_launcher.py`(절대 import; PyInstaller 가 엔트리를 `__main__` 으로 실행해 상대 import 가 깨지는 문제 해결). spec 은 사이냅 바이너리(.exe/.dll)만 + int8 모델 번들(.env/sample/백업본 제외). **스모크 통과**: 실제 HWP/DOCX 로 in-process·데몬(exe 가 자기 자신을 `--serve` 로 spawn→재사용→stop) 전부 동작.

11. ✅ **onefile 크기 최적화(A안) 검토·구현**: 압축 실측 — int8 model.onnx 는 zip 112→75MB(67%)가 한계(int8이라 압축 여지 적음), tokenizer.json 16→2.3MB. **PyInstaller onefile 은 이미 zlib 압축**하므로 수동 zip 추가는 무의미(이중압축). 순수 onefile(모델임베드)은 117MB 단일 exe 지만 **매 실행 temp 에 112MB 해제**(`--status`조차 6s) + **상주 데몬이 temp 의 snf_exe 참조 실패**(WinError2, 실측). → **A안 채택**: 모델·사이냅을 exe 밖에 두고 코드 전용 onefile(**34MB**) 빌드. 배포=exe(34MB)+synap/(7.5MB)+`e5-small-ko.tar.xz`(75MB). 런타임이 모델 tar.xz 를 캐시에 1회 해제(`resolve_model_dir`), 사이냅은 exe옆(`synap_exe_path` exe측 우선). **데몬 반복호출 견고성 실측 통과**(call1/2/3 model_load=0, ~1s). 구현: `resources.resolve_model_dir`/`synap_exe_path`, `scripts/pack_model.py`, `build/csoclassify-onefile.spec`.

12. ✅ **L1 PII 검출(ko-pii) 성능 최적화**(§3 결정7): `detect_all`(28개 전부) → 필요 검출기 18개만 도는 `_detect_subset`(**~54%↓**), 주소 토큰 프리필터로 주소 없는 문서 **추가 ~34%↓**. 지연 가드는 초판 '앞 10K 절단'(2026-08-14) → **청킹 개정**(2026-08-15): 선형=전량 / 초선형(phone·address·account)=10K 청크(오버랩 128, 절대오프셋 병합)+앞 100K 상한(env `_KOPII_MAX_CHARS`/`_MAX_TOTAL`/`_OVERLAP`) → **10K 초과 문서 미탐 해소 + 지연 선형화**. 소형 문서는 단일패스로 **검출 결과 불변**. 처방전 라벨 오타(`PRESCRIPTION`→`PRESCRIPTION_ID`) 수정. 회귀 테스트 `test_rules.py` 15→21→**24 pass**.

13. ✅ **규칙셋 외장화**: C/S/O 규칙셋(`cso_rules.yaml`)을 exe 에 **내장하지 않고** exe 옆 외장 파일로 배포 → 재빌드 없이 규칙 교체 가능. `default_rules_path` 가 (frozen)exe 옆 → (소스)`resources/policy` 순으로 해석하고, 우선순위는 `CSOCLASSIFY_POLICY_DIR` > `--rules` > exe 옆. 두 spec 에서 정책 번들 제거(ko-pii 사전·모델·사이냅은 유지). 파일 누락 시 원시 스택 대신 "어디에 두라"는 안내 후 `EXIT_ARG_ERROR` 종료. 배포 구성이 5개(exe/cso_rules.yaml/synap×2/모델)로 늘어남.

14. ✅ **크로스플랫폼(리눅스) 준비**: 사이냅 필터를 OS 하위폴더로 분리(`synap/windows/{snf_exe.exe,snf_win.dll}`, `synap/linux/snf_exe`). `resources.synap_exe_path()` 가 OS 별 이름·폴더를 자동 해석(평면 배치 폴백 유지), spec `collect_synap()` 이 빌드 OS 폴더에서 번들. 리눅스 `snf_exe` 는 정적 링크라 단독 실행(.a/.h 불필요). 리눅스 실행파일은 리눅스에서 PyInstaller 로 빌드(크로스컴파일 불가) — 절차는 README §4(C). 그 외(ko-pii·onnxruntime·규칙엔진)는 이미 크로스플랫폼. 기본 출력 JSON(단건=객체/배치=배열), 인자 `--file`/`--dir` 통일(구 `-file`/`-dir` 별칭)도 함께 반영.

15. ✅ **onedir 기본 배포(외장 리소스)**: onefile 은 실행마다 자기 압축해제로 웜 시작이 느려(~4.6s) 대화형에 불리 → **onedir 를 기본 배포로 채택**(웜 ~2s). 두 spec 모두 사이냅·모델·규칙셋을 번들하지 않고 exe 옆 외장(`synap/<os>/`·`models/<name>/`·`cso_rules.yaml`)에 두는 구성으로 통일(코드는 이미 외장 경로 해석). 리눅스 빌드는 numpy 확장/구형 libstdc++(CXXABI) 이슈를 `collect_submodules(numpy)`+conda libstdc++ 번들로 해결, strip·numpy테스트/f2py 제외로 슬림화. 조립본: `dist-onedir/{windows,linux}`(리눅스 본체는 심볼릭링크 보존 위해 tgz), 참고 onefile 은 `dist-pkg`. 구조·실행은 README §4「배포 구조」.

**남은 일(선택)**: Named Pipe IPC 격상. **배포 전 필수**: 사이냅 라이선스 재배포 조건 확인(§14-1).

**패키징 선택 가이드**: 단순·자기완결이면 **onedir**(227MB 폴더, zip 전송시 ~90MB); 작은 단일 exe 가 필요하면 **onefile+A안**(exe 34MB + 외부 모델/사이냅). 둘 다 데몬 안정.
