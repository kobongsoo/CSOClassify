1 배경 — writer 가 이미 둘이고, 모양이 다르다

지금도 CLI 는 class_seed.jsonl 을 쓴다(--make-doctype-seeds). 그런데 UI 와 다른 모양으로 쓴다.

누가어디쓰는 모양어떻게 쓰나
화면ui/seedstore.py 함수 38개 v3 — v·file·doc_id·hash·grade·doctype·source·
approved_by·note·ts·dim·(hold)·vector		 save_seeds() 한 곳
CLIclassify/seedgen.py::merge_into v3 — 2026-09-08 맞춤
다만 hash·doc_id·approved_by 는 못 채운다		 json.dumps 로 직접
seedstore 를 거치지 않는다

즉 모양은 같아졌지만 쓰는 길이 아직 둘이다. 아래가 그래서 남은 문제다.

표의 '지금'은 v3 이전 상태다 2026-09-08 갱신 — 화면은 이제 v3(평평) 로 쓰고, seedgen 도 v3 모양으로 쓰도록 함께 고쳤다. 모양은 맞췄지만 writer 는 아직 둘이다 — seedgen.merge_into() 가 seedstore 를 거치지 않고 여전히 직접 파일을 쓴다. 아래 문제는 그대로 남아 있다.
지금 무슨 일이 벌어지고 있나
--make-doctype-seeds 로 만든 줄에는 누가 넣었는지가 없다 (source: "make-doctype-seeds" 와 ts 는 v3 전환 때 넣었지만, approved_by 는 여전히 비어 있다 — CLI 가 검토자를 받을 수단이 없어서다). 기준 문서는 다른 문서의 등급을 정하는 잣대라, 출처가 없다는 것은 가볍지 않다.
그래서 이 작업의 본체는 CLI 옵션이 아니다. 여기에 세 번째 writer 를 붙이면 상태가 더 나빠진다. writer 를 하나로 합치는 것이 먼저이고, --seed-add 는 그 위에 얹는 얇은 껍데기다.
다행히 ui/seedstore.py 는 json·os·datetime·numpy 만 쓴다 — streamlit 의존이 전혀 없어 그대로 옮길 수 있다(실측 확인).

목표내용

여러 프로세스의 동시 파일 쓰기를 완전히 보장 9장 — 원자적 교체와 잠금까지는 하되, "여러 대에서 동시에"까지는 이 도구의 몫이 아니다

3 설계 원칙

#원칙뜻
P1writer 는 하나 화면·CLI·--make-doctype-seeds 가 같은 seedstore 를 쓴다. 모양이 갈리면 어느 쪽이 맞는지 아무도 모른다
P2출처 없는 기준 문서를 만들지 않는다 --seed-reviewer 는 필수. 화면이 검토자 없이는 등록을 막는 것과 같은 규약
P3반쪽 파일을 남기지 않는다 전체 다시 쓰기라 중간에 죽으면 파일이 깨진다 — 임시파일 + 원자적 교체(12장)
P4부분 실패가 숨지 않는다 10건 중 3건이 벡터를 못 얻으면 7건 성공·3건 실패가 종료코드와 요약에 드러난다
P5stdout 은 기계가 읽는 것 stdout 에는 jsonl 만 나간다. 사람이 읽는 안내·진행률은 전부 stderr

4 1부 — seedstore 를 라이브러리로 옮긴다

ui/seedstore.py  →  src/csoclassify/seedstore.py
확인결과
UI 의존없음 — json · os · datetime · numpy 뿐
exe 포함패키지 안이라 PyInstaller 가 자동으로 담는다
화면 쪽 수정ui/app.py · ui/doctype_review.py · ui/uiwords.py 의 import 한 줄씩
테스트test_ui_seedstore.py 등 4개 파일의 import 경로
화면에서 지우지 않고 '옮긴다' — ui/seedstore.py 를 남겨 두고 라이브러리를 다시 내보내는 얇은 파일로 만들면 import 를 안 고쳐도 되지만, 그렇게 하지 않는다. 같은 이름의 모듈이 두 곳에 보이면 다음 사람이 "어느 쪽이 진짜인가"를 매번 되짚는다. import 를 고치는 편이 한 번의 수고로 끝난다.

5 2부 — --make-doctype-seeds 도 v3 로

절반은 이미 됐다 — v3 전환 때 seedgen 이 쓰는 줄의 모양을 맞췄다. 남은 절반은 seedstore.save_seeds() 를 거치게 하는 것이다 (지금은 merge_into() 가 json.dumps 로 직접 쓴다 — writer 가 둘인 상태).

:: 옛 모양(v1) — 2026-09-08 이전
{"file": "...", "labels": {"doctype": ["DC_0061"]}, "vector": [...]}

:: 지금(v3) — 모양은 맞췄다
{"v": 3, "file": "...", "doctype": ["DC_0061"],
 "source": "make-doctype-seeds", "ts": "2026-09-08 10:00:00",
 "dim": 384, "vector": [...]}

:: 이 작업 뒤 — 지문·문서ID·검토자까지 채운다
{"v": 3, "file": "...", "doc_id": "<sfile_id 를 얻었을 때만>",
 "hash": "2438eafe…", "doctype": ["DC_0061"],
 "source": "make-doctype-seeds",
 "approved_by": "<--seed-reviewer 또는 빈값>",
 "ts": "2026-09-08 10:00:00", "dim": 384, "vector": [...]}
지금 이 명령을 운영 파일에 돌리면 사람이 넣은 기준 18건이 지워진다 실측
merge_into() 는 doctype 이 있는 줄을 전부 '이전 회차의 씨앗'으로 보고 버린다. 운영 파일 ui/policy/class_seed.jsonl 을 재어 보면: 
전체 19행 · doctype 있는 줄 18행
그 중 source 가 make-doctype-seeds 인 줄  :  0행
사람이 화면에서 넣은 줄(phase4+phase6·upload) : 18행   ← 전부 지워진다
이 파일에는 자동 생성 씨앗이 한 줄도 없는데, 명령을 돌리면 18행이 통째로 사라진다. 아래 표의 '갈아 끼우기 기준'을 source 로 바꾸는 일이 이 작업에서 가장 급한 대목이다.
지켜야 할 것내용
기존 파일 호환 이미 있는 v1/v2 줄은 ensure_v3 가 올려 읽는다 — 깨지지 않는다. 다만 그 줄들의 approved_by 는 여전히 비어 있다(없던 정보를 지어내지 않는다)
'갈아 끼우기' 동작 유지 지금 merge_into 는 이전 회차의 doctype 씨앗을 지우고 새로 넣는다. 이 뜻은 그대로 둔다 — 다만 판단 기준을 "doctype 이 있는 줄"이 아니라 source 에 make-doctype-seeds 가 든 줄로 바꿔, 사람이 손으로 넣은 doctype 씨앗을 지우지 않게 한다 지금은 사람이 넣은 것도 함께 지워진다 — 이 참에 고친다
보안등급 씨앗건드리지 않는다(지금도 그렇다)

6 3부 — --seed-add 옵션

MpowerClassify.exe --seed-add "D:\문서\계약서.docx" "D:\문서\보고서.hwp" \
                --seed-grade C \
                --seed-doctype DC_006_001,DC_001_003 \
                --seed-reviewer "고봉수" \
                --seed-note "표준 계약서 본보기" \
                --seeds "D:\policy\class_seed.jsonl"
옵션값뜻
--seed-add파일 경로 1개 이상 등록할 문서. 여러 개를 한 번에 임베딩한다(모델을 한 번만 올린다). 아래 축 값이 모든 파일에 그대로 적용된다
--seed-add-from목록 파일 또는 - 문서마다 다른 값을 줄 때(7장). 한 줄에 한 문서인 jsonl. --seed-add 와 배타
--seed-gradeC·S·O 보안등급 축
--seed-doctypedc_id 콤마 나열 업무분류 축(여러 개 가능)
--seed-reviewer이름 필수 — 없으면 bad_args 로 끝낸다(P2)
--seed-note메모선택
--filelist 기존 옵션{path, sfile_id} 목록 doc_id 를 채우는 유일한 정당한 출처. 주면 그 목록에서 찾아 doc_id 를 적고, 못 찾으면 적지 않는다(아래 상자)
--seeds경로 기존 옵션 재사용. 주면 그 파일에 병합, 안 주면 stdout(9장)
doc_id 는 지어내지 않는다 v3 — 분류 레코드는 doc_id 를 sfile_id 로 채워진 경우에만 싣는다. 2026-09-10 부터는 분류 레코드도 같은 규칙이라 (doc_id = sfile_id 뿐), 아래 서술의 '폴백 doc_id' 는 그 이전 이야기입니다. 폴백(content)은 파일 해시 앞 40자였고 그 값을 한 칸 더 실으면 MpowerV11 문서 ID 처럼 생긴 값이 적재 쪽으로 흘러가 같은 문서가 두 건으로 들어간다. 이 규약은 이미 cli.py::_simple_record 에 그렇게 구현돼 있다.
기준 문서도 같은 규약을 따른다 — doc_id 를 얻는 길은 두 가지뿐이고, 둘 다 실패하면 그 칸을 아예 안 적는다(받는 쪽은 "없으면 hash 로 가린다"):
① 목록 파일(--seed-add-from)의 doc_id 칸 — 웹이 직접 준다(권장)
② --filelist 로 준 {path, sfile_id} 매핑에서 찾기
인자 검사(문서를 읽기 전에)결과
--seed-reviewer 없음bad_args · exit 3
등급도 업무분류도 없음bad_args · exit 3 축을 하나도 안 정하면 아무 뜻이 없는 줄이 된다
--seed-grade 가 C/S/O 가 아님bad_failsafe 와 같은 결 — 새 코드 없이 bad_args
--seed-doctype 이 분류체계에 없는 dc_id 막는다(bad_args) — 없는 분류로 씨앗을 만들면 전파가 조용히 헛돈다. --taxonomy 가 있을 때만 검사하고, 없으면 경고 후 진행
--seed-add 와 --file/--dir 을 함께 배타 — mode_conflict · exit 3
목록 줄의 doc_id 가 서로 다른 문서에 같은 값 막는다(bad_args) — 같은 신분증을 두 문서에 붙이면 받는 쪽에서 한 문서가 다른 문서를 덮는다

7 문서마다 다른 등급·분류 주기 핵심

여러 문서를 한 번에 넣을 때 문서마다 등급과 업무분류가 다른 것이 보통이다. 이것을 어떻게 받을지가 이 옵션 설계에서 가장 조심할 지점이다.

7-1. 나란한 목록(positional)은 쓰지 않는다

:: 이렇게 하자는 안 — 채택하지 않는다
--seed-add "a.txt" "b.txt" "c.txt" \
--seed-grade C,S,S \
--seed-doctype "DC_006,DC_005_001" "DC_004" "DC_006_003,DC_005"
이 방식은 틀려도 성공한 것처럼 보인다. 파일이 3개인데 등급을 2개만 적으면(또는 하나가 밀리면) 모든 문서의 등급이 한 칸씩 어긋난다. 그런데 실행은 정상 종료하고 "3건 등록"이라고 나온다 — 잘못된 등급이 잣대로 들어앉는다. 기준 문서는 다른 문서의 등급을 정하는 값이라, 이 실수의 대가가 특히 크다.
문제내용
조용한 어긋남 개수가 맞기만 하면 순서가 틀려도 아무도 모른다. 파일 이름과 등급이 떨어져 있어 사람이 눈으로 검토하기도 어렵다
따옴표 지옥 업무분류는 '문서마다 여러 개'라 목록의 목록이 된다. "DC_006,DC_005_001" "DC_004" — 셸·PowerShell·subprocess 마다 따옴표 처리가 달라, 웹에서 부를 때 가장 깨지기 쉬운 부분이다
빈 칸 표현 불가 "이 문서는 업무분류를 안 준다"를 어떻게 적나? "" 를 넣으면 셸이 지워 버리는 경우가 있다
메모도 문서마다 메모까지 나란한 목록으로 만들면 목록이 넷이 된다 — 관리 불가

7-2. 채택 — 문서마다 한 줄(jsonl) 권고

여러 문서에 서로 다른 값을 줄 때는 목록 파일로 받는다. 이 프로젝트에는 이미 같은 규약이 있다 — --files-from - 가 표준입력을 받는다.

MpowerClassify.exe --seed-add-from list.jsonl --seed-reviewer "고봉수" --seeds "…/class_seed.jsonl"

:: list.jsonl — 한 줄에 문서 하나
{"file":"a.txt","doc_id":"SF-100231","grade":"C","doctype":["DC_006","DC_005_001"],"note":"표준 계약서"}
{"file":"b.txt","doc_id":"SF-100232","grade":"S","doctype":["DC_004"]}
{"file":"c.txt","doctype":["DC_006_003","DC_005"]}          ← 등급 없이 업무분류만 · doc_id 없음
{"file":"d.txt","grade":"O"}                                ← 등급만
칸필수뜻
file필수등록할 문서 경로
doc_id v3 신설선택 외부 시스템(MpowerV11)의 문서 식별자. 주면 그대로 적는다. 안 주면 만들어 내지 않고 칸을 비운다(6장) — --filelist 를 함께 주면 거기서 찾아 채운다
grade선택C·S·O
doctype선택dc_id 배열(문자열 하나도 허용 — 배열로 정규화)
note선택이 문서의 메모(없으면 --seed-note)
reviewer선택이 문서의 검토자(없으면 --seed-reviewer)
hash 칸은 받지 않는다 — CLI 가 직접 잰다 v3
hash 는 "지금 이 파일의 내용"이어야 뜻이 있다. 부르는 쪽이 준 값을 그대로 믿으면, 값이 낡았거나 다른 파일의 것이어도 알 수 없고 원본 변경 판정(stale)이 조용히 헛돈다. 어차피 문서를 열어 임베딩하므로 지문은 그 김에 공짜로 얻는다(8장 ③).

--seed-add-from - 로 표준입력도 받는다 — 웹이 임시파일을 만들지 않아도 된다.

왜 이 방식인가
① 짝이 한 줄 안에 있다 — 파일과 등급이 붙어 있어 사람이 눈으로 검토할 수 있고, 개수가 어긋날 수가 없다.
② 따옴표 문제가 없다 — 웹이 만드는 것은 JSON 이지 셸 문자열이 아니다.
③ 늘리기 쉽다 — 나중에 칸을 더해도 기존 호출이 안 깨진다. 실제로 그렇게 됐다 — v3 전환으로 doc_id 칸이 늘었지만, 그 칸을 안 주는 옛 호출은 그대로 돈다.
④ 받는 쪽(웹)은 이미 JSON 을 다룬다 — 새로 배울 문법이 없다.

7-3. 간단한 경우는 지금 플래그 그대로

모두 같은 등급이면 목록 파일이 과하다. 6장의 플래그를 그대로 쓴다.

:: 세 문서 모두 C · 같은 업무분류 — 이건 지금도 자연스럽다
--seed-add "a.txt" "b.txt" "c.txt" --seed-grade C --seed-doctype DC_006 --seed-reviewer "고봉수"
쓰는 법언제
--seed-add <파일…> + --seed-grade/--seed-doctype 여러 문서가 같은 값일 때 — 그 값이 모든 파일에 그대로 적용된다
--seed-add-from <목록> 또는 - 문서마다 다른 값일 때 — 웹에서 부를 때 권장
둘을 섞으면 어떻게 되나 — --seed-add 와 --seed-add-from 을 함께 주면 거절한다(mode_conflict · exit 3). "목록에도 있고 인자에도 있는데 값이 다르면 무엇이 이기나"를 사람이 매번 되짚어야 하는 상태를 만들지 않는다.
다만 --seed-reviewer·--seed-note 는 목록의 기본값으로 함께 쓴다 — 줄마다 검토자를 반복해 적지 않아도 되게.

7-4. 그래도 나란한 목록을 쓰고 싶다면

지금은 만들지 않는다. 만약 나중에 넣는다면 개수가 정확히 같지 않으면 거절하는 조건이 반드시 함께 가야 한다 — 그것만으로도 7-1 의 '조용한 어긋남'은 막힌다. 다만 순서가 틀린 것은 여전히 못 잡는다.

8 처리 흐름 — 화면과 같은 7단계

화면(ui/app.py::render_seed_add)이 하는 일을 그대로 한다. 같은 함수를 쓰므로 결과가 갈릴 수 없다.

① 인자 검사        검토자·축·경로 (6장)
② 대상 확인        파일이 실제로 있나 — 없으면 그 건만 실패로 세고 계속
③ 지문·벡터        한 번 읽어 둘 다 얻는다
                   · hash    = SHA-256 (cli.py::_file_hash) — --hash 옵션과 무관하게 항상
                   · vector  = --with-vector 와 같은 경로로 임베딩
                   화면은 exe 를 다시 불러 얻지만, CLI 는 이미 그 안이라 바로 계산한다
④ 문서 ID          목록의 doc_id → 없으면 --filelist 에서 찾기 → 둘 다 없으면 칸을 안 적는다 (6장)
⑤ 축 얹기          seedstore.set_axis(..., doc={"hash": …}) 를 축마다 — security · doctype 따로
⑥ 감사 기록        seedstore.append_seed_audit(...) 를 축마다 (12장)
⑦ 저장             --seeds 있으면 save_seeds(원자적 교체) · 없으면 stdout (9·10장)
⑧ 요약·종료코드    stderr 에 성공/실패 건수, exit 코드로 결과 구분 (12장)
지문(hash)을 빠뜨리면 그 기준 문서는 영영 늙지 않는다 v3 에서 중요해진 대목
v3 는 원본이 바뀌었는지 보는 근거가 hash 하나뿐이다 (size·mtime 은 읽는 코드가 없어 뺐다). 지문 없이 등록된 줄은 check_seeds() 의 stale 판정에서 "모르면 조용히 넘어간다" 가지에 걸려, 원본이 아무리 바뀌어도 경고 한 줄 없이 옛 벡터로 계속 전파한다.
그래서 --hash 를 안 줘도 --seed-add 경로에서는 항상 잰다. 파일을 어차피 열어 읽으므로 추가 비용이 사실상 없다. 화면은 이미 그렇게 한다 — ui/app.py::seed_doc_meta() 가 분류 레코드의 hash 를 그대로 실어 준다.
화면보다 단순해지는 지점 — 화면은 벡터를 얻으려고 exe 를 자식 프로세스로 다시 띄운다(gerunner.embed_files: 임시폴더에 번호를 붙여 하드링크 → --dir 실행 → 파일명 앞 번호로 원본과 다시 잇기). CLI 는 이미 그 프로세스 안이라 그 왕복이 통째로 사라진다 — 번호 붙이기·되잇기도 필요 없다.
저장되는 file 값 — 화면은 업로드라 파일 이름만 남긴다 (임시 경로를 적으면 다음 실행 때 '원본 없음'이 되므로). CLI 는 진짜 경로가 있으므로 경로를 그대로 남긴다. 그래야 나중에 원본 점검·재임베딩이 된다. 두 경로가 섞여도 문제없다 — norm_file 이 비교를 맡고, 업로드 줄은 이미 '이름만' 형태로 취급된다.

9 출력 — 파일 · stdout

--seeds동작쓰임
줬을 때 그 파일을 읽어 병합하고 전체를 다시 쓴다(원자적 교체). stdout 에는 아무것도 안 나간다 배치·운영 스크립트
안 줬을 때 등록된 줄만 jsonl 로 stdout. 파일은 건드리지 않는다 웹에서 부르기 — 권장. 파일을 안 만지므로 동시성 사고가 원천적으로 없다
:: stdout 모드 — 한 줄에 한 문서(벡터는 맨 뒤)
{"v":3,"file":"D:/문서/계약서.docx","doc_id":"SF-100231",
 "hash":"2438eafeea3011f854a704ef2e8c13b3ad27eabd5585ca7f24c9e601d1f9c1cb",
 "grade":"C","doctype":["DC_006_001"],
 "source":"cli","approved_by":"고봉수","note":"표준 계약서 본보기",
 "ts":"2026-09-08 10:00:00","dim":384,"vector":[...]}
칸 차례는 seedstore._ordered() 가 정한다 — 무엇인가(file·doc_id·hash) → 무엇으로 정했나(grade·doctype) → 누가 언제(source·approved_by·note·ts) → 벡터. CLI 가 직접 json.dumps 하지 않고 같은 함수를 거쳐야 화면이 쓴 줄과 키 순서까지 같아진다(P1 · 15장 T1).
source 는 "cli" — 화면은 "upload", 문서함 선택은 "phase4" 를 쓴다. 어디서 들어온 씨앗인지 나중에 셀 수 있어야 한다.
stdout 모드에서도 --seeds 로 준 기존 파일을 읽지 않는다 — 즉 중복 검사를 안 한다. 이미 있는 문서를 또 넣으면 받는 쪽이 병합하며 정리해야 한다. 중복까지 봐 주려면 기존 파일을 읽어야 하는데, 그러면 "파일을 안 만진다"는 이 모드의 장점이 사라진다. 대신 같은 실행 안에서의 중복(같은 파일을 두 번 준 경우)은 합친다.

10 동시 쓰기 주의

지금 저장 방식은 동시 쓰기에 안전하지 않다. save_seeds 는 open(path,"w") — 전체 다시 쓰기다. 화면에서만 쓸 때는 사람이 한 번에 하나씩 눌러 문제가 없었지만, 웹에서 부르면 두 요청이 겹치는 것이 정상이다. 그대로 열면 한쪽 등록이 아무 말 없이 사라진다.
장치내용
원자적 교체 같은 폴더의 임시파일에 다 쓴 뒤 os.replace() 로 바꾼다. 중간에 죽어도 반쪽 파일이 남지 않는다(P3)
파일 잠금 읽기~쓰기 구간을 잠근다(윈도우 msvcrt.locking · 리눅스 fcntl.flock). 잠금 파일은 <seeds>.lock — 대상 파일 자체를 잠그면 교체가 막힌다
대기 상한 기본 10초. 넘으면 output_write_failed 로 실패한다 — 무한정 기다려 배치를 세우지 않는다
stdout 모드파일을 안 만지므로 이 장치가 필요 없다(9장)
두 판의 잠금은 서로를 막지 못한다 2026-09-08 구현하며 확인
파이썬은 운영체제의 바이트 잠금(msvcrt.locking·fcntl.flock)을 쓰고, Rust 는 잠금 파일(<파일>.lock 을 '이미 있으면 실패'로 만들기)을 쓴다. Rust 에서 같은 방식을 쓰려면 플랫폼 FFI 의존이 하나 늘어나는데, "정적 단일 바이너리"와 CentOS 7 빌드 조건 때문에 의존을 늘리지 않기로 했다.
결과: 같은 판끼리는 서로를 막지만, 파이썬 판과 Rust 판이 동시에 같은 class_seed.jsonl 을 쓰는 경우는 막지 못한다. 지금 운영에서는 한 번에 한 판만 부르므로 문제가 되지 않지만, 두 판을 같은 파일에 동시에 붙이려면 먼저 이 대목을 맞춰야 한다. 막지 못하는 것을 막는 것처럼 적어 두면 나중에 원인을 못 찾는다 — 그래서 여기 적어 둔다.
화면(ui/app.py)도 같은 save_seeds 를 쓰므로 이 개선이 화면에도 그대로 적용된다 — 지금 화면이 갖고 있던 같은 위험도 함께 사라진다.

13 Rust 판도 지원한다

두 판이 같은 일을 하는 것이 이 프로젝트의 규약이다. --seed-add 도 Rust 판에서 똑같이 동작한다.

13-1. 이미 있는 것 — 새로 만들 것

필요한 조각Rust 현황
문서 → 벡터있다 — embed.rs::embed_document() (--with-vector 가 쓰는 그 경로)
분류체계 로딩(dc_id 검증)있다 — axes.rs::load_taxonomy() · Taxonomy::get()
class_seed.jsonl 읽기있다 — propagate.rs 가 전파에 쓴다
class_seed.jsonl 쓰기없다 — src/seedstore.rs 신설이 이 작업의 Rust 쪽 본체
원자적 교체·파일 잠금없다 — 표준 라이브러리로 구현 (fs::rename · 잠금 파일)

13-2. 가장 조심할 것 — writer 가 다시 둘이 된다

1장에서 지적한 문제가 형태만 바꿔 돌아온다. 파이썬 seedstore.py 와 Rust seedstore.rs 가 같은 파일 형식을 각자 구현하게 된다. 한쪽이 칸을 하나 빠뜨리거나 순서가 달라지면, 두 판으로 만든 기준 문서가 미묘하게 다른 모양이 되고 그것을 아무도 눈치채지 못한다.
그래서 시험으로 묶는다 — 같은 문서·같은 축·같은 검토자로 두 판이 각각 등록한 뒤, ts 를 뺀 JSON 이 완전히 같은지 대조한다(15장 T1b). ts·부동소수 벡터를 뺀 나머지가 키 순서까지 같아야 한다.
이미 레코드 칸 차례·signals 표·ts 모양을 같은 방식으로 묶어 왔다 — 새로운 방식이 아니라 하던 대로 하는 것이다.

13-3. 벡터가 두 판에서 같지 않다는 점

같은 문서라도 두 판의 벡터는 완전히 같지 않다. 추출기가 다르고(파이썬=사이냅·하이브리드, Rust=순수 Rust 파서), 플랫폼이 다르면 부동소수 마지막 자리가 갈린다 — 이미 실측으로 확인해 실행가이드에 적어 둔 사실이다.
그래서 대조 시험은 벡터 값을 비교하지 않는다(차원만 본다). 대신 어느 판으로 만든 씨앗인지가 결과에 남아야 한다 — 평평한 engine 칸에 "python"/"rust" 를 적는다 (v3 에는 embed 블록이 없다 — dim 만 평평하게 남았다). 이것은 v3 에 없는 새 칸이다 — 16장 Q5 에서 정한다.

뜻밖의 결과 — 추출은 다 다른데 벡터는 거의 같다. 두 추출기가 뽑은 글자는 18건 전부 달랐지만(표·머리말 처리가 다르다), 임베딩 모델이 그 차이를 대부분 흡수했다. 즉 두 판이 같은 저장소에 써도 전파 결과가 갈릴 위험은 실측상 낮다. 다만 이 코퍼스는 doc 7 · docx 10 · pptx 1 로, 두 판의 추출기가 가장 크게 갈리는 PDF(사이냅 vs pdfium)·HWP 는 들어 있지 않다. 그 종류에서는 더 벌어질 수 있다 — 이 숫자를 "모든 문서에서 안전하다"로 읽으면 안 된다.
