1 배경 · 문제 정의

현재 MpowerClassify 는 문서를 C(기밀) · S(민감) · O(공개) 세 등급으로만 분류한다. 이 세 글자는 규칙 파일(cso_rule.yaml) 안에서는 단순한 문자열이지만, 코드 안에서는 상수로 박혀 있다. 그래서 조직마다 다른 분류 체계를 요구할 때 대응할 수 없다.

왜 지금 다루는가 — 규칙 데이터(cso_rule.yaml)는 이미 base_grade: S 처럼 문자열로 라벨을 적는 구조다. 즉 데이터 쪽은 이미 절반쯤 열려 있다. 막고 있는 것은 코드에 흩어진 서열표·기본값·집계 키·UI 상수 뿐이다. 이것들을 규칙 파일로 끌어내리면 라벨 체계 자체가 운영 데이터가 된다.
지금 손대지 않으면 생기는 더 큰 문제
라벨을 자유화하지 않은 채 조직마다 cso_rule.yaml 의 grade 값만 다른 문자열로 바꿔 쓰면 (예: grade: 대외비), 현재 코드는 이를 오류로 잡지 않고 조용히 무시한다 (6장 참조). 결과는 “등급이 낮게 나오는” 형태의 보안 사고다. 라벨 자유화 설계는 이 fail-open 을 fail-closed 로 바꾸는 작업을 반드시 포함해야 한다.

4 핵심 설계 — label_set 블록

규칙 파일 최상단에 라벨 체계 선언 블록을 새로 둔다. 코드에 흩어진 계층 B·C 상수를 전부 이리로 옮긴다.

4-1. 스키마

# cso_rule.yaml
version: "cso-2026.08.3"

label_set:
  id: cso                       # 라벨체계 식별자. 결과·seed 에 각인돼 혼용을 막는다(필수)
  name: "기본 C/S/O 체계"        # 사람이 읽는 이름
  revision: 1                   # 라벨 정의가 바뀔 때마다 +1 (마이그레이션 판정용)

  # ── 서열: 낮은 위험 → 높은 위험 순. 이 배열의 순서가 서열의 유일한 근거다. ──
  order: [O, S, C]

  labels:
  - id: O                       # 규칙에서 grade/base_grade 로 쓰는 값 (분류가 쓰는 유일한 필드)
    name: 공개                   # [표시용·선택] 없으면 id 를 그대로 보여 준다
    description: 외부 공개 가능    # [표시용·선택] 이 등급이 무슨 뜻인지 — 검토자 안내
  - id: S
    name: 민감
    description: 사내 한정, 반출 시 승인 필요
  - id: C
    name: 기밀
    description: 지정 인가자만 열람

  unclassified_name: 보류       # [표시용·선택] 미분류(null)를 화면에 뭐라고 부를지

  # ── 코드에 박혀 있던 '분류 동작' 상수를 여기로 이전 (아래 4-1-2 설명) ──
  policy:
    acl_failsafe: C             # 접근제한 폴더인데 아무 신호도 없을 때 줄 등급 (fuse.py:66 대체)
                                #   ↳ paths 규칙에 grade 없이 acl_restricted: true 만 적었을 때 쓰인다
    default_failsafe: S         # --failsafe 를 값 없이 줬을 때의 등급 (cli.py:87 대체)

  # ── 규칙이 등급을 생략했을 때의 기본값(섹션별) ──
  defaults_by_section:
    regex_pii:  {base_grade: S}
    pii_combos: {grade: C}
    keywords:   {base_grade: S}
    sensitive:  {grade: C}
    stamps:     {grade: C}
    paths:      {grade: S}
기존 규칙 본문은 한 글자도 바뀌지 않는다. base_grade: S, grade: C, bulk_grade: C 표기는 그대로다. 달라지는 것은 “S 가 무엇을 뜻하고 C 보다 낮은가”를 코드가 아니라 이 블록이 정한다는 점뿐이다.

4-1-2. policy 블록 — “규칙이 아무것도 못 잡았을 때” 무엇을 할지

규칙 스캔은 대개 무언가를 잡아낸다. 문제는 아무것도 못 잡았을 때다. 주민번호도 없고, 기밀 키워드도 없고, 스탬프도 없고, 파일명도 평범한 문서 — 이걸 어떻게 할 것인가는 규칙으로 표현할 수 없다. 그래서 따로 정한다. 지금은 이 판단이 코드에 리터럴로 박혀 있어 조직마다 바꿀 수 없다.

[해결됨 2026-08-24] acl_failsafe 분기를 살렸다 — 15장 Q6 은 (A)로 결정
아래는 그 전의 진단이다. 이제 경로 규칙에서 grade 를 생략하고 acl_restricted: true 만 적을 수 있고, 그런 규칙은 스스로 등급을 내지 않는다. 다른 신호가 하나도 없을 때만 fail-safe 로 최고 등급을 만든다 — 즉 분기가 실제로 동작한다. 
paths:
- id: secure_server
  name: 기밀 서버·보안파일서버
  match: ["//secure/", "/secret/", 보안파일서버]
  acl_restricted: true          # grade 를 적지 않는다
  weight: high
  seed_eligible: false
# → 내용에서 뭔가 잡히면 그 등급을 따르고,
#   아무것도 못 잡으면 그때만 acl_failsafe 등급(현재 C)을 준다.
함께 정한 것
  • 검증 V12 신설 — 경로 규칙은 grade 또는 acl_restricted: true 중 하나 이상을 가져야 한다. 예전에는 grade 를 생략하면 조용히 S 가 됐는데, 그건 관리자가 적지도 않은 등급을 시스템이 지어내는 것이라 더 나빴다.
  • seed_eligible=False 로 변경(기존 코드는 True였다). 이 등급은 ‘내용’이 아니라 ‘위치’에서 나왔다. 전파(Signal B)는 문서 내용 벡터끼리 비교하므로, 내용 근거가 없는 문서를 씨앗으로 삼으면 무관한 문서에까지 최고 등급이 번진다. 등급은 보수적으로 주되, 그 등급을 남에게 퍼뜨리지는 않는다. 분기가 죽어 있어 한 번도 실행된 적 없는 값이라 기존 동작을 바꾸지 않는다.

4-2. 이 블록에 무엇을 넣고 무엇을 빼는가

판단 기준은 하나다 — “분류(규칙 매칭 → 융합 → 결과 출력)가 이 값을 읽는가?” 읽지 않는 것은 분류 스키마에 두지 않는다. 정책 파일에 표현(presentation)이 섞이면 관리자가 고칠 것이 늘고, 잘못 고칠 여지도 늘기 때문이다.

색·아이콘을 뺀 이유 — 편의 문제가 아니라 안전 문제다
  1. 분류가 읽지 않는다. 등급 판정·융합·전파·출력 어디에도 쓰이지 않는다. 규칙 파일은 “무엇을 어떤 등급으로 볼 것인가”만 담아야 한다.
  2. 손으로 정하면 서열과 어긋날 수 있다. 관리자가 실수로 최고 위험 등급에 초록색을, 최저 등급에 빨간색을 줄 수 있다. 그러면 화면이 위험도를 거꾸로 알려 준다 — 검토자가 잘못된 문서를 통과시키는 실제 사고로 이어진다. 서열에서 유도하면 색이 위험도와 어긋나는 일 자체가 불가능해진다.
  3. 검증할 항목이 늘어난다. 색 형식(#RRGGBB)·대비·중복까지 검사해야 하는데, 그 노력에 비해 얻는 것이 없다.
  4. 라벨을 추가할 때 손이 덜 간다. 5→6단계로 늘려도 색을 다시 배분할 필요가 없다.

색은 이렇게 유도한다 (UI 계층에서, 규칙 파일과 무관)

order 안의 위치를 0~1 로 정규화해 초록 → 노랑 → 주황 → 빨강 고정 램프에 태운다. 라벨이 2개든 7개든 같은 규칙으로 자동 배분되고, 항상 위험도 순으로 진해진다.

# 개념 (구현 아님)
t = rank / max(1, len(order) - 1)        # 0.0(가장 낮음) ~ 1.0(가장 높음)
color = SEVERITY_RAMP(t)                 # 초록 → 노랑 → 주황 → 빨강 보간

# 예) order: [O, S, C]        → O=0.0 초록 · S=0.5 주황 · C=1.0 빨강
# 예) order: [일반, 대외주의, 비밀3, 비밀2, 비밀1]
#     → 일반=0.0 · 대외주의=0.25 · 비밀3=0.5 · 비밀2=0.75 · 비밀1=1.0

아이콘도 같은 t 로 고른다(🟢 🟡 🟠 🔴 ⛔). 이모지가 부담스러운 환경이면 UI 가 색 점(dot)으로 대체하면 되고, 이것 역시 규칙 파일이 알 바 아니다.

그래도 색을 지정하고 싶다면 — 조직 CI 색을 맞춰야 하는 등 정말 필요해지면, 규칙 파일이 아니라 UI 설정(예: ui/theme.yaml)에 {라벨 id: 색} 로 둔다. 거기 없는 라벨은 위 유도값으로 떨어지므로, 설정을 빼먹어도 화면이 깨지지 않는다. 정책과 표현을 같은 파일에 섞지 않는 것이 요점이다.

5 서열 모델과 융합 로직

5-1. 왜 전순서(total order)를 유지하는가

이 시스템의 융합 원칙은 한 문장이다 — “여러 신호가 충돌하면 더 위험한 쪽을 택한다.” 코드로는 max_grade() 다. max 가 정의되려면 모든 라벨 쌍을 비교할 수 있어야 하므로 라벨 집합은 일렬로 세워진 전순서여야 한다.

그래서 order: 배열을 서열의 유일한 진실 출처로 삼고, 배열 인덱스를 그대로 rank 로 쓴다. 현재 코드의 _GRADE_RANK(Python)와 Grade::rank()(Rust)는 이 배열에서 생성된다.

# 개념 (구현 아님)
rank = { label_id: i for i, label_id in enumerate(label_set.order) }
# order: [O, S, C]  →  {O:0, S:1, C:2}   ← 현재 하드코딩과 동일한 결과
# order: [일반, 대외주의, 비밀3, 비밀2, 비밀1] → {일반:0, …, 비밀1:4}
order 와 labels 를 왜 분리하나 — labels 목록의 나열 순서를 서열로 쓰면, 관리자가 라벨 설명을 추가하려고 순서를 바꾼 것만으로 등급 서열이 뒤집힌다. 서열은 명시적으로 한 줄에 적혀 있어야 하고, 그 줄을 고칠 때만 바뀌어야 한다. (검증에서 두 목록의 원소 집합이 정확히 일치하는지 확인한다 → 6장)

fuse_signals() 의 알고리즘 자체는 그대로 둔다. 바뀌는 것은 “rank 를 어디서 얻는가”뿐이다.

“미분류”는 라벨이 아니다. 라벨 목록에 넣지 않고 null 로 유지한다. 근거 없이 부여된 등급과 “판단할 근거가 없었음”은 감사 관점에서 전혀 다른 상태이고, --failsafe 는 이 둘을 잇는 명시적 선택으로 남아야 한다.

5-3. 함수 시그니처 방향

서열이 전역 상수가 아니라 규칙셋에 딸린 값이 되므로, 서열을 쓰는 함수는 라벨셋을 인자로 받거나 라벨셋의 메서드가 되어야 한다. 전역 싱글턴으로 두면 여러 규칙셋을 동시에 다루는 데몬 모드에서 체계가 뒤섞인다 (daemon/registry.py 는 규칙셋을 캐시한다).

10 Rust 구현 대응

Python 은 문자열 dict 라 자연스럽게 열리지만, Rust 는 enum Grade { O, S, C } 로 타입 수준에서 3값이 고정돼 있다. 여기가 가장 큰 구조 변경이다.

10-1. 방향 — enum 을 “인덱스 뉴타입”으로

// 현재 (Rust/src/rules.rs:12-28)
pub enum Grade { O, S, C }
impl Grade {
    fn rank(&self) -> i32 { match self { Grade::O => 0, Grade::S => 1, Grade::C => 2 } }
}

// 변경 방향 — 라벨은 '라벨셋 안에서의 위치'로만 존재
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord)]
pub struct Grade(u8);                // order 배열의 인덱스 = rank

pub struct LabelSet {
    pub id: String,
    pub revision: u32,
    pub order: Vec<String>,          // index → id
    pub by_id: HashMap<String, Grade>,
    pub meta: Vec<LabelMeta>,        // name/description (표시용, 선택)
    pub policy: Policy,
}
impl LabelSet {
    pub fn parse(&self, s: &str) -> Option<Grade>;  // from_str 대체
    pub fn name(&self, g: Grade) -> &str;           // as_str 대체
    pub fn max<I>(&self, it: I) -> Option<Grade>;
}
이점내용
비교가 공짜Grade(u8) 에 Ord 를 유도하면 max 가 정수 비교. 현재보다 오히려 빠르다
문자열 비교 제거로드 시 1회만 문자열→인덱스 변환(인터닝). 스캔 루프에는 문자열이 등장하지 않는다
잘못된 라벨 표현 불가Grade 는 LabelSet::parse 로만 생성. 검증을 통과한 값만 존재
대가 — Grade 가 어느 라벨셋 소속인지를 타입이 보장하지 못한다. 라벨셋이 두 개 이상 살아 있는 경로(데몬 캐시, seed 비교)에서 인덱스를 섞으면 조용히 틀린다.
  • 최소 대책 — Grade 를 다루는 모든 공개 함수가 &LabelSet 을 함께 받게 한다
  • 강한 대책 — Grade 안에 label_set_hash: u32 를 함께 담고 디버그 빌드에서 대조
Python 판은 문자열을 그대로 쓰므로 이 문제가 없다. 대신 비교 비용이 조금 더 든다 — 양쪽의 성격 차이로 받아들인다.

10-2. Python ↔ Rust 동작 일치

두 구현이 같은 규칙 파일에서 같은 판정을 내야 한다(G5). 특히 검증 결과가 갈리면 안 된다 — 한쪽은 돌아가는데 다른 쪽은 거부하면 운영에서 혼란이 크다.

  • 검증 항목 V1~V11 을 같은 순서·같은 판정으로 구현하고, 종료코드를 통일한다.
  • 고의로 잘못 만든 규칙 파일 모음(검증 테스트 벡터)을 저장소에 두고 양쪽에서 돌린다. 각 파일은 “어떤 검증에 걸려야 하는지”를 기대값으로 함께 둔다.
  • 정상 규칙 파일에 대해서는 기존 parity 검증 절차(Rust/README.md)를 라벨 체계별로 1회씩 수행한다.

11-1. label_set 이 없는 기존 규칙 파일

블록이 없으면 아래 암묵 기본값을 주입한 것으로 간주한다. 기존 배포본·규칙 파일이 그대로 돈다(G6).

label_set:
  id: cso
  name: "기본 C/S/O 체계"
  revision: 0                    # 0 = 암묵 정의
  order: [O, S, C]
  labels: [{id: O, name: 공개, …}, {id: S, name: 민감, …}, {id: C, name: 기밀, …}]
  unclassified_name: 보류
  policy: {acl_failsafe: C, default_failsafe: S}

11-2. 체계 전환 절차 (예: cso → gov5)

순서작업주의
1새 label_set 블록 작성새 id 를 부여할 것. 같은 id 재사용 금지
2매핑표 작성 — 옛 라벨 → 새 라벨 N:1 축약은 가능. 1:N 분해는 자동으로 불가(사람이 재검토해야 함)

11-3. 마이그레이션 도구 (설계안)

# 매핑표 (label_map.yaml)
from: cso
to:   gov5
map:
  O: 일반
  S: 대외주의
  C: 비밀3          # N:1 축약 예 — 옛 C 를 새 비밀3 으로 보수적 배치

# 사용

            --rules cso_rule.yaml --seeds class_seed.jsonl --dry-run

--dry-run 은 “무엇이 몇 건 바뀌는지”만 보고하고 파일을 건드리지 않는다. 1:N 이 필요한 매핑은 도구가 거부하고, 사람이 재분류해야 한다고 안내한다.

축약(N:1)의 함정 — 옛 C(기밀)를 새 비밀3 으로 내리는 매핑은 등급을 낮추는 방향이다. 도구는 이런 매핑을 발견하면 명시적 확인을 요구해야 한다 (“기존 C 판정 412건이 비밀3 으로 하향됩니다. 계속?”). 반대로 올리는 방향은 경고 없이 진행해도 안전하다.

  • 경로 규칙의 grade 를 선택 항목으로 — acl_restricted: true 인 규칙은 생략 가능. 예전의 “생략하면 조용히 S” 기본값을 없앴다

13-3. 단계별 완료 기준 (DoD)

단계이걸 만족하면 끝난 것이다
Phase 0 ✔ 정의되지 않은 등급이 조용히 무시되는 경로가 하나도 없다. 기존 규칙셋 전부 위반 0건. Python·Rust 보고문·종료코드 동일
Phase 1 label_set 을 5단계로 적은 규칙셋으로 분류가 끝까지 돈다. label_set 없는 기존 파일은 결과가 이전과 완전히 같다. 코드에 등급 리터럴이 남아 있지 않다
Phase 2 요약·압축 롤업이 라벨 개수와 무관하게 동작한다. 다른 체계의 seed 를 주면 거부한다. 레코드에 체계가 각인된다
Phase 3 관리자가 UI 만으로 라벨을 추가·순서변경할 수 있고, 저장 시 검증을 통과해야 기록된다. 규칙 편집기에서 등급 오타가 구조적으로 불가능하다
Phase 4 체계 전환이 한 번의 명령으로 끝나고, 위험한 매핑(하향·1:N)에서 멈춘다
중단 지점 — Phase 1 까지만 하고 멈춰도 “관리자가 라벨을 정의한다”는 원래 목적은 달성된다. Phase 2 는 요약이 어색한 것을 고치는 일이고, Phase 3 은 편의, Phase 4 는 전환 도구다. 예산이 한정되면 Phase 1 + Phase 2 까지가 실용적인 최소 단위다.

15 결정 필요 사항

아래는 구현 착수 전 사용자 결정이 필요한 항목이다. 각 항목에 권고안을 함께 적었다.

Q1. 블록 이름 — label_set 으로 확정할 것인가?

대안: grades(기존 필드명 grade 와 일관), classification(가장 서술적). label_set 은 사용자의 표현(“분류 라벨”)에 가깝지만, 규칙 안 필드는 계속 grade 라 어휘가 둘로 갈린다.

권고 — label_set 유지. ko-pii 의 label 과 구분되고, 필드명 grade 는 기존 규칙 파일 호환을 위해 그대로 두는 편이 이득이 크다.

Q2. 서열 없는 체계를 허용할 것인가? — 예: “인사 · 재무 · 법무” 같은 분류(위험도 아님)

권고 — 이번 범위에서 제외(N1·N2). 융합 원칙이 무너진다. 필요하면 등급과 별개 필드로 태그를 다는 별도 과제로 다룬다. 지금 허용하면 max 를 “첫 번째로 걸린 것”으로 바꿔야 하는데, 이는 보수적 융합의 포기다.

Q3. 출력 호환 정책 — 안 A(스키마 교체) vs 안 B(이중 표기)?

권고 — 안 A. 현재 결과 소비자는 ui/ 와 내부 배치로 한정돼 있고, 이중 표기는 “두 스키마가 영원히 남는” 비용이 크다. 다만 외부 연동처가 이미 있다면 안 B 를 한 릴리스만 과도기로 두는 절충이 가능하다 — 연동처 유무 확인 필요.

Q4. 외부 도구 연동 — 마킹도구·반출통제(plan/NEOPC-*)가 C/S/O 를 전제하는가?

전제한다면 라벨→외부코드 매핑표를 label_set 에 함께 둘지(예: labels[].export_code), 아니면 연동 계층에서 따로 관리할지 결정해야 한다.

Q5. Phase 0 를 즉시 진행할 것인가?

Phase 0(fail-open 제거)는 라벨 자유화와 독립적으로 현재 운영의 잠재 사고를 줄인다. 변경 범위도 작다(검증 추가 + .get(g,-1) 제거).

권고 — 라벨 자유화 결정과 무관하게 선행 진행. 다만 현재 규칙 파일에 이미 오타가 있다면 배포 직후 분류가 멈추므로, 먼저 검사만 하는 모드로 한 번 돌려볼 것을 권한다.

Q6. acl_failsafe 를 살릴 것인가, 없앨 것인가? → (A)로 결정·구현 완료 (2026-08-24) — 상세는 4-1-2

(A) 살린다 — 경로 규칙에 grade 를 생략하고 acl_restricted: true 만 적는 것을 허용한다. 그러면 “이 폴더가 접근제한인 건 분명하지만, 등급은 내용을 보고 정하라. 단 내용에서 아무것도 못 잡으면 acl_failsafe 로” 라는 표현이 가능해진다. 지금은 이걸 적을 방법이 없어서(등급을 반드시 적어야 해서) 분기가 죽었다.

(B) 없앤다 — 분기와 설정 항목을 함께 제거한다. 코드가 단순해지지만, “위치만으로 잠그는” 표현 수단이 사라진다.

권고 — (A). 실제 운영에서 “보안 폴더인데 내용을 못 읽는 파일”(암호 zip·이미지·구형 포맷)이 꾸준히 나오는데, 그런 문서가 미분류로 빠져나갔다. 이 안전망은 그 구멍을 막으라고 설계된 것이므로, 없애기보다 작동하게 만드는 편이 원래 의도에 맞다.

결정·구현됨 — 경로 규칙의 grade 를 선택 항목으로 바꾸고, 검증 V12(“grade 또는 acl_restricted: true 중 하나 이상”)를 함께 넣었다. Phase 1 이 아니라 Phase 0 에 이어서 즉시 반영했다 — 라벨 자유화와 무관하게 “보안 폴더의 못 읽는 파일이 미분류로 새는” 현재의 구멍을 지금 막는 일이기 때문이다. acl_failsafe 등급 자체를 규칙 파일에서 지정하는 것은 예정대로 Phase 1(P1-4)이며, 그때까지는 코드의 C 를 쓴다.
