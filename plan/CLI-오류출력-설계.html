CLI 오류 출력
— 기계가 읽는 오류 계약

다른 프로그램이 csoclassify 를 부를 때, 실패를 사람이 읽는 한 줄이 아니라 고유 코드가 붙은 JSON 으로 받게 한다. 지금은 같은 상황에서 두 엔진이 서로 다른 종료코드를 내고 있어, 부르는 쪽이 실패의 종류를 구분할 수 없다.

대상 Python · Rust 두 엔진 방식 --json-errors (선택) 필드 code · kind · message · path 상태 구현 완료 · 2026-09-01 작성일 2026-08-31
한 줄 요약

--json-errors 를 주면 실패할 때 stdout 에 JSON 한 줄을 내고 끝낸다. code 는 오류마다 다른 고유 번호(1001·2002…)이고, 프로세스 종료코드(0~4)는 지금까지의 약속을 그대로 지킨다 — 거친 종료코드로는 "왜 실패했는지"를 구분할 수 없기 때문이다.

01

지금 무엇이 문제인가

① 실패가 사람이 읽는 글자로만 나온다

> MpowerClassify-rs.exe --dir "D:\Sample2" --simple
[MpowerClassify-rs] 처리할 파일이 없습니다. --file 또는 --dir 지정.

부르는 쪽이 이 문장을 글자로 맞춰 봐야 원인을 안다. 문구를 한 글자만 고쳐도 상대 프로그램이 깨진다.

② 같은 상황인데 엔진마다 종료코드가 다르다

없는 폴더를 준 채 실제로 돌려 확인한 값이다.

상황Rust 판Python 판실행가이드 문서
없는 폴더 / 대상 0건233
규칙셋 파일 없음233
왜 나쁜가

Rust 는 인자 문제를 2(임베딩 실패) 로 낸다. 받는 쪽이 code==2 를 보고 "모델이 없구나" 하고 재설치를 안내하면, 실제 원인(경로 오타)과 전혀 다른 대응을 하게 된다. 이 불일치는 JSON 여부와 관계없이 지금 고쳐야 하는 버그다.

③ 종료코드는 5개뿐이라 원인을 못 담는다

0·1·2·3·4 다섯 값에 실패 열댓 가지가 뭉쳐 있다. "인자 오류(3)"만 해도 대상 없음 · 규칙셋 없음 · 분류체계 없음 · seed 없음이 전부 같은 값이다.

02

오류 객체 — 네 칸

{"error":{
  "code": 1001,                          // 오류마다 다른 고유 번호(이것으로 분기한다)
  "kind": "no_input",                    // 사람도 읽을 수 있는 고유 이름(코드와 1:1)
  "message": "처리할 파일이 없습니다 — --file 또는 --dir 로 대상을 지정하세요.",
  "path": "D:\\Sample2"                   // 문제가 된 경로(없는 오류면 키 자체가 없다)
}}
칸형규약
code정수 오류마다 유일하다. 한번 부여한 번호는 뜻을 바꾸지 않는다 — 오류가 사라져도 그 번호는 다시 쓰지 않는다(받는 쪽 분기가 조용히 뒤바뀌는 것을 막는다).
kind문자열 code 와 1:1. 로그에서 눈으로 읽을 때 쓴다. 분기는 code 로 하는 것이 안전하다 (이름은 오타·번역 논쟁의 여지가 있다).
message문자열 사람에게 보여 줄 한국어 한 문장. 이 값으로 분기하지 말 것 — 문구는 다듬어질 수 있다.
path문자열 문제가 된 파일·폴더. 경로와 무관한 오류에는 키가 없다(빈 문자열을 넣지 않는다 — "경로가 비었다"와 "경로와 무관하다"는 다른 뜻이다).

어디로 내보내나

  • stdout 에 한 줄. 실패하면 결과가 없으므로 결과와 부딪히지 않고, 부르는 쪽은 stdout 만 파싱하면 된다.
  • stderr 로는 오류를 내지 않는다. [2026-09-01 구현 중 변경] 설계 때는 "같은 내용을 사람 문장으로 한 번 더 낸다"고 했는데, 부르는 쪽이 두 갈래를 합쳐 받으면(2>&1) JSON 뒤에 그 문장이 따라붙어 파싱이 깨졌다. 옵션을 준 호출은 "기계가 읽겠다"는 뜻이므로 사람용 줄을 뺀다. 진행률·요약·경고는 오류가 아니므로 그대로 나가고, 오류 로그 파일에도 그대로 남는다.
  • 프로세스 종료코드는 표의 exit 값으로 끝낸다 — 셸 스크립트가 그것만 보고도 굴러가게.
왜 선택 옵션인가

지금 이 CLI 를 쓰고 있는 쪽이 있다면 stdout 모양이 바뀌는 순간 깨진다. --json-errors 를 준 호출만 새 계약을 받는다. 옵션을 안 주면 오늘과 똑같이 동작한다.

번호 정책

번호는 재사용하지 않는다. 어떤 오류가 없어져도 그 번호는 영구히 비워 둔다 — 재사용하면 옛 버전을 상대하던 프로그램이 조용히 다른 뜻으로 분기한다. 새 오류는 그 무리의 다음 번호를 받는다.

04

문서 하나의 실패는 오류가 아니다

이 계약은 실행 전체가 멈춘 경우에만 쓴다. 문서 100건 중 3건에서 텍스트를 못 뽑은 것은 정상적인 결과이고, 지금처럼 그 문서의 레코드에 담겨 나간다.

{"file":"D:/sample/그림만있는.pdf","grade":null,
 "method":"extract_failed","signals":{},…}
왜 이렇게

못 읽은 문서를 결과에서 빼면 "18건 중 11건" 처럼 조용히 줄어든 숫자만 남는다. 무엇이 왜 빠졌는지 알 수 없는 것은 거버넌스 도구에서 가장 나쁜 실패다. 그래서 실패도 결과의 일부로 낸다. 실행 전체의 종료코드는 그런 문서가 하나라도 있으면 1 이다(결과 파일은 정상적으로 만들어진다).

05

부르는 쪽 예시

# 파이썬에서 부를 때
r = subprocess.run([EXE, "--dir", folder, "--json-errors",
                    "--format", "jsonl", "--out", out],
                   capture_output=True, text=True, encoding="utf-8")
if r.returncode != 0:
    err = json.loads(r.stdout).get("error", {})
    if err.get("code") == 1001:        # 대상이 없다 → 사용자에게 폴더를 다시 묻는다
        ask_folder_again(err.get("path"))
    elif err.get("code") == 3002:      # 모델을 못 올렸다 → 설치 안내
        show_install_guide()
    else:
        log.error("%s(%s): %s", err.get("kind"), err.get("code"), err.get("message"))
권장

code 로 분기하고, 모르는 code 는 백의 자리로 뭉뚱그려 처리하면 좋다 — 1000번대면 "부른 쪽 잘못", 2000번대면 "정책 파일 문제", 3000번대면 "환경 문제", 4000번대면 "디스크·권한". 나중에 새 오류가 늘어도 그 코드가 자동으로 옳은 갈래에 들어간다.
