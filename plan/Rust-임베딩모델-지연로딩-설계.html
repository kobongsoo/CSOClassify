Rust 임베딩 모델 지연 로딩
— 규칙으로 끝나면 모델을 읽지 않는다

Rust 판은 임베딩이 한 건도 필요 없는 실행에서도 ONNX 모델(118MB)과 토크나이저(17MB)를 빠짐없이 읽는다. 상주 데몬이 없어 이 비용을 프로세스마다 새로 낸다. 1차 규칙 스캔 결과를 보고 필요할 때만 모델을 올리도록 게이트를 세우고, 함께 죽어 있는 --embed-needed 를 살린다.

대상 Rust 엔진 (MpowerClassify-rs) 범위 main.rs 모드결정 · 2차 임베딩 단계 결과 변화 없음(동작 불변) 상태 설계 · 구현 완료 2026-09-02 작성일 2026-09-02
한 줄 요약

임베딩은 문서 단위로는 이미 지연돼 있다. 남은 것은 모델 로딩 자체를 조건부로 만드는 것 — need 를 먼저 한 바퀴 돌려 한 건도 필요 없으면 세션을 만들지 않는다. 데몬이 있는 Python 은 얻을 게 없지만, 데몬이 없는 Rust 는 개별 호출 건당 약 1.4초를 통째로 덜어낸다.

01

지금 무엇이 문제인가

① 문서 단위 지연은 이미 있다 — 없는 것은 "모델 로딩" 지연이다

두 판 모두 어떤 문서를 임베딩할지는 이미 가린다. 판정 조건도 글자 그대로 같다.

항목PythonRust
문서별 벡터 계산 지연 있음 cli.py:1583 need_vec 있음 main.rs:1309 need
모델(세션) 로딩 지연 있음 cli.py:1297 · client.py:241 — 첫 요청 때 생성/기동 없음 main.rs:1298 — 무조건 로드

Rust 도 "프로그램 시작 시" 읽는 것은 아니다. 1차 규칙 스캔이 전부 끝난 뒤(main.rs:1297)다. 문제는 시점이 아니라, need 를 한 번도 따져보지 않고 세션을 만든다는 것이다.

// Rust/src/main.rs:1297
if embed_mode != "none" {
    match embed::Embedder::load() {          // ← need 를 보지 않고 무조건
        Some(mut embedder) => {
            for it in items.iter_mut() {
                let need = embed_mode == "all" || it.grade.is_none()
                        || it.seed_eligible || dt_undecided;
                if need { it.vector = embedder.embed_document(&it.text); }
            }                                 // need 가 전부 false 면 → 한 건도 안 돌리고 끝

이때 실제로 치르는 비용은 다음과 같다.

  • model.onnx 118MB — Session::builder().with_optimization_level(Level3).commit_from_file()
  • tokenizer.json 17MB — Tokenizer::from_file()
  • onnxruntime.dll 16MB 동적 로딩
중요

반복 호출이면 OS 페이지 캐시가 118MB 를 물고 있어 디스크 I/O 는 사라진다. 그런데도 고정비가 안 줄어드는 이유는 ORT 세션 구성과 Level3 그래프 최적화가 CPU 작업이기 때문이다. 워밍으로 없어지지 않는다.

② 데몬이 없어서, 이 비용을 프로세스마다 새로 낸다

Rust 판에는 상주 데몬이 없다. --daemon·--serve·--status·--stop 은 호출부 호환을 위해 인자만 받고 조용히 무시한다(main.rs:231). 즉 모든 실행이 콜드 스타트다.

③ --embed-needed 가 파싱만 되고 읽히지 않는다

Rust 는 이 인자를 Opts.embed_needed 에 받아두지만, 그 필드를 읽는 코드가 없다. 선언(main.rs:60) · 초기화(main.rs:146) · 대입(main.rs:204) 세 곳이 전부다. 모드 결정은 이 값을 보지 않는다.

// Rust/src/main.rs:1168 — embed_needed 가 등장하지 않는다
let m = if opts.with_vector { "all" } else if auto_prop { "needed" } else { "none" };

결과적으로 Rust 는 --embed-needed 를 무시하고 seed 파일 존재 여부로만 모드를 정한다.

상황Python cli.py:1239Rust 현재
--embed-needed + seed 파일 있음neededneeded (우연히 일치)
--embed-needed + seed 파일 없음needed (강제)none — 임베딩 전혀 안 함
지금 영향

UI 는 --seeds 로 빈 파일이라도 반드시 만들어 넘기므로(app.py:2085) 현재 화면 경로에서는 결과가 같다. 하지만 --seeds 없이 Rust 를 직접 부르는 연동처에서는 --embed-needed 가 먹지 않는다. --serve 를 조용히 무시하는 것과 같은 종류의 함정이다.

02

데몬 유무가 이 최적화의 값어치를 정한다

핵심은 하나다 — 모델 로딩 비용을 프로세스 수명이 얼마나 희석해 주는가. 이 최적화의 값어치는 그 희석률에 반비례한다.

Python — 데몬이 기본 on, 무한 상주

  • DEFAULT_DAEMON = True · DEFAULT_IDLE_TIMEOUT = 0(무한, 자동종료 없음) config.py:95-96
  • 모델이 별도 프로세스에 상주 → 2회차 호출부터 model_load = 0 cli.py:1322
  • 데몬 기동조차 request_embed_text → _ready_record() 안에서만 일어난다 client.py:241 → 임베딩이 한 건도 필요 없으면 데몬이 아예 안 뜬다

→ 이 지연 로딩은 Python 에 이미 구현돼 있고, 게다가 얻을 것도 거의 없다(어차피 웜). 유일하게 남는 이득은 상주 데몬이 안 떠서 수백 MB RSS 가 안 잡히는 것이다. 유휴시간 무한이 기본이라 이건 은근히 크다.

Rust — 데몬 없음, 매 프로세스가 콜드 스타트

실측 근거는 Rust/README.md:163-196. 200건(pdf 69·txt 64·pptx 28·docx 18·md 11·xlsx 6·hwpx 3·html 1), --with-vector, 동일 PC.

여기서 건당 고정비 ≈ 1.60 − 0.22 ≈ 1.4초가 나온다. 사실상 전부 모델 로딩이다. README 가 "갭"이라 부른 개별 호출에서 Python(데몬)에 지는 구간(320.6s vs 265.5s)의 정체가 이것이다.

달리 말하면

이것은 "데몬이 없기 때문에" 하는 최적화다. 훗날 Rust 데몬을 만들면 값어치는 Python 수준(≈0)으로 떨어진다. 그래도 무해하고 정확성은 그대로라 되돌릴 필요는 없다.

03

판정

주의

04

설계 A — 로딩 게이트 need_any

로딩 직전에 need 를 미리 한 바퀴 돌려, 하나라도 참일 때만 로드한다. 구조상 Option<Embedder> 지연 초기화보다 이쪽이 기존 코드를 덜 건드린다.

// 배치 전체를 보고 한 번에 판정 — 2차 단계 진입 직전
let has_undecided   = items.iter().any(|it| it.grade.is_none());
let dt_undecided_any = items.iter().any(|it|
        it.dt.as_ref().map_or(false, |s| s.values.is_empty()));

let seed_elig_any    = items.iter().any(|it| it.seed_eligible);

let need_any = embed_mode == "all"   // --with-vector / --vector-only : 전량 필요
            || has_undecided          // security 전파 대상이 있다
            || dt_undecided_any       // 업무분류 전파 대상이 있다
            || (opts.embed_needed && seed_elig_any);  // 승격 후보 벡터가 '출력물'이 될 때

if embed_mode != "none" && need_any {
    match embed::Embedder::load() { ... }   // 기존 블록 그대로
}

seed_eligible 은 '그 벡터를 쓰는 곳이 있느냐'로 갈린다

질문에서 짚으신 대로 seed_eligible 문서도 1차 검출 뒤에 임베딩하면 된다. 다만 그 벡터가 어디에 쓰이느냐에 따라 판단이 갈린다 — 두 경우를 나눠 봐야 한다.

쓰임벡터가 필요한가근거
전파용으로만
(인자 없는 기본 실행)		 필요 없다 — has_undecided 가 흡수 내부 seed 인덱스 SeedIndex::from_records 는 오직 security 전파 루프에서만 쓰이고, 그 루프는 if it.grade.is_some() { continue; } 로 보류 문서만 돈다. 보류가 0건이면 만들어 놓고 아무도 안 쓴다.
출력물로
(--embed-needed)		 필요하다 — 조건에 넣어야 한다 그 벡터가 결과 레코드에 실려 나간다(§11 다안). seed_eligible 문서는 seed 승격 후보이고, 이 인자의 존재 이유가 바로 "보류거나 seed_eligible 인 문서만 임베딩"(설계서 §185)이다.
구현 중 정정

이 문서는 처음에 "seed_eligible 은 언제나 has_undecided 에 흡수된다"고 적었다. §11 에서 다안(--embed-needed 일 때 벡터를 싣는다)을 채택하면서 그 전제가 깨졌다 — 벡터가 '아무도 안 쓰는 중간 계산'에서 '산출물'로 바뀌었기 때문이다. 실제로 구현 후 리눅스 배포본 검증에서 규칙으로 확정된 seed 승격 후보 3건의 벡터가 통째로 안 나오는 것을 잡아 조건을 추가했다. 게이트 조건은 "쓰는 곳이 있느냐"로 판단해야 하고, 그 답은 출력 규칙이 바뀌면 같이 바뀐다.

예외

--with-vector(embed_mode == "all")는 그대로 둔다. class_seed.jsonl 승격용 벡터 추출이 이 경로로 나가므로 영향이 없다(§03 2·3행).

문서 단위 need 는 그대로 둔다

main.rs:1309 의 need 는 손대지 않는다. Python(cli.py:1583)과 글자 그대로 같아야 두 판의 벡터·전파 결과가 일치한다는 기존 계약이 유지된다.

05

설계 B — --embed-needed 살리기

게이트를 넣으려면 어차피 모드 결정부를 건드린다. 죽어 있는 embed_needed 를 같은 자리에서 살린다. Python 의 우선순위 규칙(cli.py:1239 — "임베딩 정책 needed > all > none. embed_needed 가 우선")을 그대로 따른다.

// Rust/src/main.rs:1168 — 개정안
let m = if opts.embed_needed { "needed" }        // ① 명시 지정이 최우선(Python 과 동일)
        else if opts.with_vector { "all" }
        else if auto_prop { "needed" }
        else { "none" };

--embed-needed + seed 없음needednoneneeded
--embed-needed --with-vectorneededallneeded

확인 필요

3행(--embed-needed --with-vector 동시 지정)에서 현재 Rust 는 all, Python 은 needed 로 갈린다. 개정안은 Python 에 맞춘다 — 두 판의 동작을 맞추는 것이 이 프로젝트의 일관된 원칙이기 때문이다. 다만 이 조합을 쓰는 호출부는 확인된 바 없으므로(§03) 실질 영향은 없다.

부수효과

embed_needed 를 읽게 되면 "필드가 한 번도 읽히지 않는다"는 컴파일 경고도 함께 사라진다. 지금은 인자를 받아 저장까지 하고 버리는 상태다.

06

07

잃는 것 — 모델 배포 이상의 조기 감지

유일한 실질적 트레이드오프다. 그리고 Rust 쪽이 Python 보다 위험하다.

판모델·런타임 누락을 알아채는 경로
Python데몬 기동 실패 → in-process 폴백 + log.warning(cli.py:1325) · --status 로 상태 확인 — 경로가 여럿
Rust--status 를 조용히 무시(main.rs:231) → Embedder::load() 시도 그 자체가 유일한 신호

게이트를 걸면 규칙으로 다 끝난 배치에서는 조용히 성공하고, onnxruntime.dll·models/ 누락이 나중에 미분류가 나오는 배치를 만나서야 드러난다. 거버넌스 도구에서 "그때는 되고 지금은 안 되네" 는 곤란하다.

보완 — 셋 다 넣는다

  1. 경량 프리체크 — 세션을 만들지 않고 존재 여부만 확인한다(model_dir() + dylib 경로 is_file()). 파이프라인 진입 시 1회. 비용은 stat 몇 번. 없으면 note 로 남긴다. 구현: embed::check_deployment()
  2. 스킵 사유를 남긴다 — [MpowerClassify-rs] 임베딩 불필요(전 문서 규칙 확정) → 모델 로드 생략. 로그만 봐도 "안 돈 것"과 "안 필요했던 것"이 구분돼야 한다.
  3. 전파 요약 로그 공백을 메운다 — main.rs:1477 [전파] seed=… 전파결정=… 미분류잔여=… 가 안 나가게 되므로, 이를 파싱하는 쪽이 있다면 위 note 로 대체한다.
구현 중 추가

프리체크를 넣고 실제로 모델을 뺀 배포로 돌려 보니, 알리고 나서 그대로 죽었다. onnxruntime 을 못 찾으면 ort 는 PATH 에 있는 아무 onnxruntime.dll 이나 집어 들고, 버전이 다르면 Err 가 아니라 패닉으로 끝난다 (실측: expected 1.22.x, but got 1.17.1 · 종료코드 101 · 결과 파일 없음). Embedder::load() 가 실패하면 None 을 준다는 전제가 여기서 깨진다. 이 판 이전부터 있던 문제지만, "알리고 죽는다"는 프리체크의 취지와 정면으로 어긋나므로 함께 고쳤다 — 점검이 실패하면 load() 를 아예 부르지 않는다. 결과: 종료코드 101(결과 없음) → 0(규칙 등급이 담긴 결과 파일 + 사유 한 줄).

겸사겸사

--status 를 Rust 에서 "모델·런타임 배포 확인" 으로 실제 구현하는 것도 고려할 만하다. 지금 조용히 무시하는 것 자체가 이미 문제다(README 도 함정으로 지적).

후속 카드 — 최적화 그래프 캐싱 (측정 완료 · 보류)

판정 · 보류

측정 결과 채택하지 않는다(2026-09-02). 절감은 145.5 ms · 12.5% 인데 배포본이 +112MB 늘고 하드웨어 의존·무효화 리스크가 따라온다. 결정적으로, 고정비의 최대 항목은 그래프 최적화(153.8 ms)가 아니라 tokenizer.json 파싱(817.6 ms) 이라 이 카드는 더 작은 쪽을 공격한다. 아래는 그 판단의 근거 기록이다.

왜 이 카드가 존재하나

§01 에서 본 대로 "모델 로딩"은 사실 두 가지 일이다.

단계하는 일OS 페이지 캐시로 사라지나
① 읽기model.onnx 118MB 를 파일에서 메모리로 사라진다 — 2회차부터 메모리에서 복사만
② 준비ORT 세션 구성 + Level3 그래프 최적화(연산 융합·메모리 배치·실행 계획) 안 사라진다 — CPU 계산이고, 결과물은 그 프로세스 메모리에만 있다

OS 는 "파일 내용"은 캐시해 주지만 "그 파일로 만들어낸 구조물"은 캐시해 주지 않는다. 프로세스가 끝나면 ②의 결과는 같이 사라지고, 다음 실행은 캐시에서 118MB 를 공짜로 받아놓고 ②를 처음부터 다시 한다. 건당 고정비 1.4초가 200회 내내 줄지 않는 이유이자, Python 데몬이 model_load = 0 을 만드는 이유다 — 데몬은 프로세스를 안 죽여서 ②의 결과물을 그대로 재사용한다.

이 카드는 ②의 결과를 파일로 저장해 두고 다음 실행에서 다시 쓰자는 것이다. ONNX Runtime 이 부르는 이름은 offline graph optimization 이다.

API 확인 — 지금 이 빌드에서 쓸 수 있다

확인 항목결과

구조 — 두 단계

    .commit_from_file(&cache_path)?;

실측 결과 2026-09-02

결론

절감 145.5 ms (12.5%) — 이 카드는 덮는다(구현하지 않음). 배포본이 +112MB(158MB→271MB) 늘고 하드웨어 의존·무효화 리스크를 떠안는 대가로 얻는 것이 이미 게이트가 통째로 없앤 구간 밖에서의 12.5% 뿐이다. 채산이 맞지 않는다.

측정 방법 — Rust 로 Embedder::load() 의 각 부분만 부르는 도구를 따로 만들어 (프로젝트 소스는 건드리지 않음, 같은 ort 2.0.0-rc.10·tokenizers 0.21· 같은 onnxruntime.dll 1.26.0), 매번 새 프로세스에서 한 번씩 쟀다 — 이 판은 데몬이 없어 실행마다 콜드 스타트이고, 한 프로세스 안에서 반복하면 2회차부터 비현실적으로 빨라진다.

왜 부분 합과 다른가

부분별로 재면 세션 절감이 346.9 ms 로 보이지만, 둘을 이어서 돌리면 145.5 ms 다. 앞선 작업이 페이지 캐시·할당자를 덥혀 뒤 작업이 빨라지기 때문이다. 실제 코드는 둘을 이어서 하므로 145.5 ms 가 정직한 값이다.

핵심 발견 — 병목은 그래프 최적화가 아니라 토크나이저다

고정비를 부분으로 쪼개 보니 tokenizer.json 파싱 817.6 ms 가 단일 최대 항목이었다. 이 카드가 겨냥하는 그래프 최적화는 153.8 ms 뿐이다. 이 카드는 더 작은 쪽을 공격하고 있었다. 그리고 토크나이저 쪽은 tokenizers 크레이트에 "미리 만들어 둔 것을 읽는" 경로가 없어 같은 수법을 쓸 수도 없다.

채택 조건 판정 (아래 4개를 모두 만족해야 착수)

#조건판정
1게이트 후에도 모델 로딩이 체감될 만큼 자주 일어나는가 미지 — 코퍼스에 달렸다. 다만 --files-from 200건(44초) 배치에서는 145 ms 가 0.3% 라 의미가 없다
2의미 있는 절감이 확인되는가 아니오 — 12.5%. 배포본 +71%(158→271MB)의 대가로는 작다
3R3(무효화)를 해시+버전으로 막는 설계가 함께 들어가는가 미구현 — 2번이 아니므로 진행하지 않음
4벡터가 캐시 전/후 동일한가 예 — 384차원 바이트 동일(최대 절대오차 0.000e+00). --emb-test 로 원본/최적화 모델 대조

4번은 통과했지만 2번에서 걸린다. 정확성은 문제가 없되 이득이 값을 못 한다.

ORT 의 경고

최적화 모델을 만들 때 ORT 가 직접 경고를 냈다 — R1(하드웨어 의존)이 문서상 우려가 아니라 실제였다: "Serializing optimized model with Graph Optimization level greater than ORT_ENABLE_EXTENDED and the NchwcTransformer enabled. The generated model may contain hardware specific optimizations, and should only be used in the same environment the model was optimized in."

다시 꺼낼 조건

이 카드를 다시 볼 만한 경우는 하나다 — 토크나이저 로딩까지 함께 없앨 방법이 생겼을 때. 817 ms 를 그대로 둔 채 153 ms 를 깎아 봐야 체감이 안 된다. 그때가 오면 이 카드가 아니라 Rust 상주 데몬(§08 ③) 이 두 비용을 한 번에 없애는 정답이다.

리스크 — 다섯 가지, 전부 해결책이 필요하다

#리스크대응
R1하드웨어 의존 — Level3 는 레이아웃 최적화를 포함해 결과가 실행 환경에 매인다. 빌드 PC 에서 만든 파일을 배포에 동봉하면 다른 PC 에서 틀리거나 못 읽을 수 있다 배포에 넣지 않는다. 설치처 PC 에서 최초 1회 생성하는 방식만 쓴다
R2쓸 수 있는 위치가 아닐 수 있다 — exe 옆(Program Files 등)은 쓰기 권한이 없을 수 있다 쓰기 가능한 사용자 경로(%LOCALAPPDATA% 등)에 두고, 실패하면 조용히 캐시 없이 진행
R3무효화(가장 위험) — 모델을 교체했는데 낡은 캐시를 그대로 쓰면 다른 벡터가 나오고, 전파 판정이 조용히 흔들린다 캐시 파일명에 model.onnx 의 SHA-256 + ORT 버전을 박는다. 하나라도 다르면 캐시를 안 쓰고 새로 만든다
R4디스크 발자국 — 최적화 모델이 118MB 한 벌 더 생긴다 설치 안내에 명시. 용량이 문제인 배포에서는 이 기능을 끌 수 있게 한다
R5경합 — 여러 프로세스가 동시에 첫 실행이면 같은 파일에 함께 쓴다 임시 파일에 쓰고 원자적 rename. 실패하면 캐시 없이 진행(치명적이지 않다)

정확성 — 두 판 벡터 일치 계약

이 프로젝트의 핵심 계약 중 하나는 "두 판의 벡터와 전파 결과가 일치한다"(실행가이드 4장)이다. 다행히 전제는 유리하다 — Python 도 같은 최적화 수준을 쓴다.

즉 캐시를 쓰더라도 실행되는 그래프는 지금과 같은 그래프다(최적화를 미리 해 두었을 뿐). 그래도 가정으로 넘기지 않는다 — 채택 시 --emb-test 로 뽑은 384 벡터가 캐시 전/후, 그리고 Python 판과 완전히 같은지 확인하는 것을 착수 조건으로 둔다.

아래를 모두 만족할 때만 착수한다. 하나라도 아니면 카드를 덮어 둔다.

  1. §04·§05 게이트가 들어간 뒤에도 모델 로딩이 체감될 만큼 자주 일어난다(미분류·seed 후보 비중이 높은 코퍼스)
  2. --emb-test 실측에서 의미 있는 절감이 확인된다(최소 기준을 미리 정할 것)
  3. R3(무효화)를 모델 해시 + ORT 버전으로 막는 설계가 함께 들어간다
  4. 벡터가 캐시 전/후 및 Python 판과 바이트 동일하다

이 카드는 "②를 빨리 하기" 이고, §04 게이트는 "②를 아예 안 하기" 다. 안 하는 것이 언제나 빨리 하는 것보다 낫다. 순서를 바꾸지 않는다.

검증 기준

이 설계의 성공 조건은 "빨라졌다"가 아니라 "결과가 그대로다" 이다. 7번 — 같은 코퍼스·같은 인자로 게이트 전/후의 결과 파일이 완전히 같아야 한다. 다르면 §06 의 no-op 논증 중 어딘가가 틀린 것이므로, 게이트가 아니라 그 전제를 다시 봐야 한다.

구현 중 드러난 것 — 결정이 필요하다

결정 · 다안

채택: 다(절충) — --embed-needed 를 명시했을 때만 벡터를 싣는다. 기존 기본 출력(UI 경로)은 한 글자도 안 바뀌고, 인자는 제 뜻을 갖는다. 구현·확인 완료 — --embed-needed 실행에서 미분류 문서에 384차원 벡터가 실리고, 인자 없는 기본 실행은 vector 필드 0건으로 baseline 과 바이트 동일하다.

배경

--embed-needed 를 살려 놓고 보니, seed 파일이 없는 상태에서 이 인자를 주면 벡터를 만들어 놓고 아무 데도 쓰지 않는다. 실측(문서 2건)에서 19ms → 1,144ms 로 느려지는데 결과 레코드는 바이트 단위로 똑같았다. 순수한 낭비다.

원인은 두 판의 벡터 출력 규칙이 다르다는 데 있다. 이 설계의 범위(모드 결정) 밖이라 손대지 않았다.

판레코드에 vector 를 싣는 조건위치
Python벡터를 만들었으면 언제나 싣는다cli.py:1591
Rust--with-vector 를 줬을 때만 싣는다main.rs (3차 조립)

즉 --embed-needed 는 파이썬에서 "못 정한 문서의 벡터를 결과에 실어 달라"는 뜻인데, Rust 에서는 그 벡터가 나갈 구멍이 없다. 세 갈래가 있고 출력 계약을 바꾸는 문제라 임의로 정하지 않는다.

안내용영향
가현행 유지 — 모드만 맞추고 벡터는 --with-vector 로만 기존 출력 그대로. 대신 --embed-needed 단독 사용은 낭비로 남는다
나파이썬과 완전 일치 — 벡터가 있으면 항상 싣는다 두 판 일치. 대신 기본 경로 출력 파일이 커진다(미분류 문서당 384개 실수)
다 ✔절충(채택) — --embed-needed 를 명시했을 때만 싣는다 기존 기본 출력은 그대로, 인자는 제 뜻을 가진다. 대신 Rust 안에서 규칙이 하나 늘어난다
범위 밖

Rust 상주 데몬(③)은 이 설계에 포함하지 않는다. 최적화 그래프 캐싱(§10)도 후속 카드이고, §09-B(doctype 후보 추가 미작동)도 별건이다 — 같이 손대면 "결과 불변"이라는 이 설계의 검증 기준이 무너진다.
