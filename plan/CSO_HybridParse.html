1 배경과 목적

현재 CSOClassify 는 모든 문서를 사이냅 문서필터(snf_exe) 하나로 추출한다. 이는 HWP/HWPX 를 포함한 전 포맷을 안정적으로 처리하는 검증된 방식이지만, 두 가지 개선 여지가 있다.

  • 속도 — Office/PDF 계열은 순수 Rust 오픈소스 추출기가 snf 대비 3~20배 빠르다(실측).
  • 라이선스 의존 — snf 는 상용이라 재배포·라이선스키 제약이 있다. 오픈소스로 대체 가능한 포맷은 의존을 줄일 수 있다.

다만 한국어 HWP 계열은 오픈소스 성숙도가 낮아 전면 교체는 위험하다. 따라서 기본 동작은 지금 그대로 두고, 실험적 opt-in 플래그 --hybridparse 로만 확장자별 최적 엔진 라우팅을 켠다. 이 문서는 그 추출 계층의 설계를 정의한다(구현은 별도).

한 줄 요지(최종 구현) — --hybridparse 는 파일 내용을 감지해 포맷별 오픈소스 파서로 사이냅 없이 추출한다: pdf→pypdfium2, hwp→HWP5, hwpx→zip/OWPML, 구형 doc/ppt→자체 olefile 파서, xls→xlrd, 현대 docx/xlsx/pptx→zip/OOXML 직접파싱(stdlib), text→직접읽기. 각 파서 실패 시 snf 폴백(snf 없으면 그 파일만 미분류). 전부 순수 파이썬/소형 wheel 이라 Windows·Linux(CentOS 7) 동일 번들이고, 결과가 비면 snf 로 떨어져 커버리지가 줄지 않는다.

아키텍처 변천(요약) — HWP: libhwp(Rust, 패닉·wheel 문제) → 순수 파이썬 HWP5 파서로 확정. 그 외 포맷: xberg(Rust, 117MB·CentOS7 불가·PDF 느림/저품질) 검토 후 기각 → 포맷별 조립형 스택(pypdfium2·xlrd·stdlib OOXML 파서·자체 doc/ppt 파서)으로 확정. 확장자가 아니라 내용 기반 감지로 라우팅한다. 아래 §5·§6·§10 은 이 최종안 기준으로 갱신됨(그 전 절들엔 검토 이력이 남아 있다).

3 설계 원칙

원칙내용
기본 불변--hybridparse 미지정 시 기존과 100% 동일(SynapExeExtractor 단독). 코드·출력·성능 회귀 없음.
안전 우선하이브리드 경로의 모든 분기는 실패 시 snf 로 폴백. 신규 엔진이 없거나(미번들) 죽어도 최소한 현행 커버리지를 보장.
크래시 없음HWP5 파서는 순수 파이썬 in-process. 실패해도 파이썬 예외뿐이라 프로세스 격리가 필요 없다(예외 → snf 폴백).
인터페이스 보존기존 TextExtractor.extract(input_path, save_dir) 계약을 그대로 구현 → 상위(파이프라인/분류/데몬)는 무변경.
관측 가능어떤 파일을 어떤 엔진이 처리했고 폴백이 일어났는지 로그·타이밍에 남긴다.
점진 도입1차는 HWP/HWPX 만 신경로, Office/PDF 는 snf 유지(보수적 기본값). xberg 경유는 뒤 단계의 선택 확장.

4 인자 정의

인자기본의미
--hybridparseoff(미지정)모든 포맷을 전용 파서로 라우팅(hwp→hwp5, hwpx→zip/OWPML, 그 외→xberg). snf 는 폴백 전용. 미지정이면 snf 단독(현행).
단일 플래그로 통합 — 초기엔 Office/PDF 를 --hybridparse-office 로 분리했으나, --hybridparse 하나가 전 포맷을 전용 파서로 보내도록 통합했다(별도 office 플래그 제거). snf 는 1차 엔진으로 쓰지 않고 폴백 전용이며, snf 가 없으면(미설치) 전용 파서가 실패한 파일만 미분류로 둔다(크래시 없음).

동작 요약:

  • 단독 플래그(값 없음, store_true). 기존 모드 플래그(--rule-only/--vector-only, --embed)와 직교 — 추출 방법만 바꾼다.
  • 모든 실행 모드(분류 / --embed / --dir 일괄)에서 동일하게 적용.
  • 플래그는 추출기 팩토리에만 전달된다(§6). 규칙·임베딩·전파 로직은 건드리지 않는다.

# 팩토리 시그니처 (설계 — 구현 아님) def build_extractor(*, hybrid=False) -> TextExtractor: if not hybrid: return SynapExeExtractor() # 현행 그대로 try: snf = SynapExeExtractor() # 폴백 전용 except ExtractError: snf = None # snf 없어도 됨(실패 파일만 미분류) return HybridExtractor( snf=snf, hwpx=HwpxZipExtractor(), hwp=Hwp5Extractor(), # 순수 파이썬 HWP5 office=XbergExtractor(), # 그 외 전부(Office/PDF 등) )
상위 코드(pipeline.process_file, 분류 엔진, 데몬)는 extractor.extract(path, save_dir) 만 호출하므로 팩토리 교체 외 수정이 없다. 이것이 기존 TextExtractor 인터페이스를 지키는 이유.

6.3 계층도

cli / daemon / pipeline │ extractor.extract(path, save_dir) ← 인터페이스 불변 ▼ build_extractor(hybrid=?) ├─ hybrid=False → SynapExeExtractor (현행) └─ hybrid=True → HybridExtractor ├─ .hwpx → HwpxZipExtractor ─┐ ├─ .hwp → Hwp5Extractor ────┤ 실패 시 폴백 ├─ 그외 → XbergExtractor ───┤ (snf 있을 때만; └────────────────────────────┴─→ SynapExeExtractor 없으면 미분류)

7 HWP5 순수 파이썬 파서 채택

구형 HWP(.hwp)는 외부 실행파일·Rust 라이브러리 없이 파이썬만으로 파싱한다. 초기 검토에서 후보였던 libhwp(Rust/pyo3)는 실문서 절반에서 Rust 패닉으로 프로세스를 죽였고, 3.12/3.13 wheel 도 없어 배포가 까다로웠다. 대신 HWP 5.0 포맷을 직접 해석하니 그 두 문제가 함께 사라졌다.

왜 파이썬 직접 파싱이 더 나은가 — ① 크래시 0(우리가 제어 → 실패해도 파이썬 예외뿐, 프로세스 격리 불필요) ② 3.12 그대로(버전 제약 없음) ③ 의존성은 순수 파이썬 olefile 1개 ④ 실측 snf 와 sim 1.00, libhwp 가 패닉하던 문서까지 정상 추출 ⑤ in-process라 프로세스 기동 비용조차 없어 snf·libhwp-워커보다 빠름.

7.1 HWP 5.0 구조와 추출 절차

HWP 5.0 은 OLE/CFB 복합문서(구형 .doc 와 같은 컨테이너)다. 본문은 BodyText/SectionN 스트림에 태그 레코드로 담기고, 글자는 PARA_TEXT 레코드(UTF-16LE + 인라인 제어문자)에 있다.

단계처리
1) 열기olefile 로 OLE 인지 확인·오픈(아니면 실패 → snf 폴백). 구형 3.x·손상도 여기서 걸러짐
2) 헤더FileHeader 속성비트: bit0=압축, bit1=암호화. 암호화면 포기(→ snf)
3) 섹션BodyText/Section0,1,… 을 번호순으로 읽고, 압축이면 raw-deflate(zlib, wbits=-15) 해제
4) 레코드32비트 헤더에서 태그·크기 파싱 → PARA_TEXT(태그 67)만 수집
5) 텍스트UTF-16LE 해독. 제어문자 0/10/13 은 1글자(10·13→개행), 그 외 1~31 은 8글자(16바이트) 컨트롤이라 건너뜀

7.2 흐름

Hwp5Extractor.extract(path): if not olefile.isOleFile(path): raise ExtractError # HWP5 아님 → snf 폴백 ole = olefile.open(path) flags = FileHeader[36:40]; compressed=flags&1; encrypted=flags&2 if encrypted: raise ExtractError # 암호화 → snf 폴백 parts = [] for sec in sorted(BodyText/SectionN): data = zlib.decompress(sec, -15) if compressed else sec for tag, payload in records(data): if tag == PARA_TEXT: parts.append(decode(payload)) return "\n".join(parts) # 빈 결과면 상위가 snf 폴백

7.3 한계와 폴백

  • HWP 5.0 전용 — 2007 이전 HWP 3.x(다른 바이너리 포맷, 희귀)는 OLE 가 아니라 자연히 실패 → snf 폴백.
  • 암호화/DRM 문서 — 스트림 해독 불가 → snf 폴백.
  • 배포용(ViewText) 문서 — 본문이 암호화된 ViewText 에만 있으면 BodyText 가 비어 폴백된다.
  • 즉 파서가 못 다루는 경우는 모두 snf 가 받는다 — 커버리지는 현행 이상.
의존성 — olefile(순수 파이썬, BSD, ~200KB)만 추가된다. PyInstaller 번들이 자명하고 파이썬 버전 제약이 없다. 만약 번들 누락 등으로 olefile import 가 실패해도, hwp5 경로만 조용히 포기하고 snf 로 폴백한다(본체는 olefile 을 지연/방어 취급).

8 HWPX zip/OWPML 파서

HWPX 는 ZIP+XML(OWPML, KS X 6101) 컨테이너다. 본문 텍스트는 Contents/section0.xml, section1.xml… 안의 <hp:t>…</hp:t> 런에 들어 있다. 표준 라이브러리만으로 안전하게 뽑는다(외부 의존 0).

단계처리
1) 열기zipfile.ZipFile(path) — 손상/비ZIP 이면 예외 → snf 폴백
2) 대상 선택이름이 Contents/section<n>.xml 인 항목만, 번호 순 정렬
3) 텍스트 런각 XML 에서 <hp:t>(.*?)</hp:t> 추출 → 내부 잔여 태그 제거
4) 엔티티 복원&lt; &gt; &amp; &quot; &apos; → 원문자
5) 합치기런을 개행으로 결합 → 정제(clean_text)는 상위 파이프라인이 담당
견고성 — 정규식 기반이라 네임스페이스 접두사 변형이나 스키마 세부에 덜 민감하다. 만약 <hp:t> 매칭이 0건이면(스키마 상이) “빈 결과 → snf 폴백”으로 자연 처리된다. 추후 정확도를 높이려면 Preview/PrvText.txt(요약 미리보기) 병용이나 XML 파서 전환을 고려.

실측: 3/3 성공, snf 대비 sim 1.00, 파일당 1~6ms. section 기반이라 전체 본문을 담아 미리보기(PrvText)보다 완전하다.

9 데몬 연동

추출이 일어나는 위치는 두 갈래이며, --hybridparse 전달 방식이 다르다.

경로추출 위치플래그 전달
분류(--file/--dir)클라이언트측(cli). 임베딩만 데몬 embed_text op 로 전송cli 가 팩토리에 직접 반영 → 데몬 무관(가장 단순)
--embed + 데몬서버측. 데몬이 경로를 받아 추출·임베딩선택지 A/B (아래)
--embed in-process 폴백클라이언트측cli 팩토리에 직접 반영

데몬 서버측 추출의 플래그 전달 방식:

  • 선택 A(권장·단순) — 데몬은 항상 snf 로 추출하고, --hybridparse 는 클라이언트측 추출 경로에서만 유효하다고 정의. 즉 하이브리드가 필요하면 클라이언트가 추출해 텍스트를 embed_text 로 보낸다(분류 경로가 이미 이 구조). 데몬 프로토콜/상태 무변경.
  • 선택 B(완전) — embed op 요청에 hybrid 불리언을 실어 보내고, 데몬이 요청별로 build_extractor(hybrid=...) 를 선택. 데몬이 여러 클라이언트를 섞어 받을 때 일관되나, 프로토콜·캐싱 규칙이 복잡해진다.
권장: 1차는 선택 A. 데몬은 “워밍업된 임베딩 모델 재사용”이 목적이고 추출은 저렴하므로, 하이브리드 추출은 클라이언트가 맡고 데몬엔 텍스트만 넘기면 된다. HWP5 파서는 in-process 라 클라이언트에서 그대로 돌아간다.

10 패키징·배포 3.12 유지

버전 제약 없음 — HWP 를 순수 파이썬 HWP5 파서로 처리하므로 빌드 파이썬을 3.12 그대로 둔다. 초기 검토의 libhwp(Rust)는 3.12 wheel 이 없어 3.11 다운그레이드·사이드카 같은 복잡한 선택이 필요했지만, 순수 파이썬 파서로 전환하면서 그 문제 자체가 사라졌다.

추가 의존성 — 전부 순수 파이썬 또는 manylinux2014(glibc 2.17) wheel 이라 Windows·Linux(CentOS 7) 동일 번들:

라이브러리용도라이선스용량

  • docx/xlsx/pptx 를 stdlib(zipfile+ElementTree)로 직접 파싱 → python-docx/openpyxl/python-pptx 가 끌던 Pillow(13MB)·lxml(7MB)+라이브러리(3MB)=−23MB(양 OS 공통).
  • [Linux] 빌드 환경(conda) 오염 패키지 numba·llvmlite(153MB)·jedi·IPython·jupyter 를 spec excludes 로 차단(이전 tgz 엔 섞여 있었음).
  • [Linux] numpy 의 BLAS 백엔드 libblas/libcblas/liblapack.so.3 가 한 openblas(40MB)를 가리키는 심링크인데 PyInstaller 가 3벌 복사(120MB) → 빌드 후 1실파일+2심링크로 dedupe(−80MB).
텍스트만 뽑는 용도라 결과 품질은 동일(sim≈1.0)하고 의존이 오히려 줄어 더 견고하다. 두 배포본 모두 Windows·Linux(CentOS 7·glibc 2.17) 완전 동일 동작 — Linux 는 실제 CentOS 7.9 에서 추출·규칙·임베딩(onnx) 전 경로 실행 검증 완료.
xberg 를 채택하지 않은 이유(요약) — 단일 Rust 바이너리 _xberg.pyd 117MB(내부 분리 불가), CentOS 7 불가(glibc 2.28+ 요구), PDF 느림(snf 40배)·읽기순서 저품질(sim 0.62). 조립형 스택이 용량·속도·품질·이식성 전부에서 우위라 기각했다.

11 로깅·타이밍·출력

  • 로그 — 추출 성공 시 추출 engine=hwpx_zip|hwp5|snf|xberg file=… chars=…, 폴백 발생 시 추출 폴백 from=hwp5 to=snf reason=….
  • 타이밍 — 기존 elapsed_ms.extract 는 그대로. 필요 시 어떤 엔진이었는지 별도 필드(extract_engine)로 남긴다(출력 스키마 가산만, 기존 필드 불변).
  • 진단성 — hwp5 실패 사유(HWP5 아님·암호화·빈결과)를 폴백 로그에 포함해, 어떤 문서가 왜 snf 로 넘어갔는지 사후 집계 가능.
출력 스키마 변경은 추가 전용. --hybridparse 를 안 쓰면 새 필드도 나타나지 않아 기존 소비자와 호환된다.

14 테스트 계획

  • 단위 — 라우팅 선택(확장자→엔진 리스트), 폴백 판정(예외/0자), HWPX 파서(정상/손상ZIP/빈section/엔티티), HWP5 파서(레코드 순회·PARA_TEXT 디코더·인라인 컨트롤 skip·비OLE 실패). (현재 15개 통과)
  • 폴백 — hwp5 가 비-OLE(HWP5 아님)에서 실패하면 snf 폴백이 텍스트를 반환하는지.
  • 동치성 — --hybridparse off 결과가 현행과 동일(회귀 없음, 전체 110 테스트 통과).
  • 품질 — tests/compare_extractors_4way.ipynb 지표를 회귀 가드로 활용(hwpx·hwp 모두 snf 대비 sim≈1.0).
  • 통합 — 분류/--embed/--dir 세 경로 모두에서 플래그가 먹는지, 데몬(선택 A)에서 텍스트 경로가 정상인지.
