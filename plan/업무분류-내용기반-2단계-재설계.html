1. 배경 · 이 문서의 범위

업무 분류 축은 doc_rule.yaml 의 규칙을 문서에 걸어 labels.doctype 후보를 만든다. 신호원은 세 가지다.

신호원대상현행 판정이 문서의 판단

3-2. 문제 목록

P1 단일 키워드 1건 = 확정 — 정밀도 붕괴

회의록 규칙의 회의 가 사업계획서 본문에 한 번만 나와도 그 문서는 회의록이 된다. 한국어는 띄어쓰기가 없어 부분문자열 오탐도 그대로 탄다. exclude 로 막는 방식은 오탐 사례를 사람이 전부 열거해야 하므로 확장되지 않는다.

P2 검색 범위가 문서 전체 — 위치 정보 소실

"이 문서가 회의록이다"(제목)와 "회의록을 첨부한다"(본문 언급)를 구분하지 못한다. 전자는 강한 신호, 후자는 오히려 반대 증거(회의록을 첨부하는 문서는 회의록이 아니라 공문·품의서다)인데 둘이 같은 값을 받는다.

P3 문서 종류를 판별하는 신호를 안 본다

회의록을 회의록으로 만드는 것은 회의록 이라는 단어가 아니라 일시 · 장소 · 참석자 · 안건 이라는 서식 골격이다. 현행 문법에는 이런 필드어 조합을 표현할 방법이 없다.

P4 max(confs) — 근거가 누적되지 않는다

terms · filename · paths 가 모두 맞은 문서(0.70)와, 흔한 단어 하나만 걸린 문서(0.70)의 신뢰도가 같다. 근거가 쌓여도 보상이 없으므로, top_n 으로 전략을 바꿔도 변별이 생기지 않는다.

P5 동점 정렬이 비결정적 — 재현성 없음

_finalize() 는 후보를 survivors(set)에서 만들고, resolve_multi() 는 confidence 만 정렬 키로 쓴다. P4 때문에 전부 동점이므로 순서가 set 순회 순서에 좌우된다. top_n 을 켜는 순간 같은 문서를 두 번 돌리면 결과가 달라질 수 있다.

P6 근거가 결과에 남지 않아 튜닝이 불가능하다

security 축은 terms:[{term,count}] 를 남기는데, doctype 축은 from:["rule"] 뿐이다. 어떤 단어가 몇 번 걸려서 이 라벨이 붙었는지 알 수 없다. 검토 담당자는 오분류 이유를 볼 수 없고, 개발자는 임계값을 정할 근거 데이터를 얻을 수 없다.

P7 이미 만들어 둔 임베딩 자산이 놀고 있다

propagate.propagate_doctype() · DoctypeSeedIndex 라는 전파 엔진이 이미 구현되어 있다. 문서 임베딩도 파이프라인에서 이미 계산된다. 그런데 seed 를 만드는 경로가 없어 size == 0 → no_seeds 로 항상 빠진다. 추가 연산 비용이 0 인 강력한 신호를 안 쓰고 있는 상태다.

P4 · P5 · P6 은 이 재설계의 전제조건이다. 1단계 신호를 아무리 정교하게 만들어도, 근거가 누적되지 않고(P4) 근거가 기록되지 않으면(P6) 개선을 확인할 방법 자체가 없다. 8장 · 13장에서 함께 해소한다.

8-1. 결합 방식 — noisy-OR

단순 덧셈은 1.0 을 넘어 상한 처리가 지저분해진다. 독립 증거의 결합으로 해석되는 noisy-OR 를 제안한다.

score = 1 - Π (1 - cᵢ)      cᵢ = 성립한 각 신호의 개별 신뢰도

예) head_term(0.70) + form_set(0.50) + filename(0.30)
    = 1 - (0.30 × 0.50 × 0.70)
    = 1 - 0.105
    = 0.895

예) 본문 term 만 걸린 문서
    = 1 - (1 - 0.15)
    = 0.150     ← 채택 임계 미달 → 후보에서 탈락
  • 항상 [0, 1) 구간에 머문다 — 별도 상한 처리 불필요
  • 근거가 늘수록 단조 증가하되 포화한다 — 약한 증거를 아무리 모아도 강한 증거 하나를 못 넘는다
  • 기존 confidence 스케일(0~1)과 호환되어 min_confidence · top_n 이 그대로 동작한다

9-3. 변경이 필요한 지점

(a) 신뢰도 상한 캡 필수

벡터 단독으로 만든 후보는 0.65 를 넘지 못하게 캡을 건다. 이유: knn_vote 의 score 는 "이웃 중 몇 %가 이 라벨인가"이지 "이 문서가 이 라벨일 확률"이 아니다. seed 가 편향돼 있으면(10-3) 쉽게 0.9 가 나온다. 근거를 제시할 수 있는 규칙 히트보다 세지면 안 된다는 것이 이 설계의 원칙 1이다.

(b) 청크 단위 최대 유사도 필수 · 실측 확정

현재 문서 벡터는 청크 벡터의 평균 풀링이다. 실측(3-B-2) 결과 한 청크에 다 들어가는 문서는 25.1%뿐이고 중앙값 문서조차 5청크, p90 이 60청크, 최대 902청크다. 즉 74.9%의 문서에서 앞부분의 양식 신호가 평균에 묻힌다. 검토 대상이 아니라 반드시 해야 하는 변경이다.

10-1. 절차

단계 1 — 고신뢰 문서 선별

1단계 점수 ≥ T_seed 이면서, 아래를 모두 만족하는 문서만 고른다.

  • 독립된 두 신호원이 같은 노드를 가리킬 것 (예: filename ∧ head_term, 또는 path ∧ form_set)
  • 대상 노드가 leaf 일 것 (중간 노드는 조상 흡수로 어차피 사라진다)
  • 그 문서에 채택된 노드가 1개일 것 (다중 라벨 문서는 seed 로 모호하다)
  • 추출 텍스트 길이가 최소치 이상일 것 (빈 스캔 PDF 배제)

단계 2 — seed 인덱스 구축

선별된 문서의 본문 벡터와 dc_id 를 class_seed.jsonl 에 기록한다. 이 형식은 DoctypeSeedIndex.from_seed_file() 이 이미 읽는 형식이므로 새 저장 포맷이 필요 없다.

단계 3 — 적용

파일명이 무의미한 문서(최종_v3_진짜최종.hwp, scan_0412.pdf)에 이 seed 로 kNN 전파를 돌린다. 파일명이 멀쩡한 절반이 나머지 절반을 덮는다.

단계 4 — 성장

검토 화면에서 사람이 confirmed 로 확정한 문서를 seed 에 추가한다. 이쪽이 품질이 높으므로, 확정 seed 가 쌓이면 약한 라벨 seed 의 비중을 낮춘다.

10-2. 이 방식의 장점

장점설명
수작업 0건초기 라벨링 없이 오늘 있는 데이터만으로 시작된다
인프라 재사용산출물이 그대로 DoctypeSeedIndex 형식 — 새로 만들 것이 없다
조직 특화사전적 정의가 아니라 우리 조직이 실제로 쓰는 문서가 기준이 된다
자체 진단노드별 seed 개수가 곧 "이 노드를 믿어도 되는가"의 지표가 된다

10-3. 반드시 인지해야 할 편향 중요

파일명으로 뽑은 seed 는 편향되어 있다. "회의록.hwp" 라고 이름 붙는 문서는 정식 서식 회의록이고, 이름이 안 붙는 회의록은 메모에 가깝다. 프로토타입이 정식 서식 쪽으로 쏠려 비정형 문서를 놓치게 된다.
  • 완화 1 — seed 채택 시 경로 다양성을 강제한다. 한 폴더에서 N건 이상 뽑지 않는다
  • 완화 2 — 노드별 seed 개수 상한/하한을 둔다. 특정 노드가 seed 를 독식하면 kNN 투표가 그 노드로 쏠린다
  • 수용 — 초기에는 재현율을 포기하고 정밀도만 챙기는 것으로 받아들인다. 놓친 문서는 검토 큐로 가고, 사람이 확정하면 단계 4 로 흡수된다

10-4. drift 방지 (기존 원칙 유지)

전파로 붙은 라벨은 절대 seed 가 되지 않는다. seed 자격은 (a) 1단계 규칙 고신뢰 또는 (b) 사람 확정, 두 경로뿐이다. 이 원칙이 깨지면 초기 오분류가 스스로를 강화하며 코퍼스 전체로 번진다.

11. 두 단계 결합 규칙

11-1. 1단계 결과에 따른 2단계의 역할

1단계 상태2단계의 역할최종 신뢰도
확정 후보 score ≥ T_high 후보를 추가만 한다. 기존 후보는 건드리지 않는다 1단계 점수 유지. 벡터가 같은 노드를 지지하면 noisy-OR 로 소폭 상승
약한 후보 T_low ≤ score < T_high 벡터가 같은 노드를 지지하면 승격, 아니면 약한 채로 둔다 noisy-OR 결합. 캡 미적용 (규칙 근거가 있으므로)
후보 없음 벡터가 주도해서 결정한다 0.65 캡 적용 (9-3a)
벡터는 빼앗지 않는다. 벡터 결과가 1단계 후보와 다른 노드를 가리켜도, 1단계 후보를 제거하지 않는다. 두 후보가 함께 남고 conflict 전략이 처리한다. 이는 merge_embed_candidates() 의 현행 동작과 동일하며, "자동 판정은 확정하지 않는다"는 기존 원칙의 귀결이다.

11-2. 조상 흡수 (현행 유지)

_absorb_ancestors() 를 그대로 쓴다. 2계층 노드가 채택되면 그 1계층 조상은 자동 제거된다 — path_ids 에 이미 조상이 들어 있으므로 별도 라벨로 낼 이유가 없다.

11-3. 계층 정합성 보정 신규

4장의 구조상, 두 계층은 서로 다른 엔진이 결정한다. 다음 세 경우를 명시적으로 다룬다.

상황처리
2계층 확정 + 1계층 미결정조상 흡수가 알아서 처리 — 2계층만 남는다. 추가 처리 불필요
1계층 확정 + 2계층 미결정
(주제는 알겠는데 양식을 모름)		 1계층 라벨만 제안하고 검토 큐로 보낸다. 억지로 2계층을 고르지 않는다 — "인사/총무인 건 확실하나 어떤 문서인지 모름"은 정당한 답이며, 이걸 표현할 수 있는 것이 계층 구조의 이점이다
1계층 A + 2계층 B(A의 자손 아님)
(모순)		 둘 다 남기되 모순 플래그를 붙여 검토 큐 우선순위를 올린다. 자동으로 하나를 버리지 않는다

11-4. conflict 전략

all / top_n 문법은 유지한다. 다만 8-5 의 tie-break 보강이 적용되며, 가산 점수 도입으로 top_n 이 비로소 의미 있게 동작한다. 현행에서는 후보가 전부 0.70 동점이라 top_n 이 사실상 무작위 선택이었다.

P6 해소. 이건 편의 기능이 아니라 이 재설계의 전제조건이다. 근거가 없으면 8-2 의 임계값을 실측으로 정할 방법이 없고, 검토자는 오분류 이유를 볼 수 없다.

13-1. 현행

"doctype": {
  "values": [
    { "dc_id": "DC_001_002", "path": "경영/관리 > 회의록",
      "path_ids": ["DC_001","DC_001_002"],
      "confidence": 0.7,
      "from": ["rule"] }          ← 이게 전부. 왜 걸렸는지 알 수 없다
  ],

13-2. 변경안

"doctype": {
  "values": [
    { "dc_id": "DC_001_002",
      "path": "경영/관리 > 회의록",
      "path_ids": ["DC_001","DC_001_002"],
      "confidence": 0.895,
      "stage": "rule",                    ← 신규: rule | embed | both
      "from": ["head","form","name"],     ← 확장: head/form/structure/body/name/path/embed
      "evidence": {                       ← 신규 블록
        "head":   { "terms": [{"term":"회의록","pos":18}] },
        "form":   { "matched": ["일시","장소","참석"], "required": 3 },
        "body":   { "terms": [{"term":"회의록","count":4}], "distinct": 1 },
        "name":   { "terms": ["회의록"] },
        "embed":  { "method":"knn_vote", "top1_sim":0.71, "share":0.44,
                    "neighbors":["…/2026Q1_영업회의록.hwp", "…"] }
      },
      "score_parts": [                    ← 신규: noisy-OR 재현용
        {"signal":"head","c":0.70},
        {"signal":"form","c":0.50},
        {"signal":"name","c":0.30}
      ]
    }
  ],
  "strategy": "all", "status": "proposed", "truncated": 0,
  "conflicts": []                         ← 신규: 11-3 모순 플래그
}
[2026-09-10 개정] 두 칸을 signals 한 칸으로 합쳤다. evidence 와 score_parts 는 둘 다 열쇠가 '신호 이름'이라, 읽는 쪽이 매번 {이름: 점수} 표를 만들어 이름으로 맞춰 붙여야 했다 (검토 화면이 실제로 그렇게 하고 있었다). 실제로 쓰이는 모양은 처음부터 "head 신호는 0.70점이고 이런 말이 걸렸다" 한 덩어리였다. 
"signals": {
  "head": { "c": 0.70, "terms": [{"term":"회의록","pos":18}] },
  "form": { "c": 0.50, "matched": ["일시","장소","참석"], "required": 3 },
  "name": { "c": 0.30, "terms": ["회의록"] },
  "embed": { "method":"knn_vote", "top_sim":0.71, "share":0.44 }   ← c 없음
}
담기는 값은 하나도 줄지 않았다 — 자리만 합쳤다. 순서는 근거가 만들어진 순서(title→head→body→name→embed)를 그대로 따르므로 두 판의 결과 파일을 나란히 비교할 수 있다.
c 가 없을 수 있다 — 전파(embed)가 이미 있는 후보에 근거만 더하는 경로가 있다(11-1). 그때는 점수 몫이 따로 없으므로 c 키를 만들지 않는다. 0.0 으로 채우면 "0점 기여"라는 없는 사실을 말하게 되고, 화면의 "근거 N가지가 겹쳐…" 문장에서 N 이 틀어진다.
옛 결과 파일은 그대로 읽는다 — 검토 화면과 전파 병합이 두 모양을 모두 읽는다. 안 그러면 전파를 한 번 거친 옛 문서만 "왜 이 라벨인지"를 통째로 잃는데, 그 손실은 조용히 일어나서 더 나쁘다.

13-3. 프라이버시 원칙 (기존 유지)

근거 블록에는 규칙에 정의된 단어와 그 건수만 담는다. 문서 원문 조각을 스니펫으로 담지 않는다. head.pos 는 위치 인덱스이지 내용이 아니다. embed.neighbors 는 파일 경로이므로, 경로 자체가 민감할 수 있는 환경에서는 마스킹 옵션이 필요할 수 있다(Q7).

13-4. 검토 화면에서의 활용

이 블록이 있으면 검토자가 "왜 이게 회의록으로 잡혔지" 를 즉시 볼 수 있고, 규칙을 고칠 사람이 바로 그 화면에서 근거를 확인할 수 있다. score_parts 는 임계값을 바꿨을 때의 결과를 재실행 없이 시뮬레이션하는 데 쓸 수 있다 — 튜닝 사이클이 극적으로 짧아진다.

14. 하위호환 · 이행 계획

14-1. 하위호환 원칙

기본값을 현행 동작과 동일하게 두면 기존 doc_rule.yaml 을 한 글자도 안 고쳐도 돌아간다.
  • min_distinct: 1, min_count: 1 → 현행 OR 1건 매칭과 동일
  • head_terms · form 없음 → 해당 신호 미적용
  • embed.enabled: false → 2단계 미가동
즉 신규 기능은 전부 옵트인이다. 정책 파일에서 켠다.
단, 8장의 점수 결합 방식 변경(max → noisy-OR)과 8-2 의 신뢰도 재조정은 옵트인으로 만들 수 없다. 이 둘은 기존 결과의 confidence 값을 바꾼다. → 14-2 의 0단계에서 baseline 을 확보한 뒤 차이를 측정하고 전환한다.

표제부/첫 줄 제한 + 가산 점수(noisy-OR) + 본문 term 격하 세 가지를 함께 넣는다. 셋은 서로 맞물려야 효과가 나므로 쪼개면 안 된다 — 격하 없이 표제부만 넣으면 오탐이 안 죽고, 가산 점수 없이 격하만 하면 재현율만 떨어진다.

규칙 파일 작성 비용이 거의 없다 — head_terms/title_terms 는 노드 title 로 자동 생성된다.

이 단계에서 회수는 아직 일어나지 않는다. 다음 단계를 안전하게 만드는 것이 목적이다. 실측(3-B-4) 기준 2개 이상 라벨이 23.2% → 1.7% 로 떨어질 것으로 예상된다.

결과 — 재현율 44.9% → 65.6%, 정밀도는 86.8% → 90.6% 로 오히려 올랐고 오탐(오라벨·헛라벨)은 하나도 늘지 않았다. 실제로 넣은 어휘와 배치는 3-C-5. 아래 예상 어휘 중 가이드·매뉴얼 계열은 적중했으나, 실측에서 더 큰 덩어리는 정부 보도자료(보고서) 21건이었다 — 아래 표에는 없던 항목이다.

1단계 안전장치 위에서 어휘를 공격적으로 늘린다. 실측(3-B-7) 기준 C군 45건이 회수 대상이며, 놓친 어휘가 이미 특정돼 있다.

Q5. 다중 라벨이 실무에서 필요한가 — 한 문서에 업무분류를 2개 이상 붙이는 것이 맞는가?
→ 단일 라벨이면 문제가 훨씬 쉬워진다(top_1 + 임계). 실측 근거(2026-08-26) — 검증셋 150건에서 사람이 정답을 2개 붙인 문서가 21건(14%) 나왔다. 제품비교자료(보고서+제안서) 처럼 실제로 두 분류가 다 맞는 문서가 존재하므로, 다중 라벨 자체는 실무에서 필요하다. 남은 결정은 "허용하느냐"가 아니라 몇 개까지 허용하느냐다(현재 코퍼스 최대 3개 · 2개 이상 13.5%).
현재 기본값은 conflict: all 인데, 이게 의도된 정책인지 결정을 미룬 기본값인지 확인이 필요하다. 16-1 검증셋 라벨링 방식도 이 답에 달려 있다.
Q6. 재현율 vs 정밀도 — 어느 쪽이 더 나쁜가? 이제 실제 값으로 결정 가능
3단계까지 마친 현재 위치는 정밀도 91.3% · 재현율 71.6%(3-D)다. 즉 제안된 라벨 10개 중 9개는 맞고, 붙어야 할 것의 4분의 1 이상은 빈칸으로 남는다. 검토 화면에서 전수 확인하는 전제라면 재현율 쪽으로 더 밀어야 하고, 자동 확정에 가깝게 쓸 거라면 지금 위치가 적당하다. 이 결정이 곧 5단계(임계값 재보정)의 목표값이 된다.
→ 사람이 검토 화면에서 전수 확인하는 전제면 관대하게(재현율 우선), 자동 확정에 가깝게 쓸 거면 보수적으로(정밀도 우선) 임계값을 잡아야 한다. 8-3 의 T_high/T_low 값이 여기서 결정된다.

19. 유의어 사전 겹 구조 · 업종 사전 2026-08-26 구현 완료

12장의 doc_rule.yaml 은 규칙이고, 그 규칙의 어휘는 doc_synonyms 사전에서 나온다("분류 불러오기"). 이 장은 그 사전이 한 장에서 세 겹으로 바뀐 경위와 구조를 적는다.

19-1. 왜 겹으로 나눴나 — 관리자에게 사전을 쓰게 할 수 없다

출발점은 이 질문이었다. 관리자는 문서분류체계(doc_classification_export.json)만 작성한다. 거기에는 분류 이름밖에 없고, 규칙이 필요로 하는 "같은 뜻 다른 말" (요구사항정의서 ↔ 요구사항명세서 ↔ SRS)은 없다. 그 말을 관리자에게 적으라고 할 수는 없다.

게다가 업종마다 문서 이름이 다르다. 금융의 여신심사서, 의료의 판독소견서, 건설의 기성검사원 은 서로 아무 관계가 없다. 그렇다고 고객사마다 사전을 새로 쓰면 유지가 안 된다.

공개 사전을 찾아봤으나 쓸 수 있는 것이 없었다. 우리말샘(CC BY-SA)은 일반어 위주라 "보고서→리포트"는 나와도 "결과보고"는 안 나오고, 라이선스가 전염성이라 제품 내장 사전에 넣기 어렵다. KorLex 등은 연구용 제한이 있다. 한국어 "문서유형 유의어 사전"에 해당하는 오픈소스는 존재하지 않는다는 것이 조사 결론이다. 쓸 만한 것은 공공데이터 공통표준단어(KOGL, 영문약어 포함)와 국가법령정보 OPEN API 두 가지였다(19-6).

19-2. 사전은 세 겹이다 — 아래로 갈수록 세다

doc_synonyms.core.yaml       ← 업종 무관. 제품이 들고 다닌다. 고객이 안 건드림
doc_synonyms.<업종>.yaml     ← 업종 고유 문서명. doc_rule.yaml 의 industry 가 선택
doc_synonyms.local.yaml      ← 그 회사에만 있는 말. 관리자가 고치는 자리(최우선)
이름 없는 doc_synonyms.yaml 은 읽지 않는다. 겹으로 가르기 전에 쓰던 단일 파일이라 처음에는 호환용으로 local 바로 앞에 얹었으나, 쓰는 고객사가 없어 겹에서 뺐다(2026-08-26 결정). 어중간하게 읽으면 "core 를 고쳤는데 안 듣는다"는 증상이 생기고, 원인이 옛날 파일이라는 것을 아무도 떠올리지 못한다. 폴더에 남아 있어도 무시하므로, 되살리려면 core 나 local 로 이름을 바꿔야 한다. 회귀 테스트 test_예전_단일_파일은_무시한다 가 이 결정을 고정한다.

모두 doc_rule.yaml 과 같은 폴더에 둔다. 한 겹도 없어도 되고, 한 겹이 깨져도 나머지 겹은 살아남는다 — 사람이 손으로 고치는 파일이라 YAML 이 깨지는 일이 실제로 있는데, 그때 사전이 통째로 사라지면 규칙 생성이 조용히 빈약해진다.

업종 지정

industry: manufacturing                      # 하나
industry: [medical, public]                  # 여럿 — 앞에 적은 것이 더 세다

공공병원·국공립학교·관급공사 건설사처럼 한 조직이 두 업종에 걸치는 일이 실제로 있어 리스트를 받는다. 값은 그대로 파일 이름이 되므로 경로 문자가 섞이면 거부한다(경로 주입 방지).

19-3. 사전 안은 다시 두 층이다 — 업종차는 위층에만 있다

층동작업종을 타는가어디에 두나
aliases / filename_only / excludes 분류 이름이 사전에 그대로 있을 때만 쓰인다. 가장 정확하지만 사전에 없는 이름은 하나도 못 건진다 탄다 업종 사전
tails / heads 이름이 사전에 없어도 꼬리말·머리말만 같으면 걸리는 그물. "OO정의서 → OO명세서" 처럼 한국 문서 이름의 조립 규칙을 쓴다 거의 안 탄다 core

이 구분이 이 설계의 핵심이다. 비싼 층(그물)은 업종을 타지 않으므로 core 에서 한 번만 만들면 되고, 업종 사전은 얇게 간다. 실제로 core 는 꼬리말 103개인데 업종 사전은 7~14개다. 그래서 새 업종을 추가하는 일이 프로젝트가 아니라 반나절 작업이 된다.

행정 공통 꼬리말(신고서·통지서·허가증· 자격증·면허증·수료증·명령서· 결정서·지정서 등 17개)은 처음에 의료 사전에 넣었다가 core 로 올렸다. 금융·법률·교육·공공에도 똑같이 필요한 말이라, 업종마다 되풀이하면 고칠 때 일곱 곳을 함께 고쳐야 하는 사전이 된다.

19-4. 병합 규칙 — 그리고 반드시 필요한 재정렬

  1. 키별로 이어 붙인다. 같은 분류 이름이 두 겹에 다 있으면 지우지 않고 합치되, 센 겹의 말을 앞에 둔다(순서가 곧 우선순위이고 뒤가 잘린다).
  2. 합친 뒤 꼬리말·머리말을 길이순으로 다시 세운다(_order_longest_first).
2번이 없으면 조용히 망가진다. synonyms_of() 는 위에서부터 훑다가 처음 걸린 하나만 쓰고 멈춘다. 파일 한 장일 때는 사람이 순서를 지키면 됐지만, 업종 사전이 core 뒤에 끼어드는 순간 파일 순서로는 보장할 수 없다 — 업종 사전이 짧은 보고서 를 들고 오면 core 의 결과보고서 가 뒤로 밀려 영영 쓰이지 않는다. 증상은 "그 분류만 유의어가 조금 적다" 라서 사람 눈으로는 못 잡는다.
길이만 보면 충분한 이유 — 두 꼬리말이 같은 이름에 동시에 걸리려면 한쪽이 다른 쪽의 끝토막이어야 하고, 그러면 반드시 더 길다. 상관없는 항목끼리는 순서가 바뀌어도 결과가 같다. 같은 길이끼리는 원래 순서를 지킨다(사람이 적어 둔 우선순위 보존).

19-6. 씨앗 수집기 — 국가법령정보 별표·서식

scripts/collect_law_forms.py. 업종 사전을 사람이 상상해서 적으면 실제로 안 쓰는 말이 섞이고 정작 쓰는 말이 빠진다. 그래서 그 업종의 공식 문서 이름 목록을 먼저 구한다 — 「의료법 시행규칙 별지 제○호서식」 같은 서식 이름이 곧 그 업종에서 오가는 문서 이름이다.

의료 실측 — 서식 825건 → 문서유형 229종, 그중 62%는 core 가 이미 잡았다. 남은 것이 업종 사전 후보다.

진짜 산출물은 aliases 가 아니라 tails 다. 의료에서 신고서(10종)·통보서(9종)·허가증· 통지서 가 반복해서 나왔다. 꼬리말 하나가 이름 수십 개를 한꺼번에 잡으므로 값어치가 가장 크다. 이 발견 때문에 위 17개를 core 로 올렸다.

만들면서 두 번 고쳤다.

  • 아는 꼬리말이 없는 이름(처방전·소견서)을 버리고 있었다 — 버리면 새 업종에서 아무것도 못 배운다.
  • 뒤 2~4글자를 그냥 세니 후보 23개 중 16개가 고서·사반원증 같은 조각이었다. → "그 말이 홀로 문서 이름으로 나온 적이 있는가" 를 조건으로 걸어 해결했다(신고서는 서식으로 존재, 고서는 없음).
이 수집기의 한계 — 행정 문서에 치우친다. 진료기록부·소견서·판독지 처럼 법정 서식이 아닌 임상 문서는 거의 안 잡힌다. 정작 병원에서 가장 많이 오가는 문서인데도 그렇다. 금융은 더 나빴다 — 검색어 보험 이 사회보험(건강보험·고용보험)을 끌어와 처방전·방문간호지시서 가 섞였다. 결국 7개 사전은 모두 사람(LLM)이 작성했고, 수집기는 검증·보완 도구로 쓴다.
