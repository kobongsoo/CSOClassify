저장소 설계 · Seed Store

기준 문서(seed) 저장소
— 보안등급 · 업무분류 두 축 통합 설계

기준 문서 하나가 보안등급(C/S/O) 과 업무분류(dc_id) 두 축을 동시에 떠받치게 만든다. 파일 이름·한 줄 스키마·축별 해제 방식을 정하고, 원본이 바뀌거나 사라졌을 때 그것을 어떻게 알아채고 반영할지까지 규정한다.

대상 class_seed.jsonl 축 security + doctype 엔진 Python · Rust 공통 상태 구현 완료 · 2026-08-28 작성일 2026-08-28
한 줄 요약

한 문서 = 한 줄 = 벡터 하나를 유지한 채, 엔진이 읽는 키(grade · labels.doctype · vector)는 모양을 그대로 두고 축별 이력·상태를 담는 axes 블록을 새로 얹는다. 파일 이름은 class_seed.jsonl 로 새로 시작한다(옛 파일 이관 없음). 원본 변경·삭제·분류체계 변경은 시스템이 표시만 하고, 지우는 것은 사람이 한다.

01

현재 상태 — 두 축은 이미 한 파일에 들어가 있다

설계를 새로 짜기 전에 코드가 이미 하고 있는 일부터 확인했다. 결론은 출발점이 생각보다 앞서 있다는 것이다.

축저장 위치(한 줄 안에서)읽는 코드
보안등급 행 맨 위 grade ("C"/"S"/"O") propagate.py · SeedIndex.from_seed_file
propagate.rs · SeedIndex::from_seed_file
업무분류 labels.doctype (dc_id 배열) propagate.py · DoctypeSeedIndex.from_seed_file
propagate.rs · DoctypeSeedIndex::from_seed_file

한 문서가 한 줄을 차지하고, 그 줄의 벡터 하나를 두 축이 나눠 쓴다. 즉 "두 축을 담을 수 있게 만드는" 일은 이미 끝나 있다. 실제로 없는 것은 그 다음이다.

없음 1
축별 이력

누가·언제·왜 이 축을 확정했는지 축마다 따로 남지 않는다. approved_by·ts 가 행에 하나뿐이라 나중에 확정한 축이 앞의 기록을 덮는다.

없음 2
축별 해제

삭제 버튼이 행을 통째로 지운다. "업무분류만 기준에서 빼고 보안등급은 유지"가 불가능하다.

없음 3
원본과의 동기화

seed 는 원본의 사본(벡터) 을 들고 있다. 원본이 수정·삭제돼도 알아채는 장치가 전혀 없다.

지금 있는 함정

UI 의 add_doctype_seed() 는 labels.security 를 미러링해 두지만 엔진 어느 쪽도 그 키를 읽지 않는다(둘 다 맨 위 grade 만 본다). 지금은 무해하지만, 나중에 정리한다며 grade 를 지우고 labels.security 만 남기는 순간 보안축 전파가 에러 없이 0건이 된다. 아래 스키마는 이 지점을 정면으로 다룬다.

02

파일 이름 — class_seed.jsonl 로 새로 시작

cso_ 접두사는 이 프로젝트에서 보안축 전용 표식이다(cso_rule.yaml = 보안규칙, doc_rule.yaml = 업무분류규칙). 두 축 공통 저장소에는 어느 쪽 접두사도 맞지 않으므로 제3의 이름을 쓴다.

03

한 줄 스키마 (v2)

불변 규칙

엔진이 읽는 키의 모양은 절대 바꾸지 않는다. labels.doctype 을 배열에서 객체로 바꾸면 Rust 의 as_array() 가 None 을 돌려주고 그 줄을 조용히 건너뛴다 — 에러 한 줄 없이 기준 문서가 사라지는, 가장 나쁜 종류의 고장이다. 새 정보는 전부 엔진이 무시하는 새 블록에 넣는다.

{
  "v": 2,
  "file": "d:/sample/03.경조사지원규정.txt",
  "vector": [ ... 384개 ... ],

  // ── 엔진이 읽는 키 (모양 고정 · axes 로부터 자동 생성되는 파생값) ──
  "grade": "C",
  "labels": { "security": "C", "doctype": ["DC_004_003"] },

  // ── 진실은 여기 · 엔진은 이 블록을 읽지 않는다 ──
  "axes": {
    "security": { "state": "active", "value": "C",
                  "source": "phase4", "approved_by": "홍길동",
                  "ts": "2026-08-28T09:10:00+09:00", "note": "" },
    "doctype":  { "state": "active", "value": ["DC_004_003"],
                  "source": "phase6", "approved_by": "홍길동",
                  "ts": "2026-08-28T09:12:00+09:00", "note": "" }
  },

  // ── 원본·벡터의 신원 (동기화 판정 재료) ──
  "doc":   { "hash": "9f2c4a…(SHA-256 16진수)", "size": 12345,
             "mtime": "2026-08-20T18:03:11+09:00" },
  "embed": { "dim": 384,        // model 은 엔진이 아직 안 알려 준다
             "ts": "2026-08-28T09:10:00+09:00" },

  "ts": "2026-08-28T09:12:00+09:00", "approved_by": "홍길동"
}

읽는 법 — axes 가 진실, 위쪽은 파생값

저장 직전에 axes → grade/labels 로 한 번 투영(project)하는 함수 하나만 두고, 다른 어떤 코드도 grade 를 직접 쓰지 않는다. 투영 규칙은 두 줄이면 끝난다.

# axes 를 읽어 엔진용 키를 다시 만든다 — 저장할 때마다 무조건 이 함수를 통과시킨다
security.state == "active"  →  grade = value,  labels.security = value
doctype.state  == "active"  →  labels.doctype = value

# 비활성 축은 키 자체를 지운다 (빈 값으로 두지 않는다)
그 외  →  해당 키를 행에서 삭제
왜 빈 값이 아니라 삭제인가

"labels.doctype": [] 는 엔진이 이미 건너뛰므로 동작은 같다. 하지만 "값이 없다"와 "축을 해제했다"를 사람이 구분할 수 없게 된다 — 점검 화면에서 둘은 완전히 다른 조치를 뜻한다.

새 필드가 각각 막아 주는 사고

필드없으면 무슨 일이 생기나
doc.hash원본 내용이 바뀌어도 낡은 벡터로 계속 전파한다. 두 엔진 모두 --hash(SHA-256)를 이미 지원하므로 UI 가 분류 실행에 그 인자만 붙이면 공짜로 얻는다.
doc.size / mtime해시를 못 구한 경우의 보조 판정 재료. 사람이 눈으로 확인할 때도 쓰인다.
embed.dim임베딩 모델을 교체했을 때 옛 벡터와 새 벡터를 코사인으로 비교하게 된다. 유사도가 의미 없는 숫자가 되는데도 전파는 태연히 돌아간다. 구현 메모 — 엔진이 모델 이름을 결과에 담지 않아 model 은 아직 비어 있다. 대신 벡터 차원이 대다수와 다른 줄을 점검에서 잡아낸다(모델 교체의 실제 흔적은 대부분 차원 변화로 나타난다).
axes.*.source / approved_by / ts축별 책임 추적 불가. 행에 하나뿐인 approved_by 를 나중 축이 덮어쓴다.

왜 파일을 두 개로 쪼개지 않는가

seed_security.jsonl + seed_doctype.jsonl 로 나누는 안은 권하지 않는다.

  • 한 문서가 두 축 모두의 기준일 때 384차원 벡터가 두 벌로 복제된다(행당 대략 6~8KB).
  • 더 중요한 것 — near-dup 중복 검사가 축을 가로질러 돌지 못한다. 같은 문서를 보안축에선 사본으로 거르고 업무분류축에선 통과시키는 상황이 생긴다.
  • 원본 변경·삭제 판정을 두 파일에서 각각 해야 하고, 두 결과가 어긋날 수 있다.

문서가 원자 단위인 이상 행도 문서 단위여야 한다.

04

축 하나만 지운다는 것 — state

두 축이 생긴 이상 "업무분류만 기준에서 빼고 보안등급은 유지"가 반드시 필요하다. 상태값은 셋이면 충분하다.

state뜻누가 붙이나전파에 쓰이나
active관리자가 확정한 기준사람예
retired관리자가 이 축을 해제사람아니오 (이력만 남김)
suspect원본 변경 · 원본 없음 · 유령 분류코드시스템아니오
  • 축 하나 해제 → 그 축만 retired, 다른 축은 그대로. 행은 남는다.
  • 두 축을 모두 사람이 해제(retired)하면 행을 파일에서 제거한다. 이력은 감사 로그가 갖고 있다.
  • 다만 suspect 행은 반드시 남긴다. 구현 중에 실제로 겪은 함정이다 — "살아 있는 축이 없으면 지운다"로 만들었더니, 원본이 바뀌어 두 축이 suspect 로 빠진 문서가 저장하는 순간 파일에서 사라졌다. 사람이 확인해 되살릴 대상인데 되살릴 방법도, 무엇이 있었는지 알 방법도 없어진다.
  • suspect 는 사람이 아니라 시스템이 붙인다. 사람이 확인해서 되살리거나(active) 지운다.
05

원본이 바뀌거나 사라지면 — 반영 규칙

이것이 설계의 진짜 어려운 절반이다. seed 는 원본 문서의 사본(벡터) 을 들고 있어서 원본과 조용히 어긋날 수 있다. 시나리오별로 판정과 조치를 못박아 둔다.

무슨 일어떻게 아나조치
1. 등급 변경
S → C		 UI 편집 axes.security.value 교체 + ts/approved_by 갱신 → 투영 → 감사 update
2. 한 축만 해제 UI 축별 해제 버튼 axes.doctype.state = "retired", labels.doctype 키 삭제. 보안축은 무사
3. 원본 내용이 수정됨 doc.hash ≠ 이번 분류 결과의 hash suspect (사유 stale). 자동 삭제 금지 · 자동 재임베딩도 금지 — 등급까지 바뀌었는지는 사람만 안다. UI 가 "원본이 바뀐 기준 문서 N건" 배지 → 관리자가 [다시 읽어 갱신] 을 누르면 재추출·재임베딩 후 active 복귀
4. 원본이 삭제/이동됨 분류 시 경로 부재 suspect (사유 missing). 즉시 지우지 않는다 — 벡터·라벨은 원본이 없어도 여전히 쓸모 있는 지식이고, 네트워크 드라이브가 잠깐 안 붙은 것과 진짜 삭제를 구분할 수 없다. 같은 doc.hash 가 다른 경로에서 발견되면 "이동된 것 같습니다 — 경로를 갱신할까요?" 로 자동 재연결 제안
5. 분류체계에서 dc_id 가 사라짐 doc_taxonomy.yaml 에 그 dc_id 없음 그 dc_id 만 axes.doctype.value 에서 빼고 orphan 으로 기록. 남은 dc_id 가 없으면 축을 suspect. 이미 빠진 축은 다시 세지 않는다 — 안 그러면 정리를 끝낸 뒤에도 경고가 영영 사라지지 않는다(그 줄은 ‘확인 필요’ 목록에서 처리한다). taxonomy 에 renamed_from 별칭을 두면 자동 이관(미구현)
6. 결과 화면에서 seed 와 다르게 확정 확정 시 seed 조회 조용히 덮지 말 것. "이 문서는 기준 문서(C)입니다 — 기준도 O 로 바꿀까요?" 를 물어야 한다. 안 물으면 결과와 기준이 어긋난 채로 다음 분류에서 그 문서가 스스로를 잘못 가르친다
대원칙

시스템은 절대 스스로 지우지 않는다. 표시만 하고, 지우는 것은 사람이 한다. 기준 문서 한 건이 잘못 사라지면 그와 비슷한 문서 수십 건의 분류가 함께 흔들린다. 오탐으로 지우는 쪽이 남겨 두는 쪽보다 훨씬 비싸다.

비용 0

위 판정은 분류를 돌릴 때 공짜로 얻는다 — 어차피 전 문서를 훑으므로 --hash 결과와 seed 를 대조만 하면 된다. 별도 스캔 작업이 필요 없다.

07

감사 로그

지금은 detail 이 자유 문자열이라 나중에 기계가 못 읽는다. 축과 전후값을 칸으로 분리한다.

{"ts":"2026-08-28T09:12:00+09:00", "action":"update", "axis":"security",
 "file":"d:/sample/03.경조사지원규정.txt",
 "before":"S", "after":"C", "reviewer":"홍길동", "reason":"오분류 정정"}
  • action = add | update | retire | restore | suspect | delete
  • axis = security | doctype | -(행 전체)
  • append-only 는 그대로 유지 — 이 파일이 행을 지운 뒤의 유일한 이력이다.
