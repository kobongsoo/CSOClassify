3 설계 개요 — 분류 축(axis)

축을 일급 개념으로 도입한다. 축이란 “서로 배타적인 라벨 한 벌 + 그 라벨을 정하는 방법”이다. 기존 C/S/O 는 축이 하나뿐이었던 특수한 경우가 된다.

3-1. 스키마 — 축의 성격은 개념, 실제 문법은 파일 2개

“축”이라는 개념(라벨 구조·서열·충돌 전략)은 아래처럼 하나의 표로 설명할 수 있지만, 실제로 규칙 파일에 이 문법 그대로 적는 것은 아니다. 3-2 결정에 따라 축마다 파일이 통째로 나뉘고, 각 파일이 자기 축의 성격을 스스로 담는다. 아래는 두 파일의 실제 스키마다.

파일이 이미 축을 하나로 고정하고 있는데(3-2 — doc_rule.yaml은 항상 doctype 축 전용), 그 파일 안에 id: doctype라고 또 적는 것은 자기소개를 두 번 하는 것과 같다. 여섯 필드를 하나씩 짚어 보면 실제로 바뀔 수 있는 값은 하나뿐이다.

필드실제로 바뀌나왜 고정인가 / 왜 남기나판정
id: doctype아니오 doc_rule.yaml 이라는 파일 자체가 “이건 doctype 축 규칙”이라는 뜻이다(3-2). 파일 하나에 축 하나만 담기로 한 순간 이 필드는 항상 같은 값이 된다 제거

결과 — doc_rule.yaml 맨 위는 이제 conflict: all (그나마도 생략 가능) 한 줄뿐이다. 이건 cso_rule.yaml 이 애초에 axes: 블록을 쓰지 않는 것(3-2 표)과 같은 정신을 doctype 쪽까지 끝까지 민 것이다 — 안 바뀌는 값을 적으라고 하지 않는다.

3-3. 분류 실행 시 doc_rule.yaml + doc_taxonomy.yaml 두 파일을 함께 로드한다

5 업무 분류 규칙 형태

DOC_CLASSIFICATION 은 어휘만 준다. “무엇이 계약서인가”는 규칙이 있어야 한다. 기존 규칙 문법(키워드·경로·파일명)을 그대로 재사용하고, 결과가 향하는 축만 바꾼다.

5-1-1. 필드별 출처 — doc_taxonomy.yaml(DB) 참조 vs 관리자 수동 입력

doc_rule.yaml 한 규칙 블록 안에서도 필드마다 출처가 다르다. 이걸 구분하지 않으면 “DB를 다시 내보내면 이 필드도 자동으로 채워지겠지”라는 오해가 생긴다. 실제로는 한 줄뿐이다.

필드출처동기화되나비고
node: doc_taxonomy.yaml 참조 (DB 값) 예 — DC_ID 가 스냅샷에 없으면 로드 실패(T5) 이 규칙이 어떤 분류에 대한 것인지를 가리키는 유일한 링크. 4-3 참조

id: 관리자 수동 동기화 없음 규칙 자체의 이름표. DB에는 없는 값 — 관리자가 임의로 붙인다

filename: 이 “DB 참고”처럼 보이는 이유와, 실제로는 아닌 이유
doc_taxonomy.yaml 의 title(예: “계약서”)이 filename: 후보와 글자가 겹치는 경우가 많다 — 그래서 헷갈리기 쉽다. 하지만 이건 실행 시 참조가 아니라, export_taxonomy.py --scaffold-doc-rule(3-2)이 골격을 만들 때 딱 한 번 title 을 filename: 의 첫 제안값으로 복사해 주는 것뿐이다. 그 뒤로는 doc_rule.yaml 안의 평범한 텍스트일 뿐, doc_taxonomy.yaml 이 갱신돼도 따라 바뀌지 않는다 — title 이 “계약서”에서 “계약서(용역)”으로 바뀌어도 이미 써 놓은 filename: 은 그대로다. terms:·exclude:·paths: 는 이런 제안조차 없다 — 처음부터 사람이 채운다.
한 줄 요약 — doc_rule.yaml 에서 DB(doc_taxonomy.yaml)를 진짜로 참조하는 필드는 node: 딱 하나뿐이다 (3-2-1 로 axis.taxonomy: 마저 없앴다). 나머지(weight·terms·exclude·filename·paths· conflict)는 전부 관리자가 채우는 영역이고, filename 조차 최초 제안값만 DB를 베낄 뿐 이후로는 독립적인 텍스트다. 이래서 3-2에서 “doc_taxonomy.yaml 을 다시 내보내도 doc_rule.yaml 의 사람 입력을 건드리지 않는다”고 단정할 수 있었다.

5-2. 신뢰도와 계층 — 깊은 노드가 이긴다

한 문서가 설계문서(중분류)와 요구사항정의서(소분류)에 동시에 걸리는 일은 흔하다. 이건 “충돌”이 아니라 같은 가지의 조상-자손이다.

규칙 — 조상은 자손에 흡수된다. 요구사항정의서가 걸리면 설계문서·기술/개발은 이미 경로에 들어 있으므로 별도 라벨로 내지 않는다. 결과가 중복되지 않고, 상위 집계는 path_ids 로 언제든 가능하다.
서로 다른 가지끼리 걸린 경우(계약서 + 제안서)만 진짜 충돌이며, 그때 6장의 전략이 작동한다.

“여러 신호가 충돌하면 어떻게 할 것인가”를 축마다 다르게 정한다. 지금은 max(더 위험한 쪽) 하나만 코드에 박혀 있어, 서열이 없는 축을 다룰 수 없다.

all — 해당하는 모든 라벨 doctype 기본

임계값(min_confidence)을 넘은 후보를 전부 낸다. 신뢰도 내림차순 정렬. “보고서인지 계약서인지 혹은 둘 다인지”에 답하는 것이 목적이므로, 개수를 줄이지 않는 것이 기본이다.

저장과 표시를 나눈다(Q2 후보 제안) — 결과 파일에는 all 로 전부 저장하고, 검토 화면에는 상위 3~5개만 보여 준다. 데이터를 버리지 않으면서 사람이 볼 것은 줄인다. top_n 을 쓰면 저장 단계에서 잘리므로 되돌릴 수 없다 — 화면을 정리하려는 목적이라면 top_n 이 아니라 표시 제한을 쓴다.
후보: 계약서(0.85) · 제안서(0.70)
결과: {"values": [
         {"dc_id":"DC0061","path":"법무/규정 > 계약서",   "confidence":0.85},
         {"dc_id":"DC0031","path":"영업/마케팅 > 제안서", "confidence":0.70}]}

top_n — 상위 N개 all 의 안전밸브

all 과 같되 개수를 자른다. 규칙이 아직 거칠어 문서 하나에 분류가 8개씩 붙는 초기 단계에서만 쓴다. 규칙이 정밀해지면 all 로 되돌린다.

conflict: {strategy: top_n, n: 3, min_confidence: 0.6}
잘라낸 것은 반드시 알린다. 후보가 7개인데 3개만 냈다면 "truncated": 4 를 함께 낸다. 조용히 자르면 “전부 나온 결과”로 오해된다 — “둘 다인지 확인”이라는 목적 자체가 무너진다.

6-4. 실행 모드 — 어느 측면으로 돌릴 것인가

7-1. 레코드

[2026-09-10 개정] labels 껍데기를 없애고 두 축을 최상위로 올렸다. 아래 원안은 '축을 한 상자에 모은다'는 뜻은 맞았지만, 실제 구현에서는 하위호환을 위해 같은 값을 최상위에도 한 벌 더 두게 됐다(grade·confidence· method·decided_by·seed_eligible). 두 벌이 되면 한쪽만 갱신되는 사고가 가능해진다 — 실제로 전파는 한동안 labels.security 만 다시 만들었다. 지금은 축마다 한 벌만 둔다. 
{
  "file": …, "hash": …, "doc_id": …, "doc_id_source": …,
  "security": { "grade", "confidence", "method", "decided_by",
                "seed_eligible", "signals": {…} },       ← cardinality: 1
  "doctype":  { "values": […], "strategy", "status",
                "truncated", "conflicts", "embed"? },    ← cardinality: n
  "meta":     { "rule_version", "doctype_rule_version",
                "taxonomy_version", "ts" }
}
바뀐 것 셋. ① value → grade(최상위에서 쓰던 이름을 그대로 쓴다). ② strategy 제거 — 등급 축은 늘 max 고정이라 문서마다 적어도 새 정보가 없다. ③ candidates 제거 — signals 에서 '등급이 있는 것만' 추리면 같은 값이라 두 번 적던 것이다(감사 목적은 signals 가 그대로 수행한다). 또 최상위 doctype(dc_id 목록)은 values 에서 기계적으로 나오는 세 번째 사본이라 없앴고, 근거는 각자 자기 축 안으로 옮겼다(security.signals / doctype.embed) — 예전에는 등급 신호와 doctype_embed 가 같은 상자에 섞여 있어 축이 둘이라는 사실이 레코드 모양에서 드러나지 않았다.
판정은 달라지지 않았다(실측: 변경 전 배포본과 등급·업무분류 후보가 전 건 동일). 옛 결과 파일은 그대로 읽는다 — 흡수를 csoclassify/record.py· Rust/src/record.rs 한 자리에 모아 뒀다.
--simple 은 그대로다 — 받는 쪽과의 계약이라 손대지 않았다.

아래는 개정 전 원안이다(기록용).

버전이 세 개로 늘어난 것은 파일이 세 개(3-2 + 4-1)이기 때문이다 — cso_rule.yaml(규칙·security) · doc_rule.yaml(규칙·doctype) · doc_taxonomy.yaml(어휘). 셋 중 무엇이 바뀌어서 결과가 달라졌는지 줄 하나로 구분된다.

ts — 이 레코드를 만든 시각 2026-09-07 정의
모양: ISO-8601 초 단위 + 로컬 타임존 오프셋 (2026-09-07T14:11:45+09:00). 밀리초를 붙이지 않고, UTC 라도 Z 가 아니라 +00:00 으로 쓴다.
언제: 레코드를 조립하는 시점마다 새로 찍는다 — 한 실행 안에서도 줄마다 값이 다를 수 있다(같은 실행을 묶는 것은 ts 가 아니라 위의 세 버전 필드다).
어디에: 정상 판정·추출 실패·보류·압축 집계(7-1b) 레코드까지 모든 줄에 있다. 한쪽에만 시각이 있으면 같은 실행의 레코드끼리 모양이 갈린다.

왜 UTC 가 아니라 로컬인가 — 사람이 "언제 분류했나"를 보는 값이고, 오프셋이 붙어 있어 시점 비교에도 애매함이 없다. 저장·비교가 목적인 필드가 아니라 감사 흔적이다.
두 판이 같은 값을 낸다 — 파이썬 classify.engine.now_iso(), Rust main.rs::now_iso(). Rust 판은 2026-09-07 이전까지 이 필드를 null 로 두었다 — 그때 나온 결과 파일에는 "ts": null 이 들어 있다.
candidates 를 왜 남기나 — max 로 하나를 고르는 순간 나머지 근거가 사라진다. 검토자가 “왜 C 인가”를 되짚으려면 후보 목록이 필요하다. 저장 비용은 문서당 수백 바이트다.
이 필드가 “충돌하는 신호를 모두 보고 싶다”를 충족한다 — 보안 등급 값은 max 로 하나만 내면서도, 어떤 신호가 어떤 등급을 주장했는지는 전부 남는다. 등급을 여러 개 낼 필요가 없다.

7-1b. 압축파일 '자체' 레코드 — 업무분류는 분포로 싣는다 2026-09-07 추가

압축파일을 넣으면 내부 문서가 각각 분류되고(그 레코드는 7-1 과 완전히 같다), 압축파일 자체에는 집계 레코드 한 건이 뒤에 붙는다. 이 레코드에서 두 축은 다르게 다뤄야 한다.

{
  "file": "D:/자료/2026계약.zip",
  "archive": true,
  "method": "archive_rollup",
  "decided_by": ["archive"],
  "grade": "C",                      ← 보안등급: 내부 최고 위험 하나
  "contains":         {"total":4, "C":1, "S":2, "O":1, "unclassified":0},
  "contains_doctype": {"DC_001_001":2, "DC_003_002":1, "unclassified":1},
                                     ↑ 업무분류: 대표를 고르지 않고 분포
  "ts": "2026-09-07T14:11:49+09:00"  ← 집계 레코드에도 똑같이 붙는다
}
왜 한쪽은 값 하나이고 다른 쪽은 분포인가
보안등급은 C > S > O 서열이 있다. 그래서 '가장 높은 위험'이 자명한 롤업이 된다 — 평균이나 다수결을 쓰면 C 문서 1건이 O 문서 99건에 묻히는데, 거버넌스에서 문제는 정확히 그 1건이다(6장 충돌 해소의 max 와 같은 정신).

업무분류는 서열이 없고, 7-1 에서 보듯 cardinality: n — 한 문서가 여러 라벨을 갖는다. '계약서 3건 + 보고서 5건이 든 압축'의 업무분류가 무엇인지에는 자명한 답이 없다. 대표를 하나 고르면 반드시 무언가를 버린다. 그래서 고르지 않고 건수를 그대로 보여준다 — 화면은 그것으로 "이 압축엔 계약서와 보고서가 섞여 있다"를 바로 말할 수 있다.
규칙내용이유
세는 값dc_id (경로 제목이 아니라) 제목은 분류체계를 다시 내보내면 바뀔 수 있다. dc_id 는 그 분류의 이름표라 바뀌지 않는다
다중 라벨라벨마다 각각 센다 한 문서가 라벨 2개면 둘 다 세므로, 분포의 합계가 contains.total 보다 클 수 있다
라벨 없음"unclassified" 로 따로 센다 축은 돌았는데 못 맞힌 것도 사실이다 — 감추면 분포가 실제보다 좋아 보인다
축 미사용키 자체를 넣지 않는다 7-1 의 labels.doctype · --simple 의 doctype 과 같은 규칙 — "분류 못 함"과 "축을 안 씀"은 다른 상태다

구현: cli._archive_record() · cli._collect_archive_doctype(), Rust main.rs::archive_record(). 두 판이 같은 값을 낸다(실측 대조 완료). 압축 확장 자체와 해제 상한은 문서 크기 상한 설계서 의 G4 를 본다.

7-5-1. 형식 — VARCHAR(40)

DC_ID 가 VARCHAR(40) 이므로 doc_id 도 같은 폭으로 맞춘다. 매핑 테이블에서 두 컬럼이 나란히 놓일 것이고, 집 스타일을 따르는 편이 낫다. 이 제약이 형식을 결정한다.

후보길이판정
SHA-256 hex 전체64자불가 — 40 을 넘는다
SHA-1 hex정확히 40자 비권장 — 충돌 내성이 약하다. 지금은 문제없어도 굳이 고를 이유가 없다
SHA-256 앞 40 hex 자40자 (160비트) 채택 — 이미 계산하는 값을 자르기만 하면 된다. 충돌 확률은 1억 문서 기준 약 10⁻³³ 로 사실상 0

SHA-256 은 이미 구현돼 있다 — cli.py:354 _file_hash() · Rust/src/main.rs:149. 지금은 --hash/--simple 일 때만 계산하지만, 추출 단계에서 파일을 어차피 전부 읽으므로 항상 계산해도 추가 I/O 가 없다.

위 표는 폴백(②·③)에만 해당한다. 기본값은 sfile_id 이고, 그 값의 형식·길이는 MpowerV11 이 정한다. VARCHAR(40) 에 들어가는지 확인이 필요하다 → Q6. 40자를 넘으면 매핑 테이블의 DOC_ID 폭을 sfile_id 에 맞춰 넓히면 된다 — ID 를 자르는 선택은 하지 않는다(자르면 충돌이 생기고, 원래 시스템과 대조도 못 한다).

대소문자는 OS 에 걸려 있다. Windows 는 경로 대소문자를 구분하지 않고 Linux 는 구분한다. 정규화 규칙을 OS 별로 다르게 하면 같은 결과 파일이 OS 를 옮길 때 다르게 해석된다. 그래서 정규화는 대소문자를 보존하되(리눅스 기준), 매칭 실패 시 ③으로 한 번 더 시도하고 그 사실을 기록한다. 조용히 같게 취급하지 않는다. 지금 저장소의 4건이 정확히 ③으로 구제된다.

7-5-5. 추후 매핑 테이블 (제안 — 지금 만들지 않는다)

doc_id 를 지금 심어 두면 나중에 이런 테이블에 그대로 들어간다. 기존 DOC_CLASSIFICATION 의 스타일(VARCHAR(40) 키 · CHAR(14) 일시 · CHAR(1) 상태)을 따랐다.

-- 문서 ↔ 분류 체계 매핑 (추후)
CREATE TABLE Mpower10U.DOC_CLASSIFICATION_MAP (
    -- 문서 식별자 = MpowerV11 sfile_id
    --   폭은 sfile_id 실제 형식에 맞춘다(Q6). 40 을 넘으면 넓힌다 — 자르지 않는다.
    DOC_ID        VARCHAR(40)   NOT NULL,
    -- 분류 체계 아이디 (DOC_CLASSIFICATION.DC_ID)
    DC_ID         VARCHAR(40)   NOT NULL,
    -- 신뢰도 0.000~1.000
    CONFIDENCE    DECIMAL(4,3)  DEFAULT NULL,
    -- 어떤 신호가 정했는지 (rule,name,path …)
    DECIDED_BY    VARCHAR(100)  DEFAULT NULL,
    -- 판정 출처 (A:자동, M:사람확정)
    SOURCE        CHAR(1)       DEFAULT 'A',
    -- 등록일시 (YYYYMMDDHH24MISS)
    REG_DATE      CHAR(14)      NOT NULL,
    -- 사용여부 (1:사용, 0:미사용)
    STATUS        CHAR(1)       DEFAULT '1',
    PRIMARY KEY (DOC_ID, DC_ID)
) ENGINE=InnoDB
DEFAULT CHARSET=utf8mb4;

CREATE INDEX IX_DOC_CLASSIFICATION_MAP_01 ON Mpower10U.DOC_CLASSIFICATION_MAP (DC_ID);
복합 PK (DOC_ID, DC_ID) 가 다중 라벨을 자연스럽게 받는다. “계약서이면서 제안서”는 두 행이 된다. 6장의 all 전략과 정확히 맞물린다 — 1:1 컬럼이었다면 하나를 버려야 했을 것이다.
역인덱스 (DC_ID) 는 “계약서인 문서 전부” 조회용이다.

그 이상 · 동시 접근 필요저장 방식 재검토(SQLite 등). 이 설계의 범위 밖이며, 그때 결정을 다시 하면 된다 — 지금 미리 만들 이유는 없다

Q2. 업무 분류를 자동으로 매길 것인가, 사람이 고르는 것을 보조만 할 것인가? → 결정됨 (2026-08-24) — 후보 제안

설계 반영 — 7-4-1(제안/확정 상태 · 확정 기록 형태) · 6-3(저장은 all, 화면은 상위 N) · 5-4(확정본이 전파 seed) · 로드맵 D6.

  • 업무분류 결과는 status: proposed 로 나오고, 사람이 확정하면 confirmed 가 된다. 매핑 테이블에는 확정된 것만 넣는다 — 제안을 넣으면 “분류됨”으로 오인된다.
  • 거절한 후보(rejected)도 기록한다. 규칙을 개선할 때 어떤 제안이 거절당했는지가 가장 값진 정보다.

Q3. 보안등급 축의 conflict 를 실제로 바꿀 일이 있는가? → 결정됨 (2026-08-24) — 바꾸지 않는다

확정된 내용 — 문서분류는 두 측면으로 나뉜다.

  1. 보안 측면(CSO 분류) — 보안이 중요하므로 무조건 max 정책 적용. 선택지가 아니다.
  2. 분류 측면(기업 문서분류) — 보안보다 분류체계에 따른 분류만 중요. 이 문서가 ‘보고서’인지 ‘계약서’인지 혹은 둘 다인지 확인할 수 있으면 된다. 보안은 차선 고려사항.

설계 반영 — 2-1(두 측면 표) · 6-2(전략은 축에서 따라 나온다, 초안 6종 → 3종) · 6-4(--axis 실행 모드, 분류 측면은 PII 검출 생략) · 8장 T2·T11(보안 축을 약하게 만들 경로를 검증으로 차단) · 7-1(candidates 로 충돌 근거는 전부 보존).

Q4. 임베딩 전파(Signal B)를 doctype 축에도 적용할 것인가? → 결정됨 (2026-08-24) — 적용한다

설계 반영 — 5-4(라벨별 독립 점수 · seed 파일 두 축 통합) · 로드맵 D7 · 리스크 R9 갱신.

  • “비슷한 문서는 같은 주제”는 임베딩이 가장 잘 하는 일이다. 보안등급보다 오히려 잘 맞는다 — 등급은 문서 안 한 줄로 갈리지만 주제는 문서 전체의 성격이라 벡터가 그대로 담는다.
  • 알고리즘은 ④ 가중 다수결만 바꾼다. “1등을 뽑는” 대신 라벨별 점수를 각각 계산해 임계값을 넘는 것을 전부 채택한다. ①최근접 ②사본상속 ③너무멂 은 그대로다.
