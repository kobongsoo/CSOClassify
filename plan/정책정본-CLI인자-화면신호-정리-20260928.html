1.CLI 인자 이름 — 두 축의 짝 맞추기 #27

무엇이 문제였나

두 축의 규칙셋 인자 이름이 짝을 이루지 못했다.

축전후
업무분류--doc-rules--doc-rules
보안등급--rules--cso-rules

어느 쪽 규칙을 주는 자리인지 매번 헷갈렸다. 이름만 바꾸면 되는 일이지만, 옛 이름을 어떻게 할지가 실제 결정이었다.

결정 — 조용히 받아 주지 않는다

처음에는 프로젝트의 기존 관례(--save-text → --textsave)를 따라 옛 이름도 받되 안내만 내도록 했다. 그러나 그 관례 자체가 문제였다 — 받아 주면 아무도 옮기지 않고, 두 이름이 같은 자리를 가리키는 상태가 굳는다. 실제로 --save-text 는 그렇게 오래 남아 있었다.

그래서 둘 다 끊었다. 다만 '모르는 인자'로 흘리지는 않는다 — 그러면 왜 안 되는지 알 수 없다. 이미 있는 폐기 옵션과 같은 길로, 없어졌다고 사실대로 답하고 무엇을 쓰면 되는지 알린다.

[MpowerClassify] --rules 는 없어졌습니다 — 보안등급 규칙셋은 --cso-rules 로 지정합니다(업무분류는 --doc-rules).
[MpowerClassify] --save-text 는 없어졌습니다 — 추출 본문을 남길 폴더는 --textsave 로 지정합니다.

  · unsupported_option(1012) · 종료코드 3
  · 두 판의 문구·코드가 같다(접두만 다름)
  · 값을 받던 옵션이라 값 없이 줘도 '값이 없습니다'로 새지 않는다

곁가지 — 실제로 멎던 스크립트

인자를 끊고 나서 저장소를 훑다가 scripts/PII_검출테스트.bat 이 --rules 를 쓰고 있는 것을 찾았다. 문서가 아니라 실제로 도는 스크립트라 그대로 뒀으면 종료코드 3 으로 멎었다 #29.

이름을 바꾸면 문서만이 아니라 스크립트·배치·테스트까지 같이 훑어야 한다는 것을 다시 확인한 자리다.

2.정책 파일의 정본 — ui/policy 하나로 #37 #38 #39

세 곳에 흩어져 있었다

같은 이름의 정책 파일이 resources/policy(제품) · ui/policy(고객) · 배포 폴더 4곳에 있다. scripts/sync_policy.py 가 파일마다 '원본'을 정해 사본에 복사한다. 문제는 화면이 보는 자리가 그 어느 쪽도 아니었다는 것이다.

default_paths()  →  ui/doc_rule.yaml        (없음)
                 →  resources/policy/…      (제품 폴더로 떨어짐)
실제 고객 파일    →  ui/policy/…             (아무도 안 봄)

그래서 새로 설치한 자리에서는 화면이 고친 규칙이 제품 폴더에 쓰이고, 동기화가 ui/policy 를 원본으로 보므로 다음에 조용히 되돌아간다. 지금 쓰는 자리에서는 settings.yaml 이 올바른 경로를 덮어써서 가려져 있었다 — 그래서 오래도록 아무도 못 봤다.

고친 것 — 파일의 '주인'으로 가른다

묶음파일원본사본
고객doc_rule.yaml · doc_rule.local.yaml · class_seed.jsonl · 체계 JSON · synonyms/…local.yaml ui/policy저장소 + 배포 4곳
고객 (오늘 옮김)cso_rule.yaml ui/policy배포 4곳만
제품doc_rule_template.yaml · synonyms/ core·업종 resources/policy저장소 + 화면 + 배포 4곳
cso_rule.yaml 의 사본에서 저장소를 뺀 까닭

원본만 옮기고 사본 목록을 그대로 뒀다면 새 구멍이 생길 뻔했다 — 동기화가 고객의 cso_rule.yaml 을 저장소로 밀어 넣는다. 이 파일에는 그 회사의 기밀 키워드·제품명이 들어간다. 회사 겹 유의어(local)를 뺀 것과 같은 까닭이다. 저장소의 resources/policy/cso_rule.yaml 은 이제 새 고객이 복사해 가는 기본값이고 동기화 대상이 아니다.

대가 — 제품 기본값이 안 내려간다

방향을 뒤집은 대가로, 제품 기본값을 개선해도 이미 나간 고객 폴더에는 내려가지 않는다. 자동 병합 도구는 두지 않기로 했다 — 드물게 바뀌는 데다, 자동으로 덮으면 고객이 고친 것을 다시 잃는다(방향을 뒤집은 까닭이 바로 그것이었다). 바뀌었을 때는 릴리스 노트 → 고객별로 골라 옮기기 → --check-rules → version 상향 → sync_policy --apply 로 손수 처리한다.

업무분류는 이 문제가 없다 — doc_rule.yaml 은 생성물이라 다시 만들면 제품 사전의 개선이 들어오고, 고객 결정은 doc_rule.local.yaml 에 따로 있어 살아남는다. 보안등급도 언젠가 같은 구조로 갈지 판단할 때 이 대비가 근거가 된다.

3.화면이 엔진을 못 따라온 자리 #35 #36

오늘 찾은 것 중 가장 무거운 것

엔진이 내는 보안등급 신호는 rule · sensitive · stamp · name(+embed)인데, 검토 화면의 '왜 이렇게 판단했나' 패널은 rule · path · name · embed 만 읽고 있었다. path 는 2026-09-08 에 걷어낸 신호다(설계: 보안등급-신호정리-paths제거).

· 대외비 문서 — grade C · confidence 0.95 · decided_by ["rule","stamp"]
  화면이 적은 것: 기밀 표식 1회(rule) + "이 폴더에 대한 규칙이 없습니다"(죽은 줄)
  → 0.95 를 만든 stamp 를 한 마디도 못 했다

· 건강정보 문서 — grade C · decided_by ["sensitive"]
  화면이 적은 것: "개인정보·키워드가 발견되지 않았습니다" 한 줄
  → 등급이 C 인데 근거가 하나도 없다
감사 도구에서 "왜 C 인가"를 못 적는 것은 기능이 없는 것보다 나쁘다

화면이 조용히 그려지므로 아무도 고장으로 인식하지 않는다. 검토자는 근거가 없는 것을 '근거가 없는 문서'로 읽지, '화면이 못 읽는 신호'로 읽지 않는다.

고친 것

  • 패널에 sensitive·stamp 블록 추가, 죽은 path 줄 제거
  • 히트가 없으면 줄을 내지 않는다 — 엔진은 걸린 신호만 싣기 때문에 '없음'과 '안 봤음'을 구분할 수 없고, 빈 줄이 모든 카드에 붙으면 정작 근거가 묻힌다(방금 걷어낸 그 문제가 된다)
  • 이름표에 sensitive("민감정보")·stamp("보안 표식") 추가
  • 규칙설정 확신값 표가 ("regex","keyword","path") 로 박혀 있어 없어진 path 는 빈 줄로 뜨고 sensitive·stamp 는 안 보였다 — 지금 규칙 파일에 맞췄다
  • 데모 생성기가 path 레코드를 만들고 있었다. 그대로 뒀으면 데모 카드 두 장이 근거 없는 카드가 된다 — 민감정보·스탬프 예로 바꿨다
  • 업무분류 쪽의 죽은 갈래(form·structure·path)도 함께 걷어냈다
이제 이름표에 남은 것은 엔진이 실제로 내는 신호뿐이다 — 보안등급 rule·sensitive·stamp·name·embed · 업무분류 title·head·body·name_head · 사람 manual.

4.안내문의 화면 번호 — ③ → ② #32

실제 설정 화면은 1️⃣ 회사 분류 체계 / 2️⃣ 판단 기준 / 3️⃣ 분류 실행 인데, 여러 안내문이 "설정 ③ 판단 기준" 이라고 적고 있었다. ③ 은 분류 실행이라 엉뚱한 데를 가리킨다. 같은 폴더 안에서도 docbuild.py 는 ②, docvocab.py 는 ③ 이었다 — 화면이 한 번 재번호된 뒤 일부만 안 고쳐진 것으로 보인다.

38군데 · 29파일을 고쳤다. --suggest-terms 마지막 줄(두 판), 유의어 사전·보안등급 규칙 머리글, 저장소·화면·배포 폴더의 정책 사본 전부. plan/ 과 작업기록은 날짜가 박힌 기록이라 뺐다.

주석 한 줄이 규칙 재생성을 불렀다 — 유의어 머리글이 바뀌면 규칙 생성 입력의 지문이 달라진다. 그대로 두면 "입력이 바뀌었습니다" 경고가 뜨므로 규칙을 다시 만들고 사본에 전파했다.
doc_rule.yaml doctype-gen-bd1dd3bcd1f6 → doctype-gen-26fcb558a6ea(7곳) · policy01 4aaae0aa131b → c20cf160a67b. 규칙 내용은 그대로다 — 바뀐 것은 주석 한 줄과 그 지문뿐이다.
