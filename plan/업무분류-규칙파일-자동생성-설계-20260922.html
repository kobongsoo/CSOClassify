업무분류 규칙 파일(doc_rule.yaml) 자동 생성 설계

분류체계가 바뀔 때마다 doc_rule.yaml 을 통째로 새로 만든다. 사람은 규칙 파일을 고치지 않고, 회사마다 다른 조정은 local 겹에만 적는다. doc_taxonomy.yaml 은 없애고, 규칙마다 제 분류의 제목·경로만 적는다. 2026-09-22 설계 · 구현 없음

2026-09-22 수정 — 새 규칙 파일에 taxonomy: 칸(출처·내보낸 시각·노드 목록)을 두지 않는다. 분류체계 정보는 각 규칙 줄 안에 title·path·path_ids 로만 적는다(9장). 옛 분류체계 파일의 흔적을 규칙 파일에 남기지 않기 위해서다. 같은 날 3장 ①의 P2 되돌아감은 바로잡았다(15장 0번).

2지금 구조

엠파워 관리화면 ─ 내보내기 ─▶ doc_classification_export.json │ CLI ① --export-taxonomy ▼ doc_taxonomy.yaml ──────────────┐ │ │ CLI ② --sync-doc-rule (+ 사전 3겹) │ (판정할 때마다) ▼ │ 핵어 계산 doc_rule.yaml ◀── 사람이 화면에서 고침 │ │ ▼ ▼ 엔진(분류) ◀── 사전 3겹 ◀──────────┘
  • CLI ② 는 규칙이 없는 분류에만 새 규칙을 만들고, 말이 들어 있는 규칙은 건드리지 않는다. "빠진 유의어 더하기"(--sync-enrich)를 켜면 빠진 말만 덧붙인다. 지우는 일은 없다.
  • 그래서 doc_rule.yaml 에는 자동으로 들어간 말과 사람이 고친 것이 한데 섞인다. 어느 것이 어느 쪽인지 파일만 보고는 모른다.
  • local 사전에는 이미 회사별 말을 적는 칸이 있다 — aliases(같은 뜻 다른 말) · filename_only(파일 이름에서만) · excludes(제외어) · extra_terms(칸별 추가 단어). 이 설계는 그 방향을 끝까지 밀고 가는 것이다.

3무엇이 문제인가 — 실례 셋

① 사람이 비운 칸이 되살아났다 2026-09-22 확인

2026-09-21 에 자사 제품 분류(DC_007) 규칙의 앞부분(head_terms)·본문(terms) 칸을 비웠다(P2 — 제품 이름을 "언급만 한" 구입의뢰서·사업계획서에 붙던 오라벨을 걷어냄, 설계서 13-8). 그런데 지금 규칙 파일은 이렇다.

사본수정 시각head_termsterms
Rust/resources/policy09-21 09:550 (P2 그대로)0
ui/policy (고객 원본)09-21 14:091010
배포 폴더 4곳09-21 14:091010

P2 판에 [분류 불러오기] + "빠진 유의어 더하기"를 다시 돌리면 두 칸이 정확히 10개씩 다시 채워진다(재현 확인). 덧붙이기가 일부러 비운 칸을 "빠진 말"로 알아본 것이다. 지금 배포본은 13-8·13-10 에서 잰 성적과 다른 규칙으로 돌고 있다.

규칙 파일 한 곳에 "자동값"과 "사람의 결정"을 섞어 두면, 자동 도구는 사람의 결정을 알아볼 수 없다. 이 설계의 가장 큰 이유다.

② 사전을 고쳐도 규칙 파일은 따라오지 않는다

core 사전에서 '보도자료'를 보고서의 별칭에서 뺐지만(2026-09-18), 고객 규칙 파일에는 그대로 남아 있다. 규칙 파일은 예전에 불러오기를 할 때 사전 말을 적어 넣은 것이라 사전과 연결이 끊겨 있다.

③ 분류 이름이 바뀌면 옛 말이 남는다

"매뉴얼"을 "업무지침서"로 바꿔도 규칙에는 매뉴얼 계열 말이 그대로 있다. 화면이 "제목이 바뀌었습니다"라고 알리기는 하지만(7장 ③), 옛 말을 지우는 것은 사람이 하나씩 해야 한다.

4목표와 하지 않는 것

목표

  1. 규칙 파일은 결과물 — 체계 JSON·사전·local 로 언제든 똑같이 다시 만들 수 있다. 두 엔진(Python·Rust)이 만든 결과가 글자까지 같다.
  2. 회사별 조정은 한 곳 — local 겹만 보면 "이 회사에서 제품 기본값과 다르게 한 것"이 전부 보인다.
  3. 엔진은 파일 하나만 읽는다 — doc_rule.yaml. 분류체계·사전은 만들 때만 쓴다.
  4. 옮긴 뒤 판정이 같다 — 평가셋 500건에서 옮기기 전과 판정이 한 건도 달라지지 않아야 넘어간다(P2 처럼 되돌아간 것은 먼저 바로잡는다 — 13장).

하지 않는 것

  • 판정 방식(점수 계산·문턱값·신호)은 바꾸지 않는다. 규칙이 어디서 오느냐만 바꾼다.
  • 보안등급 규칙(cso_rule.yaml)은 이번 범위가 아니다.
  • 엠파워 쪽 내보내기 형식(doc_classification_export.json)은 그대로 쓴다.

5제안 구조

엠파워 관리화면 ─ 내보내기 ─▶ doc_classification_export.json ─┐ │ 제품(저장소) synonyms/doc_synonyms.core.yaml ───────────────────┤ synonyms/doc_synonyms.<업종>.yaml ─────────────────┤ doc_rule_template.yaml (기본 설정값) ───────────────┤ │ CLI ② --build-doc-rule 고객(local) synonyms/doc_synonyms.local.yaml (말) ────────────┤ (분류체계가 바뀌거나 doc_rule.local.yaml (조정·설정) ─────┤ 입력 중 하나라도 바뀌면) ▼ doc_rule.yaml (자동 생성 · 사람이 고치지 않음) │ · 규칙마다 제 분류의 제목·경로(path·path_ids) │ · 분류별 규칙 · 핵어 · 잡음 꼬리 │ · 만들 때 쓴 입력의 지문 ▼ 엔진(분류) — 이 파일 하나만 읽는다
  • CLI ① (--export-taxonomy)과 doc_taxonomy.yaml 은 없어진다. CLI ② 가 체계 JSON 을 바로 읽는다.
  • 엠파워 연동의 "준비" 단계가 두 번 호출에서 한 번으로 준다.

6파일마다 누가 고치나

파일누가 고치나저장소배포 때담는 것
doc_classification_export.json엠파워(내보내기)아니오고객 것 유지분류 노드·제목·부모·사용 여부
doc_synonyms.core.yaml제품팀만예덮어씀업종 무관 유의어·꼬리말·머리말·핵어 판정 목록

doc_synonyms.local.yaml고객 관리자아니오고객 것 유지회사 말 — "이 말은 이 분류 이름과 같은 뜻"
doc_rule.local.yaml 새 파일고객 관리자아니오고객 것 유지분류별 조정(말 더하기·빼기·칸 비우기·가중치·끄기)과 전체 설정 덮어쓰기
doc_rule.yaml아무도 — 만들어짐아니오다시 만듦엔진이 읽는 전부
core 는 고객 사정으로 고치지 않는다. core 는 모든 고객이 함께 쓰는 한 벌이라 한 고객 때문에 고치면 다른 고객 판정도 바뀐다. 또 다음 배포 때 덮어써진다. 2026-09-14 에 '고객·인증·휴가·계약' 단독어를 core 에서 뺀 것은 "어느 고객에게나 너무 넓은 말"이라서 맞는 결정이었지만, 앞으로 한 고객에게만 맞는 조정은 doc_rule.local.yaml 의 빼기로 한다.

local 을 두 파일로 나누는 이유

사용자 제안은 "고객 조정을 local 사전에 모은다"였다. 말 목록은 그대로 사전에 두되, 말이 아닌 것은 작은 파일 하나로 뗀다.

  • 사전은 분류 이름을 열쇠로 쓴다("보고서"라는 이름에는 이런 말들이 같은 뜻). 이름이 바뀌면 따라서 바뀌는 게 맞다.
  • 조정은 그 분류(dc_id)에 대한 결정이다("DC_007 은 본문을 보지 마라"). 이름이 바뀌어도 살아 있어야 한다 — 10장.
  • 가중치·문턱값·2차 분류 설정은 말이 아니라 사전 모양(이름 → 말 목록)에 맞지 않는다.

한 파일로 합치고 싶다면 local 사전에 rules:·settings: 칸을 두는 안도 된다(16장 결정 ①). 원칙 — "고객이 고치는 곳은 local" — 은 어느 쪽이든 같다.

doc_rule.local.yaml 모양(안)

# 회사별 업무분류 조정 — 이 파일만 사람이 고친다. doc_rule.yaml 은 여기서 만들어진다.
version: 2026.09.22
industry: [finance]            # 얹을 업종 사전(없으면 core 만)

settings:                      # 적은 것만 본보기 기본값을 덮는다
  defaults: {t_low: 0.35}
  embed: {enabled: true}

rules:                         # 열쇠는 dc_id — 분류 이름이 바뀌어도 조정이 살아 있다
  DC_007:                      # 자사 제품
    title_at_decision: 엠파워제품    # 적을 당시 이름(바뀌면 만들 때 안내 — 10장)
    clear: [head_terms, terms]       # P2 — 제품명 '언급'만으로 붙지 않게
    why: "2026-09-21 P2 · 평가셋 오라벨 14건 제거(설계서 13-8)"
  DC_002_002:                  # 매뉴얼
    add:
      title_terms: [도움말]
    why: "제품 도움말 html 118건 — 사람 전수 판정 매뉴얼"
  DC_001_003:                  # 보고서
    add:
      title_terms: [현황분석, 참관, 실태조사, 이슈페이퍼, 동향]
      head_terms:  [현황분석, 참관, 실태조사, 이슈페이퍼]
    remove:
      title_terms: [보도시점]
  DC_004_009:                  # (예시 — 설명용 dc_id)
    enabled: false             # 이 회사는 쓰지 않는 분류
    weight: low

head:                          # 핵어(파일 이름 끝자리) 조정
  title_exclude: [결과서]        # (예시)
  node_off: []
  • why 칸을 둔다. 규칙 파일이 자동 생성이 되면, "왜 이렇게 했나"를 적을 자리는 여기뿐이다. 지금 규칙 파일은 화면이 저장할 때마다 주석이 날아간다.
  • add·remove·clear 는 자동값 위에 적용된다. 그래서 사전이 좋아지면 그 덕은 그대로 받고, 사람의 결정만 덧씌운다.
  • 지금 local 사전의 extra_terms(이름 열쇠)는 이 파일의 add(dc_id 열쇠)로 옮긴다 — 13장.

8만드는 순서(생성 규칙)

  1. 노드 읽기 — 체계 JSON 에서 dc_id·부모·제목·순서·사용 여부를 읽고 경로를 만든다. 서랍(자식이 있는 뿌리)과 꺼 둔 분류는 지금과 같은 기준(syncable_nodes)으로 규칙을 만들지 않는다.
  2. 사전 합치기 — core → 업종(industry) → local 사전 순으로 겹친다(지금 load_synonyms 그대로).
  3. 분류별 기본 말 — 잎마다 제목에서 네 칸(제목·앞부분·본문·파일 이름)과 제외어를 만든다(지금 rule_vocab 그대로).
  4. 조정 덧씌우기 — doc_rule.local.yaml 의 rules.<dc_id> 를 clear → remove → add 순으로 적용한다. clear 한 칸에도 add 는 들어간다(비운 뒤 사람이 고른 말만 두는 경우).
  5. 핵어 — 지금 판정기(taxhead.build_head_lexicon)를 그대로 돌리고 head.title_exclude·node_off 를 적용해 분류별 핵어 목록을 적는다. 잡음 꼬리 목록도 함께 적는다.
  6. 설정 — 본보기 기본값 위에 settings 를 덮는다.
  7. 검사 — 만든 파일을 엔진 로더로 다시 읽어 검증한다(지금 T·V 검증 그대로). 아래를 경고로 알린다.
    • local 조정의 dc_id 가 체계에 없다(분류가 지워졌거나 잘못 적음)
    • title_at_decision 과 지금 제목이 다르다(이름이 바뀜 — 10장)
    • remove 하려는 말이 애초에 없다(사전이 바뀌어 이미 빠짐 — 지워도 되는 조정)
  8. 쓰기 — 맨 위에 "자동 생성 — 고치지 마세요"와 입력 지문을 적고, 정해진 순서로 쓴다(dc_id 순·칸 순). 입력이 같으면 결과가 글자까지 같아야 한다.
3·5단계는 지금 있는 함수를 그대로 쓴다. 새로 만드는 것은 4단계(덧씌우기)·7단계 일부·8단계의 머리말과 지문뿐이다.

12화면 변경

  • 업무분류 규칙 화면 — 지금은 doc_rule.yaml 을 직접 고친다. 바뀐 뒤에는 표의 각 칸이 "자동 말 + local 조정"으로 보이고, 고치면 doc_rule.local.yaml 의 add/remove/clear 로 저장된다. 저장 뒤 규칙을 다시 만든다.
  • [분류 불러오기] → [규칙 다시 만들기] — 누르면 새로 만들 규칙과 지금 규칙의 차이(분류별로 더해질 말·빠질 말)를 먼저 보여 주고, 확인하면 쓴다.
  • 핵어 표(설정 ③ › 업무분류) — 끄기 체크가 doc_rule.local.yaml 의 head: 에 저장된다.
  • 규칙 단어 제안 — 채택한 말이 doc_rule.local.yaml 의 add 로 들어간다(지금은 local 사전의 extra_terms).
  • "제목 확인" 칸 — 규칙 쪽에서는 없어지고, local 조정의 title_at_decision 이 다를 때 안내하는 것으로 바뀐다.

13옮겨 가기(마이그레이션)

지금 고객 규칙 파일에는 사람이 한 조정이 자동값 속에 섞여 있다. 그냥 새로 만들면 그 조정이 전부 사라진다. 아래 순서로 옮긴다.

  1. 기준 규칙부터 정한다 — P2 가 되돌아간 지금 판(ui/policy)과 P2 판(Rust/resources/policy) 중 무엇이 맞는지 먼저 정한다. 13-8·13-10 성적은 P2 판으로 잰 것이다.
  2. 차이 뽑기 도구 — "지금 입력으로 자동 생성한 규칙"과 "기준 규칙"을 분류·칸별로 견줘, 차이를 doc_rule.local.yaml 초안(add·remove·clear·weight)으로 뽑는다. local 사전의 extra_terms 도 dc_id 열쇠로 바꿔 함께 옮긴다.
  3. 사람 확인 — 초안의 각 줄에 이유(why)를 적는다. 이유를 댈 수 없는 차이(예전에 사전에 있다가 빠진 말이 규칙에 남은 것 — '보도자료')는 옮기지 않는다.
  4. 다시 만들어 견주기 — 새 구조로 만든 규칙으로 평가셋 500건을 두 엔진에서 돌려, 기준 규칙과 판정을 견준다. 달라진 문서는 모두 설명할 수 있어야 한다(3단계에서 일부러 버린 말 때문인 것만 허용).
  5. 배포 사본 맞추기 — scripts/sync_policy.py 목록에서 doc_taxonomy.yaml(과 체계 JSON 사본)을 빼고 doc_rule.local.yaml 을 고객 파일로 더한다.
