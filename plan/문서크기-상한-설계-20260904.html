문서 크기 상한(Size Gate) 설계

MpowerClassify 에는 문서 크기 상한이 없었다. 초대형 문서에서 시간·메모리·IPC 세 방향으로 무너지는 것을 막는 5중 게이트 설계이며, G1~G5 전부 구현되었다. 구현 완료 · 2026-09-04

※ 1·4장은 구현 전 상태를 기록한 것이다(왜 이 게이트가 필요했는지의 근거라 그대로 둔다). 현재 동작은 5·6·9장을 본다.

1 배경 — 현재 상한 인벤토리

코드 전수 조사 결과, 파일 크기로 걸러내거나 자르는 코드가 한 군데도 없다. 존재하는 제약은 아래가 전부이며, 대부분 크기가 아니라 시간·구조 제약이다.

제약값위치성격
SNF_TIMEOUT60초 / 1파일config.py시간 상한 (크기 아님)
MAX_MSG16MBdaemon/ipc.py:12IPC 메시지 상한
max_depth3extract/archive.py:302압축 깊이만 — 폭 방향 무방비

상한이 전혀 없는 항목 — 입력 파일 바이트 수 · 추출 텍스트 글자 수 · PDF 페이지 수 · 청크 개수 · 압축 해제 누적 용량 · 전용 파서 실행 시간

1-1. 전용 파서에는 타임아웃조차 없다

extract/hybrid.py 는 감지된 포맷의 전용 파서를 제한 없이 끝까지 돌린다. PDF 경로(extract/pdf_pdfium.py)는 for page in doc 로 전 페이지를 무제한 순회하며 페이지 텍스트를 리스트에 모두 모은다. snf 는 60초 타임아웃이 있지만 기본값이 DEFAULT_HYBRID_PARSE=True 이므로, 기본 경로에는 시간 방어가 없다.

1-2. 모든 파서가 스트림을 통째로 메모리에 올린다

office_legacy.py:73 ole.openstream("WordDocument").read() office_ooxml.py:73 z.read("word/document.xml") office_ooxml.py:153 ET.fromstring(z.read("xl/sharedStrings.xml")) hwp5.py:146 ole.openstream(e).read() plaintext.py:32 f.read() synap_exe.py:136 f.read()

스트리밍 파싱은 어디에도 없다. 원본 bytes + 추출 str + 청크 리스트 + np.vstack 행렬이 한 시점에 동시에 살아 있다. 특히 xlsx 의 sharedStrings.xml 을 ET.fromstring 으로 통째 파싱하는 경로는 원본 대비 수 배의 메모리를 쓴다.

1-3. 하이브리드는 실패 시 같은 파일을 두 번 판다

hybrid.py 는 전용 파서를 save_dir=None 으로 돌려보고, 실패하면 snf 로 재시도한다. 초대형 파일은 최악의 경우 전용 파서 풀타임 + snf 60초를 연속으로 소모한다.

2 실측 근거

2-1. 코퍼스 크기 분포 — D:\분류함 2,254 파일 / 3,749.8MB

평균p50p90p95p99최대
1.66MB0.07MB3.14MB6.15MB25.01MB328.76MB

중앙값이 70KB 인데 최대가 328MB다. 분포의 꼬리가 4,000배로 길다 — 평균 기준으로 설계하면 반드시 꼬리에서 터진다.

2-2. 결정적 반례 — 바이트 크기와 처리 비용은 비례하지 않는다

파일원본 크기페이지추출 글자수추출 시간
[지미션] 회사소개서_2603.pdf55.3MB36p343자0.5초

55MB 짜리에서 343자가 나온다. 이미지 위주 회사소개서라 텍스트층이 거의 없다. 여기에 "50MB 초과 스킵" 같은 바이트 게이트를 걸면 정상적인 36페이지 회사소개서를 통째로 놓친다.
반대로 코퍼스 최대 파일 328MB news_talk_en_ko_train.tsv 는 plaintext 라 328MB ≈ 3억 자가 그대로 PII 정규식과 임베딩으로 들어간다.

결론 — 포맷별 압축률 차이가 100배를 넘으므로 원본 바이트는 비용의 대리지표로 부정확하다. 바이트 게이트는 크래시 방지용 안전핀으로만 쓰고, 진짜 상한은 추출 후 글자수에 걸어야 한다.

2-3. 페이지 ↔ 글자수 환산 계수

445p → 380,130자 = 페이지당 약 854자. 이 계수로 상한값을 페이지로 환산해 검증한다.

2-4. 기존 발표자료 실측(375파일 / 409MB)과의 정합

  • 최악 케이스 581페이지 PDF 1건 → 7.5초 (854자/p 환산 시 약 50만 자)
  • 룰 스캔이 전체 시간의 66% — "PII 정규식이 대용량 문서 전문을 훑기 때문"
  • 평균이 중앙값보다 크게 높음 = "소수의 대용량 문서가 시간을 끈다"
  • 같은 자료의 대응 방향: "실시간은 크기 임계를 두고 초과분은 비동기 큐로 이관" → 임계값이 있어야 하는데 아직 없다가 현재 상태
추출보다 분류(룰 스캔) 단계가 크기에 더 민감하다. 그래서 게이트의 무게중심도 추출 전이 아니라 추출 후 글자수에 둔다.

3 설계 원칙

원칙 1 — 바이트 게이트는 안전핀, 글자수 게이트가 본체

2-2 의 반례 때문이다. 바이트 상한은 "명백히 문서가 아닌 것"만 걸러내는 느슨한 값으로 두고, 실제 비용 통제는 clean_text() 이후 글자수로 한다.

원칙 2 — 초과 시 스킵이 아니라 절단(truncate) 이 기본

cli.py:1573 이 이미 이 원칙을 명문화해 두었다.

"못 읽은 문서도 '결과'다 — 레코드를 안 내면 그 문서는 결과에서 통째로 사라져, 화면에는 '18개 중 11건'처럼 조용히 줄어든 숫자만 남는다. 무엇이 왜 빠졌는지 알 수 없는 것은 거버넌스 도구에서 가장 나쁜 실패다."

따라서 글자수 초과는 앞부분만 보고 등급을 내되, 레코드에 "일부만 본 판정"임을 반드시 표시한다. 사람이 그 표시를 보고 재검토할 수 있어야 한다.

원칙 3 — 기존 설정 관례를 따른다

모든 값은 config.py 에 상수로 두고, MIN_TEXT_LEN 과 동일하게 환경변수로 현장 조정이 가능해야 한다. 코드 곳곳에 숫자를 흩지 않는다.

원칙 4 — Rust 판과 값을 일치시킨다

EXIT_RULES_INVALID 를 두 구현이 같은 값 4로 맞춘 것과 같은 정신이다. 크기 게이트도 MpowerClassify-rs 와 동일 상수를 공유해야 두 구현의 결과가 갈리지 않는다.

G1 MAX_FILE_BYTES = 100 * 1024 * 1024 — 원본 바이트 안전핀

이것이 "TEXT 추출 전 원본 문서의 최대 크기"다. os.path.getsize(path) 를 어떤 파서보다 먼저 검사한다.

  • 왜 100MB인가 — 2,254건 중 초과는 2건(0.09%)이며 둘 다 문서가 아니라 학습 코퍼스 tsv다. 즉 정상 문서를 한 건도 잃지 않는 값이다.
  • 50MB는 안 된다 — 10건이 걸리는데 그중 55.3MB 회사소개서가 정상 업무문서다(2-2).
  • 20MB는 확실히 과하다 — 33건, 1.46%가 걸린다.
G1 은 비용 통제 장치가 아니다. 55MB/343자 사례가 보여주듯 바이트로는 비용을 예측할 수 없다. G1 의 역할은 "문서가 아닌 것이 파이프라인에 들어오는 것"을 막는 것뿐이다.

G2 MAX_FILE_BYTES_TEXT = 20 * 1024 * 1024 — 텍스트류 별도 상한

detect_format() 결과가 "text" 인 경우(txt/csv/tsv/json/html)에만 적용한다. 이 포맷군은 바이트 수 = 글자 수 라서 압축률 문제가 없고, 따라서 바이트 게이트가 유일하게 정확한 비용 지표가 된다.

plaintext.py:32 의 f.read() 가 전체를 메모리에 올리는 지점을 직접 막는다. 328MB tsv 는 여기서 걸린다.

G3 MAX_TEXT_CHARS = 2_000_000 — 본체 게이트

실제 비용을 지배하는 값이다. 근거 세 가지:

근거계산판정
페이지 환산854자/p → 200만 자 ≈ 2,340페이지최악 케이스(581p)의 4배 여유 — 정상 문서 절단 위험 없음
16MB IPC 벽200만 자 × 3바이트(한글 UTF-8) ≈ 6MB16MB 안에 안전 — R4 구조적 제거
룰 스캔 병목PII 정규식 대상 길이가 상한을 가짐전체 시간의 66%를 차지하던 항목이 유계가 됨
여기서는 스킵이 아니라 절단이다(원칙 2). 앞 200만 자로 자르고 등급을 내되, 레코드에 text_truncated 를 실어 "일부만 본 판정"임을 남긴다. 
text = clean_text(raw)
n_orig = len(text)
truncated = n_orig > config.MAX_TEXT_CHARS
if truncated:
    text = text[:config.MAX_TEXT_CHARS]   # 앞부분 우선 — 표지·개요·머리말에 신호가 몰린다

앞부분을 남기는 이유: 보안등급 신호(스탬프·머리말의 "대외비", 표지의 문서 종류)와 업무분류 신호가 문서 앞쪽에 집중되기 때문이다. 뒤쪽을 버려도 등급 판정 손실이 가장 작다.

G4 MAX_ARCHIVE_BYTES = 500MB / MAX_ARCHIVE_MEMBERS = 5000

현재 archive.py:302 는 max_depth=3 으로 중첩 깊이만 막고 폭 방향(해제 총량·파일 개수)은 무방비다. 깊이 1짜리 zip 하나로도 디스크를 채울 수 있다.

_extract_members() 루프에서 누적 바이트와 멤버 수를 세다가 상한을 넘으면 해제를 중단하고, 그 압축을 원본 1건으로 처리한다(기존 "빈 압축/손상 압축" 폴백 경로와 동일하게 동작).

G5 PARSER_TIMEOUT = 60 — 전용 파서 시간 상한

현재 전혀 없다. snf 는 subprocess 라 timeout= 으로 간단히 걸리지만, 전용 파서는 in-process 호출이라 구조가 다르다. 세 가지 안이 있다(11장 미결정).

안방식장점단점
APDF 페이지 수 상한(MAX_PDF_PAGES)단순 · 이식 쉬움PDF에만 적용 · 시간 보장 아님
B페이지 루프에서 경과시간 체크 후 중단진짜 시간 상한 · 부분 결과 확보포맷별로 각각 손봐야 함
C파서를 별도 프로세스로 격리완전한 격리(메모리 포함)구조 변경 큼 · 프로세스 기동 비용

권장: B + A 병행. PDF 는 페이지 루프에 시간 체크를 넣고(B), 동시에 MAX_PDF_PAGES = 3000 을 두어 이중 안전을 만든다. C 는 필요성이 확인되면 그때 간다.

7-2. 크기 초과로 스킵된 문서의 레코드 (G1·G2)

기존 _extract_failed_record() 경로를 그대로 재사용한다. 등급 없이(=보류) 사유를 실어 내보내면, 못 읽은 문서와 동일하게 사람이 처리하는 흐름에 올라탄다.

{
  "file": "...",
  "grade": null,
  "error": "크기 상한 초과: 328.8MB > 100MB (MAX_FILE_BYTES)",
  "error_kind": "size_limit",      // 신규 — 추출 실패와 구분
  ...
}
error_kind 를 나누는 이유: "파일이 깨져서 못 읽음"과 "너무 커서 안 읽음"은 운영 대응이 다르다. 후자는 상한을 올리거나 비동기 큐로 넘기면 처리 가능한 문서다.

7-2b. 게이트별 관측 수단 (2026-09-04 보강)

초기 구현의 결함 — G4·G5 는 발동해도 로그 파일 한 줄만 남겼다. 압축이 안 펼쳐지면 결과에는 압축파일 1건만 조용히 남아, 내부 문서 수백 건이 통째로 빠진 사실이 어디에도 드러나지 않았다(실측: 총 30개 → 총 1개). 원칙 2("무엇이 왜 빠졌는지 알 수 없는 것이 가장 나쁜 실패")와 정면으로 어긋난 상태였다.

모든 게이트가 요약 카운터 · 레코드 표식 · 조치 안내 세 가지를 갖도록 맞췄다.

7-3. 종료코드

기존 EXIT_EXTRACT_FAIL = 1 을 그대로 쓴다. 크기 초과는 추출 실패의 한 종류이며, 배치 스크립트 입장에서 구분이 필요하면 error_kind 로 충분하다. 새 종료코드는 만들지 않는다.

7-4. 요약 카운터

counts 옆에 n_size_skipped, n_text_truncated 를 추가해 실행 요약에 찍는다. 운영자가 "이번 배치에서 상한에 걸린 문서가 몇 건인가"를 즉시 알아야 상한값을 조정할 수 있다.
