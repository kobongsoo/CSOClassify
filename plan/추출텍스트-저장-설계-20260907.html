1 배경 — 지금은 어디까지 되나

--save-text 라는 옵션이 이미 있다. 그런데 정작 분류할 때는 아무것도 저장하지 않는다. 코드를 전수로 확인한 결과다.

실행 모드--save-text 가 먹나근거
분류(기본) — 가장 많이 쓰는 모드 안 먹는다 cli.py 가 추출기를 save_dir=None 으로 못박아 부른다. 바로 위 주석: "분류에서는 원문 텍스트를 (기본은) 디스크에 남기지 않는다(민감정보 잔존 방지)"
--text-only먹는다추출 텍스트를 그대로 출력하는 모드
--embed먹는다임베딩 경로는 opts["save_dir"] 를 그대로 넘긴다
Rust 판 전부 인자를 삼키고 아무 일도 안 한다 main.rs 인자 파싱: "--save-text" => { take(true); } — 값까지 먹고 끝. 경고도 없다
이건 그냥 "기능이 없다"가 아니라 조용한 실패다. Rust 판에 --save-text D:\파싱 을 주면 오류도 경고도 없이 정상 종료하고, 폴더는 비어 있다. 사용자는 "저장했는데 왜 없지"를 혼자 헤맨다. 이 프로젝트가 계속 지켜 온 원칙 — "무엇이 왜 빠졌는지 알 수 없는 것은 거버넌스 도구에서 가장 나쁜 실패다" — 에 정면으로 어긋난다. 이번 작업은 기능 추가이면서 이 결함의 해소이기도 하다.

지금의 파일 이름 규칙도 이대로는 못 쓴다

extract/base.py::save_extracted_text() 는 원본 파일명을 쓴다.

계약서.docx  →  계약서.txt
계약서.docx  →  계약서__2.txt   ← 다른 폴더의 동명 파일이면 이렇게 밀린다
계약서.hwp   →  계약서__3.txt   ← 확장자가 달라도 stem 이 같으면 또 밀린다

문제는 __2 가 어느 문서인지 결과 레코드만 보고는 알 수 없다는 것이다. 2,254건을 한 폴더에 쏟으면 계약서__37.txt 같은 파일이 생기는데, 그게 어느 원본인지 되짚을 방법이 없다. 저장은 됐는데 쓸 수가 없다.

2 왜 필요한가

쓰임설명
판정 근거 눈으로 확인 "이 PDF 가 왜 C 인가"를 볼 때, signals.rule.hits 만으로는 문장 앞뒤 맥락이 안 보인다. 추출 본문이 있으면 규칙이 걸린 그 문장을 직접 읽는다
추출 품질 점검 스캔본·표 중심 문서는 본문이 거의 안 나온다. 텍스트를 봐야 "추출이 부실해서 미분류"인지 "본문은 멀쩡한데 규칙이 없어서 미분류"인지 갈린다. 지금은 이 둘이 결과에서 똑같이 미분류로만 보인다
규칙 실험 규칙을 고칠 때마다 문서 2,000건을 다시 파싱하면 수십 분이 든다. 텍스트가 있으면 그것만 놓고 규칙을 돌려볼 수 있다
사고 재현 "이 문서가 왜 O 였나"를 나중에 물었을 때, 원본이 이미 지워졌어도 본문이 남아 있다

3 설계 원칙

#원칙뜻
P1분류 결과를 바꾸지 않는다 저장은 곁다리다. 저장이 되든 안 되든 grade·doctype 은 같아야 한다
P2저장 실패로 분류를 멈추지 않는다 디스크가 차거나 권한이 없어도 분류는 끝까지 간다. 대신 반드시 표식을 남긴다(9장)
P3레코드에서 파일로 갈 수 있어야 한다 결과 한 줄만 보고 그 문서의 .txt 를 바로 찾을 수 있어야 한다. 못 찾으면 저장한 의미가 없다(1장의 __37 문제)
P4기본은 꺼짐 본문에는 개인정보가 그대로 들어 있다. 명시적으로 켠 사람만 남긴다(10장)
P5두 판이 같다 파이썬·Rust 가 같은 플래그·같은 파일명·같은 색인을 낸다. 옵션을 삼키고 무시하지 않는다

4 플래그 — 이름과 형태

--textsave <폴더>      ← 요청하신 형태. 폴더는 필수

MpowerClassify.exe --dir "D:\분류함" --textsave "D:\파싱"

기존 --save-text 와의 관계 — 세 가지 길

안내용장점단점
A--textsave 를 새로 만들고 --save-text 는 그대로 둔다 기존 동작이 안 깨진다 비슷한 옵션이 둘이 된다 — 무엇을 써야 하는지 매번 헷갈린다
B
권고		 --textsave 를 정식 이름으로 하고, --save-text 는 같은 동작의 옛 이름으로 남긴다 (쓰면 "--textsave 를 쓰세요" 한 줄 안내 후 정상 동작) 옵션은 실질적으로 하나. 옛 명령줄도 그대로 돈다. 분류 모드에서도 저장되도록 고쳐지는 김에 통일된다 옛 이름의 파일명 규칙(원본명)이 hash 로 바뀐다 — 기존 스크립트가 파일명을 짚어 쓰고 있었다면 영향
C--save-text 만 고쳐 쓰고 --textsave 는 안 만든다 새 이름을 안 외워도 된다 요청하신 이름이 아니다
B 를 권합니다. 지금 --save-text 는 네 모드 중 둘에서만 동작하고 Rust 에서는 아예 무시되므로, "기존 동작"이라고 지킬 만한 것이 사실상 없다. 옵션을 둘로 늘리는 비용이 더 크다.

값을 안 주면

지금 --save-text 는 값을 생략하면 ./_extracted 로 간다. --textsave 는 폴더를 필수로 받는다 — 개인정보가 담긴 파일이 어디에 쌓이는지 모르는 채로 생기면 안 되기 때문이다. 값이 없으면 bad_args 로 즉시 종료한다(두 판 동일).

5 파일 이름 규칙 (핵심)

안파일명평가
원본명 (지금 방식)계약서.txt · 계약서__2.txt 사람은 읽기 쉽지만 충돌이 잦고, __2 가 어느 문서인지 되짚을 수 없다. 한글·공백·특수문자·긴 경로 문제도 그대로 안는다
doc_idSF20260724110933031.txt sfile_id 를 얻은 문서에만 있다. --filelist 없이 돌리면 폴백이라 결국 hash 앞 40자가 되므로, 규칙이 상황에 따라 달라진다
파일 SHA-256
권고		567b4e6e3af751a1….txt 항상 있고, 충돌이 없고, 결과 레코드의 hash 칸과 그대로 이어진다(P3). 내용이 같은 문서는 자동으로 한 파일이 된다
D:\파싱\
  ├ 567b4e6e3af751a1b7f07a82045266b6c35ca3a74273fccfd28f3725c6769e08.txt
  ├ ad5b1c65c028685998e15f285d3b5bceb157fe2a6198ef07011bebcddd1d56c9.txt
  └ _index.jsonl                ← 어느 원본인지는 여기서 본다(7장)
hash 이름이 주는 덤 세 가지
① 중복 제거 — 같은 문서가 여러 폴더에 복사돼 있으면 .txt 는 한 개만 생긴다. 실측 폴더에 99_중복파일 이 따로 있을 만큼 중복이 많다.
② 경로 길이 안전 — 이름이 64자로 고정이라 Windows 260자 제한에 걸리지 않는다. 압축 내부 문서는 표시명이 압축경로/내부경로 라 특히 길다.
③ 파일명에 정보가 안 샌다 — 2026년_홍길동_징계의결서.txt 같은 이름이 폴더 목록만으로 보이는 일이 없다.
대가 — 폴더를 열어도 사람은 무슨 파일인지 모른다. 그래서 색인 파일(7장)이 선택이 아니라 필수다.

hash 는 항상 계산되지 않는다 — 켜 줘야 한다

지금 파일 해시는 --hash 나 --simple 일 때만 계산한다 (need_hash = args.hash or simple). --textsave 를 주면 해시 계산을 강제로 켠다. 이름의 근거이기 때문이다. 문서당 비용은 파일 1회 순차 읽기라 추출 비용에 비하면 무시할 수준이다.

6 어느 단계의 텍스트를 저장하나

본문은 분류에 닿기까지 세 단계를 거친다. 무엇을 저장하느냐로 쓰임이 달라진다.

추출기 원문(raw)  →  clean_text()  →  truncate_text(G3, 기본 200만자)  →  규칙·임베딩
     ①                   ②                      ③
저장 대상얻는 것잃는 것
① 원문추출기가 실제로 뱉은 것 — 파서 품질 점검에 가장 정확 공백·제어문자 잡음이 그대로라 사람이 읽기 나쁘다
③ 정제 + 절단본
권고		 도구가 실제로 보고 판정한 바로 그 텍스트. "왜 이 등급인가"를 되짚을 때 어긋남이 없다. 규칙 재실험에도 이게 맞다 절단된 문서(text_truncated=true)는 뒷부분이 없다
③ 을 권하는 이유 — 이 옵션의 첫 번째 쓰임이 "판정 근거 확인"이다. 판정에 안 쓰인 텍스트를 보여 주면 근거가 아니라 혼란이 된다. 절단된 문서는 레코드에 이미 text_truncated 표식이 있고, 색인에도 truncated 를 넣어(7장) "여기까지만 보고 판정했다"가 드러나게 한다.

원문(①)이 필요한 경우는 파서 디버깅인데, 그건 이미 --text-only 가 담당한다.

7 색인 파일 _index.jsonl

저장 폴더에 한 줄에 한 문서로 쌓는다. 이것이 hash 이름과 원본을 잇는 유일한 다리다(P3).

{"hash":"567b4e6e…","txt":"567b4e6e….txt","file":"D:/분류함/01_제품매뉴얼/MCCS 이중화 테스트 시나리오.xlsx",
 "doc_id":"SF_20260724110933031","chars":18452,"truncated":false,"ts":"2026-09-07T15:02:11+09:00"}
칸뜻
hash파일 SHA-256 — 결과 레코드의 hash 와 같은 값
txt저장된 파일 이름(폴더 기준 상대). 규칙이 바뀌어도 여기만 보면 된다
file원본 경로. 압축 내부 문서면 압축경로/내부경로 표시명 그대로
doc_id있으면 넣는다(sfile_id 일 때만 값, 아니면 null)
chars저장한 글자 수
truncatedG3 절단본인가 — 뒤가 잘렸다는 사실을 색인만 봐도 알게 한다
ts저장 시각(레코드의 ts 와 같은 모양)
같은 문서가 여러 경로에 있으면 — .txt 는 하나지만 _index.jsonl 줄은 경로마다 하나씩 쌓는다. 중복 제거의 이득은 챙기면서, "그 본문이 어느 경로들에서 나왔는지"는 잃지 않는다.
이어붙이기(append)다. 같은 폴더에 두 번 돌리면 줄이 쌓인다. 덮어쓰지 않는 이유는, 어제 돌린 색인을 오늘 실행이 말없이 지워 버리는 것이 더 위험하기 때문이다. 새로 시작하려면 폴더를 비우면 된다.

8 레코드 · 요약 변경

레코드

{"file":"…/계약서.docx", "hash":"567b4e6e…", "doc_id":null, "grade":"C", "doctype":["DC_006_001"],
 "text_saved": "567b4e6e….txt",     ← 저장에 성공했을 때만 붙는다(폴더 기준 상대명)
 …}

칸 차례는 ④ 부속 묶음이다(seed_eligible 곁). 판정값이 아니기 때문이다. --textsave 를 안 쓴 실행에는 키 자체가 없다 — 이 프로젝트가 계속 지켜 온 "안 씀 / 못 함"을 가르는 규약과 같다.

요약(summary)

[summary] 총 311개 / … , 텍스트저장=305, 저장실패=6
[summary][텍스트 저장] 305건을 D:\파싱 에 남겼습니다(중복 12건은 한 파일로 합쳐졌습니다).
[summary][텍스트 저장 실패] 6건은 남기지 못했습니다 — 분류 결과에는 영향이 없습니다.
                            사유는 레코드의 text_save_error 를 보세요.

세는 칸을 따로 두는 이유는, 저장이 조용히 반쯤 실패하는 것을 막기 위해서다. 기존 게이트(크기·절단·압축)들과 같은 방식이다.

9 실패 처리 — 분류를 멈추지 않는다

상황동작
폴더를 만들 수 없다 (권한·경로 오류) 시작 전에 검사해 bad_args 로 즉시 종료. 2,000건을 다 돌린 뒤 "한 건도 저장 못 했다"를 알게 되면 안 된다
쓰는 중 실패 (디스크 가득·잠김) 그 문서만 건너뛰고 분류는 계속(P2). 레코드에 "text_save_error": "<사유>", 요약에 저장실패 N
본문이 없다 (추출 실패·빈 문서) 파일을 만들지 않는다. 0바이트 파일을 남기면 "저장됐다"로 오해된다. text_saved 키가 없는 것으로 구분된다
이미 같은 hash 의 파일이 있다 다시 쓰지 않는다(같은 내용이므로). text_saved 는 그대로 붙고 색인 줄만 추가된다
종료코드는 바뀌지 않는다 — 저장 실패는 분류 실패가 아니다. 자동화가 저장 실패로 파이프라인을 멈추면 P1·P2 가 무너진다.

10 프라이버시 (가장 중요)

이 옵션은 개인정보를 평문으로 디스크에 복제한다. 지금 분류 경로가 save_dir=None 을 일부러 못박아 둔 이유가 정확히 이것이다. 이 옵션은 그 방어를 사용자가 의식적으로 여는 문이며, 설계는 그 사실을 숨기지 않아야 한다.

11 경계 사례

사례동작
압축 내부 문서 내부 문서 각각 저장한다. hash 는 임시로 풀어 놓은 실제 파일의 것이라 압축을 다시 풀어도 같은 값이다. 색인의 file 은 표시명 (D:/자료/a.zip/문서.docx)
압축 집계 레코드 본문이 없다(집계일 뿐). 저장하지 않고 text_saved 키도 없다
크기 상한 초과(G1·G2) 애초에 읽지 않았으므로 저장할 것이 없다
분할 압축 조각 읽지 않는다 — 저장 없음
--text-only 와 같이 준 경우 화면으로도 내고 파일로도 남긴다(모순이 없다)
데몬 모드 저장은 추출을 실제로 한 쪽(데몬 프로세스)이 한다. 경로는 요청과 함께 넘긴다 — 데몬의 작업 폴더를 기준으로 삼으면 엉뚱한 데 쌓인다. 상대경로는 CLI 쪽에서 절대경로로 바꿔 보낸다

[정정 · 구현하며 드러남] 두 판은 같은 폴더를 쓰면 안 된다.
설계 단계에서 "파일명이 내용 해시라 서로 덮어써도 같은 내용"이라고 적었는데 틀렸다. 파일명은 원본 파일의 해시지만, 저장하는 것은 원본이 아니라 추출한 본문이다. 두 판은 파서가 아예 다르므로(파이썬=사이냅·하이브리드, Rust=순수 Rust 파서) 같은 문서에서도 본문이 다르게 나온다 — 실측으로 확인했다.
문서파이썬 판Rust 판
하이브리드 문서분류_초안.PPTX9,312 B9,330 B

그래서 이렇게 막았다 — 같은 이름이 이미 있으면 내용까지 비교한다. 같으면 중복 제거로 넘어가고, 다르면 덮지 않고 오류로 알린다: text_save_error="같은 해시의 다른 본문이 이미 있습니다 — 다른 엔진이나 다른 버전으로 만든 폴더로 보입니다. 폴더를 나누세요". 실측: 파이썬으로 만든 폴더에 Rust 를 돌리면 저장실패=3 이 뜨고 파일은 그대로 남는다.
